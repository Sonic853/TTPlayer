# 播放列表信息读取：原版与重建版的取舍

日期：2026-09-16。范围：添加歌曲后的标签、时长、格式等信息读取，不涉及随机播放索引。

实施状态：已按此方向完成第一阶段优化，见
[实现与验证记录](PLAYLIST_INFO_LOADING_OPTIMIZATION.md)。下文的“当前重建版”指优化前基线，
保留原始对比依据；新的实现、测量结果和范围以实施记录为准。

基准为工作区 TTPlayer 5.7.9.0：
`c7999ea5823469c1684148cac1bd196009824348ccac5cdd45978f8fb574e28c`。
依据 `../reverse/decompiled/TTPlayer.exe.pseudo.c`，并用原 EXE 的 x86 汇编核对
`004801E7` 的数量分支、线程入口传递、`0042CE94` 的线程创建、`00481759` 的出队和
`004AE7FD` 的缓存分支。本文是静态分析，没有新增原版／重建版吞吐量实测。

## 结论

建议在重建版上优化，吸收原版的数据组织和调度方式，保留隔离子进程及超时取消。
原版在正常文件上的固定开销更少；重建版当前有重复创建进程、重复加载插件和
回写扫描全表的成本，但其读取任务与主窗口隔离，故障恢复边界更清楚。

没有证据支持“原版靠多个线程同时读很多首”。已核对的批量路径是单工作线程串行处理，
按需路径则在 UI 空闲处理中逐项读取。

## 1. 原版有多条读取路径

### 添加时／主动批量读取

`00480386` 在满足预读条件时，先调用 `004801E7`，再提交歌曲到目标列表。
条件涉及媒体库状态和 `ReadInfoMode == 1`，不是所有添加都必然完整预读。

`004801E7` 按传入批次的条目数分流：

- **1–5 项：**在调用线程中循环调用 `004AE7FD(item, ..., 1)`。从普通添加 UI 路径
  进入时，这就是主线程；没有为小批次新建读取线程。
- **6 项及以上：**创建进度对话框，将 `_LoadSoundInfoProc`（`004800EE`）交给
  `0042CB90`。该函数进入模态 `DialogBoxIndirectParamW`；对话框初始化后经
  `0042CE94 → _beginthreadex → 0042CA27` 启动一个工作线程。
- `004800EE` 顺序取出歌曲对象，读取信息，更新进度，在条目之间检查取消事件。
  它没有为每首歌曲创建独立线程或进程。

汇编确认的边界是 `cmp edi, 5; jg ...`。这与重建版随机播放索引的 5000 首阈值无关。

### 可见行按需读取

`00487C0D` 的自绘分支检查 `ReadInfoMode != 2`、未读取状态 `duration == -2`
及本地来源，把需要读取的行号去重加入待处理数组。

主线程空闲回调 `00459F27` 调用 `00481759`：

1. 每次取待处理数组最后一个行号；汇编确认使用 `count - 1`。
2. 取得该行矩形，与客户区求交，确认它仍可见。
3. 可见时直接定位歌曲对象，调用 `004AE7FD`；仍未读出的 `-2` 转为 `-1`。
4. `0047FD7D → 00413637` 发出 `LVM_REDRAWITEMS`，只请求重绘该行。
5. 移除本次行号；仍有任务时投递 `WM_NULL`，推动后续消息／空闲处理。

这是把工作拆到多次 UI 空闲机会，并非后台读取线程。滚出可见区域的待处理行会在
这一步跳过，避免继续为已经看不到的条目做读取。

### 悬停提示

`004887AA` 处理曲目提示。在允许读取且歌曲尚需加载时，直接调用 `004AE7FD`，
然后刷新该行并格式化提示。此路径也没有另起线程。

因此，原版快速读取正常本地文件时开销小；遇到慢文件或卡住的插件，单次同步读取
仍可能阻塞主线程。把任务安排在 idle 阶段并不保证一次读取能够及时返回。

## 2. 原版减少开销的机制

### 直接持有歌曲对象

批量线程取出的是歌曲对象引用，并通过引用计数保持对象存活；按需路径通过行号
直接取对象。信息写回对象本身，结果不需要再遍历全部歌曲寻找相同路径。
`004D6CCF` 是带边界检查的数组索引，`0047FE60` 将行号映射到歌曲对象。

重建版目前用 `vector<Track>` 存值，不能直接把元素裸指针交给异步任务：插入、删除
和扩容可能使它失效。适合采用稳定的歌曲 ID，加上来源／列表版本校验及重复行映射。

### 缓存和文件时间检查

`004AE7FD` 使用歌曲对象的 `+0x88` 缓存显示文本，并在指定检查条件下通过
`004C7D16` 更新文件时间，与 `+0x1C` 保存的时间比较。发现时间变新后调用
`004ADA76` 重新读取。对象状态由共享临界区保护。

这不等同于“每次访问都重新打开文件”，也不等同于文件监视服务。
重建版普通列表读取队列主要用 `duration_ms == -2` 判断是否需要读取，尚未在这条
队列中复刻上述文件时间重检逻辑；媒体库文件监视是另一条路径。

### 模块／工厂复用

原版在播放器进程内调用 Sound Library 和 AddIn；`004CD67C` 等函数惰性获取并
缓存插件类别接口。逐首读取仍可能创建各自的 reader，不能说成复用同一个已打开的
歌曲 reader，但不需要为每首启动一个 EXE 并重新构建整套插件管理器。

## 3. 当前重建版的特点

相关实现：

- `src/ui/player_window_file_intake.cpp`：添加时将读取请求排入队列。
- `src/ui/player_window_playlist_info.cpp`：同一队列同时只有一个活动任务；后台协调
  线程读取完成后投递消息，UI 再写回结果。
- `src/ui/file_info_probe_client.cpp`：每次读取创建请求／结果临时文件和隔离子进程。
- `src/app/file_info_worker.cpp`：子进程读取内置格式或旧 AddIn，返回结构化结果。

| 比较项 | 原版 | 当前重建版 |
| --- | --- | --- |
| 小批次、可见行、提示读取 | 部分路径直接在 UI 线程执行 | 信息探测异步执行 |
| 大批次读取 | 一个线程顺序处理，模态进度窗口 | 非模态队列逐首处理 |
| 插件运行位置 | 播放器进程内 | 信息探测子进程内 |
| 每首固定开销 | 复用进程及插件基础设施 | 新协调线程、新进程、临时文件、初始化 |
| 结果定位 | 原歌曲对象或直接行号定位 | 按来源身份扫描列表中的未读取重复项 |
| 刷新范围 | 按需读取完成后重绘目标行 | 使整个播放列表窗口失效，等待重绘 |
| 滚走后的任务 | idle 读取前重检可见性 | 已排队的有效任务仍会继续读取 |
| 单次读取卡死 | 相应 UI 调用或工作线程可能一直等待 | 探测客户端有 15 秒超时和进程回收 |

重建版并非每首完成都立即同步重画整窗：`InvalidateRect` 可由系统合并；但失效区域
仍比原版的目标行更大。全表扫描则是明确发生在 UI 回写路径的额外工作。

另一个明确的可优化点：`ReadPlaylistInfo` 内置读取成功后，目前仍调用
`manager.Load(addin_directory)`；成功路径可以跳过该初始化。

## 4. 为什么不建议完整恢复原版的执行方式

- 原版同步读取的响应时间取决于文件和插件。重建版已有的后台探测边界值得保留。
- 原版进度线程每首结束后才检查取消事件。`0042CBE7` 请求取消后调用
  `0042A617`，后者一边泵消息一边以无限等待等待线程结束；它没有保证能打断
  正在执行的插件读取。取消确认还涉及 `SuspendThread/ResumeThread`。
- 整体移回主进程会失去当前信息探测的崩溃隔离；增加普通线程不能替代进程隔离。
- 原版共享对象及其引用计数，与当前按值保存的 Track 模型不同，直接照搬会引入
  对象生命周期和并发修改问题。

这些是已核对调用链的取舍，并非实测原版一定会卡死或重建版一定更快。

## 5. 推荐优化路线

1. **先移植原版的低开销做法。**稳定歌曲 ID／来源到行的映射、局部刷新、缓存与
   文件时间失效；仅为内置读取失败的歌曲初始化 AddIn。
2. **按需与全量任务分开调度。**可见行和悬停请求优先；按需任务在滚走后可以撤销，
   “添加时读取全部”任务继续完成。保留去重和原始歌曲顺序。
3. **复用一个隔离读取进程。**在进程内保留插件管理器，逐首创建 reader；每首仍有
   独立任务编号、结果校验、超时和取消。故障时重建进程，继续剩余任务。旧插件出现
   连续任务状态问题时，可对该插件保留一次性进程路径。
4. **优化导入和落盘。**后台收集文件、分批提交；保存仍按版本确认结果，避免旧快照
   覆盖新编辑。原版已有“约 30 秒或修改计数超过 4”触发条件，改变保存时机属于另一个
   行为调整，不能当作纯粹的线程优化悄悄修改。
5. **最后再测并发收益。**普通版先以 1 个复用进程作基线，再比较 2 个任务；
   XP／Win7 版优先保持单个读取任务。机械硬盘、大文件、压缩包及插件内锁的情况
   可能不随并发数增加而加速，需要测量。

建议测量首次可见行完成时间、5000 首全部完成时间、UI 最长无响应间隔、进程创建次数、
CPU／峰值内存，以及损坏文件、慢插件、读取中排序删除和取消的恢复表现。
现有 XP／Win7 单份随机索引策略不受信息读取方案影响。

以上为实施前的分析与建议；后续实现和分发包验证见实施记录。
