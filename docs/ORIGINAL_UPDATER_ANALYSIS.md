# 原版 5.7.9 更新链路与 Updater.exe 伪代码分析

分析日期：2026-09-25。

## 1. 分析对象与结论

本次分析用户补充到工程根目录的 `Updater.exe`，以及与之配套的根目录 `TTPlayer.exe`、`ttpres.dll`。

| 对象 | 身份与作用 |
| --- | --- |
| `TTPlayer.exe` | 文件版本 5.7.9.0；负责定时/手动检查、通知展示、生成更新任务、启动更新器 |
| `Updater.exe` | 文件版本 5.7.9.0，文件说明 Updater Module；64,432 字节，x86 PE，入口 `0040C2A2` |
| `ttpres.dll` | 提供更新窗口、图标和中文提示；更新器运行时从自身目录加载 |
| `TTPlayer5719/bdupdate.exe` | 另一套 5.7.19 更新体系，不作为本次 Updater.exe 行为的依据 |

Updater.exe SHA-256：

```text
f23a9fed8376cfb91c0730401a21b6bdb9399714a7566c60405e2540cb13c8d2
```

**核心结论：这份 Updater.exe 实现了“读取本地更新任务 → 多来源下载可执行安装包 → 校验 → 启动安装程序”。它没有实现检查最新版本、直接替换播放器文件、安装回滚及重启播放器的完整事务。** 最后的实际安装工作交给下载得到的 EXE。

本次为静态分析：完整导出了 Ghidra 识别的 452 个函数，452 个均成功反编译；对核心业务函数、间接回调、关键分支同时检查了机器码/汇编。没有执行旧更新器、访问历史更新服务器或安装历史更新包。“成功反编译”不等于每个库函数都恢复成了可编译原始源码。

## 2. 主程序如何进入更新流程

### 2.1 定时检查与手动检查

| 函数 / 数据 | 已确认行为 |
| --- | --- |
| `0049257C` | 更新周期选项的数据值：不检查 `-1`、每天 `1`、每周 `7`、每月 `30`；无效选择回到 `7` |
| `004B605A` | General 配置保存/读取 `CheckUpdateDays`、`LastCheckedDay`、`LastMessageVer` |
| `0045EBA8` | 周期大于 0、没有检查线程运行，且达到检查日期或处于首次启动条件时，设置 ID 13、5,000 ms 的一次性定时器 |
| `00492B9C` | 手动检查：置手动标志，再向主窗口发送 `WM_TIMER`，ID 13 |
| `0046010E` | 消耗检查定时器，补充请求参数，启动检查线程 |
| `00411A5B` / `00411A12` | `_beginthreadex`、调用工作对象、退出后清理线程句柄 |
| `00458FCC` | 检查工作对象的执行入口，调用 `00458B9C` |

`004C551F` 使用系统 FILETIME 计算小时数，调用方再除以 24 得到天数。因此这里的周期是日期间隔，不是累计播放时长。语料中 `0045EBA8` 的旧分析名 `CPlayerWnd_ArmUsageTimer` 容易造成误解，应以函数内容为准。

### 2.2 所给主程序样本的入口已被直接返回

根目录 TTPlayer.exe 的 `00458B9C` 首字节是 `C3`，即 `RET`：

```text
00458B9C: C3              ret
后续原始字节：D0 F2 50 00 E8 3A 07 0B 00 ...
```

**当前提供的这份主程序不会通过该入口执行后面保留的网络检查代码。** 这说明该样本的检查入口处于被禁用/改写后的状态；不能据此断言所有官方 5.7.9 发行文件都如此，也不能确定修改来源。

下一节描述的是样本仍保留的检查实现，不是声称此入口在当前样本中可正常完成联网。

### 2.3 保留的版本查询实现

`00458BA6–00458FCB` 的汇编保留了以下流程：

1. 创建 HTTP 请求对象，超时参数 60,000 ms，使用播放器代理配置。
2. 组合版本号 `5.7.9.MMDD`，末尾月日来自主程序 PE 时间戳，参见 `004C176C`。
3. 顺序尝试四个历史服务基址，直到解析出非零版本值。
4. 解析 `<ttp_msg ver="..." url="...">`。
5. 向主窗口发送 `0x7F7`，携带版本值；存在新版本/通知时还携带转换成宽字符串的 `url`。

保留的地址为：

```text
http://ttlrc.qianqian.com/
http://ttlrccnc.qianqian.com/
http://ttlrcct.qianqian.com/
http://ttlrcct2.qianqian.com/

%sdll/ttp_ver.asp?ver=%s&id=%s&%s%s&LD=%s&TTPSvr=%s
```

附加参数能看到皮肤名 `skn`、作者 `ska`、首次启动 `fst`、歌词状态 `lrc`，以及辅助模块提供的字符串。`id` 可追溯到 `004C2C0F(...,1)` 读取的模块 DOS 头保留字段；没有把它直接称为硬件 ID。辅助模块字段未在本次进一步还原其完整语义。

`00458A36` 按 `%d.%d.%d` 解析版本，再组合：

```cpp
version = ((major & 0xffff) << 16)
        | ((minor & 0xff) << 8)
        |  (patch & 0xff);
```

### 2.4 通知与下载之间还有一层消息桥

主窗口的 `00462D2A` 处理 `0x7F7`：

- 更新 `LastCheckedDay`，依据当前版本、手动标志及 `LastMessageVer` 决定是否展示。
- `ttpres.dll` 的字符串 132、133、135 分别对应“最新版本”“最新消息”“已是最新版本”。
- `ttpsvr.exe` 可用并通过原版文件检查时，生成 `<NewVersion>` 任务，由它展示网页式通知；否则使用主程序内部的通知窗口。
- `<NewVersion>` 包含 `title`、`message`、`bhtml`、`cfgmsg=0x7F4`、`wparam=0x417`、`lparam=0` 等。
- 更新通知与安装下载是不同任务；不能把返回的通知 URL 直接当成已验证的安装包 URL。

进入安装下载的主程序入口有两处：

| 入口 | 行为 |
| --- | --- |
| `00460EDF`：`WM_COPYDATA`，`dwData=0x1102` | 将收到的更新任务文本写成文件，再启动 updater.exe |
| `00463BE5`：内部消息 `0x784`，`wParam=5` | 经 `0045F672` 将来源、大小、MD5 等字段组合为更新任务，再启动 updater.exe |

任务写入播放器目录的 `packs\`，名称由 TickCount、随机值组合，并检查是否重名。更新器启动失败时主程序删除刚写的任务文件；成功时关闭新进程/线程句柄。

主程序验证 Updater.exe 的函数为 `004566E2`。它不是安装包 MD5 检查，详见第 8 节。

## 3. Updater.exe 的入口和任务文件

### 3.1 启动约定

`0040C2A2` 是 CRT 入口，跳过自身程序名后，将剩余命令行交给 `00402879`。

其语义是：

```text
Updater.exe <本地更新任务文件完整路径>
```

`00402879` 立即调用 `004021BB` 读取任务，随后无论解析成功与否，都调用 `DeleteFileW(taskPath)`。有效包数量小于 1 时直接退出，没有任务格式错误提示。

任务路径是原始命令行余下部分，业务层没有再做标准 argv 分解、引号剥离。主程序原有启动代码也使用字符串拼接。这些是原版约定及其路径处理限制，重建时应使用明确的应用程序路径和规范的参数转义。

### 3.2 XML 格式

主程序 `0045F672` 生成的主要形式：

```xml
<setuppackinfo ver="2">
  <ttpack size="安装包字节数" md5="安装包MD5">
    <source url="下载地址1" />
    <source url="下载地址2" />
  </ttpack>
  <proxy type="代理类型" port="端口" svr="代理地址"
         usename="用户名" password="密码" />
</setuppackinfo>
```

`usename` 是原样保留的字段拼写。Updater 的根节点解析检查 `setuppackinfo`，但没有看到读取 `ver` 后选择协议版本的代码。

另一条分支接受：

```xml
<setuppackinfo>
  <proxy type="1" />
  <pack name="组件名" size="字节数" md5="MD5">
    <source url="下载地址或本地执行路径" />
  </pack>
  <pack name="另一个组件" size="字节数" md5="MD5">
    <source url="下载地址" />
  </pack>
</setuppackinfo>
```

这些示例用于解释解析结构，没有使用真实下载任务或代理凭据。

### 3.3 解析器的实际规则

`004021BB` 逐个处理根节点的直接子元素：

- `proxy`：读取 `type`、`port`、`svr`、`usename`、`password`。
- `ttpack`：读取大小和 MD5；将包名固定成 `ttpsetup`；收集所有 `source`；将有效包数设为 1，然后立即退出根节点遍历。
- `pack`：读取 `name`、大小、MD5 和所有 `source`，累计包数量，继续遍历。

包记录以 `0x1C` 字节为步长，前三个字段为名称、大小字符串、MD5 字符串，后面是来源列表。

**因此 `ttpack` 不是任意位置都等价的 XML 节点：它后面的 `proxy` 或其它包不会继续被读取。** 主程序的 XML 追加函数 `004C5D4E` 确认为追加到末尾，而 `0045F672` 恰好先追加 `ttpack`、后追加 `proxy`。对于这条主程序生成链路，代理设置会被漏读，更新器保留默认 `type=1` 的系统代理模式。

## 4. `ttpack`：可见的播放器升级流程

### 4.1 文件名和界面资源

主流程以第一个包的名称是否等于 `ttpsetup` 决定进入可见升级路径。因此严格来说，分支判断依据是解析后的名称，不是再次检查 XML 元素类型。

下载目标为：

```text
<任务文件所在目录>\ttpsetup.exe
```

更新器 `004020EE` 从**自身 EXE 所在目录**查找 `ttpres.dll`，先执行自定义校验，再 `LoadLibraryW`。缺少 DLL、校验失败或加载失败时，该路径直接退出。

下载对话框 `0040313B` 使用资源 379 / `0x17B`。核心资源如下：

| ID | 内容 / 用途 |
| --- | --- |
| 379 | 下载对话框 |
| 5 | 程序图标 |
| 2181 / `0x885` | 下载进度条 |
| 2254 / `0x8CE` | 百分比文本 |
| 1 | “安装”按钮，下载阶段隐藏 |
| 2 | 取消 |
| 33441 / `0x82A1` | 升级失败及到官网手工下载的提示正文 |
| 33442 / `0x82A2` | “升级失败”标题 |
| 33443 / `0x82A3` | 下载完成、点击安装、运行中的程序将关闭的说明 |
| 33444 / `0x82A4` | “千千静听在线升级”标题 |

### 4.2 下载消息和进度显示

`00401185` 创建下载协调对象，调用 `00406DB5`，指定最多 2 个来源工作对象。回调 `0040110D` 通过 `PostMessageW` 将状态投递为 `0x432`。

`004012B6` 的实际处理如下：

| 回调状态 | 含义 | 对话框处理 |
| --- | --- | --- |
| 1 | 已取得有效长度，进入数据下载 | 保存总长度；设置进度范围 0–100；启动 ID 100、200 ms 定时器 |
| 2 | 数据下载完成 | 停止定时器；显示 100%；显示完成文字；停止下载对象；显示并聚焦“安装”；恢复/前置窗口 |
| 3 | 下载失败或无法继续 | **没有对应处理分支** |

`004013AD` 每次读取下载进度，以 `received * 100 / total` 计算百分比，下载过程中最高显示 99%。只有完成通知才显示 100%。

取消调用 `00406F8B` 停止下载，再 `EndDialog(...,2)`。在这条路径没有看到取消后主动删除 `ttpsetup.exe` 的逻辑。

### 4.3 点击“安装”之后才执行最终校验

点击安装只是 `EndDialog(...,1)`。随后 `00402879` 才：

1. 打开并映射已经下载的 `ttpsetup.exe`。
2. 使用 `00409ED4` 对文件内容计算 MD5，输出 **32 个大写十六进制字符**。
3. 将下载对话框记录的总长度转为十进制字符串，与任务中的 `size` 比较。
4. 将计算出的 MD5 与任务中的 `md5` 比较。
5. 发现不匹配时显示 33441/33442，退出升级路径。

需注意三个细节：

- `size` 比较取值来自对话框对象 `+0x20` 保存的下载总长度（汇编 `00402A70`），不是这一处重新调用文件大小查询。MD5 则针对映射文件内容计算。
- 此分支使用 `_mbscmp`，MD5 的大小写会影响比较结果。通用 `pack` 分支使用 `_mbsicmp`，两者行为不同。
- 校验分支外面有“计算结果字符串非空”的条件；并非所有打开/映射/计算失败都会进入明确的失败提示。这是原版的错误处理缺口，不能概括为所有异常都已阻止安装。

### 4.4 关闭播放器：原版等待事件并不等于等待进程退出

校验路径通过后：

1. 查找 `TTPSvr_MessageWnd`，存在则同步发送 `WM_CLOSE`。
2. 创建或打开 `{2A85B11F-C71F-4fbd-9B99-EBC6613D63C4}_Event`。
3. 仅当事件已存在（`ERROR_ALREADY_EXISTS=183`）时，查找 `TTPlayer_PlayerWnd`。
4. 主窗口存在则同步发送 `WM_CLOSE`，再 `WaitForSingleObject(event,10000)`。
5. 不检查等待返回值，继续启动安装包。

对照主程序：`004B5519` 创建同名手动复位事件，保存在 `DAT_00547094`；主窗口创建完成后就调用 `SetEvent(DAT_00547094)`，供单实例启动同步使用。`004B55CF` 清理时关闭该事件句柄。

**所以这个事件不是可靠的“播放器已退出”事件。** 更新器没有将它复位，也没有持有并等待播放器进程句柄，正常运行时事件可能早已置位，等待立即返回。此外，前面的同步 `SendMessageW(WM_CLOSE)` 本身没有 10 秒超时限制。不能将整段代码描述成“最多等 10 秒，确保播放器退出”。

### 4.5 启动安装包后的责任边界

更新器以 `CreateProcessW(NULL, setupPath, ...)` 启动 `ttpsetup.exe`，启动信息设置 `STARTF_USESHOWWINDOW`、`SW_SHOWDEFAULT`。

- 此路径没有附加 `/S` 等静默安装参数。
- 启动成功仅关闭安装器线程/进程句柄，**不等待安装完成**。
- 没有读取安装器退出码，也没有直接重新启动 TTPlayer.exe。
- 没有更新器自身执行的文件备份、目录替换或失败回滚。
- 启动失败没有看到额外错误对话框。
- 正常启动后没有删除 `ttpsetup.exe`；最终是否自清理取决于未提供的安装程序。

因此，仅有 Updater.exe 还不足以推断实际安装包采用何种安装引擎、是否迁移配置、怎样覆盖插件，以及安装后是否重启播放器。

## 5. `pack`：顺序处理多个通用安装程序

这条路径仍位于 `00402879`，不创建前述下载进度对话框。

每个包首先取第一个 `source.url`：

- 转为小写后以 `http://` 开头：使用全部来源列表启动下载，目标为 `<任务目录>\<name>.exe`。
- 其它情况：将第一个 `source.url` 直接作为待启动命令行，跳过本分支的下载和大小/MD5 检查。

HTTP 下载时：

1. 用事件等待下载结束，等待参数 600,000 ms。
2. 回调 `0040285E` 在状态 **2 或 3** 时都置位该事件。
3. 停止下载对象、复位事件。
4. 如果任务提供 `size`，用 `0040508D` 获取文件大小，再比较十进制字符串。
5. 如果任务提供 `md5`，映射文件、计算 MD5，以 `_mbsicmp` 比较。
6. 校验不符删除目标文件，继续后续包。
7. 达到执行条件后 `CreateProcessW`，再最多等待安装器 600,000 ms。
8. 等待返回值不是 `WAIT_TIMEOUT` 时关闭两个句柄并删除目标文件，然后处理下一个包。

这里有几项明确限制：

- 事件置位表示“结束了”，同时覆盖成功和失败，不能直接等同于下载成功。
- 大小和 MD5 都是可选字段；缺少它们时没有等价的完整性判断。
- 非 HTTP 的直接启动分支没有单独的信任校验。
- 没有用安装器退出码区分安装成功与安装失败。
- 安装器超时分支没有看到与正常分支对应的句柄关闭及文件删除。
- 直接执行本地路径的分支也会走后面的删除调用；不能把该模式当成无副作用的通用程序启动器。
- HTTPS 字符串不符合上述 `http://` 判断，会进入直接启动分支；不能声称通用包分支已正确支持 HTTPS。

## 6. 下载器内部：多来源、多线程与范围下载

### 6.1 对象和线程组织

| 函数 | 作用 |
| --- | --- |
| `00406C5C` | 构造下载协调器，创建控制事件/锁并启动协调线程 |
| `00406DB5` | 复制来源、建立数据范围、创建最多 `min(2,sourceCount)` 个网络工作对象 |
| `00406153` | 构造单个网络工作对象并启动其线程 |
| `004092AD` / `004092E2` | `_beginthreadex` 及虚函数线程入口 |
| `00407719` | 协调线程等待控制事件、网络事件、数据范围事件；活动期有 50 ms 调度 |
| `00406992` | 单个网络工作线程的请求、响应、写文件状态机 |

因此它不是简单的“UI 线程同步下载”，也不是每个地址无上限开线程。以两个来源为例，业务层可见主线程、一个协调线程、两个网络工作线程；WinINet 还可能维护自身线程。

### 6.2 HTTP 与代理

`00407442` 使用 `InternetOpenW` 创建异步会话：

| 任务代理类型 | 实际方式 |
| --- | --- |
| 0 | 直接连接 |
| 1 | 使用系统预配置代理，亦为默认值 |
| 其它且服务器非空 | 指定代理，格式 `http=http://%s:%d`，本地绕过 `<local>` |
| 代理结构无效 / 缺少配置 | 回到系统预配置方式 |

`004064DD` 执行 URL 分解、`InternetConnectW`、`HttpOpenRequestW(GET)`、`HttpSendRequestW`；存在偏移时加入：

```http
Range: bytes=<offset>-
```

`004066F4` 检查响应：

- 处理 HTTP 401 / 407，尝试设置账号密码后重发；账号密码来自任务代理结构。
- 状态码必须小于 400，且能查询到数值 Content-Length。
- Content-Type 查询成功后，转小写并拒绝包含 `text` 的响应，避免把常见错误网页当安装包。
- 使用“请求偏移 + 响应长度”确定来源总长度，并检查后续来源长度是否一致。

这不是完整的包身份验证；同长度、非文本响应仍需最后的 MD5 判断。代码也没有建立完善的 HTTPS 分支：请求标志固定为 `0x80400200`，未根据 URL 设置安全请求标志。

### 6.3 写文件、分段与重新调度

首次接受来源长度后，`004073F3` 使用 `CREATE_ALWAYS` 创建目标文件，并通过 `SetFilePointer` / `SetEndOfFile` 预设长度。

每个工作对象以共享读写方式打开目标文件，在自己的范围偏移处写入。`00406992` 使用 1,024 字节读缓冲，并存在约 10 ms 节奏控制分支。它不是适合直接照搬到现代宽带场景的大缓冲实现；本次没有做实际吞吐测试。

`00407FF7` 在剩余范围大于 1 MiB 等条件成立时，按 `0xA0000`（640 KiB）的倍数拆分尾部工作，再交给空闲来源工作对象。`00407D81`、`00407E3D` 负责范围收敛、工作切换及完成通知。

`00405B8B` 限制某些来源在一轮选择中的失败次数小于 4；外层 `00407673` 还有约 20 秒判断及来源状态重置。因此不应简单描述成整个更新过程最多重试 4 次。

**有 HTTP Range 和同一次任务中的范围续传，不等于有跨进程断点恢复。** 本次未见把下载范围写入持久化任务的代码；任务文件一开始即删除，新任务又会 `CREATE_ALWAYS` 重建目标文件。

## 7. 精简语义伪代码

以下用于解释控制流，省略 ATL 字符串引用计数和异常清理，不是可直接编译的源码。

```cpp
int UpdaterMain(rawCommandLine) {
    task = ReadXmlTask(rawCommandLine);
    DeleteFile(rawCommandLine);
    if (task.packageCount < 1) return 0;

    directory = ParentDirectory(rawCommandLine);
    if (task.packages[0].name == "ttpsetup") {
        resources = ValidateAndLoadAdjacentTtpres();
        if (!resources) return 0;
        target = directory + "ttpsetup.exe";

        if (ShowDownloadDialog(task.sources, target, maxWorkers=2) != IDOK)
            return 0;

        // 实际样本有计算结果非空门槛；异常时并不总是 fail-closed。
        computedMd5 = Md5MappedFileUppercase(target);
        lengthText = Decimal(dialog.recordedDownloadLength);
        if (!lengthText.empty() && !computedMd5.empty() &&
            (lengthText != task.size || computedMd5 != task.md5)) {
            ShowUpgradeFailure();
            return 0;
        }

        CloseTtpSvrWindow();
        if (NamedPlayerReadyEventAlreadyExists()) {
            if (FindPlayerWindow()) {
                SendWmCloseSynchronously();
                WaitOnNamedReadyEvent(10000); // 并非进程退出确认
            }
        }
        StartProcess(target); // 不等待安装完成，不负责回滚/重启
    } else {
        for (package : task.packages) {
            command = package.sources[0];
            if (StartsWithHttp(command)) {
                target = directory + package.name + ".exe";
                StartDownload(package.sources, target, maxWorkers=2);
                ended = WaitOnSuccessOrFailureEvent(600000);
                StopDownload();
                if (!ended) continue;
                if (!OptionalSizeAndMd5Match(target, package)) {
                    DeleteFile(target);
                    continue;
                }
                command = target;
            }
            process = StartProcess(command);
            if (process && Wait(process, 600000) != WAIT_TIMEOUT) {
                CloseHandles(process);
                DeleteFile(command);
            }
        }
    }
    return 0;
}
```

## 8. 原版的两种文件校验不能混为一谈

### 8.1 自定义 PE 文件检查

主程序 `004566E2 → 004BEBFF`、更新器 `00401F62 → 00401F26` 使用同一种算法：

1. 确认 MZ 和 PE 标记。
2. 从 PE32 节表之后开始，按样本算法扣除证书数据长度，累加 16 位字。
3. 对累加结果进行字节重排和取反。
4. 与 DOS 头偏移 `0x20` 的 32 位字段比较。

静态重算结果：

| 文件 | DOS 头记录值 | 重算值 | 结果 |
| --- | --- | --- | --- |
| 用户补充的 Updater.exe | `D2A38511` | `D2A38511` | 通过 |
| 根目录 ttpres.dll | `FB67B567` | `FB67B567` | 通过 |

所以这份 Updater.exe 和当前资源 DLL 在原版自定义检查层面是匹配的。该结果不代表验证了发布者数字签名，也不代表运行时已经测试成功。

### 8.2 下载包 MD5

`0040946C` 的 MD5 初始常量、后续压缩函数和 `00409ED4` 的 16 字节摘要转十六进制，可确认安装包校验使用 MD5。

虽然 Updater.exe 的 PE 内带有证书数据，**本次追踪的下载安装链路没有看到 WinVerifyTrust 或等价的发布者签名验证调用**。证书存在、自定义 PE 校验、MD5 与可信更新源验证是不同概念。

## 9. 已确认的原版缺口与重建取舍

| 问题 | 证据 / 后果 | 重建时的处理方向 |
| --- | --- | --- |
| 主程序样本检查入口直接 RET | `00458B9C`；保留实现无法通过该入口运行 | 区分样本改写和设计流程，不把 RET 当正常功能恢复 |
| `ttpack` 后的代理漏读 | `004021BB` 提前结束；主程序把 proxy 放在其后 | 完整解析任务后再执行，与节点顺序无关 |
| 下载失败状态没有 UI 分支 | `004012B6` 只处理 1、2 | 增加失败、重试、取消状态，停止进度定时器 |
| 显示“可安装”早于最终 MD5 检查 | 先完成对话框，点击安装返回后校验 | 校验完成后才允许安装 |
| 校验失败处理不完整 | 打开/映射失败的非空门槛；大小写比较不同 | 文件不可读、摘要计算失败、清单不完整均明确失败 |
| 等待就绪事件代替进程退出 | 事件在播放器窗口创建后已置位 | 持有播放器进程句柄并等待真正退出；检查结果 |
| HTTP 与 MD5 不能确认更新发布者 | 固定 HTTP 路径、无已确认签名验证链 | 为新的更新协议另行建立可信清单和包校验 |
| 安装执行失败反馈不足 | `CreateProcessW` 失败无专门提示；无退出码判定 | 显示具体错误并保留可重试状态 |
| 包模式清理不一致 | 普通升级包保留；通用包执行后删除；超时遗漏清理 | 明确任务、缓存、安装包生命周期 |
| 无跨启动恢复、无更新事务 | 删除任务、CREATE_ALWAYS、交给外部 EXE | 按重建版发行方式设计恢复、备份和回滚 |

这些是基于当前样本得出的静态结论；文档中的重建方向没有在本次写入播放器生产代码。

## 10. 与 5.7.19 的边界，以及尚缺的证据

5.7.19 的 `bdaucommon.dll + bdupdate.exe + autoupdate.ini` 是独立体系，包含另外的检查、组件安装和操作执行逻辑。不能把其中的补丁、文件操作或回滚代码归到本次 64 KiB 的 Updater.exe 上。

本次已闭合的部分是：主程序保留的版本检查 → 通知/任务消息入口 → 本地 XML 任务 → Updater 下载器 → 校验与安装器启动。

尚未由本次样本证明的部分：

- 历史服务器现时是否可访问、当年各类真实响应的完整内容。
- 原 `ttpsvr.exe` 网页控件/脚本到消息桥的全部实现细节。
- 实际下载的 `ttpsetup.exe` 内部安装、配置迁移、重启与自清理行为。
- 真实网络错误、磁盘故障、受限目录及各 Windows 版本上的动态表现。

后续若恢复重建版更新功能，可保留原版“独立更新进程、清晰进度、用户确认安装、多来源下载”的交互；应重新实现退出同步、校验、失败反馈及文件事务。当前重建版发行物是版本化 ZIP，不能直接当作原版的可执行安装包传给 CreateProcessW。
