# 实际整轨 RAR 样本、原版对照及剩余改进（2026-10-19）

## 1. 结论

实际收到的“齐豫 1993-LOVE OF MY LIFE[滚石首版][WAV整轨].rar”是 **RAR5**，先前截图为 **RAR4.x**。原版 5.7.9 的实际工厂拒绝前者；不能用这个 RAR5 直接声称“同包在原版更快”。

已按用户要求生成同结构、同成员内容的压缩 RAR4，并对两种格式分别测量当前重建版，对 RAR4 测量原版。当前修复后的重建版可以在完整解压前获得开头的音频；仍值得修复的是 **未完成解压时的 CUE 换曲、前台与信息进程重复解压、小成员缓存和少量毫秒显示差异**。

本轮是分析与构造测试包，未修改生产代码、未提交 Git。测试仍只保存在 rebuild/tests，没有加入 Action 或发行包。

## 3. 包内内容与解析

### 3.1 WAV

- 大小：514,911,644 B，约 491.06 MiB。
- SHA-256：289a8903e559f2a18b98174aaf75ecd57e8706762b05a944c78ca5da85347750。
- CRC32：F0DF7DAA。
- 标准 RIFF/WAVE、PCM format tag=1，44,100 Hz、16 bit、双声道、块对齐 4 B。
- 每秒 176,400 B，PCM 数据 514,911,600 B，时长恰好 2,919 秒，即 **48:39**。
- 只有偏移 12 的 fmt（16 B）和偏移 36 的 data（音频从偏移 44 开始）。没有 LIST/INFO、内嵌封面或 RIFF 尾部附加数据。

所以该文件不需要额外音频插件。对于这个具体样本，不能继续将“读取 WAV 尾部标签”当作唯一慢点：完整的内建信息读取也可以仅凭头部完成；必须和外置封面、CRC 验证及 CUE 流程区分。

### 3.2 CUE

CUE 为 1,550 B，CRC32=871A478F，GBK 中文能正确解析，指向同目录唯一 WAV，含 12 首曲目。艺人为齐豫，专辑为 LOVE OF MY LIFE。第一首从 00:00:00 开始，最后一首从 45:45:52（CD 的 75 帧／秒）开始。INDEX 00 的间隙和 INDEX 01 均保留。

原版真实导入和重建版生产导入均产生 **13 行：12 首 CUE 分轨＋1 个整轨 WAV**。这是原版的归档导入规则，不属于重复导入缺陷。

重建版三个信息读取模式共 287 项检查通过。无窗口扫描分支约 3.78–4.06 ms；“不读取／显示时读取／添加时读取”的初始信息队列为 0／0／13。所有行起初保留 duration=-2，标题、艺术家、专辑、轨号和逻辑成员路径正确。这里不包含进度对话框刷新和后续信息进程耗时。

## 4. 测试方法与边界

- Windows 11 本机，Intel Core i7-14700F；每个性能场景独立进程，清空播放器内部任务缓存，两个试次。没有清空 Windows 文件缓存，不能称为冷盘基准。
- 原版：隔离原版副本完成宿主初始化后，调用其真实工厂 004738B5、导入 00474051、成员流及 CUE 信息函数；不加载用户当前播放实例，不输出声音。固定样本路径与内部成员，保留原日志。原版计时为系统 tick，精度较低。
- 重建版：私有程序链接当前生产 ttplayer_core.lib，加载当前 ttpcomm.dll，调用真正的流、DecodedAudioSource、CUE、独立信息进程及导入函数；没有改写模拟生产逻辑。采用 steady_clock。
- “首 4096 B”是包内流数据，包含 44 B WAV 头；“首段 PCM”是解码源返回的首个有效对齐数据包。二者均不等于声卡可听见首音时间。
- 完整解压指标检查完成状态及成功结果；封面在其后单独计时。测试不依赖播放 48 分钟才能完成。
- 重建 HEAD=d8905ce，ttpcomm HEAD=7bbaec3。完整文件大小、SHA-256、测试日志在私有证据目录；若后续源码改变，应重新绑定构建身份。
- 本轮未把前一轮 XP／Win7 受控样本通过当作本次实际样本实测；本次表格只涵盖 Windows 11。

两种压缩格式共 40 个场景试次均正常完成；结果取各场景两次的范围。

完整解压总时间由原版首读时间与其后等待相加估计；原版在中间还做少量状态／定位探测，不是严格的微基准。不同场景的系统负载与缓存可能不同，不能用表中某个比例预测其他电脑速度。两个实现的首段数据都明显早于成员完成，这个结论比绝对速度比值更可靠。

RAR4 首轨的封面在 7.988–8.011 s 后可用；RAR5 为 1.348–1.399 s。这与延后到完整成员验证后的设计一致。第二轨首读若保留旧源，会等到100%；明确取消则建立不同task，完整后换曲沿用同task，日志分别记录此结果。


原版对实际 RAR5 的工厂返回 0、导入返回 0／0 行；同进程 RAR4 阳性对照正常。不能通过替换 ttpcomm.dll 为原版的 EXE 内置 RAR 工厂自动增加 RAR5。

原版两次 RAR4 首读时，已解压 8,134,656／11,075,584 B，仅约 1.58%／2.15%，显然没有等待整个 514 MB 成员。当前重建版首个流块返回时也只有 206,592 B 已产生。两者都在后台保存已解压数据，并以“需要的前缀是否可用”决定读取何时返回。

对于首次直接进入第 12 轨，目标在 WAV 约 94% 处，顺序压缩流必须产生此前的数据。等待这一位置本身不是错误。应改善进度、取消和复用，不能承诺无缓存时任意位置立即返回。

## 6. 原版实现与当前差异

| 项目 | 原版 5.7.9 证据 | 当前重建版与结论 |
|---|---|---|
| 格式 | 004738B5；RAR5 实测拒绝 | 支持 RAR4/5，保留扩展 |
| 成员缓存 | 004DFBF9：整成员分页文件映射 | 大于默认 16 MiB 使用自动删除临时文件，保留 64 位范围与地址空间保护 |
| 首段读取 | 004C4CA8：只等待请求前缀，200 ms 步长 | 以生产者通知唤醒；当前首段无全成员等待 |
| 当前成员复用 | 004DFDED；第二流 task 相同 | 同一已完成 WAV 的 CUE 重开 task 相同，实测成立 |
| 尚未产生的远端 Seek | 004C4B17 实测 E_FAIL | 允许先移动游标，随后 Read 等待；这是合理改进 |
| WAV 打开 | 004E82CA／004E8395–004E83AD，接受 data 后返回 | 首段 PCM 正常，不应重新同步读取封面 |
| CUE 导入 | 00474051 产生 12＋1 行 | 实测一致 |
| CUE 重新解析 | 004E323B 也读取 CUE | 不能把“重新解析”单独判成还原缺失；需看全局锁和任务生命周期的组合 |
| 标签扩展 | 本样本原版只列 Album/Artist/Title/Tracknumber | 重建保留 REM GENRE/DATE 等可取扩展 |
| 写入 | 原版归档流写入接口不可用 | 继续只读，不采用写回 |

**两个需要排除的误判：**

1. 128 MiB 不是单成员播放上限，而是切到另一缓存音频后保存历史成员的预算条件。当前这份 491 MiB WAV 正常播放并可在同专辑 CUE 间复用。
2. 目前 CUE／封面小文件读取使用 cache=false，不会把它们提升成“当前音频”而淘汰大 WAV。问题是重复读取与等待锁，而非该淘汰路径。

## 7. 需要修正或进一步优化的地方

### P1：让同一 WAV 的 CUE 换曲继承进行中的任务

已测出两种不同现象：

- **旧源尚在（例如淡出重叠）**：下一轨先读取小 CUE，而 RAR 目录发现／提取需要同一进程的 UnRAR 全局锁。当前大 WAV 持有该锁直到解压完成，所以仅位于约 11% 的第二轨也可能被迫等待到 100%。这里浪费的不是解析 1,550 B 的 CPU 时间，而是拿不到引擎锁。
- **明确取消旧源后再开下一轨**：旧任务未完成、最后消费者释放且取消标志已置位时，任务被取消；新源启动新的 task，从头解压至目标。已完成任务则可复用，不能笼统说每次换曲都会重解压。

建议先共享有整包／分卷身份校验的播放端 CUE 快照；再实现同成员消费者的任务交接，使新消费者接管后旧消费者取消不毁掉仍需使用的任务。真正 Stop、文件变化、错误以及无人再需的任务仍应取消。不要直接删除保护 UnRAR 状态的互斥锁。

代码：audio_engine.cpp 的 CueSegmentSource::Open（约 1447）；archive_member.cpp 的 ReadArchiveMember／OpenMember（约 269）；ttpcomm/src/archive_stream.cpp 的 KnownGroup、Stream 析构、Task::DropUser（约 185、246、336）；ttpcomm/src/archive.cpp 的 engine_mutex（约 225、279、344）。

### P1/P2：前台验证结果不要让信息进程重新算一遍

独立信息进程与前台进程各自拥有 ttpcomm 任务缓存。前台正在打开／解压时，UI 暂退信息工作；但前台到 100% 后就可以恢复，并非一定要等整首播放结束。

实际验证前台已经完成后，再查询同一 CUE：信息进程仍从 S_FALSE 的初步结果开始，再经历一次整轨解压才得到 S_OK；同时观察到两个独立临时成员文件。两份流各自逻辑大小约 491 MiB；不能把目录查询显示的未刷新文件长度当成实际落盘字节或物理内存占用。

建议先把前台已经验证的格式、整轨时长和最终状态分发到引用同一 WAV 的 CUE 行，按 CUE 边界推导各首时长。只有不足的信息再送到隔离进程。更大范围的跨进程任务服务可以后续实现，但需要身份、生命周期、权限、取消和最终校验协议，不能只共享一个临时文件路径。

代码：player_window_playlist_info.cpp（约 204）；file_info_worker.cpp 的 VerifyArchiveInfo／ReadPlaylistMetadata；file_info_probe_client.cpp 的会话与归档缓存排除；ttpcomm/src/archive_stream.cpp 的模块内 cache。

### P2：目录、CUE、封面使用有界小成员缓存

当前封面刻意等 WAV 全部完成且 CRC 成功，避免回到首播阻塞问题。已经完成的 CUE 再开也会再扫描目录及读取图片。本样本的 cover.jpg 在 WAV 前方，且非固实，适合在导入阶段获取小成员快照，随后按需复用。

建议按所有实际卷的文件身份／大小／修改时间、密码来源来验证缓存，限额保存目录、CUE 文本和图片原始字节；已有内嵌封面仍优先。不要为了提前封面破坏音频优先级。

代码：archive_member.cpp:298 附近 ReadArchiveSidecarCover；lyrics/local_search.cpp:129 附近；audio_engine.cpp:1250 附近延后信息线程。

### P2/P3：明确短 CUE 结束后的晚到 CRC 错误由谁报告

从代码可见，短子轨可以先到 byte_limit 而返回 EOF，完整成员稍后才完成。若随后没有消费者，最后才发现的损坏可能没有界面订阅者。该结论是代码边界审计，本次完好样本没有触发损坏，不应标为已复现的实际样本故障。

建议把归档验证结果归属到任务和播放过该任务的会话，而非仅在某个子轨读到整成员 EOF 时检查。无需为此阻塞首段音频或每次 CUE 边界。

### P3：统一 CUE 毫秒显示规则，保留帧级音频精度

原版 004E2F69 使用 MulDiv(frame,1000,75)，004E323B 分别转换起止位置再相减。当前直接截断帧差得到毫秒。本轮额外运行信息进程，逐轨核对了实际返回值（cue-durations-rebuilt.log），不是只按公式推测。

本样本第 2、3、10 轨的显示时长可比原版少 1 ms：原版分别 258627、184907、251014 ms，直接截断分别 258626、184906、251013 ms。末轨当前 source/worker 使用整轨时长减开始位置，实际仍为 173307 ms，与原版一致。

建议只统一 UI／元数据时间换算，继续用 CD frame 定位和裁剪 PCM，避免为显示一致而引入音频采样误差。

### P3：大成员磁盘与内存策略要先测量再优化

目前使用临时文件保存完整已产生数据，不是只保留几秒音频的环形缓冲。原版则使用整成员分页映射，两者都不是“无缓存”。对 x86 和超大成员，应保留当前地址空间保护；优先消除重复任务，再评估批量 I/O、窗口映射及生产者／消费者锁等待，不建议直接回退成整首地址空间映射。

## 8. 建议实施顺序与验收

1. **P1：CUE 快照＋同成员任务交接。** 在 RAR4 解压未完成时跳第二／末轨，证明不因读取小 CUE 等到 100%，必要字节已产生则可继续；手动切换不无故更换 task，真正 Stop 仍及时取消。
2. **P1/P2：前台验证结果回填列表。** 前台完整验证后，读取相关 CUE 信息不再次解压同一 WAV；保留插件隔离和文件变更失效。
3. **P2：小成员缓存。** 同一专辑连续 CUE 切换复用目录／图片；切换密码、换卷、替换文件能失效；首播不等待封面。
4. **P2/P3：任务级晚到错误通知。** 增加尾部 CRC 损坏、短 CUE、用户停止／下一曲等边界测试，确认错误归属。
5. **P3：显示毫秒及 I/O 调优。** 单独修改显示舍入，验证采样级输出未变；有性能数据后再调整缓存实现。

本轮没有必要把 RAR5 支持、64 位范围、只读、取消、最终校验或可等待的 Seek 回退成旧版限制。
