# 原版 ZIP／RAR、拖放流程与重建版 RAR5 支持分析

> 后续实现状态（2026-10-11）：本文保留修复前的分析基线。RAR 后端已改为重建 `ttpcomm.dll` 中的 UnRAR 引擎，并完成 XP／Win7 验证；当前行为、测试结果和剩余边界见 [归档引擎实施记录](ARCHIVE_ENGINE_IMPLEMENTATION.md)。本地 `backend_results.json` 已更新为新后端结果，不能再用它代表旧 Shell 后端。

日期：2026-10-11。重建版核对版本：`e34ec60`。原版基准：本仓库根目录 `TTPlayer.exe` 与 `reverse/decompiled/TTPlayer.exe.pseudo.c`，即当前项目使用的 5.7.9 基准。

本次完成源码／伪代码核对、原版识别函数机器码核对，以及本机 Windows 11 上的局部真实解压测试。没有修改播放器生产实现或发行工作流。测试源代码、样本、构建目录及结果均在本地 `tests/archive_support/`，没有加入 Actions。

## 1. 结论

1. 原版音乐压缩包入口只有 ZIP 和 RAR。RAR 由 EXE 内嵌的旧 UnRAR 类引擎处理，不依赖已安装的 WinRAR，也不由原版 `ttpcomm.dll` 提供完整 RAR 解压器。
2. 原版识别旧 RAR 签名，不能解码 RAR5。给旧识别函数增加一个签名判断，无法使旧解码器支持 RAR5。
3. 重建版保留了 ZIP／RAR 入表、`压缩包|成员` 路径和包内 CUE 路径；RAR 解压却改为 Windows Shell 的 `NameSpace`／`CopyHere`。它没有独立的 RAR4／RAR5 解压引擎。
4. 本机 Windows 11 build 26200 的 32 位 Shell 能处理此次 RAR5 样本，现有重建版后端也读出了正确字节。因此不能说“RAR5 完全不支持”；准确描述是“依赖系统的有限 RAR5 支持”。这不构成 XP、Win7、Win10 的验证结果。
5. 重建版 RAR 的整包预解压、字母排序、完成判断、取消／错误处理与原版有明显差异。建议恢复原版的归档层边界，再使用维护中的 UnRAR 支持 RAR4／RAR5。

## 2. 原版从输入到播放的流程

### 2.1 文件分类与归档工厂

| 原版函数 | 核对结果 |
| --- | --- |
| `004739DB` | 处理文件属性、快捷方式和扩展名；类别 3 是 CUE，4 是 ZIP／RAR，5 是播放列表，6 是目录 |
| `004742DD` | 按分类分派普通文件、CUE、压缩包、列表及目录 |
| `0047444A` | 遍历目录；目录内的 ZIP／RAR 继续交给归档导入分支 |
| `004738B5` | `.zip` 创建 `0041ECD1` 对象，`.rar` 创建 `00473287` 对象，然后调用归档 Open |
| `00474051` | 枚举归档成员，展开 CUE，筛选注册的音频格式，生成播放项 |

归档工厂没有 `.7z`、`.tar`、`.gz`、`.cab` 分支。把这些扩展名加进文件对话框过滤器不足以获得播放支持。原版底层 RAR 识别器有寻找嵌入签名的路径，也不等于普通 `.exe` 文件在导入阶段会被当作自解压音乐包。

归档格式与音频编码是两层：归档层负责给出成员字节，随后仍要由 MP3、FLAC、APE、Vorbis 等对应的 Reader 解码。支持 RAR 并不自动支持包内所有文件类型。

### 2.2 拖到不同窗口的行为

| 投放位置 | 原版行为 | 主要证据 |
| --- | --- | --- |
| 主窗口 | 首文件为 `.skn` 时走皮肤路径；普通文件输入走清空当前列表、导入和开始播放路径 | `0045A8BE` |
| 歌曲列表区域 | 按命中的行插入，保持输入批次次序，使用该入口的空闲时播放规则 | `004822AD`、`00481F2A` |
| 左侧已有播放列表 | 将展开出的曲目追加到目标列表 | `004822AD` |
| 左侧列表空白处 | 普通输入批次生成新列表；不是强制每个压缩包创建一份列表 | `004822AD` |
| 歌词窗口 | 第一文件进入歌词加载路径，不进行音乐压缩包导入 | `0044AC70` |

主窗口和歌词窗口请求 `CF_HDROP`；播放列表还处理自己的内部格式和 URL 回退。这里的“拖放压缩包”是投放磁盘上的 ZIP／RAR 文件，再由播放器枚举内容。

从 WinRAR 等软件内部拖出一个文件是另一种情况：如果源软件先解压成临时文件并提供 `CF_HDROP`，播放器接收到的是那个普通临时路径；不能因此认定播放器支持其所有压缩格式。只有 `FILEDESCRIPTOR`／`FILECONTENTS` 的虚拟文件数据对象也不能视为已经由这些入口支持。

现有重建版 `src/ui/player_window_file_intake.cpp` 的 `HandleDroppedFiles`、`ImportFiles`、`CollectImportedTracks` 已复用上述大部分入口语义。细节沿用 `FILE_INTAKE_RECOVERY.md`，本次不重新宣布全部拖放界面通过实测。

### 2.3 压缩包内的内容如何入表

`00474051` 的核心次序为：

1. 创建 ZIP 或 RAR 归档对象并打开。
2. 通过虚表 `+0x0C` 获取成员记录数组，顺序遍历。
3. 将外层文件名与成员名拼为 `D:\Music\Album.rar|Disc1\song.flac`。
4. `.cue` 成员通过虚表 `+0x14` 读出内容，交给 `00473EC5` 展开分轨。
5. 其它成员先排除注册的播放列表，再按注册音频格式筛选。
6. 将符合条件的成员交给播放项创建及列表插入逻辑。

关键点：

- 入表保留归档逻辑路径，不把临时解压路径写入列表。
- 此循环没有额外按成员文件名排序；原版 RAR 列表来自顺序读取归档头。
- 普通音频不需要先整包解压到磁盘；CUE 文本会在导入阶段读取。
- 未看到在这个入口递归展开“包内另一个压缩包”，也没有把包内所有 M3U／PLS 当作列表自动展开。
- CUE 的 FILE 指令由原版成员路径逻辑处理；不能直接改成磁盘目录的路径标准化规则。

### 2.4 原版播放与定位

`0047E177` 枚举成员，用 `_wcsicmp` 查找所需名称并返回大小。`004DFBF9` 为目标成员创建分页文件支持的内存映射，设置数据／完成通知，然后调用归档读取接口。`004DFDED` 还保留同一逻辑成员的共享对象路径。

RAR 包装层 `00473580` 提供同步读取与后台工作路径；`0047366F` 有取消标志，`00473702` 定位到目标头后执行解压。`004DFD8E` 接收已产生字节、完成或失败通知。

因此，原版的边界接近“归档成员 → 内存流／共享缓冲 → 音频 Reader”。定位是对成员的解压后内容进行读取和 Seek，不是对压缩包偏移直接进行音频 Seek。固实 RAR 仍可能需要解码前面的数据来恢复字典；不能承诺任意曲目都能直接跳到其压缩块。

原版也有历史大小限制：成员查找结果和映射创建路径使用 32 位大小。重建时应保留交互语义，避免机械复制溢出风险。

## 3. 原版 ZIP 和 RAR 的能力边界

### 3.1 ZIP

`0041F422` 明确拒绝加密标志，只处理方法 0（Stored）与 8（Deflate）。`0041F481` 调用 `ttpcomm.dll` 的 ordinal 80／81／82 执行 raw Deflate 解压，使用旧 zlib ABI 字符串 `1.1.4`。

这表示原版有 ZIP 容器读取能力，`ttpcomm` 在这里主要提供压缩算法服务。不能据此推定它还支持 ZIP AES、BZip2／LZMA 方法或现代 ZIP64 全部特性。

`.skn` 皮肤加载是另一条使用 ZIP 读取器的路径（例如 `0041F73F` 还支持资源中的 ZIP），不能把“皮肤压缩包”与“音乐归档导入”混为一谈。

### 3.2 RAR4 与 RAR5

原版 `004F9332` 逐字节比较：

```text
旧 RAR：52 61 72 21 1A 07 00
RAR5：  52 61 72 21 1A 07 01 00
```

原版要求第 7 字节为零，RAR5 的这一字节为 1，因而不匹配。该函数还识别更早的 `RE~^` 标志，但本次没有验证相应历史压缩样本。

已按 PE 节表在实际 `TTPlayer.exe` 的 VA `004F9332` 读取 87 字节核对，机器码包含第 7 字节与零比较的 `38 42 06` 分支，与伪代码一致。这是识别边界的二进制核对，不是原版完整播放实测。

RAR 包装层的重要函数：

| 地址 | 职责 |
| --- | --- |
| `00473287` | 初始化 RAR 归档对象 |
| `00473338` | 打开归档、顺序读取成员头并记录大小与 Unicode 名称 |
| `00473527` | 向调用者复制成员表 |
| `00473580` | 开始同步或后台读取 |
| `00473702` | 查找目标成员并调用内嵌解压逻辑 |
| `004F5E47` | 与 `RAROpenArchiveEx` 对应的底层打开路径 |
| `004F5B6A` | 与扩展成员头读取对应的底层路径 |
| `004F580C` | 设置回调和用户数据 |
| `004F5E0D` | 关闭归档 |

底层引擎具备固实／分卷相关分支，但这不能证明播放器 UI 实现了完整密码输入、选取缺失分卷及重试。需要把“引擎能力”和“宿主可用功能”分别验收；本次不将加密、分卷列为原版已完整实测支持。

RAR5 改变了头部、整数表示和压缩信息等，不能只放宽上述字节比较。RAR5 容器内部还存在需要 RAR 7.0 及更新解码器的算法版本。依据：[RARLAB RAR5 格式说明](https://www.rarlab.com/technote.htm)、[UnRAR 7.0 实现说明](https://www.rarlab.com/unrar7notes.htm)。

## 4. 重建版当前实现

### 4.1 ZIP

`CollectImportedTracks` 的 `.zip` 分支使用 `SkinPackage` 枚举，然后 `ReadZipMember` 提取成员。当前同样主要支持 Stored／Deflate。

还应独立处理这些现代 ZIP 缺口：

- `DecodeZipMemberName` 固定使用 `CP_OEMCP`，未按 ZIP UTF-8 标志及 Unicode 扩展字段解码。
- SDK `CentralRecord` 有 flags／CRC 等信息，但 `SkinEntry` 未保留这些完整字段；当前提取路径没有核对成员 CRC。
- EOCD 成员数仍为 16 位，大小与偏移为 32 位，没有完整 ZIP64 解析。
- 读取目标成员时会把整个外层 ZIP 读入内存，再分配成员缓冲。

修复音乐归档时，应将皮肤所需的旧兼容行为与通用归档的验证策略分开，防止破坏已经兼容的旧皮肤。

### 4.2 RAR／RAR5

当前实际调用链：

```text
CollectImportedTracks(.rar)
  → ListRarArchiveMembers
  → EnsureRarExtracted
  → IShellDispatch::NameSpace / Folder::CopyHere
  → 临时目录递归枚举、按名称排序
  → Album.rar|member 入表

播放成员
  → ReadArchiveMember
  → 缓存文件读入 vector
  → MemoryStream 复制到 HGLOBAL
  → Reader / Media Foundation / 兼容系统解码路径
```

生产代码集中于：

- `src/audio/archive_member.cpp:129`：系统解压与完成判定。
- `src/audio/archive_member.cpp:279`：成员读取。
- `src/audio/archive_member.cpp:301`：枚举和排序。
- `src/ui/player_window_file_intake.cpp:1032`：RAR 导入。
- `src/audio/audio_engine.cpp:176`：内存流复制。

没有 RAR4／RAR5 魔数分支，没有集成独立 UnRAR。`ttpcomm` 当前也没有完整归档服务；ZIP SDK 的结构读取辅助不能替代 RAR 解码器。

Windows 11 24H2 的官方文档列出了系统 ZIP／RAR／7z／TAR 支持，并说明不支持加密压缩包操作；但 Explorer UI 能力不能直接当成所有系统、进程位数和 COM 自动化入口的保证。本次专门测试了播放器使用的 32 位路径。来源：[Microsoft 压缩文件支持说明](https://support.microsoft.com/en-us/windows/experience/storage-filemanagement/zip-and-unzip-files)。

### 4.3 当前差异与影响

| 差异 | 影响 |
| --- | --- |
| RAR 解压依赖 Shell | 原版不要求的系统能力成为运行前提；XP／Win7／Win10 默认环境不能据此承诺支持 |
| 添加时解压整包 | 非音频文件也占用临时磁盘；导入路径同步等待，拖入大包可能阻塞界面 |
| RAR 枚举末尾强制字母排序 | 原版归档成员顺序被改变，进而影响默认播放顺序 |
| 750 ms 数量／大小稳定即完成 | 静止不能证明所有成员解压成功；部分失败或停顿存在误标完成风险 |
| 最长等待 30 秒，无准确任务完成回调 | 可能将慢解压误报超时；没有完善进度、取消与后端终态 |
| `.ttp-complete` 命中后直接复用 | 没有逐成员完整性验证；不完整缓存一旦被标记可能持续影响读取 |
| 文件系统枚举代替归档目录 | 重名、大小写差异或 Shell 跳过的成员可能丢失，原始成员身份和顺序不能完整保留 |
| 全局互斥锁 | 无关压缩包的解压也串行；它并不替代 UI 异步任务或跨进程缓存协调 |
| 向量加 HGLOBAL 复制 | 播放时可能暂时保留两份目标成员内容，增加 32 位进程内存压力 |
| 导入异常直接 `catch` 后返回 false | 无法清楚区分系统不支持、文件损坏、缺分卷、需密码或解压失败 |

上表中的误完成、超时和重名问题是根据实现得出的风险／缺口，本次未分别构造故障注入复现。

RAR 缓存键已经包含外层绝对路径、大小和修改时间；列表也已保存 `archive|member`，这些实现可以保留。路径规范化检查发生在成员路径处理阶段，未来自有后端应在任何落盘前进行校验，并拒绝不需要的链接及特殊对象。

### 4.4 已有支持还受音频后端约束

- ZIP／RAR 内 CUE 已有内存解析与逻辑成员引用路径。
- 导入显式排除 CDA、MID、MIDI、RMI，因为对应设备／文件名后端不能直接使用该成员流。
- DirectShow 源对归档成员返回 `E_NOTIMPL`；某格式能入表不代表所有回退解码器都能使用归档流。
- 文件属性窗口把归档成员设为不可写，不能直接修改包内标签／封面并自动重压归档。
- 7z／TAR 等没有归档导入分支；显式添加未知格式可能只产生一个普通、随后无法播放的文件项。

## 6. 建议的实现方式

### 6.1 保留入口，替换归档后端

保留现有列表操作、音频 Reader 和 `archive|member` 持久化规则，提供统一归档接口：

- Open：识别真实容器，返回明确错误。
- Enumerate：按归档顺序返回成员 ID、Unicode 名称、64 位大小、压缩／加密／分卷等属性。
- OpenMember：返回可读且可 Seek 的成员流，或受控的成员读取任务。
- Cancel／Progress／Status：提供可取消任务、进度和真实完成结果。

按需读出成员时校验解压结果；小成员使用有上限的内存缓存，大成员使用受控临时文件／映射。缓存有明确完成状态与清理策略，不再依赖目录停止增长。固实包可串行复用解码上下文或做有限预取，不能给每首歌无限制开线程重复解压前序数据。

UI 线程提交任务并处理结果；后台只做归档枚举／读取，不跨线程直接修改窗口控件或播放列表。任务完成前保持原列表可用，避免慢解压或失败留下半次导入。

### 6.2 RAR 首选维护中的 UnRAR

RAR4／RAR5 解压建议使用 RARLAB 维护的 UnRAR 源码，固定版本与 SHA256，通过独立适配层提供所需接口。官方提供源码和 Windows 开发者 DLL：[RARLAB 开发者下载](https://www.rarlab.com/rar_add.htm)。

理由：

- 与原版的解压架构接近，保留 ZIP／RAR 两种后端较容易。
- 可以明确处理解压错误、固实数据、密码和分卷请求，避免系统 Shell 行为差异。
- 无需自行照抄旧压缩算法，再从头实现 RAR5 的压缩和字典逻辑。
- 不要求用户额外安装 WinRAR；它也不应作为音频 Reader 插件来实现，因为一个归档会产生多首不同编码的曲目。

现代源码不等于天然兼容 XP。需使用现有 VC-LTL／YY-Thunks 构建策略，检查静态导入、线程及文件 API，再做 XP／Win7 真机或虚拟机测试。32 位进程必须限制字典、成员和总缓存大小；现代 RAR5 的更大字典不能无限制分配。[RARLAB 实现说明](https://www.rarlab.com/unrar7notes.htm)也要求集成方考虑字典内存限制。

### 6.3 可以放入重建的 ttpcomm，但须作为新接口

如果继续采用“公共能力集中到重建 ttpcomm”的方向，可把归档引擎只编入 `ttpcomm.dll`，由播放器使用新增、带版本协商的命名 C ABI：不改变旧导出序号、不跨 DLL 传递 STL 对象，明确句柄、缓冲释放责任及错误码。

这样播放器 EXE 不再重复携带解压器；总代码量及 DLL 大小仍会增加，实际体积需在实现后测量。只迁移 ZIP 头解析辅助，或只在 EXE 静态链接 UnRAR，都不能达到共享整个 RAR 引擎的效果。

### 6.4 其它压缩格式作为扩展阶段

原版行为恢复只要求 ZIP／旧 RAR；RAR5 是兼容性扩展。若还需要 7z／TAR／GZip 等，可在统一归档接口下评估 libarchive。其项目列出了 RAR／RAR5、7z、TAR、ZIP 等格式支持，但具体特性需逐项验证，不能将格式列表等同于全部密码、分卷和算法组合都可用。[libarchive 格式列表](https://github.com/libarchive/libarchive/wiki/LibarchiveFormats)。

为所有格式直接引入完整依赖集会增加构建和体积成本。当前优先补齐 RAR 引擎更符合原版恢复范围；未来再扩展过滤器、成员路径种类、CUE、持久化及错误提示，避免只改对话框扩展名。

## 7. 建议实施与验收顺序

1. **恢复 RAR4 基础语义**：内置后端、保持归档顺序、只枚举不整包解压、保留成员逻辑路径。
2. **补齐 RAR5**：Stored／普通压缩／固实、Unicode 文件名、各压缩算法版本；明确字典与大小上限。
3. **补齐任务控制**：后台读取、取消、准确完成通知，密码、缺卷、CRC／损坏与不支持功能的独立错误。
4. **完善缓存与流**：减少重复复制，限制大文件内存，避免重复解压及缓存误完成。
5. **修复 ZIP 现代边界**：UTF-8／Unicode 字段、CRC、ZIP64；与旧皮肤兼容策略分离。
6. **端到端回归**：主窗口／歌曲列表／列表空白处拖放、添加文件／文件夹、CUE、播放和 Seek、下一首、保存列表再打开、删除缓存再播放。
7. **系统矩阵**：XP、Win7、Win11；Win10 缺少环境时明确待验证，尤其不能以 Win11 Shell 测试代替。
8. 需要时再扩展 7z／TAR 等，作为新增能力单独验收。

测试继续保存在本地 `rebuild/tests`，不提交测试代码、不进入发布 Action。上线前验证原有 ZIP 皮肤及发行更新器行为，避免共享底层变更影响其它功能。
