# 文件内容与扩展名不一致时的解析和播放

分析日期：2026-09-23。原版范围：仓库根目录的千千静听 5.7，以及
`reverse/decompiled/TTPlayer.exe.pseudo.c`。第 1～8 节保留修复前的分析和基线；
后续恢复、其他格式矩阵及旧系统验证见
[综合恢复记录](FORMAT_ROUTING_RECOVERY.md)。

## 结论

原版可以在本次环境中播放“MP3 内容、`.flac` 后缀”的文件，但原因不是
FLAC 插件能解码 MP3，也不是宿主把所有错误后缀统一纠正为真实格式。

原版有两套互相补充的机制：

1. 对文件开头进行有限的格式探测，纠正一部分内部扩展名提示。
2. 按已注册的读取器列表依次尝试，普通识别失败后继续尝试，包括不限定扩展名的
   DirectShow Audio Reader。

修复前重建版存在对应差异：只要扩展名命中 AddIn，就选定插件播放源；插件
打开失败后，没有继续尝试系统播放源。本机的同一 MP3 副本在 `.flac`、
`.wma` 后缀下均因此打开失败；空 AddIn 目录下，系统播放源能解码这两个文件。

## 1. 原版入口与扩展名提示

- `004B0B51`：普通曲目进入 `004CBC1F`；CUE 子曲目等另外进入 `004E323B`。
- `004C7EDB → 004C5757`：取得文件名后缀；URL 还处理末尾路径和 `?` 参数。
- `004CB8DB`：创建文件 `IStream`，处理读写/只读和共享方式。
- `004CBC1F`：组织路径、流、格式提示、读取器和解码器的选择。

扩展名会影响文件对话框过滤和读取器候选资格。能够加入播放列表，只代表
通过了相应入口的筛选，不代表内容已经能成功解码。

这里的“纠正扩展名”发生在内存中的格式提示上，不会重命名磁盘文件，也不
会把 MP3 转换为 FLAC。

## 2. 文件头探测：004CBA11

该函数通过流包装读取开头 **16 字节**，然后调用 `004C8800(0, 0, 0)`
回到流起点。读取不足 16 字节时沿用传入提示。读满时的主要分支如下：

| 文件头条件 | 返回的内部提示 |
| --- | --- |
| 开头三个字节 `MAC` | `.mac`，对应 APE |
| 开头三个字节 `MP+` | `.mpc` |
| 开头三个字节 `TTA` | `.tta` |
| 开头四字节 `.RMF` | `.ram` |
| 偏移 4 的四字节为 `ftyp` | `.mp4` |
| 开头 16 字节匹配 ASF GUID | `.wma` |
| ID3 检查成功，且传入提示为空指针或为 `.wma` | `.mp3` |
| MPEG 帧头检查成功，且提示为空指针或为 `.asf/.wma/.ra/.ram/.rm` | `.mp3` |
| 其他情况 | 沿用原提示 |

ID3 检查调用 `ttpcomm.dll` ordinal 52，现有接口恢复名是 `id3_tag_query`。
MPEG 帧头检查调用 `004C8B0E`，验证同步位、版本、层、码率索引和采样率索引。
两者都只是这一阶段的提示判定，不能代替完整音频解析。

需要特别注意：

- **`.flac` 不在 MP3 提示纠正的条件中。** 无论文件以 ID3 标签还是 MPEG
  帧开头，都不能据此声称这个函数会把 `.flac` 改判为 `.mp3`。
- 此函数也没有完整的 FLAC、Ogg、WAV 等通用签名识别表。这些格式需要由后续
  读取器继续判断。
- 伪代码中的“空指针提示”不能简单等同于所有“无后缀文件”；调用者还会构造
  字符串对象，最终行为需要沿调用路径确认。

`004CBC1F` 会在取得流后使用这个探测结果；如果探测得到的新提示与原提示
不同，相关分支会更新提示并重新进入读取器枚举。

## 3. 读取器筛选与失败后继续尝试：004CBC1F

原版对注册的读取器逐项进行筛选：

1. 读取器有扩展名限制时，检查是否包含当前提示。
2. 读取器的限制字符串为空时，允许尝试。
3. 创建读取器，查询其支持的打开接口。
4. 支持路径打开的读取器走路径接口；其他读取器走 `Open(IStream, flags)`。
5. 重用文件流尝试其他流读取器前，回到流起点。
6. 成功则保留读取器，并按实际返回的音频格式准备解码；普通失败则释放当前
   候选，继续枚举。

因此，“继续枚举”不等于“把所有专用插件无条件试一遍”。有格式限制的
MP3、FLAC 等读取器仍然受候选筛选约束；无扩展名限制的读取器承担后备作用。
取消、网络错误和某些严重错误另有提前结束分支，不是所有失败都应被吞掉。

### 通用 DirectShow 读取器

原版注册链：

```text
004CA48E 初始化声音库
  → 004C9364 创建最后的通用读取器 factory
  → factory vtable 00523084
  → slot 3: 004C946E → 004C931C
  → 004E86B3 构造 DirectShow reader
```

交叉检查 EXE 二进制得到：

- factory 的名称函数 `004C93AD` 使用 `005232D0` 处的字符串
  `DirectShow Audio Reader`。
- 描述函数 `004C93D0` 请求资源 ID 0，没有生成特定扩展名列表；初始化留下
  空的扩展名限制，符合 `004CBC1F` 的无条件候选分支。
- `004E8BD6` 创建 DirectShow graph，添加源过滤器，以及播放器自己的
  `Audio Renderer` / `Video Renderer`，连接音频处理路径。
- `004E92C4 / 004E93AD` 从实际连接的媒体类型中提取格式信息。

`004E8BD6` 还有一个重要区别：只查询信息、没有播放位时，会先通过
`004E8912` 检查系统登记的扩展名及内置补充列表；播放位设置时不走这个
前置扩展名检查。因此某些文件可能在预读信息阶段失败，实际播放时成功。

最终能否打开仍取决于系统可用的 DirectShow 源过滤器和解码器。不能将
“本机这份 MP3 成功”扩大为“任意格式改成任意后缀在所有系统都成功”。

## 4. MP3 内容、FLAC 后缀的具体过程

结合伪代码、二进制 factory 和本机实测，路径为：

```text
mp3-content.flac
  → 文件名提示 .flac
  → 004CBA11 不把这个提示纠正为 .mp3
  → FLAC 读取器尝试打开，拒绝 MP3 内容
  → 宿主继续枚举
  → 无扩展名限制的 DirectShow reader 尝试实际文件
  → 系统过滤器识别 MPEG 音频并解码
  → 播放器取得实际音频格式，进入播放
```

成功后仍播放原始 MP3 音频。文件属性显示的是所用解析路径提供的真实媒体
类型；不会因为后缀为 `.flac`，就把有损 MP3 当成无损音频。

相同内容改成 `.wma` 则不同：本次样本从有效 MPEG 帧开始，满足
`004CBA11 → 004C8B0E` 的 `.wma → .mp3` 条件，可以进入内置 MPEG 读取器。
这也解释了两个副本显示的编码名称不同。

## 5. 真正的 MP3 解析和解码不靠后缀

内置 MPEG 路径中的几个关键函数：

- `004E48A7`：打开音频流，取得音频数据位置和大小，探测 MPEG 信息，构造
  `WAVEFORMATEX`（该分支使用 `0x55`，MPEG Layer 3）。
- `004E4DE4`：扫描和分析音频帧，取得采样率、声道、码率、时长等信息。
- `004E5303`：逐字节寻找候选 MPEG 帧，计算帧长，并检查下一帧头，避免仅
  凭一个看似同步字的字节组合认定文件有效。
- `004CD045`：依据读取器返回的压缩音频格式选择 decoder、协商输出格式。

DirectShow 路径则由系统过滤器完成相应识别和解码。两条路径都需要内容有效；
给损坏文件、文本文件换上音乐后缀，并不会让它成为可播放音乐。

## 6. 重建版修复前的差异

### 播放源在扩展名命中时就被固定

`src/audio/audio_engine.cpp` 的 `MakeBaseSource`：

```cpp
if (plugin_manager && plugin_manager->HasReaderForPath(path))
    return std::make_unique<LegacyPluginSource>(*plugin_manager, ttpcomm);
```

`LegacyPluginSource::Open` 调用插件管理器；找不到成功打开的读取器就返回
失败。后续 Media Foundation / Windows Media 播放源没有机会接手。

`src/plugins/plugin_manager.cpp` 的 `OpenReaderWithFlags` 确实会继续尝试
**扩展名匹配的其他插件 factory**，但不包含原版那种内置通用读取器。不能
把这个循环当成完整恢复了原版的候选链。

### 文件头纠正尚未统一接入

当前选择播放源和插件 factory 的入口使用文件名扩展名，没有接入
`004CBA11` 对应的统一格式提示修正。所以 `.wma` 伪装 MP3 也会先固定进入
ASF 插件路径。

### 文件信息读取与实际播放还可能不一致

- `src/app/file_info_worker.cpp` 的列表元数据读取会在插件失败后尝试内置
  信息读取；这与播放源失败即退出的行为不同。
- `src/audio/builtin_file_info.cpp` 的 `ReadBuiltinFileInfo` 仅对 `.mp3`
  直接使用 MP3 标签解析，其他情况可能落入 Shell 属性读取。
- `ReadShellFallback` 的 codec 文本由扩展名构造，并不证明读取到了真实
  编码；显示了时长或“FLAC Audio”不能作为成功使用 FLAC 解码的证据。

## 7. 2026-09-23 实测

只使用复制的音乐和隔离的原版程序目录。没有改名、改写用户音乐，也没有
修改原版日常使用的配置。副本的 SHA-256 完全相同：

```text
986e880739c9c53f92659cd76ad592442eb62a84e173f36183b2c9a5375fd341
```

样本开头：`FF FA E5 6C 53 CC 00 00 00 00 00 69 06 00 00 00`。
这是从 MPEG 帧开始的样本，不是 ID3v2 开头的样本。

### 原版界面验证

通过 computer-use 技能，在隔离原版中实际打开文件、观察播放进度，并查看
文件属性，没有提交任何标签修改。

| 同一 MP3 内容的后缀 | 结果 | 原版文件属性 |
| --- | --- | --- |
| `.flac` | 播放进度正常推进，观察到超过一分钟 | `MPEG-1 Audio`，48000 Hz，立体声，320 Kbps，5:03.672 |
| `.wma` | 播放进度正常推进，观察到超过一分钟 | `MPEG 1 Layer 3`，48000 Hz，立体声，320 Kbps，5:03.672 |

这是界面和播放状态验证，不是主观音质或逐位音频一致性结论。具体执行路径
是由静态调用链、factory 二进制和显示结果共同判定，未进行逐指令动态跟踪。

### 修复前重建版解码入口验证

先从当前源码重新构建 `pcm_integrity_probe` 和 `sound_addin_probe`，再调用
与播放共用的 `CreateDecodedAudioSource`。解码探针不打开音频输出设备。

| 后缀 | 使用完整原版 AddIn | 使用空 AddIn 目录 |
| --- | --- | --- |
| `.mp3` | 成功 | 未额外测试 |
| `.flac` | 失败 | 成功 |
| `.wma` | 失败 | 成功 |
| `.wav` | 成功 | 未额外测试 |

成功样本都解出 30 秒、48000 Hz、双声道、16-bit PCM，共 2,880,000 个
标量采样；8192 / 65536 字节两种读取块大小的输出一致。

单独的插件探针确认 `.flac` 副本失败在
`reader slot 3 Open(IStream, flags)`，HRESULT 为 `0x80004005`。
空 AddIn 的对照说明本机系统播放源能够解码此文件，主要问题是候选链被
扩展名对应的插件截断，而非本机完全缺少 MP3 解码能力。

## 8. 建议修复顺序

1. 恢复完整候选流程：专用读取器不识别内容时，释放失败实例并继续尝试通用
   播放源；保留取消、文件访问失败等应终止的语义，避免无限重试。
2. 恢复 `004CBA11` 对应的共享格式提示探测，让播放和信息读取使用同一结果；
   实际路径保持不变，流位置在尝试间恢复。
3. 让 codec、标签和封面依据成功读取器/已验证内容决定；不要用错误后缀决定
   标签写入格式。
4. 分别验证普通版和 XP / Win7 版。普通版可评估现有 Media Foundation 作为
   系统后备源；若要求原版路径一致，需要恢复 DirectShow 后备。旧版必须单独
   验证，不能将 Media Foundation 的可用性和格式支持作为前提。
5. 再补充 MP3→FLAC/WMA/WAV、FLAC→MP3、有 ID3 和无 ID3、未知后缀、损坏
   内容等回归矩阵。

若另外实现“根据可靠文件签名，为所有支持格式重新排序候选”的完整内容
识别功能，应明确这是兼容性增强。原版 `004CBA11` 本身没有实现如此完整的
统一识别器，不能将增强功能描述为逐分支原样恢复。
