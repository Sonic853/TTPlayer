# Winamp 音效插件的 PCM 位深：接口、插件和 TTPlayer 播放链

日期：2026-10-19。本文是分析报告，没有修改播放器或第三方插件。

## 1. 结论

**Winamp DSP 接口可以承载高于 16 位的整数 PCM，但并不是所有 Winamp 音效插件都实现了高位深处理。原版 TTPlayer 5.7.9 和当前重建版的正常播放链，都会先转换成 16 位 PCM 再调用这些插件。**

需要分别判断三个问题：

| 问题 | 结论 |
| --- | --- |
| 接口能否传递 24／32 位 PCM？ | 可以，`ModifySamples` 带有 `bps` 参数；实际插件需按此解释缓冲区。 |
| 每个插件是否都能处理？ | 不能统一判断。有的明确只处理 16 位，有的有 24／32 位分支，有的存在分支但返回值仍有问题。 |
| 当前 TTPlayer 是否把高位深数据传给插件？ | 没有。原版实际调用和当前实现都传入 `16`。 |
| 将输出设备设为 24／32 位能否解决？ | 不能恢复插件输入前已经量化丢失的细节。设备格式和插件输入格式是两个边界。 |
| 没有启用 Winamp DSP 时是否也强制经过这个 16 位步骤？ | 不会经过此插件转换分支；另有“输出位深自动选择”的独立问题，见第 6 节。 |

XMPlay 开发者 Ian 对 Winamp DSP 包装层的解释也明确区分了 16／24／32 位整数输入和插件自身的支持程度；其说明与这里检查到的接口和代码一致。[开发者原帖，第 27 条回复](https://www.un4seen.com/forum/?topic=6985.20)

## 3. Winamp DSP 接口究竟规定了什么

### 3.1 `short*` 不是“整个接口只允许 16 位”的充分证据

本地 `winamp/Src/Winamp/DSP.H:17` 的核心回调为：

```cpp
int ModifySamples(winampDSPModule* module,
                  short* samples,
                  int numsamples,
                  int bps,
                  int nch,
                  int srate);
```

`samples` 的历史声明是 `short*`，但另有 `bps` 告诉插件如何解释实际字节。支持高位深的插件会重新解释该地址：

| `bps` | 常见整数 PCM 布局 | 双声道一帧的字节数 |
| --- | --- | ---: |
| 16 | 每声道 2 字节有符号整数 | 4 |
| 24 | 每声道 3 字节打包有符号整数 | 6 |
| 32 | 每声道 4 字节有符号整数 | 8 |

**不能把 `bps` 改成 24／32，却继续分配 `int16_t` 大小的缓冲区。** 那会改变插件读取步长，可能产生错误声音或越界。

本地 Winamp 宿主 `winamp/Src/Winamp/DSP.cpp:76` 将收到的 `bps` 继续传给回调；WavPack 输入插件 `winamp/Src/Plugins/Input/in_wv/in_wv.cpp:698` 也把 `curr.output_bits` 传入宿主 DSP 链。这是接口实际允许不同位深的源码证据，不只是参数名称上的推断。

### 3.2 32 位整数不等于 32 位浮点

经典接口没有 `isFloat`／采样格式枚举。`bps == 32` 不能被宿主自行解释为 IEEE float32。

SPS 的内部通用函数确实有 `isfloat`，但它自己的 Winamp 入口在 `dsp_sps.cpp:270` 明确传 `0`；同一内部算法供其他宿主使用的浮点分支，并不自动成为 Winamp ABI 的浮点能力。

同理，“插件内部使用浮点／双精度计算”不能证明它允许高位深整数输入，也不能证明能够完整保存 32 位整数的所有有效位。

### 3.3 没有统一的格式能力协商

经典 `winampDSPHeader`／`winampDSPModule` 没有查询支持位深、声道布局或浮点格式的回调。`DSP_HDRVER` 的 0x20／0x21／0x22 变化涉及头部、`sf` 和 HWND 参数，不能用来推断高位深支持。

`ModifySamples` 返回的是输出帧数，并不是“该位深支持成功”的布尔值。不支持时原样返回 `numsamples` 的插件，可以表现为完全旁路；因此“没有崩溃、返回帧数正常”不是高位深音效生效的验证。

## 4. 具体实现的支持情况

| 对象及本次证据 | 16 位 | 24 位 | 32 位整数 | 限定 |
| --- | --- | --- | --- | --- |
| Winamp SDK `dsp_test.c` 示例效果 | 有处理 | 相关效果分支跳过 | 相关效果分支跳过 | 源码反复以 `bps == 16` 作为处理条件，不能代表所有插件 |
| 本地 Winamp SPS 源码快照 | 有处理 | 有读入、处理、写回分支 | 整数输入分支仍有 TODO | 不是对本地旧版 `Plugins/dsp_sps.dll` 的版本鉴定 |
| 本地 `dsp_Dolby.dll` | 双声道处理 | 被位深条件跳过 | 被位深条件跳过 | `10001877` 比较 `bps` 与 `0x10`，同时检查双声道 |
| 本地 `DSP_VAPXP.dll` | 双声道处理 | 被位深条件跳过 | 被位深条件跳过 | `100028B8` 比较 `bps` 与 `0x10`，另检查双声道 |
| 本地 `Dsp_Dfx.dll` | 有处理 | 找到完整整数读写转换分支 | 找到转换分支，但写回返回路径异常 | 不能把“有 32 位分支”标成“32 位完整兼容”；见下文 |
| 本地 `dsp_izOzone.dll` | 有处理 | 找到通用多字节整数读写分支 | 同一分支可覆盖 4 字节整数 | 单／双声道，内部存为 float；真实初始化和高位深音频输出尚未在本轮验证 |
| 本地 `dsp_skywalker.dll` | 既有 16 位使用路径 | 尚未闭合证明 | 尚未闭合证明 | 入口使用位深计算步长，但这不足以证明下游正确 |

### 4.1 SPS：24 位明确实现，不能顺推 32 位整数也实现

`winamp/Src/Plugins/DSP/dsp_sps/sps_common.cpp`：

- 第 71／83 行：`int24todouble` 和 `doubletoint24`。
- 第 320 行附近：24 位数据按 3 字节读取，支持单声道和双声道。
- 第 442 行附近：处理结果按 3 字节写回。
- 第 337 行：剩余整数输入分支仍为 `todo: 32 bit mode?`。
- 浮点分支虽存在，但经典 Winamp 入口不启用它。

应按实际分支判断，不能因源码含有 `float`、`double` 或一个过时的 TODO 注释，就扩大或否定已实现的 24 位路径。

### 4.2 DFX：24 位转换已找到，32 位还存在明显异常

这份本地 DLL 的链路为：

```text
ModifySamples 10001810
  → 格式设置 10003A80
  → 处理包装 100037F0
    → PCM 转 float 1003EB20
    → 音效处理 10010D50
    → float 转 PCM 1003F3F0
```

经读取 DLL 内实际跳转表：

- 24 位输入选择 `1003EC91`，按 3 字节组合带符号样本，乘 `1/8388608` 后存 float。
- 24 位输出选择 `1003F485`，相应完整分支按 3 字节写回，并返回成功。
- 32 位、有效位同为 32 的输入选择 `1003F300`，以整数读入，随后存为 float。
- 对应 32 位输出选择 `1003F65A`，确实写了 4 字节样本，但尾部进入 `1003F688`，返回 `1`。
- 上层 `100037F0` 把这个非零值作为失败，再使 `ModifySamples` 的 `10001945` 路径返回 0。

因此这份 DLL **具有 24／32 位转换代码，但不能据此宣布 32 位回调完整可用**。当前 TTPlayer 忽略插件返回帧数，还可能掩盖这个问题。需要真实初始化后的离线 PCM 对照进一步确认，不应直接默认启用 32 位。

此外，内部 float32 在接近满幅时不能逐个区分全部 32 位整数值；“32 位容器输入”也不意味着“保持 32 位整数无损”。

### 4.3 Ozone：并非入口硬编码 16 位

`5941A6C0` 转入 `5941A6F0`：

1. 接收 `bps`，以 `(bps + 7) >> 3` 计算每样本字节数。
2. 创建 `WAVE_FORMAT_PCM` 格式，而不是浮点格式。
3. 对单声道和双声道分别处理；1 字节、2 字节有专门路径，其他字节数走通用整数路径。
4. 通用路径按最高字节符号位还原整数，按位深归一化，存入 float 数组后处理。
5. 处理后按字节数限制幅度并写回原来的整数布局。

具体多字节路径包含单声道的 `5941AAE3`、双声道的 `5941B0BD`；对应输出循环也按字节数写回。新鲜反编译与指令证据一致，**静态上支持“存在高于 16 位的处理实现”这一结论**。

仍未完成的验证是：实际插件初始化、预设、静音／削波／低位数据、连续换格式，以及返回帧数与全部 DSP 算法的组合。本文不把静态分支直接写成所有系统的运行通过结论。

## 5. 原版 TTPlayer 实际向插件传了什么

原版的通用包装 `004280CD` 按 `(bits >> 3) * channels` 计算步长并转发位深，包装函数本身并非完全写死 16 位。

但正常播放调用点 `004AC166` 选择了 16 位。关键指令为：

```asm
004AC1ED  PUSH 10h
004AC1EF  POP EAX
004AC1F0  CALL 004AA360       ; 转换到 16 位
...
004AC1FF  PUSH 10h           ; 给 DSP 的位深
004AC201  PUSH ECX           ; 声道数
004AC202  PUSH [EAX+4]       ; 当前输出采样率
004AC20B  CALL 0042898D
004AC213  CMP WORD [EAX+0Eh],10h
```

原版这一段的顺序是：

```text
解码／内置音效 → 重采样 → 16 位量化 → Winamp DSP
                                      ↓
                         必要时扩展为设备所需的 24／32 位
```

`004AA8B0` 的高位深扩展不会恢复已丢弃的输入低位。不能因为声卡显示 24／32 位，就认定 Winamp 插件接收到相同精度。

## 6. 重建版实际行为及另行发现的差异

### 6.1 固定 16 位是当前明确的宿主策略

- `src/audio/audio_engine.cpp:1890`：仅在有活动 DSP 时进入转换。
- `src/audio/audio_engine.cpp:1895`：创建 `vector<int16_t>`。
- `src/audio/audio_engine.cpp:1900`：用 `llround` 转整数。
- `src/audio/winamp_dsp.cpp:238`：调用包装固定给插件传 `16`。
- `src/audio/winamp_dsp.cpp:834`：公开处理入口是 `span<int16_t>`。

因此，仅增加一个“插件位深”下拉框或修改一个整数参数不够；缓冲区、步长、量化、插件选择、异常处理都必须配套。

`include/ttplayer/audio/winamp_dsp.h:50` 的注释“Winamp 的 ABI 是 signed 16-bit”表述过宽。正确含义应是“TTPlayer 当前兼容路径选择 signed 16-bit”，应在后续修复中更正。

### 6.2 位深一致，不代表调用顺序完全一致

当前微型探针直接编译真实 `audio_engine.cpp`、`winamp_dsp.cpp`、`pcm_output_transform.cpp`，使用测试 DSP，记录到：

```text
DSP bits=16 rate=44100 final_bits=24 final_rate=48000
```

当前 Winamp DSP 在重采样之前运行；原版是在重采样之后运行。启用重采样时，依赖采样率的插件会收到不同格式。转换功能的内置音效／重采样顺序也应一起整理，详见播放器总审计。

当前 `llround` 在正负半整数处远离零取整；已经恢复的原版量化器在本次默认舍入环境中采用偶数舍入。真实源码探针中：

| 以 16 位 LSB 为单位的输入 | 当前插件前量化 | 已恢复量化器 |
| ---: | ---: | ---: |
| +0.5 | +1 | 0 |
| -0.5 | -1 | 0 |
| +2.5 | +3 | +2 |
| -2.5 | -3 | -2 |

这证明有可测量的数值差异；并不等于可以在所有音乐中听出差异。插件边界的 dither／舍入时机应与原版统一。

### 6.3 “自动输出位深固定 16 位”是另一个问题

当前 `PcmOutputTransform` 对 `OutputBits=0` 默认选 16。微型探针对 8／16／24／32／64 位输入均得到 16。

原版 `004AB1C4` 在设置值为 0 时先读取解码器位深，再接受 8／16／24／32，其他值才退到 16。因此 64 位输入退到 16 本身符合该验证规则，24／32 位整数输入也全部退到 16 才是明确差异。

此问题发生在输出格式选择，不能通过修改 Winamp 插件参数解决；没有 DSP 时也需要单独修正。

## 7. 建议如何增加高位深插件能力

### 第一阶段：恢复现有兼容路径的一致性

1. 先修自动输出位深，避免把它误诊为插件问题。
2. 统一播放／转换的处理阶段，把 Winamp DSP 放在与原版一致的位置。
3. 用已有 PCM 量化器处理插件前转换，恢复舍入和 dither 时机。
4. 改正“ABI 只能 16 位”的注释。

### 第二阶段：作为扩展，增加逐插件能力表

- 未验证插件保持 16 位，与原版行为一致。
- 能力记录至少绑定 DLL SHA-256、模块编号、整数布局、位深、声道数、允许采样率，以及是否允许输出帧数改变。不能仅用 DLL 文件名判断。
- 对已验证的 24 位插件使用正确的 3 字节 PCM。不能用 32 位容器假冒打包 24 位。
- 32 位单独验证；DFX 的异常返回路径需要先查清。
- 不向经典插件直接传 float32。需要浮点插件时应使用明确的另一个接口／桥接协议。
- 只有链上存在 16 位插件时才在该边界降位；后面恢复更宽容器不会恢复此前精度。可以先实现整条链采用共同验证格式，再考虑逐插件转换，避免引入不必要的多次量化。

### 第三阶段：离线验证后再开放设置

必须验证的不只是“能播放”：

- 16／24／32 位正负极值、零、很小信号、只在低 8／16 位不同的输入。
- 已知有效的效果预设与旁路对比，防止“返回正常但未处理”。
- 单／双声道、交错顺序、连续块、seek／停止／切歌和格式改变。
- 缓冲区前后保护、返回帧数、失败和超时恢复。
- 未知插件保持兼容默认值，不在实时播放线程试探不同位深。
- XP／Win7／Win11 逐个插件验证；不能用旧的 16 位生命周期测试代替高位深 PCM 测试。

另外，当前 TTPlayer 和原版都忽略 `ModifySamples` 的输出帧数，把它当原地变换。某些变速／变长插件需要另一个可变帧数队列设计；这与高位深不是同一个功能，应独立规划。
