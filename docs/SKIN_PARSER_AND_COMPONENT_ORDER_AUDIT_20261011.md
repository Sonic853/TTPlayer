# 原生皮肤解析与组件显示顺序复核

日期：2026-10-11。初次分析的重建版源代码基线：`e34ec60`。

> 第 1～11 节保留修复前的审计结论；按第 9 节顺序实施的修复、验证和剩余边界见第 12 节。

## 1. 结论与范围

当前原生皮肤已经具备完整的主要窗口框架，但**“皮肤能加载”不等于“所有组件均按原版显示与响应”**。这次发现的主要缺口包括无滑块进度条、无图片工具栏、缺省滚动条、重复节点处理，以及组件绘制、命中和预览顺序不统一。

本报告以根目录 TTPlayer 5.7.9 的伪代码为主，必要时核对已有反汇编。6.1.2 的 PNG、动画等作为已有扩展单独看待，不把它们倒推为 5.7.9 原有行为。范围是 `.skn` / `Skin.xml` 原生皮肤；`waskin` 的 Winamp 皮肤语言、各业务对话框资源不属于同一解析器。

证据级别：

- **已确认代码差异**：原版解析/绑定路径与现有源码可直接比较。
- **样本命中**：已有包确实包含触发该分支的属性；不代表本次做过该皮肤的原版/重建版屏幕对照。
- **待动态核实**：需要原版实际窗口枚举、重叠皮肤或像素比较，不能仅凭调用顺序宣称最终画面完全一致。

本次检查 `Skin/**/*.skn` 共 **177 个包**，全部有原生 `Skin.xml`。这是静态文本盘点，不是 177 个包的逐帧实测。统计脚本及明细留在私有 `tests/skin/parser_audit_20261011.py/.json`，未加入 Actions。

## 2. 原版的实际处理链

```text
外部 SKN / ttpres.dll 内置 ZIP
  → 004A747D 读取 Skin.xml
  → 004A7929 / 004A8315 校验元数据、分派窗口节点
  → 各窗口解析器把节点写入固定用途的字段
  → 按需读取 Visual.xml、Lyric.xml、PlayList.xml
  → 控件创建函数建立固定用途的 HWND
  → 绑定图像、坐标、字体和颜色
  → 加载该皮肤的用户配置，恢复窗口状态
  → 父窗口背景绘制 + 各控件绘制/裁剪/输入
```

主要原版入口均位于 `reverse/decompiled/TTPlayer.exe.pseudo.c`：

| 地址 | 用途 |
| --- | --- |
| `004A747D` / `004A7929` | 包加载、窗口分派 |
| `004A8315` | `version=2`、名称、作者、URL、邮箱、透明色 |
| `004A8536` | 主窗口及迷你窗口 |
| `004A88D0` | 窗口歌词 |
| `004A8B73` | 均衡器 |
| `004A8DC6` | 播放列表 |
| `004A92A2` | 桌面歌词工具栏 |
| `004A95B0` / `004A962F` | 按钮、滑条 |
| `004A9770` / `004A988C` | 文字、图片元素 |
| `004A9993` | 滚动条 |
| `004A9D02` / `004A9D39` / `004AA061` / `004AA150` | 矩形、颜色、字体、对齐 |
| `004A77D4` / `004A7B06` | 单独的 `downwnd_skn.xml` 下载界面配置 |

重要区别：**XML 遍历顺序、同名节点覆盖顺序、HWND 层级、控件内部绘制顺序，是四种不同的顺序。** 原版没有把所有 XML 元素追加到一个通用显示列表，也没有从 XML 读取通用 `z-index`。

## 3. 已具备的基础能力

以下不应再列为“完全没有实现”：

- 内置 ZIP / 外部包、按内容区分 BMP 与 GDI+ 图片、图片生命周期和共享缓存。
- 主窗、迷你窗、歌词窗、均衡器、播放列表和桌面歌词工具栏的主要节点。
- 四态按钮，播放/暂停共用用途，LED 数字条、歌曲信息滚动、状态文字。
- 图片原始尺寸、标题对齐、九宫格/平铺、窗口区域、歌词迷你边框。
- 皮肤专属配置、换肤保留控件、失败回退、桌面歌词工具栏整体回退。
- 后续版本扩展：PNG Alpha、按钮/进度动画、`Color_SelText`、部分播放模式按钮。

已有 `SKIN_PNG_RECOVERY.md`、`SKIN_ALIGNMENT.md`、`PURPLEMYTH_SKIN_RECOVERY.md` 等记录了相关验证。但其测试覆盖不能证明本报告下列边界全部通过。

## 4. 优先补齐的显示缺口

### 4.1 无滑块图片的进度条被整体跳过

**已确认，优先级高。**

- 原版 `0045287B` 分别处理底图、缓冲层、进度填充和滑块。缺少 `thumb_image` 不应连带取消已有的填充图。
- 重建版 `PlayerWindow::PaintSkin` 使用 `progress && progress->thumb_image` 作为整个进度条绘制分支的入口，底图/填充都在此分支内。
- 当前点击定位的代码允许滑块宽高为零，所以可能出现“区域仍能响应，进度却不显示”。

样本：**23 个包、27 个主窗/迷你窗节点**。包括 `007 F1 racing.skn`、`008 Half-Life 2.skn`、`046 Neutral.skn`、`176 Gant2 Ocean.skn`、`Rainbow.skn`、`ouptix.skn` 等。

建议：分别判断每个图层是否存在，以进度控件本身的有效矩形作为入口；补横向、竖向和无滑块定位的对照。

### 4.2 缺少自动生成的文字工具栏

**已确认，优先级高。**

原版 `0047E6FC` 在工具栏没有图片时调用 `0047E512`：

1. 读取工具栏菜单文字；
2. 创建每项 32 像素、16 像素高的文字图带；
3. 使用系统文字色和阴影色绘制；
4. 继续绑定工具栏命令和提示。

重建版 `PaintPlaylist` 只在 `layout.toolbar.image` 存在时绘制；`UpdatePlaylistToolRects` 也在图片缺失时提前返回。因此不是仅少一幅装饰图，而是缺少原版的文字及按钮回退。

**6 个现有包命中**：`005 dudu.skn`、`020 ironger-mcEgl.skn`、`043 金属特质BIG.skn`、`077 愁.skn`、`147 DarkHeaven.skn`、`晶莹剔透.skn`。这些包均提供了非空工具栏位置。

### 4.3 缺省滚动条的回退仍不完整

**已确认绘制/几何路径缺口。**

原版 `0047E6FC` 有未提供自定义滚动图片的分支，并配置默认滚动条；具体旧系统主题下的像素外观仍需实测。

重建版 `MakePlaylistGeometry` 仅在歌曲超出一页且 `scrollbar_buttons.size.cx >= 3` 时保留滚动条宽度。没有图片时宽度为零。同时 `PlaylistListWindowProc` 吞掉 `WM_NCCALCSIZE` / `WM_NCPAINT`，不会自动让原生 ListView 补画系统滚动条。

**6 个包未提供该图像**：`014 ironger-DashAmp_Glass.skn`、`035 KK Player.skn`、`077 愁.skn`、`080 红粉佳人.skn`、`108 漂亮美媚.skn`、`xiuxiqqTT.skn`。

建议：统一自定义/缺省滚动条的几何与输入路径，覆盖右侧曲目列表、左侧列表及媒体库树的边界，不仅补一幅静态图片。

### 4.4 重复组件的覆盖语义不一致

**已确认，且现有包触发。**

原版将同一用途的节点依次写入同一个字段。反汇编中可见 `progress` 固定写入 `+0x284`，`volume` 固定写入 `+0x308`，`icon` 的文本矩形固定写入 `+0x394`，不会因第二个同名节点额外建立控件。后面的有效属性可以更新前面的值；空图片加载失败是否保留旧图片，需要按字段处理，不能简化成整对象覆盖。

重建版主窗/迷你窗把每个节点都追加到 `elements`：

- `Find` / `FindMini` 从前往后找第一个；
- 按钮绘制可以遍历多个同名元素；
- `HitTestSkin` 从后往前找；
- 预览遍历所有元素。

所以同一个组件可能出现“绘制、提示、动作几何使用不同记录”。

样本：`106 JukeOn.skn`、`143 BluePlayer.skn` 的主窗重复 `icon`；`Future.skn`、`Future 1.5版.skn` 重复 `pause`。

建议：恢复按用途归并的描述表和逐字段覆盖规则，再统一解析结果的消费者。

## 5. 各组件显示顺序与层级

### 5.1 怎样理解下面的顺序

下面列出的原版顺序是**控件创建先后**，不是声称任意重绘时刻都按该顺序直接涂像素。运行时还涉及 `SetWindowPos`、窗口区域、父背景复制、控件裁剪和显隐。

本次做了一个隐藏 Win32 父/子窗口的小探针：依次创建 101、102、103，`GW_CHILD → GW_HWNDNEXT` 枚举也是 101、102、103。因此不能把“最后创建”直接理解为“最上层”。该探针只验证本机 User32 基本行为，未代替原版各窗的动态枚举。

### 5.2 主窗口、迷你窗口

原版 `0045FAD8 → 0044E50C → 00467B9B` 的主要创建顺序：

| 顺序 | 组件 |
| --- | --- |
| 1 | 基类关闭/退出按钮、广告用途按钮 |
| 2 | 菜单工具栏框架（与皮肤可见按钮不是同一组件） |
| 3 | 最小化 → 迷你模式 |
| 4 | 均衡器 → 歌词 → 播放列表 → 浏览器 |
| 5 | 播放/暂停共用控件 → 停止 → 上一首 → 下一首 → 打开 → 静音 |
| 6 | 图标 → 滚动歌曲信息 → 可视化 → LED |
| 7 | 声道文字 → 状态文字 → 进度条 → 音量条 |

`004710FD` 将皮肤各字段绑定到这些固定控件，多次位置更新使用 `0x14`，包含 `SWP_NOZORDER`。XML 中把 `<play>` 挪到 `<info>` 前后，并不等于重新安排这些 HWND 的层级。迷你模式主要重新绑定同一组控件的布局，不是根据迷你 XML 顺序重新建立一套层级。

重建版 `PaintSkin` 的画布顺序则是：

```text
背景
 → XML 顺序中的四态按钮
 → 进度条
 → 音量条
 → info
 → LED
 → icon
 → 复制到窗口 DC
 → stereo
 → status
```

可视化是独立 HWND，其区域在父窗口最终复制时被排除。主窗按钮、文字、滑条则主要由父窗口代画。

**仍有差异：**

1. 按钮之间采用 XML 顺序，原版是固定控件结构。
2. 按钮和信息/滑条之间采用另一套固定绘制顺序。
3. 鼠标命中却按 XML 逆序，未使用上述实际图层次序。
4. 主窗按钮没有复用歌词/均衡器已经使用的首帧区域命中规则，`PtInRect` 会把透明角也计入。

一个可直接从代码构造的冲突：将重叠的 `info` 写在 `play` 前面，画面中 `info` 最后覆盖按钮，而逆序命中先得到 `play`。这已经说明绘制与输入顺序不自洽；原版精确遮挡像素还应通过重叠样本核对。

### 5.3 均衡器

原版 `00429AAA`：

```text
enabled → profile → reset
 → balance → surround → preamp
 → 十个频段
 → 0044E50C 创建 close / advertise
```

重建版 `CreateEqualizerControls` 把 `close` 放在第一个创建，其余主要控件顺序与上述主体基本对应。`PaintEqualizer` 为：

```text
背景 → title → close → enabled → profile → reset
 → balance → surround → preamp → 十个频段
```

`EqualizerHitTest` 又按 `close → enabled → profile → reset → 各滑条` 查找。滑条可能在画面中后画盖住按钮，但先命中的仍是按钮。子控件的 `WM_PAINT` 只验证更新区域，实际内容由父窗口合成，因此“已经创建 HWND”仍不能证明重叠关系还原。

建议：修正创建顺序和合成/命中顺序的关系；测试关闭按钮与其他按钮、按钮与滑条、频段之间的重叠以及透明区域。

### 5.4 播放列表

原版 `00482BAF`：

```text
ToolbarWindow32
 → 分隔/列表容器
    → LibraryTree
    → PlayLists
    → Files
 → 基类 close / advertise
```

背景与标题属于父窗口绘制；`0047EC2F` 处理标题图片。工具栏与列表属于实际子窗口，分隔区域还有父子裁剪关系。

重建版：

- LibraryTree / PlayLists / Files 已恢复真实控件相关行为，但直接挂在播放列表顶层窗口下；
- 工具栏拆成多个代理按钮；
- `PaintPlaylist` 按背景、列表内容、工具栏、滚动条、标题、关闭按钮的顺序合成；
- 列表子控件的绘制消息被截获，内容仍主要由父画布负责。

因此标题、工具栏、列表、滚动条互相覆盖时，不能宣称与原版层级相同。普通不重叠皮肤看起来一致，并未覆盖这种差异。应补原版的容器裁剪及无图片回退，而不是简单把全部节点改成 XML 正序或逆序。

### 5.5 窗口歌词

原版 `0044AD55` 主要顺序：

```text
desklrc → ontop → LyricCtrl → 基类 close / advertise
```

中间创建的桌面歌词控制窗是独立弹出窗口，不应算作同一父窗的普通子控件。

重建版 `CreateLyricControls` 的核心顺序已基本对齐：桌面歌词按钮、置顶、歌词控件、关闭，以及保留的隐藏按钮。父窗口背景/标题、按钮恢复父背景、歌词控件的独立绘制也已有实现。

此处应列为**主要结构已恢复，重叠与透明边缘待专项验证**，不应与主窗口一起归为“所有层级都未恢复”。还需覆盖标题横跨按钮、歌词矩形覆盖标题、普通/迷你往返、编辑器/全屏附着后的层级。

### 5.6 桌面歌词工具栏

原版 `00418B74`：

```text
icon → play/pause → prev → next → list
 → lines → kalaok → settings → lock → ontop → return → close
```

重建版 `CreateBarChildren` 保留了这组主要创建顺序，在末尾追加 `zoomin` / `zoomout` 扩展。

但 `PaintBarContents` 按数组正序把按钮合成到整幅背景，而原版有独立按钮绘制。**创建顺序相同不等于重叠像素已经验证一致。** 自定义工具栏按钮重叠时仍需检测实际命中、重绘和透明区；无重叠情况下没有证据把它判为普遍显示错误。

### 5.7 控件内部顺序

| 控件 | 原版要点 | 当前状态 |
| --- | --- | --- |
| 普通按钮 | 父背景/控件区域、四态中的当前帧、命中区域 | 四态已恢复；主窗透明命中未统一 |
| 普通滑条 | 底图或父背景 → 填充 → 滑块 | 大部分恢复；主窗无滑块进度条被整体跳过 |
| 网络进度条 | 底图 → 缓冲填充 → 已播放填充 → 滑块 | 缓冲层数据与绘制未接通 |
| 歌词按钮 | 先恢复父背景/标题，再画当前状态 | 已有对应实现 |
| 列表项 | 行底色/选择图 → 文本、编号、时长 → 焦点/拖放指示 | 已有实现；本次不重复宣称所有列表交互已逐像素验证 |
| 皮肤预览 | 原版复用控件配置和窗口渲染路径 | 重建版独立循环，见下一节 |

## 6. 预览和真实主窗口仍有两套规则

`RenderSkinPreview` 按 `source.Elements()` 正序绘制文字、图标、滑条和图片；实际 `PaintSkin` 使用第 5.2 节的分类绘制顺序。重叠布局下，预览与实际窗口就可能不同。

图标还有一个独立的确定差异：

- 预览已按 ICO 原始尺寸在 XML 矩形中居中，并裁剪到矩形；注释对应原版 `00415D3D / 0041606F`。
- 实际主窗口仍在 `icon.bounds.left/top` 直接绘制系统小图标尺寸，没有相同的居中及局部裁剪。

例如较高的图标槽位不能仅靠正常 16×16 皮肤测试证明正确。应共享图标布局、组件描述、图层/遮挡规则；预览保留停止状态、零进度、固定示例音量等原版预览状态，不强行使用实时播放状态。

另一个边界是未知节点：原版 `004A8536` 仅分派已识别名称；当前主/迷你解析会保存任意元素。预览末尾的通用图片分支可能把未知节点的 `image` 画出来，而实际主窗口不会按同样方式显示。应明确原版白名单与扩展白名单，避免“预览有、实际没有”。

## 7. 字体、默认值和解析边界

### 7.1 播放列表字体：必须同时修复数据模型和应用规则

原版 `0048E635` 从现有设置复制完整 `LOGFONTW`；`0048E696 → 0048DE50` 支持 13 个数值字段和字体名，也支持 `base64:` 的 ANSI/Unicode LOGFONT。

当前 `LoadPlaylistColors` 只取字体名和高度，`ApplyPlaylistSkinDefaults` 还会清空 `font_descriptor_valid`。包内的字重、斜体、字宽、字符集等无法完整保留，base64 字体也没有经过完整解码。已有 `xiuxiqqTT.skn` 的包内字体包含 `lfWeight=700`，是验证该数据缺口的现成样本。

**但不能据此直接认定原版一切换到该包就必须显示粗体。** 进一步检查发现，5.7.9 `0047E6FC` 的换肤分支复制了包内列表颜色，没有像歌词 `0044919C` 那样复制整份字体。实际列表 `0048301E` 使用的是全局 `DAT_00547CC8`。完整字体还可能由主配置、皮肤旁路配置或用户导入方案提供。

因此建议：

1. 在皮肤模型中完整保留 LOGFONT 与“是否提供”状态；
2. 将普通换肤、首次启动、显式导入列表方案的字体应用规则分开；
3. 先核对原版字体保留/覆盖行为，再应用修复；不要只把 `font`/`height` 改成 LOGFONT 后无条件覆盖用户设置。

歌词包也有缺省值差异：原版 `0048EA53` 以当前全局字体为种子；重建版 `LoadLyricColors` 每次初始化为系统消息字体，仅在 `LegacySkin::Load(current)` 中继承颜色，没有继承字体。缺失/稀疏 Lyric.xml、且没有用户配置覆盖时，需要专项核对。

### 7.2 元数据验证与正式加载不共用同一入口

`ParseLegacySkinMetadata` 检查 `version == 2`，用于菜单信息；`LegacySkin::Load` 正式加载没有执行同样的版本检查。`LoadSkin` 只先检查包有 `Skin.xml`。

原版 `004A7929` 在完整加载标志 `0x7f` 时调用 `004A8315` 校验版本。当前存在“菜单元数据拒绝，而直接/配置加载仍接受”的分叉。应统一元数据校验，保留已有合法历史包的兼容修正规则。

### 7.3 透明色缺省值不一致

原版根节点和 `desklrc_bar` 的透明色解析缺省为 `0xffffffff`；重建版正式加载缺省为洋红色 `RGB(255,0,255)`。元数据读取又使用 `CLR_INVALID`。

因此缺少透明色属性时，洋红像素是否被去掉会因入口不同。盘点的 177 个包均有根透明色，这主要是边界兼容问题，不应夸大为当前所有皮肤都受影响。

### 7.4 数值/布尔/大小写规则尚未完全统一

- 原版大量字段用 `atoi`；当前 `ParseInt` 要求结尾没有残留字符。`"4 "`、`"4px"` 等的结果不同。
- 原版 `resize_tile`、`thumb_resize_tile` 使用整数；当前使用只接受 `true`/`1` 的布尔解析。`2`、`-1` 与 `true` 不能不分字段统一解释。
- 原版 `vertical` 经 `004AA12C` 只比较大小写不敏感的 `true`；当前部分滑条还接受 `1`。
- 原版标签分派使用大小写敏感的 `_mbscmp`；当前辅助窗口分派多用 `_wcsicmp`，主窗口又保留原始名称并多处用大小写敏感比较。
- 同名窗口节点：原版逐个处理；当前多个 `/skin/...` 查询只选择第一个。
- 缺省文本字体：原版 `004AA061` 在没有字体名时不新建该字体；当前 `SkinElement` 预设 Tahoma 并总是尝试创建。

应按原字段整理兼容表，区分原版行为与有意扩展。不能为追求一致而恢复原版的越界或未初始化行为。

### 7.5 宽松 XML、编码和资源路径仍需边界语料

当前 MSXML6 前置修正已处理未引用属性、部分重复属性、裸 `&`、根节点后旧数据等历史写法，但这不等于完整模拟原版流式解析器。

待补语料：非相邻重复属性、属性值中的类似 XML 文本、混合编码、空/非法矩形、相同路径不同写法、重复窗口节点。接受 UTF-8 BOM 是已有有意扩展，不应回退。

原版图片来自包读取器；重建版将包落到缓存目录再用文件路径打开。需要核对图片引用是否严格限于包内、同名条目及同长度缓存文件被外部更改后的行为。当前 ZIP 条目路径检查和完整包指纹已有实现，不能描述成“完全没有路径检查”。

## 8. 网络缓冲层和旧下载界面

### 8.1 `fill_image2` 并未完成显示链

原版 `00452638` 更新第二进度值，`0045287B` 绘制该层。`00452660 → 0045269C` 还包含未提供第二填充图时，从符合条件的 24 位填充图生成暗色副本的回退，不能任意给所有图片统一半透明代替。

当前仅解析/存储 `fill_image2`，实际主窗不消费这个字段，也没有完整的上游缓冲进度状态。现有 **5 个包、7 个主/迷你节点** 提供该图：默认 5.7.9、默认 6.1.2、TT2012、一听音乐、银色城堡。

要恢复的是“缓冲数据 → 状态 → 绘图 → 重绘”的整条链。预览缓冲值为零不构成实际功能完成的证据。

### 8.2 `downwnd_skn.xml` 是独立分支

`004A77D4` 读取的是 `downwnd_skn.xml`；`004A7B06` 处理其中的 `linklabel`、`setting`、`banner`、`splitter`、`listsinfo`、`listinfo`、`stateimage`、`header`、`progress` 等，含下载/失败/暂停/完成状态图和表头/进度配色。

现有原生解析器没有该分支。它是原版下载界面的专门皮肤，**不能把这些节点当作普通 Skin.xml 任意可放置组件来补**。本次 177 包盘点也没有发现包内该文件。

主窗、歌词、均衡器和播放列表的 `advertise` 用途亦未完整恢复。广告、登录、浏览器业务不宜因“解析差异”自动启用；其中登录/浏览器隐藏已有用户要求记录。先保留边界说明，只有恢复对应业务界面时再实现其皮肤部分。

## 12. 按建议顺序实施的修复（2026-10-11）

以下是本次实际代码改动。前述“尚未实现”等措辞描述的是审计时的基线，不能再直接当作当前状态。

### 12.1 可见性与缺省组件

- **无滑块进度条**：进度条是否存在不再以 `thumb_image` 为条件。只提供底图／填充图的进度条可以显示、点击、定位，端点计算允许滑块尺寸为零。
- **文字工具栏**：有工具栏布局但未提供位图时，恢复 `0047E512` 的七个 `32 × 16` 文字入口、系统菜单字体及文字阴影；实际命中区域和工具提示同步生成。
- **缺省滚动条**：没有皮肤按钮／滑块时使用 13 像素宽的系统色按钮、轨道和比例滑块。左右两栏独立判断溢出，分别响应箭头、长按、拖动及滚轮；媒体库树仍使用自己的原生滚动机制。

### 12.2 解析与重复节点

- 主／迷你窗口按已知用途归并到固定槽位，忽略未知用途，不再按 XML 文本顺序创建多份同名组件。
- 重复窗口节点和重复控件节点按字段依次读取。空／错误图片路径不会抹掉该槽位已成功加载的图片；几何、颜色等按原解析器各自的缺省规则更新。
- 实际加载与元数据读取都校验 `version="2"`。缺省透明色采用 `CLR_INVALID`，不再强加洋红色键。
- 数字读取恢复接受有效数字前缀；矩形空值清空、部分字段读取保留已有的未覆盖字段；按钮布尔属性、整数平铺属性分别按原类型读取。
- 原版用途名称区分大小写。图片只在解包目录内部查找，不允许绝对路径、盘符或 `..` 绕出包目录。
- 现有历史 XML 兼容处理保留。畸形 XML 的所有字节级容错结果仍不等同于已穷尽验证。

主要依据：`004A7929`、`004A8536`、`004A88D0`、`004A8B73`、`004A8DC6`、`004A92A2`、`004A9CE9`、`004A9D02`、`004A9D8C`。

### 12.3 绘制、遮挡与命中使用同一规则

新增 `skin_layers.h/.cpp`，由固定控件顺序和真实区域同时计算绘制裁剪及命中：

1. BMP 按钮区域取正常帧的颜色键形状；PNG 取正常帧非零透明度区域。
2. 按钮透明孔洞可以露出／命中下层。悬停、按下及禁用帧不重新改变窗口形状。
3. 文本、滑条、可视化等子窗口占据完整矩形。禁用控件仍占据区域，不能点击穿透或变成背景双击入口。
4. 上层拥有的区域从下层区域中扣除，避免“绘制看到甲、鼠标却点到乙”。
5. 主窗口、迷你窗口与皮肤预览共享顺序；均衡器按相同方法处理并跟随对齐后的坐标；播放列表同步裁剪真实子控件及关闭按钮。

主／迷你窗口顺序来自 `0044E50C`、`00467B9B` 及定位阶段的 `SWP_NOZORDER`：先前创建的原生子窗口处于前层。播放／暂停共用播放按钮的布置位置，并根据当前状态二选一。组件 XML 顺序反转不会反转显示或鼠标优先级。

均衡器按 `00429AAA` 将关闭按钮放在功能按钮／滑条之后；播放列表按 `00482BAF` 采用工具栏、列表容器、关闭按钮的前后关系，标题属于父背景；歌词文本子窗口补充兄弟窗口裁剪；桌面歌词工具条绘制及按钮区域遵守原创建顺序。

可视化子窗口也使用可见区域，播放／暂停形状变化后及时更新；不会再由矩形可视化窗口覆盖本应在前面的按钮或文字。

### 12.4 预览和字体

- 实际窗口与预览共用控件排序、可见区域和原尺寸图标居中裁剪，避免预览额外拉伸图标。
- `Playlist.xml` 保存完整 `LOGFONT`，包括字重、斜体、字符集等；稀疏皮肤配置从当前字体描述符继承。
- 依 `0047E6FC`／`0048301E` 区分“读到皮肤字体”和“普通换肤应用字体”：普通换肤应用列表配色，保留用户当前列表字体，不再只拿皮肤字高／字体名覆盖。
- 歌词字体使用同样的缺省继承原则，未提供字体名的文本不再强制使用 Tahoma。

### 12.5 网络下载层及旧位图回退

恢复绘制顺序：`bar → fill_image2（下载）→ fill_image（播放）→ thumb`。

- `DecodedAudioSource`／`AudioEngine` 增加内部下载百分比接口。未知值为 `-1`；换曲、停止时清空，不把播放位置当成下载位置。
- Media Foundation 网络源通过可选统计服务读取 **整个内容的下载进度**，在解码线程中限频查询，然后通过原子值供 UI 使用。未提供统计服务的源不显示虚构的下载百分比。
- 采用 `MFNETSOURCE_DOWNLOADPROGRESS_ID`，而非临时缓冲区的填充率；两者含义见 [Microsoft 的统计项说明](https://learn.microsoft.com/en-us/windows/win32/api/mfidl/ne-mfidl-mfnetsource_statistics_ids)。
- 缺少 `fill_image2` 时，按 `0045269C` 只对 **24 位 BMP** 生成 RGB 减半的暗色填充，保留颜色键像素；不把该回退套用于 PNG 或所有 32 位图片。
- 以上为内部音频源接口变化，不改变旧插件 ABI，也不增加 XP／Win7 的静态现代系统函数依赖。

网络百分比与绘图之间的数值传递、未知值和层次已做可控输入回归；尚未用真实 HTTP 音乐下载对每种后端进行端到端验证。旧插件未提供该统计数据时，仍只显示播放进度。

### 12.6 测试程序弹窗的原因和处理
