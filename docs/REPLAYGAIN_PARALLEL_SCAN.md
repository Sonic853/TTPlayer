# 多曲目并行扫描增益信息

日期：2026-10-02。

## 功能和原版关系

原版 `004A58F3 → 004A4E8C → 004A5251` 按顺序处理曲目；本次扩展批量调度，保留每首的解码、原版 `ttpcomm.dll` 响度算法、跳过条件和曲目增益标签。没有新增专辑增益算法。

- 扫描窗口新增“同时扫描”下拉框，默认 2，范围 1～4。
- 设置保存到 XML 的 `Playback/ScanGainThreads`，旧配置未设置时使用 2；越界值限制到 1～4。
- 扫描期间可调整上限。减小上限不会中断正在处理的歌曲；活跃任务数降到新上限以下后，才会领取下一项。
- 每个列表项显示自己的百分比、正在保存、完成、跳过、取消或错误状态。
- 相同规范化路径及相同子曲目的重复项合并成一个任务，列表中保留各行，并同步进度和结果。
- 暂停控制所有工作线程及尚未开始的写入；取消唤醒暂停和队列等待，关闭窗口前等待释放解码文件。
- 已开始的插件调用必须等它返回，已经完成的标签写入不回滚；没有强行终止线程。
- 全部成功／跳过仍自动关闭，有错误时保留结果窗口。

## 并发结构

[playlist_transforms.cpp](../src/ui/playlist_transforms.cpp) 保留原资源 222 和单例窗口。

一个协调线程管理最多四个工作线程；默认最多两个活跃任务（包括等待保存的任务），避免保存较慢时超出所选并发上限。每个任务独立持有解码会话、PCM 缓冲和增益分析器。分析完成后进入协调线程的写入队列。每个工作线程最多等待一份写入结果，待写入队列最多四项，不随选中曲目数无限增长。

重复项按规范化路径及 CUE 子曲目编号合并。同一 CUE 的不同曲目各自计算。不同硬链接文件名不合并：某些标签写入器会替换文件，更新一个名字并不保证另一个名字也获得新标签。

[replay_gain_scanner.cpp](../src/audio/replay_gain_scanner.cpp) 在加载标签快照／打开元数据写入器前取得统一的写入锁，因此手动扫描和播放后的自动扫描不会同时执行 ReplayGain 标签事务。CUE 每次在锁内重新读取最新内容，再使用原有的 CUE 跨进程互斥和快照检查保存，避免不同子曲目相互覆盖。

这里协调的是播放器内部的 ReplayGain 事务。文件属性编辑器及其它进程仍遵守原有的文件共享、CUE 快照和错误返回规则，不将此锁描述成覆盖所有外部标签编辑。

## 旧插件策略

旧插件接口没有声明线程安全能力。每批开始时在后台对实际 DLL 做 SHA-256 核对，文件名相同不等于允许并行。

本次并行验证的二进制：

| 模块 | SHA-256 |
| --- | --- |
| `ttpcomm.dll` 分析器 | `e349ef73e8a1d35b2c5debd2ddaeb5cc2513a90647766b7339d2605b34483b33` |
| `ttp_flac.dll` | `e2833c023377787fa9705d52215d3a02b7f5a742bdda4012f9d639c2e1f64dbd` |
| `ttp_ogg.dll` | `ee58d0603a5c4c7596219590d5e92e12748187b395e14dc1275256e0904dcdc5` |

放行范围限于 FLAC／Vorbis 路由；同一 FLAC DLL 另行声明的 TTA 格式仍串行。输入路由使用已有的真实格式探测规则；匹配到未经验证的候选插件时回退串行。CUE 检查实际候选音频文件，不能仅凭 `.cue` 后缀放行。分析器不匹配、插件更新或无法计算哈希时也回退串行。

未经验证的扫描解码会话与 ReplayGain 标签写入互斥；已验证的扫描可以同时进行。此限制针对扫描，不改变播放引擎现有的解码调度。本次没有宣称所有历史输入插件或外部 DirectShow 解码器都已通过并发验证。

XP、Win7 和新系统使用相同策略，没有按系统版本强制单线程。选择 4 是任务上限，不承诺所有格式都会同时解码四首，也不承诺固定加速倍数。

## 验证

测试源与合成文件仅保留在本地 `rebuild/tests`，没有加入 Actions 或发行包。

新增 `tests/audio/replay_gain_parallel_tests.inc`，通过实际资源窗口和正式音频接口验证：

- FLAC、Ogg 各四个不同采样率／频率／时长样本，四实例同时停留在解码回调，证明存在实际重叠；每种格式重复八轮。
- 64 次并行分析与串行对照的帧数、增益及峰值一致。
- 在隔离副本的 DLL 末尾添加数据，验证仍能加载，但哈希失配时强制串行。
- 扫描窗口 1／2／4 上限、独立结果、重复项、错误后继续、标签保存及保存后重新解码结果。
- 同一 CUE 的两首手动扫描和另一首自动提交并发，三个子曲目的标签全部保留。
- 新控件与原控件不重叠、动态上限、暂停／继续、暂停后取消、关闭后独占打开源文件。
- 配置默认值和 XML 往返保存。

另运行原有 `--replay-gain` 回归，覆盖整数／浮点 PCM、原版 DLL 对照、峰值修正、完整播放提交、提前停止／seek 保护和原扫描窗口生命周期。

### 实测结果

| 环境 | 并行专项 | 原有增益回归 |
| --- | --- | --- |
| 本地主机 | `REPLAYGAIN PARALLEL PASS` | `REPLAYGAIN REGRESSION PASS` |
| VirtualBox XP | `REPLAYGAIN PARALLEL PASS` | `REPLAYGAIN REGRESSION PASS` |
| VirtualBox Win7 | `REPLAYGAIN PARALLEL PASS` | `REPLAYGAIN REGRESSION PASS` |

日志：本地 `tests/replaygain-parallel-{host,XP,Win7}.log`、`tests/replaygain-regression-{host,XP,Win7}.log`。虚拟机通过 Guest Control 运行实际控件／插件测试，不将其等同于人工操作测试。

XP 测试条件与修正：

1. 首轮测试用 `std::async` 未呈现四实例同时进入回调；改用与生产调度相同的显式 `std::thread` 后，验证了四路实际重叠及结果一致。生产实现一直使用显式线程。
2. 当前 Ogg 插件二进制本身依赖 `MSVCR110.dll`。XP 隔离测试目录缺少该 DLL，起初加载返回 `0x8007007e`。仅向 `C:\TTPlayer-ReplayGainParallel-20261002` 添加现有 x86 运行库的本地副本后完成 Ogg 验证，没有向系统目录安装运行库，也没有把它加入播放器发行包。这是该输入插件的已有依赖。
3. 原有自动提交测试在 XP 轮询标签时碰到 `ReplaceFile` 期间的短暂打开失败。测试的异步轮询现在只对这类打开失败继续等待，仍严格检查最终标签值；没有放宽分析结果或写入成功的判定。
