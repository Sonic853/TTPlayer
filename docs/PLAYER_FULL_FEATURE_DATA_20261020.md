## 3. 四处确认差异

### D01 · P2：目录监控更新只更新媒体库副本

**触发**：同一已读取曲目存在于编号播放列表/当前曲目，媒体库监控目录中的文件标签被外部工具更改，监控重读成功。

**原版**：`004833B6`（伪代码 126205，修改分支 126205–126345）经 `004742DD` 更新源；`0041E974`/`0041EA0C`（31170/31201）缓存/复用 CPlayItem；`004AF46A`（166367）查询持有对应曲目引用。这说明它的共享曲目模型，与重建版的多份值拷贝并不相同。本轮没有新跑原版外部改标签 GUI。

**现版**：`player_window_library.cpp:1864` 将 modified 文件排入待刷新；`RunBuild:835` 重读；`ApplyMediaLibraryIndex:2008` 在 `library.enabled=true` 分支（2100–2114）替换库及 `media_library_playback_`，未发布编号列表或 `opened_track_`。`player_window_playlist_info.cpp:170–178` 只重读未加载信息行，已经有时长的旧行不会自动补救。

本轮日志：`library=external changed title`，`numbered0=old title`，`numbered1=old title`，`opened=old title`；`monitor_publication_missing=1`。相同 revision 的有效结果仍如此，现有 Edits/InfoRevision 并未阻止或修正这一缺口。

**修复建议**：把成功的监控元数据变更送入同一个身份/版本受控发布器，传播到编号列表、库结果和打开快照；按变动字段合并，保留评级、播放状态和较新的属性修改。不要直接用整个旧 BuildResult 覆盖一切。

### D02 · P2：手动扫描增益写盘成功后没有发布 gain/peak

**触发**：对已有列表行运行“扫描增益信息”，扫描与写入成功；属性/列表模型仍持有扫描前 metadata。

**原版**：`004A50B5`（157330）在写 `replaygain_track_gain` 与 `replaygain_track_peak` 后，分别调用曲目字段 setter `0041B722`；关键行 157361–157377。

**现版**：`player_window_playlist.cpp:5984–5988` 只给扫描器传曲目副本及修改并发数回调；`playlist_transforms.cpp:397–426` 成功提交后只 `finish_row`/标记 committed；`ShowPlaylistReplayGainScanner:1785` 无元数据结果回调。完整静态链可确认主模型没有收到这次成功写入。未在本轮新增真实音频扫描，不能将此称为本轮算法/解码失败实测。

**修复建议**：成功提交回传 `{identity, source_version, gain, peak}` 的局部 patch，由 UI 发布；取消/失败不修改模型。不要重做昨日已修的“删除增益后发布”路径。

### D03 · P2：普通文件改名丢显式歌词关联

**触发**：歌曲关联到不同名的外置 LRC，或被显式设为“不关联歌词”，然后用列表“重命名文件”。

**原版**：`004868E7`（129129）→ `004AF8A4`（166644）；166686–166693 对关联映射 `DAT_00546DD8` 迁移并置脏 `DAT_00546E08`。

**现版**：`player_window_playlist.cpp:6541–6560` 在 MoveFile 成功后更新编号列表、库和 opened_track 路径，但不迁移 `lyric_associations_`，不改 `lyric_document_track_`；`lyrics/association.cpp:8–15` 的键包括路径+subtrack。相反错误后缀更名路径 `player_window_extension_correction.cpp:221–236` 已有 Erase/Set 迁移。

本轮实际私有文件改名：`rename_physical_success=1`、`rename_old_association=1`、`rename_new_association=0`。该探针验证了非同名 LRC 映射；NoLyric 与歌词文档 key 是同静态缺口推导，尚未新增独立 GUI 测试。歌词分审计已交叉核查，并统一在本项报告。

**修复建议**：抽取统一成功改名 retarget，迁移关联/NoLyric/文档身份/所有模型，保留 subtrack；实际 MoveFile 失败不迁移。无需自动移动用户选择的外置 LRC。

### D04 · P2：M3U/M3U8 忽略“保存相对路径”

**原版**：`00477446`（115749），115800 读取 `DAT_00547CAC`，115817–115820 启用时剥离列表输出目录前缀；同配置的 UI 读取见 137590、141969，设置名 `SaveRelativePath` 见 177025。

**现版**：`player_window_playlist.cpp:6352–6356` 正确传配置；`playlist.cpp:1442` 选 M3U 后只调用 `SaveM3u8(path)`，丢弃布尔参数；985–1006 固定写 `track.path.wstring()`。默认参数本来为 true（`playlist.h:130–134`），因此不仅特意启用时失效。

本轮普通本地文件导出，默认/true/false 字节相同；英文/中文行均绝对路径。只测试普通文件，不把 `archive|member` 相对策略混进此结论。M3U8 无 BOM/LF 与原版 BOM/CRLF 也是字节差别，但均有有效消费者，单独列低优先互操作边界，不与失效选项混为同等故障。

**修复建议**：SaveM3u8 接收 relative，按原版路径前缀规则处理本地文件并保留 URL；为普通子目录、外目录、不同盘、Unicode 和 archive 逻辑路径分别定义测试。

## 4. 其它确认边界与待验证项

### D05 · P2：后台长下载阻塞队列状态持久化，保存失败后不保留脏状态

`http_download_queue.cpp:234–253` 只有 worker0 运行 Save（240），同 worker 的 `Run`（252）是整个下载的同步调用。若它被长任务占用，其它线程新增、取消或完成的任务可一直只在内存。析构 197–200 会取消、join、Save，因此不能说正常退出必丢；风险是长任务期间崩溃/断电及需要及时持久化的状态。

`Save:205–231` 在构造 XML 时先清 dirty（221），实际 Write/Flush/MoveFileEx 失败后仅记录 storage 错误；没有新变更就不重试。保存采用临时文件与替换是优点，不应推翻。

原版有独立缓存维护入口 `004D10EC`（197468）和保存 `004D025D`（196856）；这不是原版拥有强崩溃事务保证的证据。建议独立轻量 saver，按 generation 生成快照，成功替换后才确认该代已保存，带失败退避。此项是静态调度证据，未新增杀进程/写拒绝注入。

### D06 · P2：下载记录不能移除，最终可用满固定容量

`HttpDownloadQueue` 的公开 API（头文件 30 起）没有 Remove/Clear；UI `player_window_playlist_network.cpp:82–87` 只有 cancel/retry；`Enqueue:328` 对包含 complete/canceled 的总 jobs 数限制 10000，并且 Save 保留这些历史。实际长期使用可能无法新增，用户没有界面释放条目。

原资源菜单130含 `0x80c2 删除任务`；394含 `0x80c6 删除记录`、`0x80c7 删除文件`。这证明原功能区分记录与实际文件。建议当前独立下载窗口补“移除记录/清理已完成”，删除媒体另设显式动作。**不意味着本次要恢复已被用户暂缓的音乐窗。** 本轮没有创建10000任务实测，结论依据闭合 API/容量条件。

### D07 · P3：DownloadLrc 复选框可改但无执行消费者

当前 `settings.h:296`、`player_window_options.cpp:5600/5897/6359` 只定义、显示、持久化 `download_lyric`；全源码检索没有下载流程消费。原完成流程 `00422E0A`（35034）包含歌词下载分支。后端旧服务未恢复，应在 UI 禁用/说明，不应让开关看起来有效。

对照：在线反馈 `player_window_playlist_network.cpp:95–120` 已明确“服务不可用”并禁用提交，不能继续报告为“点击后假成功”。旧私有 temp/P2P/服务器任务、反向写回旧任务表属于明确未恢复范围；普通 HTTP/HTTPS 缓存、导入旧 XML 字段、已保存文件复用已实现。

### D08 · P2：XML/M3U 导出写失败保全不足

`core/text.cpp:21–24` 打开目标时 trunc，检查 open 后不检查 stream.write；XML 保存（playlist.cpp:1360/1421）可能写短仍返回成功。M3U（1003–1006）检查最终 write，但仍先截断原目标。静态可证故障条件存在，未新增磁盘满注入；也没有证据说原版在此具备更强原子性。

建议为用户导出和设置文本共用检查完整写入/flush 的 sibling-temp commit helper，成功后替换；不要将“跨进程音频文件写入 G01 已修”误推导成所有文本导出自动安全。

### W01 · P2 待证：CUE 整碟字段发布是否遗漏别的列表中的子轨

`player_window_playlist_properties.cpp:1231–1242` 写 Album/AlbumArtist 后只更新 context.tracks 内兄弟；2046/2079–2087 表明上下文来自当前可见列表，主窗显式曲目甚至只有一首。`PublishTrackMetadata` 以 path+subtrack 识别；整碟写入却会影响同 CUE 其它子轨。当前源码未见广播到不在上下文的不同 subtrack。

建议先用两列表各放一条同 CUE 的不同轨，从主窗属性修改 Album，再检查另一轨和库；本轮没有做该真实写入组合，故标候选，不与四个确认差异同列“已复现”。

## 5. 可以合并/简化的重复

1. **统一元数据发布放播放器层，优先级 P2。** BuildResult、文件属性、手动 RG、移除标签等目前各自提交副本。复用一个按身份/版本接收 field patch 的入口，解决 D01/D02，也降低 W01 的遗漏概率。它包含 UI/库/播放身份，不宜塞进 ttpcomm。
2. **统一成功改名 retarget 放播放器层，P2。** 普通 rename 与错误后缀修正已经重复更新编号列表/库/opened_track；只有后者迁移 RLL。提取公共事务后减少顺序差异，不是重复扩充两个长分支。
3. **原子文本保存 helper 放 core；必要时再成为 ttpcomm 通用服务，P2。** 先限定导出/队列等文件错误契约，避免把 UI 配置格式直接搬进 DLL。
4. **不要再复制底层 ID3/zlib/PCM/归档解析。** 当前 ttpcomm 标准 API、旧 ABI 已共存并修过反同步/扩展头；内置标签适配层负责播放器字段策略。真正剩余重复是少量上层 metadata merge/物理源身份传递，不是重新写第三套解析器。
5. **下载调度与保存拆职责，P2。** 不必另加一套传输/缓存；现有共享 CacheTask 已支持多消费者与独立取消，新增 saver 应只管理队列记录。
