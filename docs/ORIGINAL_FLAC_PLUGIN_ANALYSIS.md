# 原版 ttp_flac.dll：实现、重建可行性与优化建议

分析日期：2026-10-03。

## 1. 结论与本次范围

**可以重建，建议建立与 `ttp_aac`、`ttp_ogg` 同级的独立 `ttp_flac` 项目：恢复原插件的接口和宿主交互，FLAC 解码使用固定版本的现代 libFLAC，另外完整恢复原 DLL 自带的 TTA Reader。**

原 DLL 并非只有 FLAC：它同时注册 FLAC 和 TTA 两个输入工厂。如果替换 DLL 时只实现 FLAC，原版与重建版都会失去这份插件提供的 TTA 功能。

值得优先修复的是读取边界、错误传播、定位和元数据保存，其次才是速度与 DLL 大小。原版的正常播放流程可作为兼容目标，但已确认的越界写入、丢标签和保存失败不应作为必须复刻的行为。

本次完成了伪代码分析、关键机器指令复核和原 DLL 的隔离调用测试；尚未创建、构建或交付新的 FLAC 插件，也没有替换用户使用中的 DLL。

## 2. 对外接口：同一个 DLL，两个 Reader

```text
ttpGetSoundAddIn
  └─ AddIn::Enum
      ├─ index 0：FLAC ReaderCreator → FLAC Reader
      │                              ├─ Metadata
      │                              └─ Thumbnail
      └─ index 1：TTA ReaderCreator  → TTA Reader
                                     └─ Metadata → 宿主 CreateStdContent
```

| 入口 | 地址 | 行为 |
| --- | --- | --- |
| 插件入口 / 创建 AddIn | `60304EEA` / `60304EEF` | 返回引用计数对象，无需注册 COM |
| 工厂枚举 | `60304F93` | 两个 ReaderCreator；第三项返回 `E_INVALIDARG` |
| FLAC 工厂 | `60304FE9`、`60305088` | `FLAC Reader`，扩展名 `*.flac;*.fla` |
| TTA 工厂 | `6030513D`、`60305200` | `TTA Reader`，扩展名 `*.tta` |
| DLL 初始化 | `603052B5` | 先从 `ttpctrl.dll`，再从宿主 EXE 查找 `CreateStdContent` 等导出 |

类别 GUID 是 `476D15A5-D863-416A-8A59-A9C7D72CE04E`。该 DLL 没有另行枚举 Decoder 或 Encoder 工厂，Reader 自己完成解码并输出 PCM。因此，重建不需要先增加编码器或外部解码进程。

### 2.1 Reader 槽位

Reader 的前三项为 `QueryInterface/AddRef/Release`，随后依次是：

| 槽位 | 方法 | FLAC 地址 |
| --- | --- | --- |
| 3 | Open | `603012BC` |
| 4 | Capabilities | `60301620` |
| 5 | Duration，DWORD 毫秒 | `60301644` |
| 6 | Format，分配并返回 WAVEFORMATEX | `60301661` |
| 7 | BufferSize | `60301682` |
| 8 | CodecName | `603016A6` |
| 9 | Bitrate | `603016D8` |
| 10 | BitDepth | `603016F5` |
| 11 | SetCallback | `60301717` |
| 12、13 | Start、Stop | `603011BC`，空操作成功 |
| 14 | Read | `6030172C` |
| 15 | Seek | `60301876` |

字符串、格式等跨模块返回内存使用 `CoTaskMemAlloc`；音频 Buffer 属于宿主；引用计数使用 Interlocked。新实现必须保留 x86 调用约定、槽位顺序、GUID、结构体大小和内存所有权。可以复用 `ttp_ogg` 已整理的 ABI，但不能复用其浮点 PCM 输出假设。

Metadata GUID 为 `7AD84E00-5FEF-4481-B532-FBBD677E67C2`；Thumbnail GUID 为 `B5E770AF-DFB0-43E5-9B0C-3EE98E7B6248`。封面记录在 x86 下为 24 字节，包含大小、MIME、说明、数据长度、数据指针和图片类型。

## 3. FLAC 播放和定位

### 3.1 打开流程

`603012BC` 的主要步骤如下：

1. 保留宿主提供的 `IStream`，记录路径、长度及可定位等能力。
2. 若宿主提供 `CreateStdContent`，以类型参数 5 调用，获取通用标签并处理流的初始位置。
3. `60301000` 从当前位置读取四字节，回退四字节，检查 `fLaC` 签名；识别依据不是文件后缀。
4. 创建内部 libFLAC decoder，安装读、定位、当前位置、总长度、EOF、PCM、元数据与错误回调。
5. 处理 metadata，获得 STREAMINFO、Vorbis Comment 和第一张 PICTURE。
6. 构造整数 PCM 的 WAVEFORMATEX，计算时长、平均码率并分配输出缓存。

通用标签先读入，原生 FLAC 标签随后覆盖同名项。不能在重建时简单删除宿主回调，否则带前置标签文件、TTA 通用标签及原版宿主之间的配合可能改变。

签名检查使用回退 Seek，现有路径对不可定位流并不稳妥。网络能力、超时和取消应继续通过宿主流接口处理，不能仅因为改用新版 libFLAC 就认定网络播放已修复。

### 3.2 解码层与 PCM 输出层

原生 FLAC 的帧解析、残差解码、预测恢复、声道还原由内置 libFLAC 负责。插件封装在 `60302469` 接收每声道 `int32` 样本，按“一个采样时刻的所有声道，再下一个采样时刻”的顺序交错，取相应字节数交给播放器。

这与 AAC/OGG 的浮点输出路径不同：

- 16 位输出是小端整数 PCM；24 位输出是每样本 3 字节，不是默认扩为 32 位。
- 8 位需要从 FLAC 的有符号样本转换成 Windows PCM 的无符号样本，原版在 Read 中执行 XOR `0x80`。
- STREAMINFO 回调只接受 8、16、24、32 位；其他有效位深被封装拒绝。
- 32 位通过这个检查，不代表旧解码器真正支持：本次合法 32 位样本打开成功，首次 Read 就返回 `S_FALSE`，输出为 0 字节。独立 FFmpeg 解码与原始 PCM 完全相等，排除了样本无效。
- 对正常数据，目标应是与原 PCM **逐字节一致**，不能以“听起来相同”代替验证。位深容器转换和声道布局变化应单独定义并测试。

原版使用普通 WAVEFORMATEX，不提供多声道掩码。新实现需验证原版宿主是否接受 WAVEFORMATEXTENSIBLE，再决定如何为多声道及非整字节有效位深提供完整描述；不能直接把 Vorbis 的声道重排规则搬过来。

### 3.3 Read 的边界缺陷

`6030172C` 在缓存为空时调用 `process_single`，再把缓存复制到宿主 Buffer。推荐容量为 `nBlockAlign × 1024`。

本次实测：

| 场景 | 原 DLL 结果 | 问题 |
| --- | --- | --- |
| 双声道 16 位，容量 4097 字节 | `S_OK`，长度 4097 | 没有对齐到 4 字节采样帧；剩余帧数按整除扣减，与字节位置分离 |
| 容量 0 | `S_OK`，长度 0 | 成功却无进展，调用方若循环读取可能空转 |
| 正常 EOF | `S_FALSE`，Buffer 仍保留上一块长度 | 调用方必须先判断返回值，否则可能误用旧数据 |
| 合法 32 位 FLAC | Open 成功，首次 Read 为 `S_FALSE` | 不支持/解码失败被表现为曲目结束 |

错误回调 `60302553` 对部分错误允许继续，对其他错误设置中止标记；Read 又把部分失败折叠成 `S_FALSE`。修复时应区分正常结束、可恢复帧损坏、不可恢复错误和主动取消，保留原版可恢复播放的合理行为。

### 3.4 定位

`60301876` 先清空 PCM 缓存，再计算：

```text
targetSample = floor(sampleRate × milliseconds / 1000)
```

它调用 `60305D70` 的绝对采样定位后，没有检查返回值，直接返回 `S_OK`。机器指令中可见调用后直接 `xor eax,eax`，不是反编译器猜测。

测试 3.25 秒的文件：

- 定位到 1701 毫秒：后续 PCM 与源数据中相应采样位置一致。
- 定位到 5000 毫秒：仍返回成功，下一块 PCM 实际等于文件开头。

新实现应验证目标范围、检查底层结果，并明确 EOF 定位策略。失败不能伪装成成功，缓存处理也必须与 decoder 状态一致。

## 4. 标签编辑与保存

### 4.1 内存模型

`60301F0B` 解析 Vorbis Comment，以第一个 `=` 分隔字段和值，再解码 UTF-8。

原版把结果放入单值键表 `60301539`：同名字段只留下最后一个值。比较函数 `603015E9` 对每个字节做 `| 0x20`，不只折叠 ASCII 字母大小写，还会把某些不同标点误认为相同。

本次构造合法字段：

```text
ARTIST=First
ARTIST=Second
X[=Bracket
X{=Brace
```

Reader 只暴露 `ARTIST=Second` 和 `X[=Brace`。仅修改 TITLE 并释放后，文件中的其余值也丢失。这是实际的数据损失，不只是 UI 无法显示多个值。

Metadata::Set 在 `60301A8F`：

- 检查可写能力，设置 dirty。
- `Set(nullptr, nullptr)` 清空全部标签。
- 字段名非空、值为空指针或空串：删除字段。
- 其他情况：新增或替换。

重建应保留这些宿主调用语义。内部改为保序、多值集合；单值 Get 可继续返回原版的最后值，未编辑的多值和未知字段完整保存。大小写仅折叠 `A–Z`。

### 4.2 实际写盘发生在最后一次 Release

析构函数 `603011DD` 会：

1. 结束并释放 decoder。
2. 将 Unicode 文件路径转换为 `CP_ACP` 字符串。
3. 释放自己的输入流。
4. dirty 时对通用标签对象调用 `Set(nullptr, nullptr)` 并释放。
5. `6030236F` 依次执行标签保存 `6030205A` 和封面保存 `603021F9`。

两个保存函数各自打开 libFLAC simple iterator。虽然利用 PADDING，但更新标签和封面分两次完成，没有统一事务，也没有向宿主返回写盘失败的方法。

在本机 `ACP=936` 下，对含 emoji 的隔离文件名修改 TITLE：Set 返回成功，所有引用释放后文件内容完全未变。普通中文是否受影响取决于实际系统代码页，不能泛称所有中文路径都失败。

### 4.3 推荐保存方案

使用 libFLAC metadata chain，一次读取和修改全部 metadata，统一保存标签和封面：

- 使用 Unicode 文件句柄及 I/O callbacks，或者严格遵循新版 libFLAC 的 UTF-8 文件名接口。
- 不进行音频重编码；保留 STREAMINFO、音频帧、SEEKTABLE、CUESHEET、APPLICATION 等未修改内容。
- 默认采用同目录临时文件、完整写入并验证后替换；失败保留原文件并清理临时文件。
- 若提供仅覆盖 metadata/PADDING 的快速路径，应说明其崩溃恢复能力与临时文件替换不同，不称其为同等原子操作。
- 确认文件未被其他操作替换、路径未改变、所需句柄已释放后提交，处理磁盘满、共享占用和只读错误。
- 避免在 native FLAC 提交失败前先持久化删除通用标签。

**旧 Metadata ABI 没有 Commit 返回 HRESULT 的槽位，Release 返回引用计数，不能擅自改签名。** 原版宿主兼容路径仍需在最终释放时处理未提交更改；重建版可增加可选扩展提交接口，让“保存到文件”收到真实结果，同时保留旧 ABI。这个宿主层约束不是替换 libFLAC 就会自动解决的。

## 5. 专辑封面

原版使用 native FLAC 的 PICTURE metadata block，支持承载 PNG/JPEG 等图片字节，本身不负责把图像解码成位图。

| 功能 | 地址 | 原版行为 |
| --- | --- | --- |
| 声明最大图片字节数 | `60301B84` | 60,000 |
| 声明最大图片数 | `60301B9E` | 1 |
| 从 FLAC 读取 | `60301FCC` | 只保留遇到的第一张 |
| 记录初始化 | `60301E47` | 对宿主报告的 type 默认是 3 |
| 替换 / 新增 / 删除 | `60301C2E` / `60301DAB` / `60301ECE` | 修改内存，设置 dirty |
| 写盘 | `603021F9` | 只修改或删除第一块 PICTURE |

60,000 是对外声明限制，不能据此断言 DLL 会拒绝读取所有超过此大小的封面；它的内部新增路径没有完整实施同一限额。

实测两张图片，第一张 type=4（封底），第二张 type=3（封面）：

- 原 Reader 只返回封底字节，但对宿主声称 type=3。
- 删除这个可见图片并释放后，磁盘仍留有第二张图片；再次打开会重新出现图片。
- 给无图片文件新增 PNG，磁盘 PICTURE 的 type 是 0，宽、高、色深、颜色数都是 0。

最后一项与反编译和反汇编一致：写盘只设置 MIME、说明和数据，没有设置完整图片属性。既有图片替换后也可能保留旧尺寸。

建议内部保存所有图片及原始类型，UI 首选 type=3；在缩略图接口中保留可枚举能力。新增/替换时从图片数据验证格式和尺寸，填充类型、MIME、宽高和色深；为总大小、单图大小和图片数量设明确限额。删除操作只删除选中的图片，多图 UI 与“清空所有封面”需分别定义。

## 6. 容易遗漏的 TTA

### 6.1 流程与宿主依赖

| 功能 | 地址 |
| --- | --- |
| 构造 / QueryInterface | `60303AD2` / `60303BE1` |
| 读取头、验证 CRC32 | `60303C5A` / `60303E09` |
| Open | `60303E3E` |
| 初始化帧表和解码状态 | `60304381` |
| Read | `6030403E` |
| Seek / 帧定位 | `60304106` / `6030430A` |
| 核心解码 | `60304494` |
| 自适应滤波 | `60304C38` |
| Metadata 转发 | `60304192`、`603041B1`、`603041D8`、`603041FB` |

TTA Open 以参数 4 调用宿主 `CreateStdContent`。它没有像 FLAC 一样自己实现完整标签存储，而是把 Count/At/Get/Set 转发给返回的对象。无该对象时，不暴露 Metadata；本次隔离探针没有导出这个宿主函数，所以 TTA 的 Metadata QI 返回 `E_NOINTERFACE`，这不表示原播放器中 TTA 不能编辑标签。

输入头是 22 字节 `TTA1`，验证头部 CRC32，读取声道、位深、采样率和总采样数。随后读取压缩帧长度表及其 CRC，转换成可定位偏移。

核心恢复路径包括 Rice 残差、带符号映射、自适应滤波、预测和声道还原。帧时长常数从二进制读取为约 `1.0448979591836736` 秒；定位先找到目标帧，解码后跳过帧内前缀采样。这与 [TTA 官方格式说明](https://tta.sourceforge.net/en/tta-format-description/) 的结构一致。

还存在格式标记 3 的浮点还原分支，不能只凭一个普通整数 TTA 样本就宣称完整覆盖。替换为其他 TTA 库前，必须验证它是否保留这一历史分支。当前也没有证据把 TTA2 或加密 TTA 纳入原 DLL 的兼容范围。

### 6.2 已确认的问题

1. **时长丢失小数。** 头部处理先执行 `totalSamples / sampleRate` 的整数除法，再转 double，Open 最后乘 1000。因此 3.25 秒报告为 3000 毫秒，实际解码 PCM 仍有完整 3.25 秒。应以 64 位先乘 1000 再除采样率计算。
2. **忽略宿主输出容量。** Read 调用 Capacity 后未使用该值，每次按最多 2048 个采样帧解码再复制。16 位双声道、声明 4097 字节时，实际复制 8192 字节；即使 SetLength 返回失败，Read 仍返回成功。
3. **EOF 长度不清零。** 与 FLAC 路径相同，旧长度留在 Buffer 中。
4. **头部检查不充分。** 可见上限检查，部分零值、乘法范围和异常帧表仍需加固；本次没有用可能触发崩溃的畸形头运行该原 DLL。
5. **帧定位错误处理不完整。** `6030430A` 对越界帧序号仍可返回成功，内部 IStream::Seek 返回值也未完整传递；这是静态确认，未在本次进一步测试所有损坏帧表场景。

容量测试使用了大于声明容量的隔离后备分配，通过哨兵检测超出声明范围的写入，没有故意造成进程地址空间越界。报告 8192 字节和越界区内容变化共同证明容量约束被违反。

## 7. 本次实测汇总

环境为 Windows 11、本机 x86 探针直接调用原 DLL。所有音频均为生成或复制的测试样本，未修改用户音乐。

| 验证 | 实际结果 |
| --- | --- |
| 工厂枚举 | FLAC、TTA 两项；第三项 `E_INVALIDARG` |
| FLAC 16 位，44.1 kHz，双声道，3.25 秒 | 573,300 字节 PCM，与源数据逐字节一致 |
| FLAC 24 位，相同声道和时长 | 859,950 字节 PCM，与源数据逐字节一致 |
| FLAC 32 位，相同声道和时长 | 打开成功但 0 字节 PCM；独立参考解码正常 |
| TTA 16 位，相同声道和时长 | 573,300 字节 PCM，与源数据逐字节一致；时长仅报告 3000 ms |
| FLAC/TTA 定位 1701 ms | 两者返回的首块 PCM 都匹配目标采样位置 |
| FLAC 越尾定位到 5000 ms | 假成功，随后返回曲首 PCM |
| FLAC 非对齐容量、零容量 | 分别输出非完整采样帧、成功但无进展 |
| TTA 小容量 | 忽略 4097 字节容量，输出 8192 字节 |
| 重复字段与不同标点字段 | 合并且修改其他标签时写回丢失 |
| 两张图片 | 仅暴露第一张，误报类型；删除后仍有第二张 |
| 新增图片 | 像素数据保存，但类型和尺寸字段未正确写入 |
| 不属于 ACP=936 的文件名 | Set 成功，最终文件未修改 |
| 标签/封面编辑后音频帧 | 已测成功写入样本的音频部分 SHA256 保持一致 |

原始记录：`rebuild/tests/flac_analysis/artifacts/report.json`；探针 `probe.cpp`；样本生成与独立块解析 `run_analysis.py`；PE 和指令证据 `original-pe.txt`、`original-disasm.txt`。

这些是原 DLL 的行为验证，不是新插件验收。XP、Win7、真实原版 UI、重建版 UI、网络流、多声道、浮点 TTA 和损坏文件矩阵尚未在本次验证。按既定要求，后续可以用本机 Win11 代验 Win10 的应用路径，但报告仍须注明实际系统。

## 8. 推荐重建路线

### 8.1 FLAC 解码库

截至分析日期，Xiph 官方列出的最新稳定版为 **libFLAC 1.5.0**。建议固定下载并校验，而不是构建时跟随 master 或任意 latest。官方源码压缩包 SHA256：

```text
f2c1c76592a82ffff8413ba3c4a1299b6c7ab06c734dee03fd88630485c2b920
```

来源：[Xiph 下载列表](https://www.xiph.org/downloads/)。

现代库适合作为新的内部解码核心，包括 32 位 PCM 等旧核心未覆盖的能力。公开库升级也包含接口变化：例如 Windows 文件名改为 UTF-8、部分结构变化。因此要以新头文件重建封装，不能只替换二进制中的版本字符串或套用旧结构偏移。[官方更新记录](https://www.xiph.org/flac/changelog.html)

原宿主看见的是 TTPlayer Reader ABI，内部 libFLAC 的版本可以独立升级。只要 PCM、接口、所有权和错误语义经验证，新库不要求原播放器也升级。

### 8.2 项目边界

建议目录职责：

```text
ttp_flac/
  include/           TTPlayer ABI
  src/               工厂、流适配、FLAC Reader、TTA Reader、标签和图片
  cmake/             兼容 Windows 的构建与固定依赖
  docs/              分析、验证、第三方版权声明
```

复用现有 AAC/OGG 的独立构建、版本生成、PE 检查、封面图片校验和宿主探针经验。不要引入整个 FFmpeg 作为运行时依赖；本次 FFmpeg 仅用于本地样本和参考验证。

libFLAC 不解码 TTA。TTA 应单独恢复并测试，选用外部代码时逐项核对所选版本的许可证和历史浮点支持，不能把 libFLAC 的许可证套用到 TTA。

### 8.3 与 Ogg FLAC 的关系

原路径检查 `fLaC`，没有恢复出 Ogg FLAC 输入路径。新版 libFLAC 可以扩展 Ogg FLAC，但这是新增能力，并不属于原行为自动恢复。

若增加它，应让 `ttp_ogg` 继续负责 Vorbis/Opus，FLAC 插件按内容识别 Ogg FLAC，协调 `.ogg/.oga` 工厂探测次序。**libFLAC 1.5.0 对 Ogg FLAC metadata 仍不提供写回支持**，不能把 native FLAC 保存代码直接用于 Ogg；需先声明只读，或另做正确的 Ogg 重封装。[metadata 官方文档](https://www.xiph.org/flac/api/group__flac__metadata.html)

## 9. 优化应如何做

| 优先级 | 调整 | 预期收益与验收方式 |
| --- | --- | --- |
| P0 | Reader 容量、采样帧对齐、EOF、错误和 Seek | 消除已复现问题；对照错误码及 PCM |
| P0 | Unicode、多值标签和统一提交 | 防止静默保存失败和丢数据；失败注入、重开核验、音频哈希 |
| P0 | 保留 TTA 路径并修正时长、容量 | 完整替换原 DLL；普通和历史分支样本分别验收 |
| P1 | libFLAC 1.5.0 与 32 位支持 | 功能补齐；使用参考解码和边界样本确认 |
| P1 | 图片类型、尺寸、多图片保留 | 正确显示和编辑封面；原 UI 与重建 UI 验证 |
| P1 | 按需分配 PCM 缓存，元数据模式延迟初始化播放状态 | 降低扫描和并行 Reader 的内存；测峰值而非仅估算 |
| P2 | 对 8/16/24/32 位使用专门交错复制循环 | 减少每样本 memcpy 开销；吞吐测试且 PCM 不变 |
| P2 | 缓存流扩展接口，减少每次读取 QI/Release | 减少回调开销；保留取消、超时、流寿命语义 |
| P2 | 精简构建、链接时删除未使用代码 | DLL 大小与性能同时测量 |
| P3 | Ogg FLAC、更多位深和精确声道描述 | 作为明确扩展，单独验证宿主兼容性 |

### 9.1 缓存优化有具体空间

原 FLAC 封装在 Open 中固定分配 `channels × 0x3FFFC` 字节 PCM 缓存，即每声道 65,535 个 int32 的空间。双声道约 512 KiB，8 声道约 2 MiB；仅加载 metadata 也走这项分配。

改为首次需要 PCM 时，按实际最大块长与输出容器大小分配，并在后续块大小变化时带上限扩容。例如 4096 帧、16 位双声道的封装输出块只需 16 KiB。**这是封装缓存的比较，不是整个 decoder 的总内存**；libFLAC 自身仍有缓冲区，图片和标签也占用内存。

### 9.2 不建议先做单曲多线程解码

普通 FLAC 播放首先需要稳定的顺序输出和快速 Seek，额外跨线程队列可能增加复杂度和内存。多个独立曲目的标签扫描或增益扫描，可以由宿主线程池分配独立 Reader；同一个 Reader 的流位置、decoder 和 dirty 状态不要由多个线程并发修改。

libFLAC 1.5.0 新增的是**编码器多线程接口**，不能把它解释成开启一个选项就能让当前 Reader 多线程解码。[1.5.0 接口说明](https://xiph.org/flac/api/group__porting__1__4__3__to__1__5__0.html)

### 9.3 文件体积与旧系统

采用现代 MSVC，沿用现有项目的 VC-LTL / YY-Thunks 兼容方案是可行技术路线；最终仍需检查全部静态依赖的导入、CPU 指令和实际运行，不预先宣称最新版 libFLAC 的新构建已经通过 XP。

- 构建所需的 C 库接口，关闭工具、示例、测试、文档和不使用的 C++ wrapper。
- 通过静态库与 `/OPT:REF`、`/OPT:ICF`、尺寸优化裁去未使用编码路径，核对 map/PE，不能假定上游有“一键 decoder-only”开关。
- 若首版只恢复 native FLAC，可暂不启用 Ogg 容器部分，减少依赖；增加 Ogg FLAC 后重新比较大小。
- 按现有项目约定明确最低 CPU 指令集，不能全局开启 AVX2 后声称适用于所有旧机器。
- 不保证新 DLL 小于原来的 86,152 字节；完整现代库、边界修复和 TTA 功能都会影响结果，应以实际产物比较。

许可证依照当前项目要求保存在仓库，不嵌入 DLL。使用 libFLAC 库时保留其版权、条件和免责声明，并在发行页面提供对应声明；它的库许可证与命令行工具许可证不同。[FLAC 许可证](https://www.xiph.org/flac/license.html)、[1.5.0 库声明](https://raw.githubusercontent.com/xiph/flac/1.5.0/COPYING.Xiph)

## 10. 建议实施顺序与完成标准

1. 建立独立 `ttp_flac` 工程，恢复两个工厂和原 ABI，先验证原版/重建版都能加载。
2. 接入 libFLAC 1.5.0，恢复 native FLAC 的打开、PCM、定位、流回调和正确错误码。
3. 恢复 TTA，包括通用标签转发、精准时长、可靠定位与历史格式分支。
4. 实现保序多值标签、完整封面及统一可靠保存，补齐重建宿主的可选提交结果处理。
5. 完成正确性回归后再优化内存、复制循环和产物大小。
6. 在原版/重建版上验证 XP、Win7、Win11；Win11 按用户要求代验 Win10 路径，明确实际系统。

核心验收范围：

- 8/16/24/32 位、单/双/多声道、高采样率、大小块、未知总采样数、带/不带 SEEKTABLE。
- 起点、中间、末尾、越界和反复 Seek；小 Buffer、非对齐 Buffer、EOF 重读。
- 异常帧、截断、错误头和超大 metadata 的有界失败，不能崩溃或无期限循环。
- 中文及非当前代码页路径、重复值、未知字段、空字段和删除语义。
- PNG/JPEG、多图、图片类型、尺寸、替换、删除，未修改元数据与音频保真。
- 只读、占用、磁盘空间不足、写失败、取消、路径被外部替换时原文件完整。
- 原宿主通用标签接口、重建版文件属性、播放、拖动进度、扫描增益与切歌。
- TTA 的普通整数、历史浮点分支、坏帧表及标签往返；未获得样本的分支明确保留待验证状态。

本次测试代码和全部生成样本保留在 `rebuild/tests/flac_analysis/`，不纳入发行包，不上传测试代码，也不加入 Actions 测试步骤。
