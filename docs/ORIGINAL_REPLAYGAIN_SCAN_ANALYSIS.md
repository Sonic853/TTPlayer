# 原版“扫描增益信息”运作分析

分析日期：2026-09-30。

## 1. 范围与结论

本次从原版菜单入口追踪到扫描窗口、工作线程、`ttpcomm.dll` 分析器、元数据写入和播放处理，并用本地二进制核对反编译遗漏的参数、浮点常量及导入函数。本文保留修复前的分析记录；获准后完成的实现、兼容策略与运行测试见 [扫描增益修复记录](REPLAYGAIN_SCAN_RECOVERY.md)。测试使用合成音频，没有更改用户音乐标签。

分析对象：

| 文件 | SHA-256 |
| --- | --- |
| `TTPlayer.exe` | `c7999ea5823469c1684148cac1bd196009824348ccac5cdd45978f8fb574e28c` |
| `ttpcomm.dll` | `e349ef73e8a1d35b2c5debd2ddaeb5cc2513a90647766b7339d2605b34483b33` |

以下“原版”指这两个本地样本，不能直接推广到所有历史发行版本。

主要结论：

1. 扫描会读取并解码音频、计算响度信息，再通过输入插件的元数据接口保存。扫描流程本身不重新编码歌曲音频。
2. 手动扫描、播放时自动扫描、播放时应用增益是三项不同功能。
3. 手动扫描使用一个扫描窗口，逐曲启动工作线程；没有同时扫描多首歌曲的线程池。
4. 每首曲目得到 `replaygain_track_gain` 和 `replaygain_track_peak`；批量选中歌曲不会自动变成专辑增益扫描。
5. 原版手动扫描具有暂停／继续、取消、跳过已有信息、进度显示和逐项结果。
6. 本次额外确认修复前重建版存在播放扫描与手动扫描输入幅度不一致的问题，详见第 10 节；后续修复已统一两条扫描路径的输入幅度。

## 2. 三项设置分别控制什么

原版 `CSettings_SerializeXml` 在 `Playback` 节点保存以下字段：

| 字段／控件 ID | 作用 | 不负责的工作 |
| --- | --- | --- |
| `AutoGain`／`0x851` | 播放时应用已经读取的曲目增益 | 不负责计算、补齐缺失标签 |
| `AutoScanGain`／`0x852` | 播放时分析当前解码得到的 PCM | 不要求先打开手动扫描窗口 |
| `SkipScanGain`／`0x853` | 手动扫描时，已有两个非空标签就跳过 | 不阻止播放时重新分析已有标签的歌曲 |

`004930B3` 修改 `AutoGain` 后向主窗口发送更新消息；`004B180A` 在临界区内更新处理器的启用状态。`AutoScanGain` 决定打开播放处理器时是否创建分析器，不能简单视为与 `AutoGain` 同一种即时开关。

手动跳过检查来自 `004A4E8C`：

```cpp
if (SkipScanGain && !track_gain.empty() && !track_peak.empty())
    return S_FALSE; // 已跳过
```

它检查的是两个字符串是否非空，不是严格验证数字是否合法；只有一个标签时不会跳过。播放自动扫描的创建条件没有这个跳过判断。

## 3. 手动扫描：菜单到线程

### 3.1 收集选中曲目、复用窗口

`00483F27` 是命令 `0x7EF8` 的入口：

- 用列表的选中项枚举接口收集曲目引用。
- 通过 `004A5584` 获取进程内的 `CScanGainDlg` 单例，指针为 `DAT_005460FC`。
- 尚未创建窗口且队列非空时，`004A55AF → 004A5C12` 创建资源 `0xDE` 的非模态对话框。
- 窗口已经存在时，仅恢复并置前该窗口；本入口不会把新的选择追加到正在扫描的队列。

### 3.2 初始化界面并启动第一首

`004A563F` 初始化列表、状态图标、曲名和文件路径；状态文字来自资源 `0x8160`：

```text
已完成|已跳过|出错
```

资源 `0x8162` 为：`正在扫描第 %d 个文件, 共 %d 个`。

初始化结束后发送自定义消息 `0xBD0`，由 `004A58F3` 调度第一首以及后续曲目。扫描中的百分比绘制在当前行的状态区域，相关自绘函数为 `004A5BA1`。

### 3.3 一次只分析一首

`004A4E8C` 打开曲目、建立音频读取／转换对象、查询元数据接口，检查是否应跳过，然后启动工作线程。

线程入口为带原始方法名的 `CScanGainDlg::CWorkThread::Run`（`004A5430`），实际循环在 `004A5251`：

```text
建立音频缓冲区
→ 创建分析器并按采样率初始化
→ 启动 reader
→ 反复读取、解码、取得 double PCM
→ 将声道数和帧数交给分析器
→ 发布百分比消息
→ 到达结束条件后取得 gain、peak
→ 发布本曲目完成消息
```

进度按累计处理字节、音频格式的每秒字节数和曲目时长估算，只在百分比变化时发布消息。没有音频输出设备驱动扫描速度，也没有每块音频必须按真实播放时长等待的逻辑。

`004A58F3` 收到当前项结果后保存成功项、清理当前读取对象，再启动下一项。因此其主要解码／分析工作在后台线程，队列推进、界面更新以及完成处理在窗口消息路径上。

### 3.4 暂停、继续、取消与结束

| 操作 | 原版行为 |
| --- | --- |
| 暂停 | `004A5B3C → 004A4CAB`，调用 `SuspendThread`，切换按钮文字 |
| 继续 | `004A5B3C → 004A4CC9`，调用 `ResumeThread` |
| 取消／关闭 | 先恢复被暂停的线程，再设置停止事件并等待线程退出，释放读取对象；不提交当前未完成曲目 |
| 全部完成或跳过且无错误 | 自动关闭扫描窗口 |
| 至少一项出错 | 继续处理后面的曲目，最终保留结果窗口 |

取消不会回滚之前已经完成并提交的曲目。重建时可以用条件变量实现相同行为，无需照搬 `SuspendThread` 的线程挂起机制。

## 4. 计算在哪里、计算什么

计算主体在 `ttpcomm.dll`，不是播放列表窗口：

| 入口／虚表槽 | 地址 | 功能 |
| --- | --- | --- |
| ordinal 100 | `60005010` | 查询是否支持指定采样率 |
| ordinal 101 | `60005530` | 创建分析器对象 |
| 槽 0 | `60005050` | 销毁对象 |
| 槽 1 | `600054A0` | 按采样率初始化 |
| 槽 2 | `60004450` | 输入交错排列的 double PCM、声道数、帧数 |
| 槽 3 | `60004110` | 取得当前曲目增益并清理曲目统计状态 |
| 槽 4 | `60004420` | 取得累计峰值 |
| 槽 5 | `60004430` | 从累计直方图计算增益；本次手动扫描流程未调用 |

`60004420/60004430` 没有被当前伪代码完整列为函数，已通过虚表 `600273B8` 和二进制指令核对。

### 4.1 采样率与声道

本地 DLL 的采样率表有 20 项，单位 Hz：

```text
48000, 44100, 32000, 24000, 22050, 16000, 12000, 11025,
8000, 18900, 37800, 56000, 64000, 88200, 96000, 112000,
128000, 144000, 176400, 192000
```

这是一张离散表，并非任意 8–192 kHz 采样率均支持。手动流程创建分析器后检查初始化结果；播放流程还先查询 ordinal 100。

`60004450` 分别处理单声道、双声道、六声道和其它声道数：双声道拆为左右缓冲，六声道按固定公式混成两路，其它多声道按声道数求平均后进入单声道分析。不能把这套处理直接替换为现代多声道响度权重而仍声称结果完全一致。

### 4.2 响度统计

可直接恢复的计算步骤：

1. 按采样率选择滤波系数。
2. 经过十阶滤波器 `60003A70`，再经过二阶滤波器 `60003820`。从阶数、系数表和后续统计结构看，与传统 ReplayGain 的感知加权结构相符；原二进制没有保留滤波器的源代码名称。
3. 每个窗口取 `ceil(sample_rate × 0.05)` 帧，约 50 ms。
4. 累加两路滤波输出的平方，换算到对数能量。
5. 将结果计入 12,000 格直方图，每格对应 0.01 dB。
6. 从高能量一端累计约 5% 的窗口数，得到对应分位点。
7. 曲目增益由该分位点决定。

设 `EL/ER` 为一个完整窗口的两路平方和，`N` 为该窗口帧数，二进制实际使用：

```text
j = clamp(integer(1000 × log10((EL + ER) / N × 536870912 + 1e-37)),
          0, 11999)
histogram[j] += 1

gain_db = 64.82 - percentile_bin × 0.01
```

`60003EAE` 的 `fldlg2` 与 `fyl2x` 组合确认这里是 `log10`；伪代码里显示为孤立的 `log2` 调用，会漏掉底数转换及外层乘法，不能直接逐行翻译。

`60004070` 在直方图没有有效窗口时返回零。曲目结束时不足一个窗口的剩余数据不会被此结算函数补齐为新的完整窗口。

这里的 `64.82` 是样本 DLL 的实际常量，不能直接当成用户音量百分比或某个未经核对的 LUFS 目标值。

### 4.3 曲目与专辑

`60004110` 会把曲目直方图合并到对象内另一张累计直方图，槽 5 可以查询累计结果，说明底层具有累计分析能力。

但 `004A5251` 为每一首创建分析器，取得曲目结果后销毁；保存处也只写两个 `track` 字段。因此原版此菜单的批量扫描是“每首独立扫描”，没有按 Album 分组、跨歌曲保留分析器或写入 `replaygain_album_gain/peak` 的闭环。

### 4.4 峰值的实际限制

峰值由分析器记录 PCM 绝对值，独立于上述响度分位计算。它不是通过过采样计算的真峰值。

本地样本还有一个值得单列的实现问题：`60003B80` 的峰值循环只遍历第一个输入通道缓冲；双声道分离后，该缓冲是左声道。右声道仍参与响度滤波和平方和，但没有同样的峰值最大值更新循环。六声道混合后也沿用两路入口。

这项已核对对应二进制循环，但未做左右声道不对称音频的运行实验。因此可确定静态路径存在这个限制，不应把其 `track_peak` 无条件描述成所有原始声道的最大峰值。后续应使用“左声道静音、右声道有信号”的专门样本验证端到端表现。

## 5. 原版 PCM 幅度约定：本次的重要校正

原版 `004B0560` 的整数 PCM 转 double 使用以下二进制常量：

| 输入位深 | 运算 | 常量地址 |
| --- | --- | --- |
| 8 bit | `(sample - 128) / 128` | `00526420` |
| 16 bit | `sample / 32768` | `00526418` |
| 24 bit | `sample / 8388608` | `00526410` |
| 32 bit | `sample / 2147483648` | `00526408` |

所以整数 PCM 转換后的满幅约为 `[-1, +1]`，不是 `[-0.5, +0.5]`。

`004B0D1A` 为手动扫描和播放建立相同类型的读取／转换对象。手动扫描取得转换后的 PCM 再调用分析器；播放处理 `004B1950` 在增益乘法之前调用分析器，传入相同数据缓冲，没有先除以二的操作。

`004B1950` 出现的 `±0.5` 是增益处理公式的分段阈值，不能据此推断 PCM 的归一化比例。重建版现有 `RecoveredProcessorChain::Process` 对此的注释需要校正，见第 10 节。

## 6. 保存哪些信息、何时真正写入

手动完成函数 `004A50B5` 的流程：

1. 结束并清理当前工作线程。
2. 只有成功项传入曲目对象；跳过／失败／关闭路径不提交该项。
3. 再检查 `abs(gain) > 0` 且 `abs(peak) > 0`。
4. 格式化并调用元数据接口槽 6：

   ```text
   replaygain_track_gain = "%g dB"
   replaygain_track_peak = "%g"
   ```

5. 用 `0041B722` 同步曲目内存中的两个字段。
6. `004C80AC` 对本地文件检查并清除只读属性。
7. 释放音频读取对象及元数据接口；具体容器如何刷新标签由输入插件负责。

这条宿主路径没有编码器创建和重新编码循环。插件可能为保存标签重写容器的一部分或重新组织文件，所以准确说法是“不把音频重新压缩”，而不是“文件任何字节都不会变化”。

### 原版保存路径的边界问题

- 数学上合法的 `0 dB` 会被手动完成函数跳过写入。
- 峰值为零时也不写，例如纯静音；双声道峰值限制还可能影响左静音、右有声的文件。
- 手动状态在写入处理之前根据扫描返回值标成“已完成”。槽 6 的返回值在这里没有逐项判错，因而“已完成”不能单独证明标签已经成功落盘。
- 手动扫描会清除只读属性；播放自动扫描的完成函数没有调用同一清除操作。
- 能否保存到具体格式、标签类别及位置，取决于该格式 reader 的元数据实现。不能仅凭文件可以播放就保证其增益可写。
- CUE 等分段曲目由 `004B0B51 → 004E323B` 的子曲目 reader 路径打开，不能将一首 CUE 曲目的扫描结果直接当成整张底层音频的增益。

## 7. 播放时自动扫描与应用增益

### 7.1 打开歌曲

`004B107E` 先读取 `track_gain` 和 `track_peak`。两项都非空时，从 gain 中解析 dB，再计算：

```text
scale = pow(10, gain_db × 0.05)
```

例如 `-6 dB` 对应约 `0.5012` 倍幅度，`+6 dB` 对应约 `1.9953` 倍。只存在 gain、缺少 peak 的情况下，原版不会在此建立该倍率。

peak 被读取保存，但 `004B1950` 不按它计算 `min(scale, 1 / peak)`。不能把原版描述成“先用峰值限制允许增加的 dB”。

随后若启用 `AutoScanGain` 且格式受支持，创建新的分析器。已经读到旧增益不会阻止此次分析。

### 7.2 每个音频块

```mermaid
flowchart LR
    A[读取及解码 PCM] --> B[按需转换为 double]
    B --> C[自动扫描分析器]
    C --> D[按 AutoGain 应用已有曲目增益]
    D --> E[均衡器]
    E --> F[立体声扩展]
    F --> G[后续播放与输出处理]
```

分析器先读取尚未施加 ReplayGain 的 PCM，所以不会把同一次播放的增益效果重复算入新标签。此处 EQ／立体声扩展处理也在其后；主音量与淡入淡出属于另外的控制，不会通过每次改变音量重新扫描整首歌。

启用 AutoGain 且倍率不为 1 时，令 `x = sample × scale`，原版后续分段计算为：

```text
x >  0.5: y = (tan(2 × (x - 0.5)) + 1) × 0.5
x < -0.5: y =  tan(2 × (x + 0.5)) × 0.5 - 0.5
其它:     y = x
```

本地 EXE 的调用地址 `004F55A8` 和导入表均确认是 `MSVCRT!tan`，不是 `tanh`。此函数不是数学上有界的饱和器，不应仅凭“软限幅”名称就断言它能可靠防削波。若未来改变此公式，应明确属于音质／可靠性调整，而非逐项原样恢复。

### 7.3 完成、停止和跳转

- `004B1375` 的读取结束分支调用 `004B1A5C`，后者取得结果、更新倍率、通过元数据槽 6 设置两个标签，并销毁分析器。
- 正常从头读到尾会进入该分支，新的整曲统计直到此时才可用。因此缺少旧标签时，不能在第一遍播放一开始就应用尚未算出的整曲增益。
- 手动停止／切歌后销毁处理对象的路径直接销毁分析器，没有调用其结算并保存步骤。
- `004B16FE` 在请求跳转位置非零时，先销毁分析器；避免把跳过部分内容的统计当成整曲结果。即使后续 seek 失败，分析器也已经销毁。
- seek 到零在此函数中没有执行相同销毁判断；不能把原版概括为“所有 seek 都一致取消分析”。

还需区别“正常结束”与原版的实际分支条件：`004B1375` 的部分 reader 路径在返回值非零时就调用结算函数，包含负错误码的可能性，并非每条路径都严格检查正常 EOF。重建版坚持自然 EOF 才提交，属于更严格的完整性处理，不应把它误写成原版对所有错误路径已有同样保证。

## 8. 删除增益信息

命令 `0x7EF9 → 0048423C` 收集选中曲目。

- 一首时直接处理。
- 多首时通过 `_RemoveReplayGainProc`（`00484148`）逐项执行并显示可终止进度。
- `00484009` 清空曲目内存中的两个 track 字段，再向元数据槽 6 写入空字符串。

这条路径没有重新解码音频，也没有撤销已经写入音频样本的响度处理；它删除的是播放增益标签。宿主这里没有一起清空 album gain/peak 的调用。

## 9. 不能直接等同的概念

| 操作 | 原版实际含义 |
| --- | --- |
| 扫描增益信息 | 分析音频，生成供后续使用的标签 |
| 自动增益 | 按已有 gain 标签改变播放 PCM，并经过原版分段公式 |
| 主窗口音量 | 另外的音量控制，不改写 ReplayGain 标签 |
| 批量扫描 | 队列中的每首独立得到 track gain |
| 专辑增益 | 底层有累计计算入口，但本扫描菜单没有完成相应宿主流程 |
| 峰值归一化 | 不是原版的响度分位算法；原版没有仅依据最高峰决定 gain |
| 格式转换时应用增益 | 属于转换输出链，应与“仅扫描并写标签”分开判断 |

## 10. 修复前重建版的有限核对

本节记录修复前状态，作为后续实施依据，不代表修复后的代码仍有这些问题。修复后的验证范围见 [扫描增益修复记录](REPLAYGAIN_SCAN_RECOVERY.md)，没有声称所有插件、格式和操作已完全一致。

### 10.1 关键问题：两条扫描路径的幅度比例不同

证据：

- `src/audio/replay_gain_scanner.cpp::ConvertSamples`：16 位输入除以 `32768.0`，对应原版 `004B0560`。
- `src/audio/audio_engine.cpp::RecoveredProcessorChain::Decode`：16 位输入除以 `65536.0`，其它整数位深及浮点输入也缩小一半。
- `RecoveredProcessorChain::Process` 把上述样本直接交给 `PlaybackReplayGainAnalyzer::Analyze`。
- `PlaybackReplayGainAnalyzer::Analyze` 没有乘二补偿，直接调用同一个 `ttpcomm` 分析器。

因此同样的 PCM 样本，手动扫描与播放时扫描的输入幅度相差二倍。在线性滤波和未触及直方图上下限的条件下，可由算法推导：

```text
播放自动扫描的 gain ≈ 手动扫描的 gain + 6.02 dB
播放自动扫描的 peak ≈ 手动扫描的 peak / 2
```

这是源码和二进制常量支持的静态结论；精确数值还会受 0.01 dB 量化、窗口分位及边界影响。本次没有把推算结果冒充已执行的音频实测。

建议修复时先统一 ReplayGain 分析器的输入幅度约定，并独立审计播放处理链的 PCM 转换、EQ、DSP 与输出反变换。不要直接把整条处理链数值翻倍而不核对后续接口。

### 10.2 其它明确差异

| 项目 | 原版 | 当前重建版／建议 |
| --- | --- | --- |
| 计算核心 | `ttpcomm` 分析器 | 已复用，但复用 DLL 不足以保证输入幅度一致 |
| 暂停／继续 | `0x88B → 004A5B3C` | `ScanDialogProc` 将同一按钮与取消一起处理，直接关闭；需恢复行为 |

| 无错误后自动关闭 | 是 | 已实现 |

| 标签格式 | `%g dB`、`%g` | 当前固定两位／六位小数，精度和字符串不完全一致 |

### 10.3 建议后续处理顺序

1. 修正幅度约定与错误注释，验证同一音频的原版手动、重建版手动、重建版播放扫描结果。
2. 恢复扫描窗口暂停／继续，并核对取消后的线程收尾与重新打开窗口。
3. 恢复标签数字格式；继续保留写入错误检查。
4. 对纯静音、极短音频、零增益、左静音右有声、已有单个标签、只读文件、CUE、seek 和损坏文件做边界验证。
5. 将原版缺陷与兼容策略分开决定：右通道峰值遗漏、零增益不写、异常返回仍结算，不应在未说明的情况下被当作必须复制的正常行为。

后续如执行自动化验证，测试源码应继续放在 `rebuild/tests`，不加入发行包及 Actions 测试流程。
