# ttpcomm 宿主曲尾与压缩 ID3 修复

日期及播放器发行版本：2026.10.08。

## 结论与原版依据

本轮继续处理 `ttpcomm` 重建后的宿主差异。实际缺陷位于播放器的读取、处理和通知链路，核心 DLL 算法无需再次修改。

| 原版位置 | 原版行为 | 修复 |
| --- | --- | --- |
| `TTPlayer.exe!004EA0EA` | PCM Reader 建议块长为 `nAvgBytesPerSec / 24`，按完整采样帧对齐 | 恢复 WAVE/AIFF/AU 读取边界，仍尊重调用方较小的请求 |
| `004B1B81 → 004B1BF4 → 004AC166` | EQ、环绕和 SSRC 之间使用 double PCM，最后量化 | 删除转回源文件整数位深的中间步骤，保留小数精度并避免提前削峰 |
| `004B1375` | EOF 后反复以空输入取完重采样器已产生的输出 | 连续排空，重复 EOF 不重复输出，Reset 后允许新输入 |
| `004AC304 / 004AC605 / 004AC0D9` | 曲尾静音维持设备队列，到达最终音频位置时停止重置 | 不将全部已提交静音追加为曲间等待，不向 EQ 人工补零 |
| `004AAC0F` | 使用窗口消息通知播放事件 | 音频线程完成清理后异步唤醒 UI，不再只依赖 250 ms 刷新周期 |
| `00461F87` 及播放间隔逻辑 | 歌词编辑时不自动换曲，曲间间隔独立等待 | 保留保存、编辑、停止、淡出关闭保护，增加独立间隔定时器 |

原版 EQ 在 EOF 时不会把内部不足整块的输入补零后输出。本轮恢复该行为，不能称为“保留全部输入样本的无缝播放”。

## 压缩 ID3

真实文件属性窗口中，同一压缩 `TIT2` 在原版显示标题、重建版为空；换用新旧核心均如此。原因是重建版内置读取器跳过压缩帧。

参照已恢复的 `libid3tag/frame.c`、`id3_util_decompress`，新增 ID3v2.3/v2.4 压缩标题、歌词和 APIC 读取，按版本处理长度和分组标识。复用已有静态 zlib 1.3.2，无新增运行库。

检查流结束、实际长度和校验和，限制每个标签累计解压数据为 64 MiB；拒绝截断、长度不符、未知编码及加密帧。保留原始帧与现有保存保护，没有解除对特殊编码 ID3 直接重写的限制。

## 验证结果

### 有效 PCM 对比

两种播放器分别使用新旧核心，WaveOut、16 位输出、关闭抖动和淡入淡出，使用隔离配置和非静音合成信号。

| 输入与处理 | 原版有效字节 | 修复后有效字节 | 不同采样值 |
| --- | ---: | ---: | ---: |
| 44.1 kHz 双声道，44107 帧，EQ | 173416 | 173416 | 0 |
| 48 kHz 单声道，48011 帧，EQ | 94524 | 94524 | 0 |
| 44.1 → 48 kHz 双声道，45123 帧，EQ + SSRC | 191832 | 191832 | 0 |
| 44.1 kHz 双声道，44107 帧，关闭 EQ | 176428 | 176428 | 0 |

原版额外提交静音维持设备队列。测试对上述非静音样本剔除完整全零提交块后比较，生产代码不进行此剔除。捕获发生于软件提交点，不能代替声卡模拟输出测量。

- XP SP3、Win7 SP1：第一组的两种宿主、两种核心四种组合，有效 PCM 完全一致。
- 两首不同采样率歌曲连续播放，零间隔及一秒间隔在 XP、Win7、Win11 全部通过。重建版零间隔的设备关闭至下一次打开分别为 0、16、16 ms；一秒间隔分别为 1000、1031、1016 ms。这些是单次记录，不是跨设备延迟保证。
- 停止、暂停、定位曲尾、手动下一首、歌词编辑期间 EOF 五项实际窗口命令测试通过，没有额外启动歌曲。
- 30,000 个采样值的积压队列探针逐值通过，覆盖多次排空、重复 EOF 和 Reset；PCM 转换测试覆盖 24 位输出保留小数精度、拒绝部分采样帧和三种 SSRC 模式。

### 实际调用

- 生产 `SkinPackage::ReadEntry` 遍历 **176 个皮肤包、8,011 个条目、125,312,965 字节**，新旧核心输出完全一致，拒绝数为零。
- 原版/重建版 × 新旧核心，共 16 次文件属性读取：普通标题、压缩标题、截断压缩帧、末尾 `FF 00` 反同步帧。修复后显示结果一致。
- 14 组 ID3v2.3/v2.4 标题、歌词、封面及损坏输入测试在 XP、Win7、Win11 通过；Win11 原有标签读写、封面和子进程文件属性回归通过。
- 原插件可能通过宿主 `CreateStdContent` 访问标签，并非都直接导入 `ttpcomm` 的 ID3 接口；以上测试不等于每个 AddIn 的全部组合验证。

私有证据：`rebuild/tests/ttpcomm_rebuild` 下的 `pcm-hosts-eof`、`eof-vm`、`pcm-continuity`、`vm-continuity`、`pcm-guards`、`id3-host-callers` 和 `skin-caller-win11.log`。虚拟机连续播放首轮测试夹具错误生成 CR-CR-LF，修正后重新验证；有效记录为 `*-v2.bin` 和 `summary.json`。

## 核心清单与剩余边界

频谱 ordinal 105 清单更正为 `implemented`，与此前 16,384 组精确对比一致。核心 DLL 仍为 239,104 字节，SHA256：`d68023c4d3a9d132a7e1f51e17d622bf43f22c52c62da3955b12d1eeb38063c5`。

仍保留已记录的安全处理、raw DEFLATE 部分边界状态差异、MPEG/SSRC 浮点容差、历史未初始化内存确定化。压缩等特殊编码 ID3 的直接写回、加密帧、ID3v2.2 整标签压缩及所有历史畸形标签的宿主全流程尚未完整恢复。物理设备矩阵、其它输出后端、全部 DSP 和皮肤的长期 UI 组合未穷尽。

Windows 10 按用户要求由 Win11 代测。测试源码不加入发行包或 Actions，未提交或发布，原版根目录 DLL 未覆盖。


## 2026-10-08：公共实现整合

播放器现通过 `third_party/ttpcomm-sdk` 固定快照复用 `ttpcomm` 项目的 ABI 调用、PCM、ID3/封面、ZIP、Base64/UTF-8 和流派表。快照由 `ttpcomm/cmake/sync_sdk.py` 生成，CMake 校验摘要；旧 DLL 缺少能力查询时仍走原版接口。

本轮补齐重建核心的 RG 并行能力协商和五文件组合更新包识别，保持插件单独核验、自动更新只替换 EXE 的策略。没有将文件写入事务、中文标签编码规则或两种 FFT 数值模式强行合并。

详细设计、迁移清单和 XP/Win7/Win11 测试结果记录在相邻 `ttpcomm/docs/RECONSTRUCTION_STATUS.md` 第 9 节。发行版为 `2026.10.08p1`；测试仅位于 `rebuild/tests/ttpcomm_rebuild`，不加入 Actions 或运行包。
