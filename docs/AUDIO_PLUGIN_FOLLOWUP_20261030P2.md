# LTP960 与退出兼容修复：2026.10.30p2

本轮补足真实 PCM 编码的 LTP960 验证，修复 Discord 通信导致的长时间退出等待，以及实测中新出现的配置保存 `0x80070497` 弹窗。生产修改限于 `src/integrations/discord_presence.cpp` 和 `src/settings/settings.cpp`；AAC 生产 DLL 沿用已验收的 2026.10.30p1，没有为通过测试改动参考 PCM。

## LTP960 的真实编码验证

生成八组 AOT 4 的 960 帧音频：44.1／48 kHz、单／双声道，各含自动长短窗和强制长窗。输入是四秒实际 PCM，经过 MDCT、长期预测搜索、量化和码流写入；逐帧确认预测实际启用。另生成八组 1024 帧控制样本。

验证编码器为私有改造的 FAAC 1.28，复用其 DRM 分支已有的 960／120 数学几何，输出普通 MPEG-4 LTP 语法。**没有把 1024 包修改帧长标志冒充 960，也不把样本称为官方历史一致性向量。** 官方历史 LTP960 样本仍未找到。

独立 OxideAV 参考使用自己的解析、预测及 f64 合成路径。其私有过渡分析窗修复先以八组 1024 控制音频对照 FFmpeg 校准，最大 RMS 为 0.00615 LSB16；八组 960 与生产 DLL 的完整 PCM 对照最大 RMS 为 0.640271 LSB16、峰值为 4.737103 LSB16。禁用参考解码器 LTP 后输出显著不同，确认并非只测试 AOT／ASC 初始化。

Win11、XP SP3、Win7 各通过 **44 条公共接口命令／140 个展开场景**，合计 132 条命令／420 场景。每系统包含 48 次 Reset 整段重放，不能再加进场景总数。覆盖：

- 16 组 960／1024 样本的四种缓冲容量、帧长和 Reset 后 PCM 一致性。
- 16 组普通 MP4 的 Reader→Decoder 完整 PCM。
- 八组编辑列表 MP4 的整段时间轴和六次往返定位，逐样本比较 PCM。
- lag 0／1920 合法；1921／2047 在第二包明确拒绝，错误 `0x8007000D` 且无输出。

完整样本、编码器来源、私有补丁、散列、独立参考和限制见 [AAC LTP960 验证](../../ttp_aac/docs/LTP960_VALIDATION_20261030P2.md)。本批不覆盖 LTP960 的 TNS、KBD、ER-LTP、多声道及全部合法采样率；编码器 ASAN 结果不能冒称生产 DLL 的 ASAN 结果。

## 旧宿主退出超时的排查与修复

上一轮单次超时发生于 2026.10.24 的旧重建宿主，SHA256 为 `fb344f0aa53038919d9b09df4903107c7dac3d21814904bb260e5ed94e158c35`。它不是原版 5.7.9，也不是当前 Release。PE 没有匹配的 CodeView/PDB；构建时间和保存的日志支持来源映射，但不能据此声称具有精确调试符号。

本轮在 Win11 做了 67 次不同播放／关闭时机的自然复测，XP、Win7 各做八次，未再复现原来的单次超时。私有诊断程序已能记录 WM_CLOSE、窗口状态，并在七秒／十四秒捕获线程栈和 dump；失败不被重试结果抹去。

另外，在原有 Discord 组件上稳定复现了真实缺陷：慢速分片的 READY 或清除状态 ACK 每到一点数据，原来的 1500 ms 超时就重新开始，析构等待达到 **10.0～10.3 秒**。仅设置停止标志、唤醒条件变量，不能中断正在等待的管道读取。

修复内容：

1. 为一次完整请求／应答设置共享总期限，头部、正文和 PING／PONG 不再刷新预算。
2. 停止事件唤醒正在等待 I/O 的工作线程，由发起线程取消自身未完成操作。
3. 保留退出时清除 Discord 状态的行为，使用独立 250 ms 预算。
4. 安全等待取消完成后才释放 OVERLAPPED，不放弃线程或强行结束线程。

### XP 实测发现的取消兼容问题

首轮修复在 Win7 通过，但 XP 的静默管道测试触发了 20 秒 watchdog。实际记录显示 `CancelIoEx` 返回 `ERROR_NOT_FOUND`，I/O 事件尚未完成。固定版本 YY-Thunks 1.2.2 的回退不支持指定非空 OVERLAPPED，不能假设它等价于原生 `CancelIo`。

最终在 `CancelIoEx` 失败时，由同一个工作线程显式调用 XP 原生 `CancelIo`；该线程独占此管道且只保留一笔未完成操作。最终三个系统均通过 **九种新增情况＋两套原有完整 Discord 回归**，包括 seek、重连和歌词同步。XP 取消析构为 15～16 ms，清除状态为 266～281 ms；调度开销不应被误写成严格 250 ms 墙钟保证。

**上述缺陷已稳定复现并修复，但不能认定它就是上一轮那一次旧宿主退出超时的原因。** 当时没有失败线程栈，本轮自然复测也未复现该次条件；不把原因归给 AAC 或其它组件。

## 配置保存弹窗 `0x80070497`

本轮实际宿主测试出现了用户截图中的错误，目标明确为隔离目录 `host-verification/fixed/TTPlayerRebuild.xml`。它发生于 `ReplaceFileW` 提交配置时，错误 1175 表示旧目标无法删除；根据 [Microsoft ReplaceFileW 文档](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew)，此错误下旧目标和替换文件仍保持原名。

原实现遇到该错误立即弹窗并阻止退出。现在：

- 对 1175、共享冲突和文件锁冲突，每 25 ms 尝试一次，替换阶段最多重试约 500 ms。持续占用仍报告失败，不能把配置未保存当作成功。
- 提交前释放验证用 DOM；这只是明确缩短生命周期，**没有证据认定 MSXML 就是占用者**。
- `ReplaceFileW` 额外使用本次调用独有的备份路径，保护 1176／1177 的部分失败；不使用直接截断或先删目标的降级方式。
- 1177 时仅恢复到不存在的原路径；恢复失败或已有并发写入时保留恢复文件，同时保留先前已落盘的 `.bak`。

无界面测试另真实观察过一次 1175，但尚不能确定外部占用进程或具体时序。测试不通过关闭防护软件或绕过文件权限消除错误。

三个系统各通过 **12 组当前生产提交函数测试**，包含真实短时／持续共享锁、只读、损坏主文件保护备份，以及 1175／1176／1177 故障注入。每系统另做 300 次 DOM 加载、保存、验证和替换循环及四种真实锁检查。故障注入不是声称实际磁盘发生过所有 1176／1177 情况。当前函数提取、编译散列和失败原日志均保留在私有测试目录。

## 最终实际播放器验收

每系统 23 组：八种 LTP960 分别在原版 5.7.9 与最终重建版运行，共 16 组；六组既有 LTP／DRC／CCE／多配置 MP4 回归；一组 `TTPlayer.exe` 别名版本。检查实际加载插件路径、请求文件、播放时间推进、错误窗口、配置保存及正常退出。

| 系统 | 最终通过 | 最大关闭等待 |
|---|---:|---:|
| 本机 Windows 11 | 23／23 | 453 ms |
| XP SP3 | 23／23 | 469 ms |
| Windows 7 | 23／23 | 360 ms |
| 合计 | 69／69 | — |

这些数字是本批测量，不是所有设备的退出时限承诺。Win10 按用户约定由 Win11 代测，不声称真实运行过 Win10，也不把宿主运行测试当作实体音箱听音。

保留两类首败证据：保存弹窗的日志和 dump；别名 EXE 的探针初次错误读取 `TTPlayer.xml`，而重建版实际使用 `TTPlayerRebuild.xml`，修正探针后单独复验。不能仅凭批处理返回零就宣告播放／保存成功。最终统计核对了实际请求文件及非零播放时间。
