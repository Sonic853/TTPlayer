# TTPlayer 5.7.9「梦幻星空」实现分析

日期：2026-10-26。对象：本目录保存的原版 TTPlayer 5.7.9 与配套 ttpcomm.dll。

阅读提示：第 1–11 节记录二进制证据、精确行为和重建差异；第 12 节按画面生成过程逐层解释实现，包含直观例子、流程图和便于理解的伪代码；第 13 节核对 Goom 1.9.3 对应关系与后续版本的升级影响；第 14 节专门比较 wgoom 1.99、原版和 2k4。

## 1. 结论

“梦幻星空”是**由音乐驱动的分形点云、参数轨迹亮点、双声道波形线，以及历史图像反馈变形组成的二维效果**。

播放器在独立线程取得音频，调用 `ttpcomm.dll` 的 90–93 号导出；DLL 在 CPU 上生成像素，播放器负责显示和全屏拉伸。这条路径没有 GPU 粒子系统，也没有每颗星独立的三维坐标、速度和寿命。

核心控制流与历史 Goom 系列高度对应。现有重建采用 Goom 1.9.3 作为适配基础，但**尚不能凭此认定原版恰好使用未经修改的 Goom 1.9.3**。二进制中有不同的音量系数、随机表、对象布局、浮点舍入和缓冲顺序。

本轮是分析，未修改播放器或 DLL 实现，未重新运行 XP／Win7／Win11 动态测试。

## 3. EXE 和 DLL 的分工

### 3.1 宿主调用链

```text
视觉类型 Type=1／菜单命令 0x8086「梦幻星空」
  → VisualCtrl 视觉子窗口（控件 ID 0x7DDC）
  → CPlayerWnd::Run（0045F12D）
  → 按视觉类型请求音频数据（00457AAD → 004ABBDC）
  → 更新视觉控件（00457B11）
  → 梦幻星空包装（0045692F）
  → ttpcomm.dll ordinal 92（6001DCFF）
  → 得到 32 位像素缓冲
  → DrawDibDraw 显示（0045697F）
```

`00457AAD` 对梦幻星空选择“不做 FFT、取得双声道 PCM”。频谱分析选择另一条 FFT 路径，不能把频谱的 105 号导出解释成梦幻星空的内部输入。

### 3.2 四个导出

以下为按汇编恢复的语义签名，函数名是便于理解的命名：

```cpp
void* __fastcall Create(unsigned width, int height);                 // 90
void  __fastcall Resize(void* object, unsigned width, int height);  // 91
const uint32_t* __fastcall Process(
    void* object, const int16_t* left, const int16_t* right,
    int forceMode);                                                // 92
void  __fastcall Destroy(void* object);                            // 93
```

| 导出 | 原版地址 | 作用 |
| ---: | --- | --- |
| 90 | `6001D85E` | 分配对象、两个像素缓冲、滤镜、IFS、两条波形线 |
| 91 | `6001D9C4` | 改尺寸并重建相关缓冲 |
| 92 | `6001DCFF` | 送入左右各 512 个 signed short，推进一次效果 |
| 93 | `6001DAAD` | 释放对象及相关状态 |

x86 下 `Process` 的 ECX 是对象，EDX 是左声道地址，右声道地址与模式放在栈上。旧伪代码把 EDX 错认成 float，直接照抄会得到错误接口。

原版播放器给模式参数固定传 **0，即自动变化**；DLL 内部支持更多模式，并不代表播放器菜单也提供了这些选项。

## 4. 音频怎样驱动画面

### 4.1 取样与强度

输入为左右声道各 512 个 16 位采样。原版在成功向输出设备提交 PCM 后，把同一批数据写入视觉环形缓冲；查询时参考输出设备报告的播放位置，使视觉读取点跟随播放进度。

`004ABBDC` 请求 `512*nBlockAlign` 字节，转换为 16 位数据后抽取前两个声道；单声道复制为两份。8 位输入减 128 再左移，24／32 位整数取高 16 位。这里没有把所有多声道信号混成两个声道，也不向 Dream 导出传入采样率或时间戳。

这条缓冲读取会消费数据，不能把它理解成任意回看、每次严格重新切片的音频历史库。原版怎样把设备游标误差传播到视觉时刻，仍需运行测量。

DLL 的整体强度取：

```text
P = max(0, left[0], left[1], …, left[511])
```

这是**左声道最大正值**。它不是绝对峰值、均方根音量、频段能量或 BPM；负半周不会直接增大 P，右声道仍参与后面的波形绘制。

从原版语义看，交换声道、改变采样窗口或将正峰改为双声道 RMS，都可能改变效果，不能当作无差别的清理。

### 4.2 速度和扩张

用 `s` 表示旧速度，原版核心计算可概括为：

```text
d = floor(P/5000) - 1 - (s>5 ? 1 : 0) - (s>20 ? 1 : 0)
s = clamp(min(s,40) + d, 0, 40)
扩张 = min(1.5, (P*0.0002f + s*0.025f) * (2/3 的 float 常量))
```

位置：`6001DD2D` 后；常量地址 `60027EA0/60027EA4/60027E9C/60027E98`。

**原版使用 `0.0002f`。** 对照的 Goom 1.9.3 源码使用 `1/50000`，小了 10 倍。直接拿上游实现替换，会使音量引起的扩张程度明显不同。

### 4.3 音乐事件与自适应阈值

- 比较的是本帧速度变化 `d` 与阈值，阈值初值为 2。
- 达到条件后打开约 20 次更新的活跃窗口，并允许调整变形方式。
- 另有常见 50、75、100 次更新的切换冷却，以及长时间无变化时的保护分支。
- 每 100 帧检查事件数：没有事件且阈值大于 1 时降低阈值；事件达到 16 次时提高阈值。

因此它会随音乐强弱变化，但并没有先识别节拍时间轴再把动画吸附到每一拍。

## 5. 画面由哪些层组成

### 5.1 IFS 分形点云

关键函数：`6001F7BE`、`6001F687`、`6001FCD1`、`6001FAC1`、`6001F97C`、`60020A66`。

IFS 即“迭代函数系统”：对点反复施加一组平移、缩放和旋转变换，生成成簇、卷曲或放射状的复杂结构。

原版每组随机选择 2–5 个变换，对应递归深度 10、6、4、2。坐标运算大量使用小数位为 12 的定点数，单位为 4096；负数的算术右移也是效果的一部分。

变换参数不会突然全部跳到新值，而是使用四组控制参数做三次 Bézier 插值：

```text
M(t) = (1-t)^3*M0 + 3*(1-t)^2*t*M1
     + 3*(1-t)*t^2*M2 + t^3*M3
t = count * 6 * 0.001f
```

约 167 次 IFS 更新后续接下一段，并延续端点切线。因此点云可以不断改变形状，而不只是把同一张星空图片旋转。

显示层每点通常写一个像素，并把另一缓冲的同位置颜色作饱和相加。分形退场通过增大“隔多少个点画一个”的抽样步长实现；恢复时在约 5 次更新中逐渐回到密集显示。

点云亮度另有 80 次更新的明暗循环，基色按内部三组通道变化规则推进。它没有逐星独立的出生、衰老和消失计时器。

### 5.2 五组十字亮点

关键函数：`600208A9`。

这层在分形不处于密集显示时出现。速度不同，每次绘制 5、10 或 15 个轨迹点。单点位置为：

```text
x = centerX + trunc(Ax*cos(float(T)/Tx))
y = centerY + trunc(Ay*sin(float(T)/Ty))
```

振幅受前面的音量扩张控制；周期和相位各不相同，所以轨迹可以交错、绕行和扩散。每个点由 3×3 范围内的五个像素组成十字，中心为白色，四臂使用该组颜色。

五组四臂颜色为 `FFFF33`、`FFCC00`、`5500FF`、`000000`、`FFFFFF`。黑色组仍有白色中心。

旧亮点的轨迹不会靠保存一长串粒子位置维持，而是留在历史画面中，继续被后面的反馈变形搬移和衰减。

### 5.3 左右声道波形线

关键函数：`6001F3B7`、`6001EF7C`、`6001F48A`、`6001EC3D`。

每声道有一条 512 点曲线，基础形状可以是圆、水平线或垂直线。采样沿每点的方向挤动曲线：

```text
x[i] = trunc(baseX[i] + cos(angle[i])*0.001f*pcm[i])
y[i] = trunc(baseY[i] + sin(angle[i])*0.001f*pcm[i])
```

相邻点连成 511 段，并用饱和加色叠到图像里。初始两条线分别从上、下边缘的水平线，趋向大小不同的圆。

形状和颜色也逐帧缓动：

```text
形状 = (39*当前形状 + 目标形状)*0.025f
颜色字节 = (63*当前颜色 + 目标颜色) >> 6
```

因此看到的环形震动、交织曲线和被拉开的线条，都可能来自真实 PCM 波形，而不只是随机光线。

## 6. 拖尾、扩散和扭曲的来源

### 6.1 整张历史画面的反馈

关键函数：`60020131` → `6002110B` → `60026000`。

滤镜为画布中每个像素准备“到上一张图的哪里取颜色”的坐标。每次更新反复对历史图像做缩放、扭曲、剪切或波动，新加入的亮点与线条也会进入这条反馈链。

这解释了为什么画面可以形成光束、隧道和流动的星云：既有新点运动，也有整张旧图像在移动。

### 6.2 八种内部变形

名称用历史 Goom 源码辅助标注；编号和右栏行为由原版二进制核实。

| 内部编号 | 对照名称 | 原版主要变形 |
| ---: | --- | --- |
| 0 | NORMAL | 基本径向缩放 |
| 1 | WAVE | 按半径平方索引正弦表，调制缩放 |
| 2 | CRYSTAL_BALL | 在速度因子上加半径平方项 |
| 3 | SCRUNCH | 减去较弱的半径平方项 |
| 4 | AMULETTE | 减去更强的半径平方项 |
| 5 | WATER | 使用逐行偏移和波动状态 |
| 6 | HYPERCOS1 | 对横纵坐标加入交叉正弦扭曲 |
| 7 | HYPERCOS2 | 更强的交叉扭曲，并采用固定速度因子分支 |

自动模式按随机表 `%28` 的分支给它们不同权重，还会改变中心、反向、平面偏移、波纹和噪声。切换使用新旧坐标映射插值，不必立即整屏换形。

DLL 的 `forceMode=1..8` 对应上述 0..7；`0` 是自动。`-1` 会压制本次的新参数，但仍有其他状态和长周期刷新分支，不能解释成“整幅动画完全冻结”。

### 6.3 残影为什么会逐渐消失

重采样使用带 4 位小数的坐标，从四个邻近像素取加权颜色。权重接近双线性插值，但每个非零乘积会减 1。

- 普通小数位置的权重和为 252。
- 单轴落在整数位置时通常为 254。
- 两轴均为整数位置时为 255。
- 最终统一右移 8 位，即除以 256。

所以每次反馈都会损失少量亮度。它不是额外覆盖一层半透明黑色，也不是逐颗星计算 alpha 淡出。

原版使用 MMX 饱和加法和加权像素处理；高字节参与部分计算，不应直接解释成现代透明合成意义上的 alpha。

## 7. 一帧的准确顺序

设进入 `Process` 时两块工作像素分别为 S、D：

```text
读取 PCM，更新强度/速度
  → IFS 向 S 加点，底色取 D
  → 向 S 画十字点
  → 选择/推进反馈映射
  → 把 S 变形重采样到 D
  → 左右波形线画到 D
  → 帧计数加一
  → 交换工作指针
  → 返回交换前的 S
```

**本次刚写好的 D 并不是本次立即返回的画面。** 它进入下一次处理，形成一帧流水。IFS 点坐标本身也有交替缓冲。因此重写时即使各公式相同，改变处理顺序仍会造成不同画面。

## 8. 显示、全屏、帧率和停止

### 8.1 普通窗口与全屏

普通状态使用皮肤提供的视觉区域尺寸。任一维小于 2 时，宿主释放梦幻星空对象。

全屏路径 `0045775A` 分别限制内部宽高：

```text
内部宽 = min(窗口宽, 320)
内部高 = min(窗口高, 240)
```

这是两个维度分别限幅，**不是按显示器比例求一张等比 320×240 缩略图**。生成低分辨率画面后，`0045697F` 用 `DrawDibDraw(..., 0x1000)` 拉伸到目标矩形。宽屏全屏的可见形状也受到这次拉伸影响。

原版该效果是 32 位 DIB 的不透明绘制，视觉全屏使用黑色背景。它没有类似星环效果的可选背景照片、徽标或透明星层。

### 8.2 刷新方式

默认配置函数 `00401E96` 将视觉帧率设为 **25 FPS**（`00402274`），默认视觉类型为频谱分析 Type 2。开启梦幻星空后沿用这个全局帧率。不能把 FPS 为零时的后备等待误当成默认帧率。

`CPlayerWnd::Run` 使用独立工作线程，第一次处理前和每次处理后都等待：

```text
FramesPerSec 非零：1000 / FramesPerSec 毫秒（整数除法）
FramesPerSec 为零：50 毫秒
```

原版每轮处理之后再等这一段时间，实际周期还要加取样、计算和绘制耗时。因此“设定 40 FPS”不是严格锁定每 25 ms 一帧。

效果中的 20／70／80／100／167／200 等周期大多以更新次数计数；提高 FPS 会让实际时间中的形变、冷却和衰减加速。若将显示率直接提高到 120／240 FPS，这一点尤其明显。

### 8.3 暂停、停止与短读

- 宿主只在音频状态为播放时送入新帧；暂停保持已显示的画面。
- 停止清理路径 `00457BCF → 004569C3` 清零最后返回的像素缓冲，但并不等同于销毁全部 Dream 对象、清零所有全局状态。
- `004ABBDC` 在音频读取返回 0 时拒绝更新；**正数短读仍进入后续固定 512 点处理**，尾部有沿用旧工作区数据的可能。现有说明文档中的“取得完整 512 点才更新”应当按重建版策略理解，不能反推成原版事实。

暂停期间另外换肤、切换效果或重设尺寸仍可重配画面；上述暂停保持指没有这些额外操作。静音但仍处于播放状态时，只要查询成功，原版仍送入全零 PCM 并更新效果。

### 8.4 菜单与歌词同屏

- 普通视觉区左键释放按 `0→1→2→3→4→0` 轮换；全屏只在梦幻星空、频谱、示波三种动态效果之间轮换。
- 从不显示或专辑封面进入视觉全屏时，原版会改为梦幻星空。
- 歌词同屏的窗口位置、歌词占比和视觉覆盖区域由 EXE 的 `FullScreen` 设置控制，不在 Dream DLL 里。
- 原版的 `LrcSizeGoom=2` 表示歌词区占底部约 20%；是否让视觉覆盖歌词后方还取决于布局与透明条件。

### 8.5 可配置范围

原版视觉选项的 FPS 滑条为 **10–40**，修改后影响后续线程等待。全局保存项是 `Visual/Type`、`Visual/FramesPerSec`；全屏另存 `PosRelationGoom`、`LrcSizeGoom` 等布局项。

已追踪的 Dream 调用只传尺寸、两段 PCM 和自动模式 0，未见独立“星数、星色、速度、灵敏度”设置入口。频谱颜色和示波模糊选项属于另外两种效果，不控制梦幻星空。

## 9. 随机性、共享状态和原版边界

对象主体大小为 `0x40088`，包含两个 128 字节对齐的像素缓冲指针、两条波形线、内嵌滤镜与 IFS 指针。滤镜还分配三块每像素两个坐标的映射缓冲。

但宽高、随机表和多组效果计数是 DLL 全局状态。原版创建会改写这些全局量，销毁会释放共享随机表，不能据“有对象指针”就判断可以安全并行运行多个不同尺寸实例。

两处影响精确对照的历史行为：

1. **随机表尾项未初始化。** 分配 16,384 个 short，只填前 16,383 个；创建后游标恰好指向最后一项。即便固定随机种子，也不能忽略堆内容的影响。
2. **正弦表边界读到相邻字段。** 实际填充 65,535 项，但索引可到 65,535；该位置对应相邻速度字段。改成普通完整 65,536 项正弦表，会改变对应边界画面。

另有 x87 中间舍入、定点负数右移、重复随机表达式的索引推进等细节。它们说明“数学上相近”与“和原版逐像素一致”是不同目标。

1. **保留现有核心基线。** 不宜用通用 GPU 星粒子、FFT 环形频谱或未经适配的新版 Goom 代替，视觉组成和数值都不同。

4. **若增加高分辨率模式，保留原版 320×240 模式。** 内部尺寸改变会影响点坐标、线宽、速度感和滤镜映射；只换高分辨率不是无差别优化。

## 12. 从声音到星空：逐层实现说明

理解原版“梦幻星空”的关键，是把它看成一个**不断向旧画面加入新内容，再让整张画面变形、移动和变暗的循环**。

星点、光环、拖尾和星云，都是这个循环逐帧积累出来的。下面按照原版实际处理过程展开说明。公式和伪代码在本节按语义简化，用于解释原理；精确常量、舍入和缓冲边界以前面各节的二进制分析为准。

### 12.1 为什么会形成“星空”

假设在黑色画布中央画一个亮点：

1. 下一帧，把旧画面稍微向外放大，亮点就向外移动。
2. 放大的同时降低一点亮度。
3. 在中央附近再画一个新亮点。
4. 重复上述过程。

若连续执行，画面上就会出现一串从中央向外延伸、逐渐变暗的亮点。

再把“向外放大”改成带有旋转感、波纹或横向偏移的坐标变换，轨迹就会弯曲、扩散、卷成光束。

**梦幻星空正是在这个反馈循环里，不断加入分形点云、轨迹亮点和音频波形。**

```mermaid
flowchart TD
    A[左右声道 PCM] --> B[计算声音强度与运动状态]
    B --> C[生成分形点云和轨迹亮点]
    C --> D[加入历史画面]
    D --> E[缩放、扭曲和衰减]
    E --> F[叠加左右声道波形]
    F --> G[交替缓冲并显示]
    G --> D
```

这里的“历史画面”本身就是动画状态的一部分。上图概括各层之间的关系；两块缓冲的具体返回顺序见第 12.8 节。

### 12.2 播放器如何把声音送给效果

原版播放器负责从音频输出链取得数据，然后调用 `ttpcomm.dll` 的 **92 号导出**。

每次输入：

```cpp
int16_t left[512];   // 左声道，512 个有符号 16 位采样
int16_t right[512];  // 右声道，512 个有符号 16 位采样
```

单声道会复制成两份；多声道在这条路径里抽取前两个声道。

这些数据来自播放器已经提交到输出链的 PCM，并参考设备播放位置调整读取点。效果函数收到的是：

```text
当前声音波形 + 效果内部状态
```

它没有收到歌曲时间戳、采样率或每帧经过多少毫秒。动画推进主要依赖调用次数。

例如，44.1 kHz 下的 512 个采样约覆盖 **11.6 毫秒声音**；原版默认视觉刷新率为 25 FPS，因此音频采样窗口长度和视觉刷新间隔是两个不同的量。

### 12.3 声音强弱怎样改变运动

#### 12.3.1 先取得左声道正峰

原版扫描左声道：

```text
P = max(0, left[0], left[1], …, left[511])
```

也就是取这段波形中最大的正值。

右声道仍然参与后面的波形绘制，但这个控制整体运动的强度值主要来自左声道。

#### 12.3.2 强度改变运动速度

用 `s` 表示上一帧的速度，在正常的 0～40 状态范围内，原版执行过程可概括为：

```text
d = floor(P / 5000) - 1
    - (s > 5  ? 1 : 0)
    - (s > 20 ? 1 : 0)

s = clamp(s + d, 0, 40)
```

可以把它理解成：

- 声音较强时，给运动增加推动力。
- 当前速度越高，阻力越大。
- 声音变弱后，速度逐步降下来。
- 最终速度限制在 0～40。

所以它有一定惯性，声音刚变弱时不会立即静止。

#### 12.3.3 强度还改变运动范围

轨迹扩张系数为：

```text
扩张 = min(1.5, (P × 0.0002 + s × 0.025) × 2/3)
```

这个值用于放大亮点的运动范围。

例如在速度较低时：

- `P=5000`，扩张约为 `0.67`。
- `P=15000`，扩张很容易达到上限 `1.5`。

这里的 **`0.0002f` 是原版二进制中的实际常量**，恢复时必须保留。

### 12.4 第一层：分形点云怎样生成

这是画面中大量复杂星云形状的重要来源。

原版使用 **IFS，迭代函数系统**。它的基本思想是反复对点进行坐标变换。

可以用一个简化公式理解：

```text
新 x = a × x + b × y + 平移 x
新 y = c × x + d × y + 平移 y
```

其中的系数包含缩放、旋转等信息。不断把得到的新点继续送入变换，就会生成复杂的点群。

#### 12.4.1 原版如何控制复杂程度

原版随机选择 2～5 个变换：

| 变换数量 | 对应递归深度 |
| ---: | ---: |
| 2 | 10 |
| 3 | 6 |
| 4 | 4 |
| 5 | 2 |

变换分支越多，递归深度越小，以控制生成量。

这些是生成坐标的规则，不能直接当成屏幕上的星点数量。

#### 12.4.2 点云为什么能连续变形

原版保存四组控制参数，通过三次 Bézier 插值逐步过渡：

```text
M(t) = (1-t)³M0
     + 3(1-t)²tM1
     + 3(1-t)t²M2
     + t³M3
```

大约每 **167 次分形更新**续接一段新的变化。

因此，点云可以逐渐从一种形状扭成另一种形状，形成连续的展开、卷曲和收缩。

#### 12.4.3 点云怎样退出

原版通过逐渐增大绘制步长，让点云变稀：

```text
每个点都画
→ 每隔几个点画一个
→ 每隔更多点画一个
→ 暂停绘制
```

恢复时再逐步变密。已经留下的图像继续参与反馈，因此退场过程还带着残影。

### 12.5 第二层：几个明亮的星点怎样移动

除了密集点云，还有一层较少但明亮的十字点。

每个点的位置大致为：

```text
x = 中心 x + Ax × cos(T / Tx)
y = 中心 y + Ay × sin(T / Ty)
```

这里：

- `Ax、Ay` 控制横纵运动范围。
- `Tx、Ty` 控制横纵运动周期。
- `T` 是持续增加的运动计数。
- 不同组使用不同周期和相位。

横纵周期不同，轨迹就会交错、绕行。

原版有五组这样的轨迹。根据当前速度，每帧绘制 **5、10 或 15 个亮点**；这一层在 IFS 不处于密集显示状态时启用。

单个亮点只有五个像素：

```text
· 彩 ·
彩 白 彩
· 彩 ·
```

白色中心和彩色四臂形成十字。旧位置的亮点留在反馈画面里，再被缩放和扭曲，于是少量新点也能形成长轨迹。

### 12.6 第三层：声音波形怎样变成光环和线条

左右声道各有一条 **512 点曲线**。

曲线的基础形状可以是：

- 圆形；
- 水平线；
- 垂直线。

然后，音频采样沿各点的指定方向推动它：

```text
x[i] = 基础 x[i] + cos(方向[i]) × 0.001 × PCM[i]
y[i] = 基础 y[i] + sin(方向[i]) × 0.001 × PCM[i]
```

例如：

- 水平线上的点主要上下波动。
- 垂直线上的点主要左右波动。
- 圆上的点沿相应方向扩张、收缩。

每两个相邻点连接成线段，所以它是一条连续波形。

#### 12.6.1 形状和颜色也有缓动

几何位置每次更新为：

```text
新位置 = (39 × 当前位置 + 目标位置) / 40
```

相当于每次向目标靠近约 2.5%。

颜色采用更慢的过渡：

```text
新颜色字节 = (63 × 当前颜色字节 + 目标颜色字节) / 64
```

因此横线变圆、颜色变化等过程会平滑展开。原版在具体计算中保留单精度常量、浮点舍入和颜色整数右移，精确复现时需保留这些差别。

### 12.7 核心：整张旧画面怎样被扭曲

原版为每个目标像素建立一个“取色位置”：

> 这个像素应该从旧画面的哪个坐标读取颜色？

例如目标位置 `(100,100)`，可能被安排到旧画面的 `(98.5,97.8)` 附近取色；原版实际坐标会量化到 1/16 像素。

所有像素都这样重新取色，整张图就会发生变形。

原版内部提供八种主要坐标变换，包含：

- 基本径向缩放；
- 随距离变化的波纹缩放；
- 中心与边缘强度不同的径向变形；
- 逐行横向偏移；
- 横纵相互影响的正弦扭曲。

还可以改变变形中心、方向和附加偏移。

#### 12.7.1 为什么切换不会总是突然跳变

切换时保留旧、新两套坐标映射，再逐步插值：

```text
当前映射 = 旧映射 + (新映射 - 旧映射) × 过渡比例
```

这使整张画面的运动方向可以逐渐改变。

#### 12.7.2 为什么残影会变暗

取色位置通常包含小数，需要混合附近四个像素。

原版的权重刻意略小于完整亮度：

- 常见权重总和为 252；
- 最后统一除以 256。

例如四周都是亮度 255：

```text
255 × 252 / 256 → 截断为 251
```

下一轮继续处理，又会变暗一点。

于是形成：

```text
新内容明亮
→ 被反馈搬移
→ 多次采样
→ 逐渐变暗
→ 最后消失
```

这是梦幻星空拖尾的重要来源。落在整数坐标等边界时权重不同，详见第 6.3 节。

### 12.8 每一帧的真实执行顺序

原版有两块像素缓冲，记为 A、B。

按语义整理后的流程是：

```cpp
读取声音强度();
更新速度和切换状态();

把分形点云画到(A);  // 加色时读取 B 中的历史底色
把十字亮点画到(A);

把A变形并衰减到(B);
把左右声道波形画到(B);

本次显示 = A;
交换(A, B);

return 本次显示;
```

这里有个很重要的细节：

**本次新增的波形和变形结果通过后续更新进入显示；本次加入 A 的点云和亮点则可以已经可见。**

这是一种交替缓冲的流水顺序。恢复时如果把它改成“全部画完直接返回 B”，画面会发生变化。

### 12.9 音乐为什么会触发形态变化

原版会观察前面计算的速度变化量，与一个可调整阈值比较。

满足条件后：

1. 打开一段活跃窗口；
2. 按随机规则选择变形；
3. 可能移动中心、调整方向或切换线条形状；
4. 设置冷却，避免连续过快切换。

它还会根据最近的触发次数调整灵敏度：

- 长时间没有事件，就降低阈值。
- 事件过于频繁，就提高阈值。

所以它能适应不同强度的音乐，但形态变化仍包含明显的随机成分。

### 12.10 原版画面质感还来自分辨率和计时

原版默认 **25 FPS**。全屏内部尺寸分别限制为：

```text
宽度最多 320
高度最多 240
```

生成后再拉伸到屏幕。

这会让低分辨率亮点、波形和拖尾一起放大，形成原版特有的视觉质感。

另外，很多变化都是按帧推进的：

- 波形每帧靠近目标；
- 反馈每帧损失亮度；
- 点云每帧推进变形参数；
- 冷却每帧减一。

因此，直接提高到 120 或 240 FPS，会同时加快形变和衰减。要提高显示流畅度而保留原版速度，需要分别处理“效果更新频率”和“显示刷新频率”。这属于后续改进方案，原版没有独立的高刷新显示层。

### 12.11 小结

**梦幻星空用声音控制运动，用分形生成复杂点群，用真实波形生成曲线，再利用整张历史图像的反复变形和衰减，把这些简单元素积累成流动的星空。**

对应函数地址、完整常量、缓冲顺序及原版边界问题，见第 3–9 节；当前恢复程度和需要进一步对照的宿主差异，见第 10–11 节。

| IFS 配色 `60020A66` | `src/ifs_display.c:9` | 三种颜色状态、80 次更新的明暗周期 |
| 双声道线 `6001F48A` | `src/lines.c:446` | 每声道 512 点、PCM 位移、几何缓动 |
| 返回旧像素缓冲 `6001EBA5` 起 | `src/goom_core.c:665` | 相同的交替缓冲流水 |

这里的源码前缀是 `ttpcomm/build/downloads/wgoom-1.9.3-src/goom-1.9.3/`。

但仍不宜把原版标成“未经修改的精确 Goom 1.9.3”或声称知道其原始提交：

- 发布包名和目录名为 1.9.3，但包内 `configure.in:4` 仍自报 `1.9.2`；这表明版本元数据存在遗留，不能据此反向认定 TTPlayer 是 1.9.2。
- 原版有表格下一节列出的实际差异。
- 某些差异可能来自 Windows 分支或编译器行为，尚不能把作者归属全部认定为 TTPlayer 自行修改。

### 13.2 原版和未经适配的 1.9.3 有哪些差别

| 项目 | 1.9.3 发布包 | TTPlayer 原版 |
| --- | --- | --- |
| 音量扩张项 | `P/50000` | `P*0.0002f`，对应项强约 10 倍 |
| 随机表 | 65,536 个 int | 16,384 个 short，初始化范围和游标次序不同 |
| 对象状态 | 大量状态为全局 | 两帧、线条、滤镜、IFS 等进入对象，仍有部分共享全局量 |
| 对外接口 | Goom 的 init/update 等 C 接口 | 90–93 号 x86 fastcall 导出 |
| 初始圆半径 | 浮点比例计算 | 先整数除法再转浮点 |
| 标题、FPS 文字、cinemascope | 上游有相关路径 | 原版 Dream 导出没有相应参数及绘制段 |
| 算术细节 | 源码表达式 | 特定 x87 舍入、算术右移和随机宏实际编译结果 |

现有 `adapt_dream.py` 因而承担了三种不同工作：恢复原版差异、显式保留历史编译结果，以及增加现代内存边界保护。它不是一个只改编译错误的通用适配器。

另外两点应准确归类：

- 65,535 项正弦表在上游 1.9.3 已存在，不能把“少一项”归为 TTPlayer 独有改动。
- 1.9.3 源码部分 IFS／线条释放路径遗漏缓冲，但原版 DLL 对应路径已经释放；现有适配中的这部分工作是在恢复原版，不应反过来声称原版也有同一泄漏。

后续检查 wgoom 1.99 又发现：其 IFS 递归已经使用与 TTPlayer 原版相同的算术右移，而 1.9.3 档案使用整数除法。因此不能把这一差异认定为 TTPlayer 独创；原版可能吸收过后续补丁或共同分支。整体结构的对应仍成立，精确来源版本不能仅靠这个局部特征锁定。

### 13.3 “最新版本”需要区分原项目和维护移植

截至本次查询，能确认的原项目后续正式发布线是 **Goom 2k4，源码包 `goom-2k4-0-src.tar.gz`**。文件日期为 2005-02-07，正式发布公告为 2005-02-11；2009 年另有编译警告和内存泄漏修复公告。[官方文件目录](https://sourceforge.net/projects/goom/files/goom2k4/0/)、[官方新闻](https://sourceforge.net/p/goom/news/)

SourceForge 页面顶部的自动“Latest Version”按钮指向 `wgoom-1.99-src.zip`，不宜仅据这个按钮判断整个项目的最新算法线，应结合 2k4 目录和正式公告。

当前维护移植有各自的版本号和运行环境：

| 分支 | 本次确认内容 | 对本项目的意义 |
| --- | --- | --- |
| GStreamer 的 Goom | 官方 README 明确基于 goom2k4；继续保留触手、粒子和后处理模块 | 可参考维护修复；不能把 GStreamer 包版本当成新的 Goom 引擎版本 |
| Kodi `visualization.goom` | 保留 Goom 核心，并带 Kodi 宿主和图形显示封装 | 可参考 Windows 适配，不能直接作为 TTPlayer 插件使用 |
| foobar2000 `What a GOOM!` | 本次页面列出 0.1.1，2026-10-12 发布；整理过的 2k4 核心，OpenGL 4.6 显示，Win10 起 | 属于现代移植，不能据其版本号断言是 Goom 官方 0.1.1；成品不适合作为 XP／Win7 运行依赖 |

来源：[GStreamer README](https://raw.githubusercontent.com/GStreamer/gstreamer/main/subprojects/gst-plugins-good/gst/goom/README)、[Kodi 源码](https://github.com/xbmc/visualization.goom)、[foobar2000 组件页](https://www.foobar2000.org/components/view/foo_vis_goom)。

### 13.4 改为 2k4 后画面会怎样变化

官方源码的 `goom_core.c` 初始化并调用 `tentacles_fx`、`star_fx`、`convolve_fx`，同时保留 IFS、线条和反馈变形。维护分支也保留这些核心模块。[GStreamer 固定提交中的主循环](https://github.com/GStreamer/gstreamer/blob/9a401c14ebf69c532d6c5fb5e8c505aa1c78997e/subprojects/gst-plugins-good/gst/goom/goom_core.c)

本节的“增加”以 TTPlayer 原版为比较基准；触手效果在 wgoom 1.99 已经出现，并非到 2k4 才首次引入，详见第 14 节。

| 部分 | 原版梦幻星空 | 2k4 的变化与预期观感 |
| --- | --- | --- |
| 主要图形 | 分形点、五组轨迹点、双声道线 | 保留基础图层，并增加触手状立体曲面等形体 |
| 飞行点 | 少量参数轨迹点及历史反馈 | 增加具有位置、速度等状态的粒子模块，支持雨、烟花和喷泉一类表现 |
| 最终颜色 | 饱和叠加、反馈衰减 | 增加单独的亮度／颜色后处理输出，明暗起伏和强事件表现改变 |
| 声音响应 | 左声道全 512 点正峰、整数速度 0–40 | 左声道隔点正峰、按历史最大值归一化、浮点速度和平滑、独立强事件检测 |
| 自动切换 | 原版阈值、随机表和帧计数 | 阈值调整、组合状态和随机序列改变；同一首歌不会保持原版切换时间线 |
| 像素反馈 | 返回旧源缓冲，保持原版流水 | 仍使用反馈，但最终经过独立输出缓冲与后处理，不能直接视为原像素的高清版本 |

2k4 声音分析见 `src/sound_tester.c`。当前维护实现也明确包含历史峰值归一化、浮点速度和 BigGoom 条件；这仍不等同于按 BPM 网格准确对拍。[声音分析源码](https://github.com/GStreamer/gstreamer/blob/9a401c14ebf69c532d6c5fb5e8c505aa1c78997e/subprojects/gst-plugins-good/gst/goom/sound_tester.c)

**可预期的是图形种类和组合增加，整体动态风格发生变化。** “更漂亮”“更平滑”“更省 CPU”需要实际同曲目、同尺寸测试，不能从版本号保证。特别是增加形体、粒子和最终后处理，会增加新的计算与缓冲开销。

2k4 头文件把 `NB_FX` 从 8 改为 10，但这是内部反馈模式编号范围，不能据此称为“10 种独立视觉场景”。原始源码中部分模式的活跃分支还合并或注释了旧公式，应以实际执行代码为准。

### 13.5 升级不会自动解决高分辨率和高帧率

原版宿主仍会把全屏内部画布限制到 320×240；仅更换 DLL 内算法，不能消除这个宿主限制。

原始 2k4 API 的 `fps` 参数用于文字显示，没有作为所有动画的时间步长。速度、粒子、过渡和冷却仍有逐帧推进逻辑。因此直接用 120／240 次更新代替 25 次更新，会改变动画节奏。高刷新显示需要独立设计逻辑更新与显示策略。

2k4 核心仍在 CPU 上生成像素。触手使用三维几何计算，并不表示整套核心自动变成 GPU 渲染。现代移植使用 OpenGL 显示，也不能据此推断所有分形、反馈和粒子计算已迁入 GPU。

### 13.6 兼容和集成成本

不能只更改 `FetchContent` 的 URL 和哈希完成升级：

1. 当前适配脚本依赖 1.9.3 的具体函数签名和源码片段，匹配次数不符会主动失败。
2. 2k4 引入 `PluginInfo` 和视觉模块回调；缓冲、尺寸、声音状态、参数和销毁路径必须重新封装。
3. TTPlayer 原有 90–93 号导出的 x86 调用约定和参数必须保留，或为新效果新增独立接口。新库不具备原导出 ABI。
4. 提取维护分支时需要处理宿主相关依赖。例如当前 GStreamer 源码包含日志和 CPU 检测封装，不应顺带把整套 GStreamer 运行库变成播放器依赖。
5. 旧系统可研究保留纯软件绘制路径；源码层面未要求必须使用现代 OpenGL。XP／Win7 能否正常构建和运行，需要实际导入表、指令集及运行测试，现有旧核心的通过结果不能覆盖新核心。

### 13.7 推荐方案

建议保留当前 **“梦幻星空”** 的原版行为，另加 **“梦幻星空 2k4”** 供选择：

- 旧效果继续使用目前已做像素对照的适配核心。
- 新效果采用 2k4 核心，并参考持续维护分支的修复，以固定源码版本构建。
- 两者分开保存参数和随机状态；新效果不改写原版模式的内部对象。
- 新效果可分别设置内部渲染分辨率和显示帧率，保留旧系统的软件显示方案。
- 对照时既比较原始像素，也比较音乐响应、暂停／停止、换曲、改尺寸和最终全屏显示。

这样能增加更多视觉表现，同时保留用户已经熟悉的原版效果。本节仅提出方案，未执行升级。

如果目标更偏向保留早期 Goom 的反馈结构、只增加部分历史效果，wgoom 1.99 也是候选；三个方向的选择见第 14.7 节。

## 14. wgoom 1.99 是否更适合作为升级目标

补充日期：2026-10-26。本节实际检查官方 `wgoom-1.99-src.zip` 中的源码，并与原版二进制证据、1.9.3 和官方 2k4 源码比较；未构建或运行 1.99，未替换现有实现。

### 14.1 版本身份：历史 Windows 发布包，包含后续核心算法

**wgoom 1.99 可以作为增强效果的候选。它保留早期 Goom 的主要构件，也已经改变原版梦幻星空的运动和画面，不能当成原样兼容升级。**

官方目录日期为 **2003-03-05**。维护者 Fred Howell 在当时的讨论中分别介绍了核心新增触手，以及 Windows 外壳增加 WMP9 支持、DirectDraw 显示和 OpenGL 立方体模式。[官方目录](https://sourceforge.net/projects/goom/files/win_goom/)、[维护者说明](https://sourceforge.net/p/goom/discussion/95445/thread/f1fe8712/)

同一包内的版本标记并不完全统一：

| 文件 | 标记 |
| --- | --- |
| `configure.in:4` | `1.99.0` |
| `src/readme.c:18` | `1.99` |
| `src/win32/config.h:1`、`Svis.c:40` | `1.99.4` |

因此本报告称其为“官方 wgoom 1.99 源码包，Windows 插件标识 1.99.4”，不把这些标记误当成三个独立下载版本。

SourceForge 的默认下载按钮目前指向这个包，但 2k4 正式源码的文件日期是 2005-02-07。不能由默认按钮得出“1.99 是比 2k4 更新的核心”的结论。[2k4 官方目录](https://sourceforge.net/projects/goom/files/goom2k4/0/)

以下相对路径均以包内 `goom2/` 为起点。

### 14.2 与原版相同的骨架，以及不能认定为原版核心的原因

1.99 仍使用：

- 左右声道各 512 个 signed short 样本。
- 两块对齐的像素缓冲和历史图像反馈。
- IFS 分形点云及 Bézier 形变。
- 五组 sin／cos 轨迹亮点。
- 双声道圆形、横向、纵向波形线。
- 返回旧源缓冲、再由后续更新呈现新反馈结果的流水结构。

这些构件支持“延续早期 Goom 视觉风格”的判断。不过原版仍是八种反馈模式、`P/5000` 驱动的 0–40 整数速度、旧 IFS 进入退出条件和 70 帧线状态；1.99 已经改变这些路径，并加入原版没有的触手和八组图层组合。

所以，**不能因为 wgoom 是 Windows 版本，就认定 TTPlayer 内嵌的是 wgoom 1.99**。原版整体更贴近第 13 节的 1.9.3 档案，但存在与后续源码一致的局部修改，不能声称知道其精确原始提交。

### 14.3 换成 1.99 后，画面会有哪些实际变化

| 项目 | 1.99 中的实现证据 | 根据代码推断的画面变化 |
| --- | --- | --- |
| 三维触手 | `goom_core.c:734`、`tentacle3d.c:10–35/196–210`、`surf3d.c:54–75` | 六组网格随 PCM 起伏、旋转和透视投影，形成有纵深的彩色线网 |
| 图层组合 | `goom_core.c:30–55/464–487` | 八组配置选择分形、亮点、波形、触手的组合；不再只有原版组合规则 |
| 声音驱动 | `goom_core.c:219–257` | 根据相邻更新的强度变化推进速度，并周期性衰减；同一首歌的运动与切换时间线改变 |
| 强事件 | `goom_core.c:349–360` | 对源画面做按位反相并加色，产生原版没有的整幅颜色突变 |
| 波形振幅 | `lines.c:154/227–238` | 振幅目标按 99:1 平滑，再调制 PCM 位移，张合表现不同 |
| 波形亮度 | `lines.c:13–26/144–151` | 亮度公式和 power 范围改变，线条明暗、配色不保持原版结果 |
| 反馈过渡 | `goom_core.c:198–201`、`filters.c:707–717/768–784` | 更改插值参数，并每次生成 16 行目标坐标映射，变形切换时序不同 |

三维触手是 **CPU 上计算网格、投影和画线**，并不要求把整个效果改成 GPU 渲染。它属于核心，移植核心时可以保留。

1.99 仍不是 FFT 频谱或 BPM 对拍器。它取得左声道 512 点的正峰，计算 `P/1000` 派生量的跨帧差，再更新 0–50 的整数速度；每 9 帧减速，每 5 帧再乘 `7/8`。与原版相比，声音变化、静段衰减和随机切换都不同。

另一方面，1.99 的直接音量扩张项仍为 `P/50000`，没有 TTPlayer 原版的 `P*0.0002f`。因此“更新后所有运动都会更强烈”也不成立：新增形体更多，但某些原有轨迹的扩张可能更弱，实际取决于输入与状态。

### 14.4 十种反馈模式：1.99 与 2k4 不能只比较编号

1.99 的 `NB_FX` 为 10，在旧八种编号后增加两项，且这里都有实际执行公式：

| 新模式 | 实际代码 | 含义 |
| --- | --- | --- |
| `YONLY_MODE`，编号 8 | `filters.c:285–288` | 缩放强度随纵向坐标的正弦项变化 |
| `SPEEDWAY_MODE`，编号 9 | `filters.c:289–291` | 缩放强度随纵向位置变化，形成纵深拉伸的候选表现 |

这表示十个**反馈变形编号**，并非十套完整视觉场景；前述八组图层组合是另一套机制。

已有公式也有修改，例如 SCRUNCH 的半径项强度、WATER 的速度边界，以及正弦表容量与量化。恢复旧模式名称并不能保证像素一致。

官方 2k4 虽然保留相同十个名字，但活跃的 `zoomVector` 已注释 YONLY 和两个 HYPERCOS 的具名分支，WATER 位置也留下 TODO；其中仍有其他 Hypercos 叠加开关。结论是：**2k4 并非完整保留 1.99 的每个公式，再额外加特效**。不能只根据版本号认定它覆盖全部旧观感。

### 14.5 Windows 立方体显示与核心算法是两层

官方包的结构是：

```text
音频样本
  → goomdll.dll 中的效果核心
  → ARGB 像素缓冲
  → Windows 显示外壳
      ├─ 普通／DirectDraw 显示
      └─ OpenGL 纹理贴到旋转立方体
```

`src/win32/opengl.c:244–252` 先旋转，再把核心像素缓冲上传为纹理，随后绘制立方体面。维护者也明确区分了输出 ARGB 的核心与媒体播放器、屏保等 Windows 封装。[维护者说明](https://sourceforge.net/p/goom/discussion/95445/thread/f1fe8712/)

因此只移植 1.99 核心到 `ttpcomm`，会取得触手、波形、分形和反馈效果；**不会自动出现 OpenGL 旋转立方体**。若需要立方体，需要另做显示层。普通软件显示可以继续独立使用，不必为了核心算法引入这层 OpenGL 外壳。

### 14.6 接入难度、旧系统和性能

1.99 原 DLL 不能直接替换 `ttpcomm.dll`：

- `src/win32/goomdll.def` 的导出是 1–5 号 `goom_init`、`goom_set_resolution`、`goom_update`、`readme`、`goom_close`。
- TTPlayer 使用 `ttpcomm` 的 90–93 号导出，有对象参数、左右分开的样本指针及既定 x86 调用约定；DLL 还承担许多无关功能。
- 1.99 核心大量使用全局状态，不能直接当作每个窗口独立的实例；需要处理原版和新模式的状态隔离、重复创建和销毁。
- 当前 `adapt_dream.py` 针对固定 1.9.3 源码布局，不支持只改下载 URL 就完成移植。

还发现一处需要在移植时修复的明确释放遗漏：`tentacle3d.c:17–22` 的 `tentacle_free()` 只释放 `vals`；而 `surf3d.c:6–13` 为每个网格分别分配网格对象和两组顶点数组，六个网格没有对应释放。`goom_close()` 确实调用这个不完整的释放函数。因此反复进入、退出新效果时应补全这些释放，并验证重建与销毁；不能直接把历史源包当作无需修复的成品。

该包 Windows Makefile 使用 MinGW GCC、GNU 汇编相关代码与 DLL 工具，播放器插件外壳再用 VC++。维护者当时也明确要求分两阶段构建。现代接入需要提取核心、适配编译和内存生命周期，并保持现有宿主接口。[当年的构建说明](https://sourceforge.net/p/goom/discussion/95445/thread/f1fe8712/)

源码层面的软件绘制方案适合继续研究 XP／Win7 支持，但“2003 年的 Windows 包”不等于“当前重编后已在 XP／Win7 验证通过”。仍需检查导入表、CPU 指令选择、调整尺寸和运行稳定性。

性能方面可确认新增 MMX／Extended MMX 选择和分批坐标映射，但也增加触手网格等计算。本轮没有测量 CPU 占用或帧时间，不能保证比原版或 2k4 更快。1.99 的动画也按更新次数推进，不能通过提高调用频率直接获得同速度的 120／240 FPS。

### 14.7 三种方案如何选择

| 目标 | 更适合的方案 | 主要取舍 |
| --- | --- | --- |
| 原样恢复 5.7.9 梦幻星空 | 当前按原版适配的核心 | 已有原版对照基础，保留历史响应和反馈细节 |
| 保留早期构件，加入触手与历史滤镜 | 新增独立 1.99 效果 | 相对延续早期结构；仍改变声音响应，且要处理全局状态和旧代码 |
| 增加烟花／雨／喷泉粒子、独立亮度输出等 | 新增 2k4 效果，并参考维护分支修复 | 效果体系更丰富、已有上下文接口，但旧滤镜行为及整体风格改变更多 |

**针对重建版，建议继续保留当前“梦幻星空”，按需要新增一个版本，而非无条件覆盖原效果。** 如果偏好 1.99 的触手、早期反馈和变形，它有明确的独立价值；如果重点是更多图形和后处理，2k4 更符合目标。无需仅为版本齐全同时接入两套。

“1.99 更接近旧风格”是依据构件、反馈结构和输出流程的判断，尚不是同曲目运行比较。真正决定采用哪个版本，宜在同 PCM、同内部尺寸、同逻辑更新频率下检查动态画面，并分别记录 CPU／帧时间。随机序列和音乐响应已经不同，不应以新旧逐像素相等作为新增模式的验收条件。
