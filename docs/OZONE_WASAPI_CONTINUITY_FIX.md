# Ozone 与 WASAPI 播放断续分析及修复

日期：2026-09-28

## 1. 问题与结论

用户确认：勾选 `dsp_izOzone.dll` 后就出现断续，使用 WASAPI，不需要打开或拖动插件界面。

本轮确认并修复了 **WASAPI 的缓冲提交依赖解码／DSP 线程** 的缺陷：虽然播放器已经缓存后续音频，但该线程一旦忙于处理新音频，就不能及时把已有音频送入设备。原先的原生设备缓冲只有 40–80 ms；软件中的较长预读缓冲无法独立发挥作用。

证据边界：本机及 Win7 的真实 Ozone、默认测试配置连续播放没有稳定复现用户的断续；通过受控 DSP 延迟能够稳定复现上述缺陷，修复后该回归通过。因此这是已经证实的输出链路修复，不能据此声称已穷尽用户设备、曲目和 Ozone 预设的所有原因。

## 2. 原版伪代码对照

来源：`reverse/decompiled/TTPlayer.exe.pseudo.c`。

| 原版函数 | 与本次问题相关的行为 | 重建版处理 |
| --- | --- | --- |
| `FUN_004ac166`（163294 行） | 转换到 Winamp DSP 使用的 16 位 PCM，运行插件链，然后转换回输出格式 | 保留现有转换路径 |
| `FUN_0042898d`（41458 行） | 锁定插件列表，按顺序调用各插件包装对象 | 保留插件顺序和串行处理 |
| `FUN_004280cd`（40825 行） | 对包装对象加锁；计算帧数；超过 `0x3fff` 帧时只分成两半；调用 `ModifySamples`，忽略其返回长度 | 保留一次对半分块、固定输出长度及两倍临时空间的 ABI 保护 |
| `FUN_004280be` | 调用当前模块的配置函数 | 本次不修改同实例配置行为 |
| `FUN_00428061` | 撤下活动模块，再执行退出及释放 DLL | 本次不修改已有延迟卸载保护 |
| `FUN_004e27ad`（214482 行） | 准备 `WAVEHDR`，调用 `waveOutWrite`，让设备异步消费已经提交的音频 | WASAPI 现在也能在解码／DSP 忙碌时独立消费已处理音频 |

原版没有本项目新增的 WASAPI 输出，不能把新增后端说成原版 WASAPI 的逐行恢复。应恢复的是“后续音效处理不阻塞已有输出缓冲播放”的工作方式。

另一个差异仍明确保留：当前重建版把插件回调安排在持久的 DSP 窗口线程上；原版在音频链中直接调用处理函数。单独测试真实 Ozone 时，两条调用方式均未产生持续静音。没有仅凭线程差异就重写所有插件的窗口、配置和卸载模型。

## 3. Ozone 二进制与实际处理检查

检查对象为用户提供的 Ozone 1.03：

`SHA256 e3bb0eef979ea8016fb1278b373c7c70ae4507719524bfefe802b5bc3c800e59`

- `ModifySamples` 入口位于 `5941A6C0`，转入 `5941A6F0`；16 位双声道分支经过输入转换、`59413520` 处理及输出转换。
- 格式改变时会更新采样率、声道和采样宽度对应的内部状态。
- 可见的处理入口没有把每块 PCM 写入 `registry.json`；本轮没有修改插件算法、登记校验或共享注册表读写规则。
- 使用隔离的配置及已存在的登记数据副本测试，不改动用户原插件目录中的配置。

44.1 kHz、双声道、16 位、每块 11025 帧、合计 12 秒正弦 PCM 的测量：

| --- | ---: | ---: |
| 直接调用真实 Ozone | 1.717 ms | 4.580 ms |
| 重建版 DSP 线程，非实时快速处理 | 8.851 ms | 4.580 ms |

## 4. 可复现的缓冲缺陷

旧流程：

1. `AudioEngine` 预先处理四块 PCM。
2. `WasapiSink::Submit` 只把 PCM 放入软件队列。
3. 同一个解码线程调用 `Pump`，填充短设备缓冲。
4. 该线程继续解码、DSP、重采样，处理完成后才有机会再次 `Pump`。

受控测试让每块 250 ms 音频的 DSP 处理耗时 120 ms。平均处理速度仍快于实时，且软件队列中还有音频，但 120 ms 已超过原生缓冲能够撑住的时间。

| 12 秒音频，共享模式 | 播放实际耗时 |
| --- | ---: |
| 修复前，无 DSP 延迟 | 11.984 s |
| 修复前，每块处理延迟 120 ms | **14.125 s** |
| 修复后，无 DSP 延迟 | 12.000 s |
| 修复后，每块处理延迟 120 ms | **11.984 s** |

约 16 ms 内的差异来自计时及设备更新粒度。修复前额外的约 2.1 秒是该测试中累计的缓冲断流时间；不是有意改变播放速度。

## 5. 实现

- `WasapiSink` 新增专用渲染线程，每约 5 ms 检查并补充设备缓冲；新命令会立即唤醒线程。
- 音频生产线程通过同步命令提交 PCM、更新增益、暂停、重置和查询位置。没有音频处理任务时，渲染线程仍持续消耗已缓存音频。
- 所有 WASAPI COM 对象在同一个渲染线程上创建、使用、停止和释放。`Close` 等待线程退出，再允许重新打开独占设备。
- 保留四块软件队列上限、40–80 ms 原生缓冲、实际已播放帧计时及曲目末尾排空规则。
- 音量、平衡和淡入淡出增益在写入短设备缓冲时应用。恢复播放前先更新增益，避免新线程的首包使用旧增益。
- 暂停及重置命令返回时已经执行完毕；重置清空旧 PCM 和播放计数，不会把定位前的音频再次提交。
- 对外错误字符串使用同步快照，避免渲染线程异步记录错误时与调用方读取同一个字符串。
- XP 仍不支持 WASAPI，但可以正常启动，并继续使用 WaveOut；未增加较新音频 DLL 的静态导入。

微软说明应按设备剩余空间持续提交音频，并要求在取得渲染服务的线程上释放该服务。本次线程边界遵循这些要求：[音频流渲染](https://learn.microsoft.com/en-us/windows/win32/coreaudio/rendering-a-stream)、[IAudioRenderClient](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nn-audioclient-iaudiorenderclient)。
