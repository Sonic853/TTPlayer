# 主窗口“歌词秀 → 编辑歌词”核对（2026-09-23）

## 结论

命令能够到达编辑器，但此前并非所有状态都能正常操作：歌词窗口隐藏时，
RichEdit 和工具栏创建在隐藏的父窗口内，用户看不到；代码还激活了主窗口，
没有按原版激活歌词窗口。另缺少进入编辑前退出全屏的步骤。本次已修复。

## 原版与重建版对照

| 环节 | 原版依据 | 核对／处理 |
| --- | --- | --- |
| 主菜单入口 | `0045DFBA` 使用菜单 `0x8F`，编辑模式切换到 `0x94` | 共用原资源；上一步共享菜单修复已恢复显示／编辑菜单切换。 |
| 编辑命令 | `00446ED7` 分发 `0x802C` 到 `0044CB58` | 主窗口 `WM_COMMAND → HandleLyricCommand → EnterLyricEditor` 路由正常。 |
| 可用状态 | `00449E98` 按当前歌曲对象 `+0x328` 更新 `0x802C`，不按歌词行数 | 无歌曲时禁用；已有歌曲但尚无歌词时允许编辑空文档。 |
| 退出全屏 | `0044CB58` 首先调用 `0044AB8F`，有全屏状态则发送 `0x7DE7` | 补上进入编辑前的 `LeaveFullScreen`，使文本控件先返回普通歌词宿主。 |
| 内容加载 | `0044CB58 → 004431A0` 读取原始文件，或 `0043F319` 序列化当前修改 | 保留已有实现：普通本地 LRC 不凭空改写三位毫秒和元数据；有 offset／未保存修改时使用当前文档。 |
| 创建控件 | RichEdit `0x563081C4`，工具栏 `0x46018944`，资源 `0x94` | 沿用已有实现；显示编辑器和工具栏，隐藏普通歌词文本控件。 |
| 隐藏的歌词窗 | `0044CB58` 尾部调用 `00446EB4`；两个歌词表面都不可见时向主窗发送 `0x7D64` | 补调用现有歌词窗口显示路径，同时更新活动模式显示状态。完成异步淡入淡出后再设置编辑焦点。 |
| 激活与焦点 | `SetActiveWindow(歌词窗 HWND)`，`SetFocus(RichEdit HWND)` | 将原先错误的主窗激活改成歌词窗激活。 |
| 编辑菜单 | `0x94` 的保存、返回、选区编辑命令 | 主窗共用编辑器处理与状态；本次验证保存本地测试歌词、返回显示、复制／剪切可用状态。 |
| 桌面模式 | `0045DFBA` 把“歌词秀”子菜单收敛为“返回窗口模式” | 此时没有“编辑歌词”；先返回窗口模式再编辑，与原版分支一致。 |

## 回归方法

私有测试 `rebuild/tests/ui/lyric_main_menu_tests.cpp` 使用隔离目录、真实播放器窗口、
原版菜单资源和主窗口 `WM_COMMAND`，并实际读写隔离目录中的 LRC。
修复前已复现 `hidden lyric editor was not shown` 失败，证明此前只对可见歌词窗测试不足以覆盖该入口。

覆盖无歌曲禁用、有歌曲无歌词编辑、隐藏窗口显示及焦点（含窗口淡入淡出开启）、本地歌词原文加载、
主菜单切换与保存／返回、桌面模式返回后编辑、全屏退出后编辑。
测试不发布，也不加入 Actions。

实测结果：宿主机普通 Release、XP SP3 和 Win7 SP1 的旧系统构建均通过该入口回归。
宿主机原有歌词菜单、共享菜单及重新排列回归也通过。
全屏用例通过测试夹具设置播放状态以打开真实全屏窗口，检查退出、控件归属和编辑焦点，未使用音频输出作为该用例前置条件。

这份核对聚焦主菜单进入编辑的流程，不据此宣称整个歌词编辑器、所有第三方皮肤和历史在线功能已与原版完全一致。

## 2026-11-05：编辑工具栏打开／保存纠正

本次针对“第二个打开按钮出现保存窗口，第三个保存按钮无反应”的反馈，重新对照根目录
5.7.9 `TTPlayer.exe`（SHA-256 与 `reverse/README.md` 一致）、已有伪代码及资源 148。
以下结论来自原版静态证据与当前源码；不把重建版窗口测试称为原版运行实测。

### 根因及修复

| 命令 | 原版证据 | 此次处理 |
| --- | --- | --- |
| `0x8020` 返回歌词秀 | `0044D646` 结束编辑，按保存策略处理修改，再刷新显示 | 保留现有返回与保存策略，验证保存后返回显示使用新文件 |
| `0x8021` 打开 | `0044D6F1` 调用 `0042918D(1, ...)`，`0042A4A3` 的非零模式调用 `GetOpenFileNameW`；随后 `004431A0` 读取原文到 RichEdit | 将误命名的 `kCmdLyricSaveAs` 改为 `kCmdLyricOpen`，接入打开文件选择器；成功后更新编辑文档，取消／读取失败保留文本、路径、光标及撤销记录；支持有效空文件 |
| `0x8022` 保存 | `0044D824` 只有 `lParam == 歌词窗口 HWND` 的内部保存才跳过选择器；手动按钮、菜单及快捷键走 `0042918D(0, ...)`，即保存窗口 | 手动保存始终选择目标，已有路径也弹窗；内嵌歌词手动保存导出到文件。自动保存仍独立执行原有策略，不增加选择器 |
| 打开／保存失败 | 资源 `0x8181` 是“打开歌词文件 %s 失败”，`0x8182` 才是“保存歌词文件 %s 失败” | 修正误把 `0x8181` 用于保存失败的代码和注释；写盘关闭流后检查结果，成功后才清除修改标志 |
| 异步完成 | 文件选择器运行自己的消息循环 | 选择器期间使用已有歌词保存忙碌标志，避免歌词搜索／播放完成刷新替换正在操作的文档；窗口归属取编辑器实际顶层窗口 |

原先第三个按钮并非完全没有实现：已有普通歌词路径时，它直接写盘且不弹窗。
此前测试只验证这一写盘结果，反而没有检查原版要求的手动保存选择器；本次补上该缺口。
“打开”是替换编辑内容，不是自动另存当前草稿；不额外添加原版没有的打开前保存对话框。
