# 恢复 DSP DLL 的删除、重命名、移动、复制与覆盖审计

日期：2026-09-28。范围：`Plugins-out` 内 12 个恢复 DLL。

## 1. 结论

**在本次追踪到的调用路径中，未发现遍历磁盘或音乐目录后批量删除、乱重命名、搬移、复制、覆盖用户文件的逻辑；但不能把这些 DLL 判定为完全没有数据破坏风险。** 已确认的风险主要是配置文件被整体清空、同名文件直接覆盖，以及先删除旧文件再保存导致的数据丢失。

优先关注：

1. **`dsp_compwide.dll` 会整体重写 DLL 同目录的 `plugin.ini`，可能清掉其他插件的配置。** `dsp_DeFX.dll` 使用同一路径存储配置；当前原始 `Plugins/plugin.ini` 确实包含 `[DeFX v0.97]`。这是有具体交叉影响对象的缺陷。
2. **Enhancer、Jammix 都有先删除旧预设文件再写入的流程。** 后续创建、写入失败或进程中断时，可能丢失原有预设。
3. **Enhancer 复制皮肤位图时允许覆盖同名文件；ViPER、DEE 的保存对话框缺少覆盖询问标志。** 这些操作由用户选择文件／保存触发，不是后台批量改写音乐文件。
4. **OctiMax 确实包含删除、改名和写入。** 已追踪到的主要目标是 CrypKey 许可状态及请求／应答文件。不能把它简单归为“只有预设保存”，也不能从 `KillLicense` 名称推断其会删除用户文件。外部许可 DLL 的内部行为不在这 12 个文件的审计覆盖内。
5. 当前 `registry.json` 接管处理的是注册表接口，**不能阻止上述普通文件写入、复制和覆盖**。

本轮只做静态审计、证据保存和文档整理，没有运行这些文件操作分支，没有修改恢复 DLL 或播放器产品代码。

## 2. 方法与证据强度

采用 PE 导入表、ASCII／UTF-16 字符串、Ghidra 伪代码、直接调用及参数追踪，并对伪代码漏识别的业务函数补做 x86 反汇编。检查的不仅是 `DeleteFile`：

- 改名／移动：`MoveFile`、`MoveFileEx`、`rename` 等。
- 复制／替换：`CopyFile`、`CopyFileEx`、`ReplaceFile`、Shell 文件操作。
- 覆盖／截断：`CreateFile` 的创建方式、`fopen` 的 `w` 模式、`SetEndOfFile`、`_lcreat`、`WriteFile`。
- 配置修改：`WritePrivateProfileString/Section/Struct`，包括传空值删除 INI 项。
- 注册表修改：`RegDeleteKey/Value`、`RegSetValue` 的目标和上层调用。
- 间接操作：`ShellExecute`、动态解析函数、外部库加载和可疑命令字符串。

导入某接口只证明存在调用能力；框架通用函数不等于插件业务一定使用它。`DeleteObject`、`DeleteMenu`、`RemoveProp` 是 GUI 资源操作，不计作删除文件。

12 个文件共导出 7,810 个已识别函数条目；6 个条目反编译失败，包括 5 个相同规模的运行库函数和 Vinyl 的一个大型函数。该数量不代表识别了全部代码：例如 Jammix 的保存函数、ViPER 的 Init/Quit 和 SO3D 的 Init 还需要从机器码补查。本报告的具体结论以实际参数和调用链为依据，不用“反编译成功率”替代安全覆盖率。

所有地址均为**恢复 DLL 的 RVA**，即相对于模块加载基址的偏移；Jammix、NEQ 的分析基址为 `0x00400000`，其余为 `0x10000000`。它们不是压缩文件的磁盘偏移。

## 4. 需要优先处理的具体行为

### 4.1 compwide：可能清除其他插件的配置

调用链：

```text
配置窗口 WM_CLOSE（RVA 0x2615）
  → 保存配置（0x19EB）
  → 生成 DLL 同目录 plugin.ini 路径（0x196C）
  → fopen(path, "w+")
  → fprintf 写入 [comp_wide dsp] 和自身参数
```

`"w+"` 字符串位于 RVA `0x5333`。该模式在成功打开已有文件时就截断原内容。代码没有读取并合并其他 INI 节，也没有先写临时文件。

DeFX 的 RVA `0x28F0` 同样由自身 DLL 路径生成同目录 `plugin.ini`，RVA `0x2A20` 写 `[DeFX v0.97]`。因此两者放在同一插件目录时：

```ini
; 原有
[DeFX v0.97]
GUI_Enabled=1
...

; compwide 保存后，该文件被整体改成自身配置
[comp_wide dsp]
enable=...
stereo_width=...
...
```

这里是对代码效果的静态推导；本次没有在真实 `Plugins/plugin.ini` 上执行复现。风险不以故意破坏为前提，也不需要用户主动选择覆盖 DeFX 的配置。

### 4.2 Enhancer：预设文件先删后写，皮肤同名直接覆盖

**预设文件**：RVA `0x37C0` 从模块路径构造 `Enhancer\enhancer.set`。新增／保存路径 `0x3AD0` 和确认删除预设后的路径 `0x3D70` 都调用 `0x4420`：

```cpp
DeleteFileA(presetPath); // 调用点 RVA 0x4452
CreateFileA(presetPath, GENERIC_READ | GENERIC_WRITE,
            FILE_SHARE_READ, nullptr, CREATE_ALWAYS, ...);
WriteFile(...);
```

删除的是完整的预设容器文件，随后根据当前内存内容重建，不是每个预设都单独对应一个文件。旧文件删除成功而后续保存失败时，可能影响全部自定义预设。读文件失败后的默认预设生成器 `0x3E90` 也使用 `CREATE_ALWAYS`；因此不能把所有读失败都理解为“只会创建不存在的新文件”。

**皮肤位图**：RVA `0x5F80` 显示 BMP 打开对话框，`0x5E90` 先尝试加载位图，再把所选源路径复制到插件皮肤目录和所选文件名拼接出的目标。调用点 RVA `0x5F63`：

```cpp
CopyFileA(selectedBitmap, skinDirectoryPlusFileTitle, FALSE);
```

最后的 `FALSE` 表示允许已有目标被覆盖。没有看到该复制点前单独的同名覆盖确认或备份。源图片没有被这条路径删除或移动。路径来自插件目录状态及文件对话框；本次未把它当作经过安全边界验证的沙箱路径。

### 4.3 Jammix：删除预设有确认，保存预设另有先删后写

两条不同路径都调用删除包装函数 RVA `0x8A40`，后者调用 `DeleteFileA`：

- **删除按钮**：RVA `0x7BCF4` 检查列表有选中项，显示“确认／真的要删除吗?”；仅 `IDYES` 调用删除。直接调用点 `0x7BD4D`。
- **保存预设**：机器码入口 RVA `0x79814`，文件对话框成功后，先在 `0x798A6` 调用删除，再连续调用预设写入器 `0x713D0`，使用 `WritePrivateProfileStringA` 写 `Jammix XBS preset` 节。

所以“删除按钮会询问”不能推广为“所有删除都经过该确认框”。保存针对用户选择的目标文件，有旧文件丢失和部分写入风险。本轮未把 Delphi 保存对话框自身的覆盖提示是否开启作确定结论；风险即使有该提示也存在。

这条保存函数不在 Ghidra 初次识别的函数集合中，已通过删除包装函数的机器码交叉引用补查。

### 4.4 ViPER：导出配置直接覆盖，正常退出也会保存

- Init RVA `0x8CE0` 获取模块路径，拼接 `Viper.cfg`；Quit RVA `0x8FF0` 调用保存器 `0x8580`。
- 保存器通过 CRT `fopen` 包装使用 `"w+b"`（字符串 RVA `0x181D8`），写入配置结构。这会截断已有文件，且不是临时文件提交方式。
- 导出入口 `0x89B0` 调用 `GetSaveFileNameA`，`Flags = 4`，没有 `OFN_OVERWRITEPROMPT (0x2)`；选定路径后会补 `.cfg` 后缀，再弹出配置说明窗口。
- 说明窗口 `0x9360` 的保存按钮同样以 `w+b` 写目标，并显示保存成功消息。

未见该路径在写之前检查目标是否存在并另行询问。填写说明的对话框不等于对已有文件的覆盖确认；后补扩展名还要求对**最终路径**检查冲突。保存代码未显示对 `fopen/fwrite` 结果的完整核验，提示成功也不能保证写入完成。

### 4.5 DEE、SPS、SuperEQ：同为保存，提示处理不同

| 插件 | 入口 RVA | 保存行为 | 覆盖提示证据 |
| --- | --- | --- | --- |
| DEE | `0x1190`、`0x21E0` | 对选中 `.dee` 逐项写 INI 节；普通设置写 DLL 同目录 `Plugins.ini` | `OPENFILENAME.Flags = 0x81004`，不含 `0x2` |
| SPS | `0x4590` → `0x56F0` | 对选中 `.sps` 写标签、代码字符串及结构 | `Flags = 0x80006`，包含 `0x2` |
| SuperEQ | `0x2E70` → `0x1B754` | CFile 模式 `0x1001`，最终为 `GENERIC_WRITE + CREATE_ALWAYS` | 对话框构造时传入 `6`，包含 `0x2`；以反汇编参数核对 |

DEE 的 INI 写入不是 `fopen("w")` 那样每次直接把整个文件清零，但仍会改变用户选中的已有文件。文件筛选器只是选择提示，不能当作文件类型或写入范围的安全校验。

## 5. OctiMax 的移动／删除究竟操作什么

### 5.1 基准路径来自模块，扩展名由许可代码派生

RVA `0x8B20` 用 `GetModuleFileNameA` 取得模块路径并进入许可初始化。RVA `0x1021A` 是更换末尾扩展名的帮助函数：

```text
复制基准路径 → 找最后的点和反斜线 → 更换扩展名，或补点和扩展名
```

它不等于扫描文件系统后批量改名。实际 `MoveFileA` 包装函数是 `0x28DE5`。

### 5.2 许可状态文件替换

RVA `0x11D26` 可对传入的许可文件路径派生 `.41d` 临时名称；对原文件进行标记写入、关闭、删除，再将临时文件改回原名称。其上层调用出现 `.rst`、`.ent`、`.key` 等许可状态扩展名。

这里**确有删除和重命名**，且存在先删后改名的失败窗口。需要保护许可状态文件和失败恢复；未见该路径接收播放列表中的歌曲路径。

### 5.3 请求／应答文件改名和清理

RVA `0x12257` 创建并写请求数据，然后：

```text
请求文件 → MoveFileA(原路径, 原路径 + "._rq")
等待许可服务处理
超时：删除该请求文件
读取 原路径 + "._an"
关闭并删除应答文件
```

`._rq`／`._an` 常量分别位于 RVA `0x76994`／`0x769F0`。这是许可通信流程的文件改名及清理，不是把整首音乐移动到其他目录。许可转移相关分支也会对由许可基准路径派生的文件进行写入和删除。

另有 MFC 通用 `CFile` 风格改名／删除机器码（RVA `0x58225`、`0x58247`）。本次未找到直接调用或原始地址指针引用，因此仅记录其存在，不能据此宣称某项业务一定运行它们。

### 5.4 系统目录字符串：该处是查时间，另有根目录诊断写入

需要区分两种事实：

- RVA `0x13FD6` 拼接 `%SYSTEMROOT%\system32\config\software.log`、`software`，调用 `stat` 风格函数 `0x3E9BA`，实际通过 `FindFirstFileA` 和文件时间转换读取元数据。**此处未见删除、重命名、覆盖系统注册表文件。**
- RVA `0xD033` 检查 `ckldrv.sys`、`crypserv.exe` 的存在和时间，并以 `"atc"` 模式打开 **`C:\CKINFO.TXT`** 写诊断信息；这是追加，不是 `w` 模式清空。由 `0xDBEF` 的 NT 系统许可初始化分支调用，不应假定只在用户点“导出日志”时执行。

后者意味着 OctiMax 的写入范围并非绝对只在插件目录内。它是否成功取决于文件权限；反复初始化也可能累积诊断日志。本次没有执行该写入。

### 5.5 文件属性和时间戳

除改名和覆盖外，OctiMax 的 RVA `0x1031A` 还调用 `SetFileAttributesA`。许可文件创建／转移路径会传入 `6`（隐藏＋系统属性），也有传入 `0` 的调用尝试清除属性。目标仍沿许可基准路径及派生文件传递；未发现把此操作递归应用到用户目录的逻辑。这解释了部分许可文件可能不在默认目录视图中显示，不能仅按普通文件列表判断它完全没有写文件。

RVA `0x58BFC` 是同时可修改属性和文件时间的 MFC 通用状态函数，含 `SetFileTime`。本次未确认其直接业务调用路径，不把通用能力表述为“已经修改了用户文件时间”。

### 5.6 外部许可库边界

代码会 `LoadLibrary`／`GetProcAddress` 调用 `cryput.dll` 等许可组件，解析 `save_site_key`、`transfer_out/in`、`AcquireLicense`、`KillLicense` 等接口。`Plugins` 顶层未提供 `cryput.dll`，这些外部模块的实际内容和系统上可能安装的版本不在本报告范围内。

因此结论是：内置分支的文件目标可以解释为许可管理；**无法据此保证任意外部许可库没有额外文件／注册表操作**。本轮没有修改、跳过或执行许可撤销／转移分支。

## 6. 注册表删除和容易误判的操作

### SO3D

Init 的机器码把根设置为 `HKEY_CURRENT_USER`，基准子键为 `Software\Softamp\plugin`。RVA `0x73F0` 的自定义预设删除对话框先显示确认，确认后把名称记入待删数组。Quit `0x2CF0` 才循环对这些名称拼接出的子键执行 `RegDeleteKeyA`（调用点 `0x3131`），并保存保留的预设。

这不是每次退出无条件删除所有预设，更不是清空 HKCU。用户选择删除的预设会从配置中消失，是实际数据修改。

### NEQ

RVA `0x60DC` 调用：

```cpp
WritePrivateProfileStringA("Presets", selectedName, nullptr, presetFile);
```

其效果是删除 `preset.neq` 中选中的预设项，不需要 `DeleteFile`。因此“没有导入 DeleteFile”不能推出“完全没有删除数据”。

`CreateFileA(..., CREATE_ALWAYS)` 还出现于运行库错误日志输出器 `0x11E88`；调用器 `0x11F48` 必须拿到已设置的日志路径才写文件，默认可以走消息框或标准错误输出。本次未确认插件业务把该路径设置为任意用户文件，故不把这个通用分支当作正常播放时会覆盖文件的证据。

### MFC 通用配置函数

OctiMax 的 RVA `0x5FF13`、SuperEQ 的 `0x1DFFD` 均包含框架式配置逻辑：键名为空时删除配置节／子键，值为空时删除配置项，否则写入。它们的目标取决于应用的 profile 根和调用参数。不能把框架函数中出现 `RegDeleteKeyA` 解读为清空系统注册表。

### 外部程序与长度调整

已核对的 `ShellExecute` 路径主要是网站、帮助链接和 Enhancer 的 `enhancer.htm`；Vinyl 的 RVA `0x69C0` 是 `open http://www.iZotope.com`，参数为空。未发现将 `cmd /c`、PowerShell 或删除命令拼接后交给 Shell 执行的证据。

Jammix、OctiMax、SuperEQ、ViPER 中的 `SetEndOfFile` 包含运行库／文件流调整长度函数。它确实能截断文件，但需继续结合具体文件句柄和调用者判断，不能按出现次数统计“破坏次数”。

2. **为 Enhancer、Jammix、ViPER 的配置保存增加失败保护。** 自有实现使用同目录临时文件，核验完整写入和关闭成功后再替换旧文件，并保留可恢复副本。对于第三方 DLL，必须先设计删除→创建→关闭整个序列的接管，不能仅让 `DeleteFile` 假成功。
3. **统一导出覆盖确认。** DEE／ViPER 在最终扩展名确定后检查同名文件；Enhancer 复制皮肤时询问覆盖或生成新名称，并检查 `CopyFile` 结果。
4. **明确文件与注册表是两种保护范围。** `plugin_registry.cpp` 的替换表当前没有接管 `CreateFile/fopen/CopyFile/MoveFile/WritePrivateProfile*`；完成所有 DSP 共用 `registry.json` 也不会自动解决这些文件行为。
5. **如需要限制插件访问用户文件，采用独立 DSP 进程并设置实际权限边界。** 单独放到子进程或改当前目录本身不限制读写权限；同时应保留用户明确选择的预设导入／导出能力。先在虚拟机里验证配置、许可通信及音频延迟，再决定产品方案。

后续动态验证应使用 VM 快照、仅含测试副本的目录，并关闭指向真实音乐库的可写共享；记录文件 API 的路径、创建方式、调用阶段和返回结果。重点覆盖：compwide 与 DeFX 共用 INI、同名导出、磁盘满／拒绝写入、删除成功后创建失败、强制中断保存。先前的默认 Init/PCM/Quit 测试不涵盖这些条件。
