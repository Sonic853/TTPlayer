# 软件更新实现与验证

更新日期：2026-10-08（本地构建 `2026.10.08p2`）。

## 使用方式

“选项 → 常规 → 软件更新”包含检查周期、更新源、立即检查、打开更新器，以及 GitHub / Gitee 发布页链接。

- 新配置的自动检查周期为 **不检查**。已有配置中的检查周期继续保留；立即检查不受该开关限制。
- 更新源默认 **Gitee**，可以切换 GitHub。
- “打开更新器”和“立即检查”位于同一行，尺寸一致。发布页链接采用与左下角一致的纯蓝色、无下划线样式，访问后仍为蓝色。
- 更新器为独立 C++ 程序 `TTPUpdater.exe`，显示当前版本、最新版本、更新源、下载进度和状态。打开后立即检查，点击“立即更新”才安装。

播放器和更新器均采用目前统一的 x86 Release 构建，支持 XP SP3、Win7 及现代 Windows。当前发行包为 `TTPlayerRebuild-yyyy.MM.dd[pN].zip`，内含：

```text
TTPlayerRebuild.exe
TTPUpdater.exe
ttpcomm.dll
AddIn/ttp_https.dll
SHA256SUMS.txt
```

手动安装时复制包内运行文件到原播放器目录，并合并 `AddIn` 文件夹。自动更新现在安装播放器 ZIP 内除根目录 `SHA256SUMS.txt` 外的全部文件，保留相对目录结构；包内有同名文件就替换，没有的文件不删除。发行包仍依赖原播放器的运行资源，不是全新安装所需的完整资源包。旧设计文档中的现代版 / XP 版双包划分已不适用于当前构建。

Actions 默认下载并校验最新正式版 `ttpcomm.dll`；可以指定日期版本，详见 [构建说明](BUILDING.md)。本次更新器会安装该核心 DLL，也会更新包内的 HTTPS DLL、更新器自身及今后增加的资源文件，不再校验后丢弃组件。

Actions 调用 `cmake/download_https_component.py`，从 [TTPlayerHttps 最新正式版](https://github.com/TTPlayerRebuild/TTPlayerHttps/releases/latest) 下载精确匹配标签的 `ttp_https-版本号.zip`，校验 GitHub 提供的 ZIP SHA-256、包内 DLL 摘要及 XP / Win7 静态导入后，暂存到构建输出的 `AddIn` 目录。下载或校验失败即停止打包，不复用旧 DLL。组件自己的版本号独立于播放器，所选标签、下载地址和摘要记录在 Action 的 `build-info.json` 中；测试代码不会入包。

## 检查和通知

Release 另外提供 `CodecAddIn-Rebuild-版本号.zip` 和 `ExtraAddIn-版本号.zip`，
外部 `SHA256SUMS.txt` 同时记录三个 ZIP。更新器按精确的 `TTPlayerRebuild-版本号.zip`
文件名选择附件及对应校验行；插件包供用户单独安装，见 [Release 插件包](ADDIN_RELEASE_BUNDLES.md)。
2026-10-06 已使用生产解析代码验证 GitHub／Gitee 的四附件、三条校验记录场景。

读取 GitHub / Gitee 的 Release API，解析 `tag_name`，只接受严格的 `yyyy.MM.dd`、`yyyy.MM.ddpN` 日期版本。比较 `(年, 月, 日, 修订号)`，因此 `p10 > p2`，跨日比较也不会出现拼接数字或浮点精度问题。

忽略草稿、预发行、非法日期、缺少附件、重复附件、超大附件；必须同时存在版本名称匹配的播放器 ZIP 与 `SHA256SUMS.txt`。不是仅发现一个 Git Tag 就提示可安装。分页具有条数、次数和重复页上限。

后台检查在工作线程中进行；成功检查记录日期，失败后间隔一小时重试，手动检查不受重试间隔限制。默认关闭时不会发出自动更新请求。同一来源和版本的自动通知只显示一次。

| 系统 | 新版通知 |
| --- | --- |
| Windows 8 及以上 | `Shell_NotifyIcon(NIF_INFO)` 系统通知，点击后打开软件更新选项；显示形式由系统控制 |
| XP / Win7 | 根据原版 `00455308`、`00455C99`、`00462D2A` 恢复右下角 HTML 通知窗口，提供选项和关闭入口 |

旧式通知的 HTML 正文仅为“请点击选项前往更新”。正文使用 HTML 字符引用，解决 XP 上 ATL / MSHTML 系统代码页导致的中文乱码。系统通知创建失败时使用该窗口作为回退。

这不是完整照搬旧更新协议；保留原版通知入口和主要布局，新版查询与安装均使用新实现。

## HTTPS、代理与 Token

优先从安装目录的 `AddIn/ttp_https.dll` 加载 HTTPS 组件，复用播放器网络设置中的代理类型、服务器、端口、用户名和密码。更新器在临时目录运行时仍从安装目录读取配置和 DLL。

- 没有可用组件时，Win7 / 现代 Windows 使用系统 WinHTTP；能否联网取决于系统 TLS、证书和网络环境。
- XP 缺少可用组件时，播放器“立即检查”和更新器显示 **“缺少 HTTPS 组件，请前往发布页手动下载更新”**。
- 组件已经开始 TLS 校验后的证书或握手错误直接报告，不通过回退绕过验证。
- Win7 原生路径兼容 IE 显式代理及 PAC 设置；SOCKS 代理使用 HTTPS 组件。

组件新增向后兼容的 ABI 3 流式下载接口，ABI 1 / 2 保持不变。歌词 `get()` 仍限定 2 MiB；新下载接口支持已知长度、分块和正常 TLS 关闭定界，调用方把更新包限制为 64 MiB。旧 ABI 2 组件仍可下载原有小包，大包应升级 HTTPS 组件。

所有客户端请求均先匿名访问。若构建中包含专用只读 Token，仅在 Gitee 返回 401 / 403 / 404 时对 Gitee 请求重试，不把该 Token 发送至 GitHub。

Actions 构建前运行 `cmake/prepare_update_access.py`：实际匿名请求 Gitee API、下载校验文件和完整 ZIP，并验证 SHA-256。匿名成功则生成空凭据；仅在 401/403/404 时尝试用户已允许公开分发的 `GITEE_TOKEN_UPDATER`，验证整条访问成功后才嵌入。生成头文件位于构建目录，日志不打印 Token，头文件不进入发行附件。发布 Release 的 `GITEE_TOKEN` 与检查更新的 Token 分开。

## 下载、替换和恢复

1. 更新器把自身复制到独立临时目录运行，以便更新安装目录内的 `TTPUpdater.exe`。同一安装目录只允许一个更新器工作。
2. 创建独立下载目录，下载外层校验文件及 ZIP，验证长度和 ZIP SHA-256。
3. 解压所有合法相对路径；根目录 `SHA256SUMS.txt` 只用于校验，不进入安装载荷。每个普通文件必须匹配清单中的 SHA-256；播放器和更新器另外核对产品文件名、x86 架构及发行版本，XP 检查子系统版本。支持嵌套目录、UTF-8 文件名、空文件和空目录；继续接受历史仅含播放器及清单的包。
4. 在关闭播放器前检查安装目录写入权限。只对该目录的播放器发送正常退出请求并等待真实进程结束；不会强制结束进程。歌词保存中或窗口正在退出时可拒绝请求。
5. 下载完成后销毁 HTTP 对象，释放安装目录中的 HTTPS DLL。播放器退出后预检所有目标文件的占用与权限；在同卷 `.TTPlayerUpdate-{GUID}` 中暂存新文件、复制并核验所有旧文件，写入恢复清单，全部完成后才开始替换。
6. 已有文件使用 `ReplaceFileW`，新增文件使用同卷移动。任一替换或校验失败时，逆序恢复所有已更改文件，删除新增文件及本次创建的空目录。更新器自身也属于这次事务，不再允许主程序成功但更新器失败的半更新结果。
7. 创建新版进程失败，或初始化检查时发现进程异常退出，同样回退整包。进程仍在运行但初始化超时时保留新版并提示，避免强杀后盲目覆盖运行中的文件。成功后保留 `.TTPlayerUpdate-{GUID}/backup` 和 `files.txt`，状态栏显示备份目录；下载、解压及同卷的新文件暂存区会清理。

取消下载和校验失败不会进入安装。文件被占用、目录不可写、播放器拒绝退出、超时都会报告错误。替换文件期间暂时禁用取消，避免人为中断文件事务。`ReplaceFileW` 特定失败状态可能已移动旧文件，因此另有恢复处理，依据 [Microsoft 的失败状态说明](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew)。

ZIP 及解压文件总量上限仍为 64 MiB，条目上限 4096，清单上限 1 MiB。拒绝绝对路径、越界、反斜杠、ADS、设备名、尾随点/空格、大小写重名、文件/目录冲突、符号链接、重叠条目、加密、损坏 CRC 和不完整压缩流。安装路径的各层不能是 junction 或符号链接，路径必须适用于旧系统的 `MAX_PATH` 限制。其他程序仍在使用组件时提示具体文件，不强行关闭其他宿主。

回滚失败会保留恢复清单和旧文件，错误信息给出目录。手动恢复时先关闭使用这些文件的程序，再按 `files.txt` 的 `REPLACE` 项恢复 `backup` 中的文件，删除 `ADD` 项列出的新增文件。成功更新的备份不自动清理，确认新版稳定后可删除对应备份目录。旧 `.bak` 文件不再作为整包恢复依据。

多文件替换不是操作系统级原子事务；突然断电或进程被强制结束时没有自动续作/恢复机制，只保留恢复材料。HTTPS 和双层摘要也不等于独立发布签名。本次没有加入离线 ZIP、断点续传。启动验证只包含进程创建与初始消息循环，不代表穷尽播放功能。

**旧更新器的过渡限制：** 已安装的旧 `TTPUpdater.exe` 仍按其旧逻辑更新 EXE、丢弃 DLL。从 `2026.10.08p3` 起播放器强制要求重建核心运行 ABI 1，本次按用户确认采用**退出后手动替换完整发行包**，同时替换 EXE、更新器、核心与包内 AddIn。之后使用新版更新器进行整包更新。不要用只更新 EXE 的旧更新器安装本次版本，详见 [核心依赖与体积优化](TTPCOMM_REQUIRED_RUNTIME.md)。

`2026.10.08p3` 将公共 SHA256 从 ZIP 安装编译单元拆出，避免播放器仅计算插件摘要时也链接 zlib 常量。独立更新器仍自带 zlib，不依赖 `ttpcomm.dll`。本机重新通过解包/事务回归、真实 UI 安装、自身更新与启动失败回滚。
