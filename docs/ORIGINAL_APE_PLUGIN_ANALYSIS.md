# 原版 ttp_ape.dll 分析与重建、升级方案

分析日期：2026-10-04。

## 1. 结论

**适合重建，建议采用“恢复 TTPlayer 插件接口 + 静态链接官方 Monkey's Audio MACLib”的方式，固定升级到本次核实的 13.27。**

这不是给现有 DLL 换一个依赖文件：原 DLL 已将编码、解码核心编入自身，没有导入独立的 MACDll.dll。需要重新实现外部接口与流适配层，再编译新版核心。

适合的理由：

1. Reader、Encoder、元数据和封面的接口边界已经能从虚表、反汇编及运行行为相互核实。
2. 官方 SDK 提供编码、解码、历史格式兼容、定位和标签源码，不必重新手写音频压缩算法。
3. 13.27 不仅能读取标准 3990 文件，还明确兼容本次原插件编码生成的特殊 **4110** 文件；本地已经完成交叉解码验证。
4. 新库提供更宽的采样格式、64 位内部计数、CPU 指令集选择及多线程接口，适合补齐原包装层的限制。
5. 官方仍提供支持 XP／Win7 的 32 位产品，源码也保留 XP 条件编译路径。项目仍需使用自己的现代编译、VC-LTL、YY-Thunks 方案验证，不能由此直接宣称重建 DLL 已兼容旧系统。

本次完成的是原版分析、SDK 编译与接口探针验证，尚未创建可交付的重建版 ttp_ape.dll，也没有替换原插件。

## 3. 原插件的整体结构

```text
TTPlayer / TTPlayerRebuild
  └─ ttpGetSoundAddIn
       ├─ Enum(0) → ReaderCreator → APE Reader
       │                  ├─ IStream → 旧 CIO 适配 → APE 解码核心
       │                  └─ CreateStdContent → Metadata / Thumbnail
       └─ Enum(1) → EncoderCreator → APE Encoder
                          ├─ PCM / double → 16 位输出路径 → APE 编码核心
                          ├─ 编码等级对话框 → ttp_ape.ini
                          └─ CreateStdContent → 标签写入接口
```

`60102D7E` 按序号枚举两个工厂；第三个序号返回 `E_INVALIDARG`。

| --- | --- | --- |
| AddIn | `EEC6C534-FEBA-421E-AA5D-10AC66F98784` | 虚表 `60118420` |
| Reader 工厂类别 | `476D15A5-D863-416A-8A59-A9C7D72CE04E` | 创建 `60102DD4`，虚表 `60118430` |
| Encoder 工厂类别 | `5954A909-9E02-4650-995E-F7535EE2BD8B` | 创建 `60102F5A`，虚表 `60118448` |

## 4. 播放与定位

### 4.1 Open 的两种路径

`601024D3`：

1. 保存宿主 `IStream`，读取其名称和能力。
2. 如果存在宿主导出的 `CreateStdContent`，以参数 `4` 创建通用标签对象，并向它查询封面接口。
3. 当 `flags & 1 == 0`，只解析 APE 头并取得格式、时长、码率；没有建立可读取 PCM 的解码器。
4. 当 `flags & 1 != 0`，通过 `601039E0` 建立解码器，查询格式及总块数。

`601036F0` 按文件版本在旧解码实现与较新实现间选择；边界为 `3930`。重建时须保留 SDK 的 `APE_BACKWARDS_COMPATIBILITY`，不可为了缩小 DLL 删除历史分支。

APE 核心按块和帧工作。一个 block 包含同一时刻的全部声道采样；解码先恢复预测残差，再恢复声道数据及 PCM。文件有帧定位表，Seek 需要回到对应帧并恢复解码状态，而不是简单按文件字节比例跳转。声道相关性、预测和熵编码的基本过程见[官方原理说明](https://www.monkeysaudio.com/theory.html)。

### 4.2 Reader 各方法

| 方法 | 地址 | 原行为 |
| --- | --- | --- |
| Duration | `60102719` | 返回 Open 缓存的毫秒值 |
| Format | `60102736` | 返回分配的格式副本 |
| BufferSize | `60102757` | 建议值为 `blockAlign × 1024` |
| CodecName | `6010277B` | 根据文件版本格式化名称 |
| Bitrate | `601027F6` | 缓存值，以 bit/s 返回 |
| BitDepth | `60102813` | 格式中的位深 |
| Read | `6010284A` | 容量除以 blockAlign 后向核心请求块 |
| Seek | `601028E4` | `MulDiv(毫秒, 采样率, 1000)` 后调用核心 Seek |

Read 的容量处理比此前分析的部分旧插件更完整：4097 字节容量、4 字节 blockAlign 时，只写出 4096 字节，本次探针未发现越过容量。

但有四类需要修正的行为：

- **把错误当 EOF。** 核心报错或取到零块都返回 `S_FALSE`，损坏与正常结束无法区分。
- **失败／EOF 不清空有效长度。** 本次正常文件最后一次调用仍留下前一次的 544 字节；不足一个 block 的容量也留下原来的 777 哨兵值。
- **Seek 忽略核心返回码，且不更新请求位置。** 2 秒文件请求 3000 ms，报告成功并保持 3000，后续却读出末尾 1 个 block；请求 `0xFFFFFFFF` 又能从前部读到数据。
- **内部运算存在 32 位限制。** 时长在 `MulDiv` 前先以 32 位乘法计算 `totalBlocks × blockAlign`；流适配器 Seek 接收有符号 32 位偏移。大文件／超长音频需要改成内部 64 位计算并对外部 DWORD 范围做检查。此条由反汇编确认路径，尚未用数 GB 文件实测。

建议 Read 保留完整 block 对齐，单独处理容量不足、EOF、I/O 错误、CRC 错误及不支持格式；同时检查宿主 Buffer 的方法返回值。

### 4.3 不要把能读取头部等同于能播放

本次 13.27 编码的合成样本：

| 样本 | 原 Reader | 13.27 SDK |
| --- | --- | --- |
| 8 位、双声道整数 | 完整解码，与输入字节一致 | 一致 |
| 16 位、双声道整数 | 完整解码，与输入字节一致 | 一致 |
| 24 位、双声道整数 | 完整解码，与输入字节一致 | 一致 |
| 32 位、双声道整数 | Open 成功；Read 立即 `S_FALSE`，输出 0 字节 | 完整解码且一致 |
| 24 位、6 声道整数 | Open 成功；Read 立即 `S_FALSE`，输出 0 字节 | 完整解码且一致 |
| 32 位浮点 | Open 失败 | 完整解码且一致 |

本次浮点 APE 使用 `MACF` 文件标识，普通整数 APE 使用 `MAC `。原头解析器检查 `MAC `，不能仅靠原来的探测判断支持新版浮点文件。

## 5. 编码器：不能遗漏，也不能照搬错误

### 5.1 生命周期与配置

| 阶段 | 地址 | 行为 |
| --- | --- | --- |
| Open(stream, format) | `601014C7` | 校验格式、选择转换函数、建立输出流与核心 |
| Start | `601015B0` | 使用全局压缩等级开始编码 |
| Write | `601015F4` | 获取宿主 Buffer、临时转换、调用核心 AddData |
| Finish | `601015DE` | 调用核心 Finish，但无条件返回 `S_OK` |
| 配置对话框 | `60101000`、`601010FD`、`60101183` | 五种等级，修改全局设置 |
| 加载／保存配置 | `601030CB`、`601031BD` | 同路径同名 `.ini`，`[Compress] Level=` |

默认等级 2000。Fast／Normal／High／Extra High／Insane 分别为 1000／2000／3000／4000／5000。原版在 DLL 卸载时保存已修改等级；配置路径通过 ANSI API 构造，应在重建时支持 Unicode。

Finish 忽略写尾部、回填头部等步骤的失败，会使转换任务误报成功。新实现必须返回真实错误，并确保异常结束不留下被认作成功产物的文件。

### 5.2 实测发现的整数输入问题

Open 会将内部格式改为 PCM16。Write 在 `60101651` 又把常量 `16` 传入转换函数。

对 `double` 转 PCM 函数 `60101C60`，这个参数是输出位深，行为合理：缩放、取整、裁剪到 16 位。

对整数转换函数 `60101E90`，这个参数却用于解释输入位深；固定传 16 会直接复制输入字节。函数里虽然有 8／24／32 位转换分支，实际这条 Write 路径不会选择它们。

对相同的 2 秒、44.1 kHz、双声道输入进行直接接口测试：

| 输入 | 原编码器生成格式 | 输出时长 | 新库解码结果 |
| --- | --- | --- | --- |
| PCM8 | PCM16 | 1 秒 | 字节与 PCM8 源完全相同，被误当作 PCM16 |
| PCM16 | PCM16 | 2 秒 | 正确 |
| PCM24 | PCM16 | 3 秒 | 字节与 PCM24 源完全相同，被误当作 PCM16 |
| PCM32 | PCM16 | 4 秒 | 字节与 PCM32 源完全相同，被误当作 PCM16 |
| IEEE float32 | 不接受 | — | Open 返回 `E_NOTIMPL` |
| IEEE float64 | PCM16 | 2 秒 | 与预期 16 位转换逐字节相同 |

**这说明包装层接受格式与实际处理格式不一致，并非 APE 压缩算法本身有损。** 随后对原版 5.7.9 EXE 的追踪已确认：普通 APE 转换先由宿主形成 float64 数据，再交给插件转换为 PCM16。上表直接传入整数的探针没有复现这条完整宿主路径，不能用于断言原播放器正常转换时会出现同样的时长错误。完整证据见第 11 节。

重建建议：

- 保留原宿主常用的 PCM16 和 float64 输入约定。
- 正确处理所声明接受的每种格式；不支持时在 Open 阶段返回明确错误。
- 对原生 PCM8／16／24／32 可采用新版 SDK 保留原位深；这属于精度改进，应单独记录，不能声称与原错误输出字节完全相同。
- float64 仍需明确选定量化策略；本次 SDK 的 WAV 编码入口不接受 64 位浮点，不能承诺借助升级自然获得 float64 无损编码。
- 不让宿主先转成 double 后又自动生成 float32 APE，否则可能破坏与原插件及旧外部播放器的兼容预期。

### 5.3 特殊的 4110 文件版本

本次原插件编码出来的头部版本值确实是 **4110**，不是仅在名称里显示“4.11”。

13.27 的 `Source/MACLib/MACLib.cpp::CreateIAPEDecompressCore` 有明确的 `nVersion == 4110` 兼容分支，本次 PCM16 和 float64→PCM16 的原编码结果均被正确读取。

13.27 生成的普通整数 APE 使用文件格式版本 **3990**。16 位双声道在全部五种压缩等级下，都能被原 Reader 解码为相同 PCM。因此升级库不等于所有新生成 APE 都不能由旧插件播放；32 位、更多声道和浮点扩展则需要分别验证。

重建验收应比较 PCM、采样数、定位、标签与错误行为。新旧压缩器的压缩字节、填充、MD5、文件大小不必完全相同。

## 6. 标签与封面：真正的边界在宿主

`601030CB` 初始化时先查找已加载的 `ttpctrl.dll`，不存在则查询主 EXE，动态获取 `CreateStdContent` 和 `GetSoundCodecName`。

Reader 的 Metadata 方法 `60102927`～`60102990`，以及 Thumbnail 方法 `601029B3`～`60102AA2`，转发到宿主提供的对象。释放 Reader 时先销毁解码器，再释放流和宿主标签／封面引用。

这意味着：

1. DLL 里有 APETAGEX、SDK 标签类，不代表向 TTPlayer 暴露的编辑和封面能力直接由这些类实现。
2. 独立探针没有导出 `CreateStdContent`，因此 Metadata QI 返回 `E_NOINTERFACE`；这不是原播放器内的标签能力缺失证据。
3. 没有宿主封面对象时，原 Reader 仍可能让 Thumbnail QI 成功，而后续操作失败。不能把 QI 成功直接当作有封面。
4. 不能将此前 FLAC Reader 的“最后一次 Release 写盘”结论直接套到 APE；这里需要继续追踪宿主 StandardContent 的写入策略。

重建版已经在 `src/app/exports.cpp` 暴露 `CreateStdContent`，实现位于 `src/audio/builtin_file_info.cpp`，可以复用现有衔接路径。

推荐先恢复这条委托关系，再决定是否为无宿主回调的环境增加 SDK 标签后备实现。两套实现不能同时修改同一文件。标签改写还要验证未知字段、二进制字段、Unicode、多值、ID3v1／APEv2 并存、封面类型与音频区保持不变；本轮尚未进行这些保存测试。

## 7. APL：库有代码，不代表原插件已接通

原 DLL 有 `[Monkey's Audio Image Link File]`、Image File、Start Block、Finish Block 解析代码，但 Reader 公布的扩展名只有 APE／MAC。

原 Reader 的 Open 走流版核心创建函数 `601039E0`，未走按文件名处理 APL 的入口。

本次同一份 APL 引用一个 2 秒 APE，并截取第 22050～44100 block：

- 13.27 SDK 输出 88200 字节，即正确的 0.5 秒双声道 PCM16，逐字节匹配对应区间。
- 原 DLL 的 Reader::Open 返回 `E_FAIL`。

所以 APL 应标为**可增加的扩展支持**，不能标为已经恢复的原 Reader 既有行为。若加入，还要处理相对／Unicode 路径、目标缺失、越界范围、分段时长和标签归属。

特别注意新版 SDK 的 `APE_INFO_TOTAL_BLOCKS` 是源文件总块数，APL 应使用解码范围对应的信息；不能读对了片段，却仍显示整张专辑的时长。

## 8. 新版依赖与构建方案

### 8.1 固定的 SDK

截至本次核实，[官方 SDK 页面](https://www.monkeysaudio.com/developers.html) 提供 **13.27**，[版本历史](https://www.monkeysaudio.com/versionhistory.html) 的发布日期为 2026-10-01。

- 地址：`https://www.monkeysaudio.com/files/MAC_1327_SDK.zip`
- 下载大小：1,791,730 字节。
- 本地计算 SHA-256：`c47c6b36f6a7bd50d990f2eb36a70915c0074a7b9634be396c94464905e76686`。
- 内部接口版本：17；普通编码文件版本：3990。

后续项目建议沿用 ttp_aac／ttp_ogg／ttp_flac 的方式：构建时下载固定版本并校验散列，仓库保留适配源码、构建描述和许可材料，不提交 SDK 的整个源码包。

### 8.2 为什么选择官方 MACLib

| 方案 | 评价 |
| --- | --- |
| 官方 MACLib 静态链接 | 同时覆盖编码、解码和历史版本，最适合恢复原插件范围 |
| 直接分发官方 MACDll.dll | 仍需适配旧 ABI，还多一个运行时 DLL；不符合目前单插件 DLL 的构建方向 |
| 转用另一套解码器 | 可以作为 PCM 交叉验证手段，但不能自动恢复原 Encoder、配置和宿主交互 |
| 从伪代码手写全部算法 | 工作量与验证风险更高，也失去直接吸收上游修复的优势 |

13.27 的 `IAPEDecompress`、`IAPECompress`、`IAPEIO` 已不同于旧库：例如 GetData／Seek 和流读写使用 64 位计数。必须编写新适配层，不能复用旧 C++ 虚表或假定二进制兼容。

### 8.3 本次实际编译结果

已将 13.27 静态 MACLib 和独立测试前端编译成功并运行。

上游 CMake 把 `Source/MACDll/MACDll.cpp` 加进核心目标，它在 Windows 下引入 MFC，直接构建会缺少 `afxwin.h`。本次从测试构建目标中排除了这层 DLL 包装代码；编码、解码及历史核心正常编译，不需要为插件安装或携带 MFC。

同时清除了上游目标中的 GCC 风格警告选项，使用 MSVC 选项。下载源码本身保持原样，调整位于测试工程。

这次验证程序使用本机静态 CRT，**没有据此验证 XP 运行兼容性**。最终插件应接入现有 VC-LTL 5.3.1／YY-Thunks 1.2.2 构建，做导入表检查与真实系统运行测试。

### 8.4 旧系统与 CPU

[官方下载页](https://www.monkeysaudio.com/download.html) 明确列出 32 位版本支持 XP、Win7；源码的 `PLATFORM_WINDOWS_XP` 会设置对应最低系统宏。

建议：

- 统一 x86 插件，与原版及重建版宿主位数一致。
- 保留 `/Zc:threadSafeInit-` 等旧系统构建设置，并检查最终 PE 子系统版本和实际导入。
- 保留运行时 CPU／OS 能力检测，按条件选择 SSE／AVX 路径；不能把整个项目全局编译成 AVX2。
- 不因支持 XP 就承诺支持所有没有 SSE2 的古老 CPU；CPU 基线需要单独定义和验证。
- 内部仍使用完整 64 位偏移，宿主接口参数不足时明确限制，避免无声截断。

### 8.5 性能和体积

优先优化适配层，而不是修改预测／熵编码的数学过程：

1. 原格式不需要转换时直接交付 PCM，避免多余的临时复制。
2. 复用缓冲区，严格限制分配大小和乘法溢出。
3. 播放先采用单实例单解码线程策略，再测量高压缩等级的收益；SDK 提供 SetNumberOfThreads，不等于每首歌都应该启用全部核心。
4. 批量增益扫描已有歌曲级并发时，应限制单实例线程数，防止两层并发叠加。
5. 转换任务可独立评估多线程编码；同一个旧 IStream 的并发 Seek／Read 必须串行化或使用独立句柄。
6. 使用 Release、尺寸优化、LTO、无用节删除；只链接核心，排除 GUI、DirectShow、Winamp、命令行等包装代码。
7. 历史解码分支不能以体积优化为由删除。最终 DLL 体积须在正式工程链接后比较，本次不提供未经构建的大小承诺。

## 11. 原版播放器是否真正引用 APE Encoder

### 11.1 明确结论与范围

**有实际引用。原版通过 AddIn 编码器工厂动态调用 APE Encoder，使用入口是“转换格式”。** 它不是仅被枚举后闲置的对象，也不依赖 EXE 内写死 `APE Encoder` 名称的直接调用。

本节核对的是工作区根目录的 `TTPlayer.exe`：文件版本 **5.7.9.0**，SHA-256 为 `c7999ea5823469c1684148cac1bd196009824348ccac5cdd45978f8fb574e28c`。依据为 `reverse/decompiled/TTPlayer.exe.pseudo.c` 和原 EXE 的反汇编、GUID 字节。本节没有据此宣称其他版本的地址相同。

### 11.2 从插件发现到进入转换列表

1. `004CA48E` 初始化声音插件库，先由 `004CA86C` 注册内置工厂，包括 Wave Encoder，再扫描 AddIn。
2. `004CABC0` 使用 `ttp_*.dll` 通配符发现插件。
3. `004C88D9`（恢复名 `CSoundAddInModule_CreateInstance`）加载模块、查找 `ttpGetSoundAddIn` 并调用。
4. `004C8954`（`CSoundAddInModule_Invoke`）调用 AddIn 虚表 `+0x0C` 的枚举方法。
5. `004CABC0` 将返回类别与 EXE 中 `00518868` 的 GUID 比较；二进制值确实是 `5954A909-9E02-4650-995E-F7535EE2BD8B`，与 APE 插件 Enum(1) 返回的 EncoderCreator 类别完全相同。
6. 类别相同时，经 `004CD5D2 → 004C8625 → 004CDB93` 保存编码器工厂、名称、扩展名及是否有设置功能。
7. 转换设置窗口 `0047D682` 遍历编码器目录，以 `004CD1CC` 取出条目并填充控件 `0x802`。APE 的显示名称由插件工厂返回，不需要 EXE 自带一份 APE 名称字符串。

所以搜索 EXE 是否存在 `ttp_ape.dll` 或 `APE Encoder` 字面量，不能判断实际是否使用该编码器。这里的引用关系由类别 GUID、工厂对象和虚表调用建立。

### 11.3 设置按钮确实调用 APE 插件

`0047D9A4 → 004CD21E → 004CD865` 找到当前选择的编码器工厂，然后调用工厂虚表 `+0x1C`，即 slot 7 的 Configure。

对 APE，该方法对应 `ttp_ape.dll!601030AB`，再进入 `60101000` 打开五档压缩等级对话框。`0047D9C7` 根据工厂能力启用设置按钮，并只对列表第 0 项 Wave 启用位深控件。

因此，原版 UI 里选 APE 后不能像 Wave 那样直接从公共位深下拉框选 24／32 位；APE 输出精度由插件自己的编码路径决定。

### 11.4 创建、打开、写入和结束的完整对应

| 阶段 | 原 EXE 位置 | 对 APE 的实际对应 |
| --- | --- | --- |
| 创建编码实例 | `004122CD → 004CD28F`，工厂 slot 3 | `60102FED → 60102FF9` |
| 查询流初始化扩展 | `004CD30C → 004CD65A` | QI `FFB27DF8-77EF-4BA7-8945-7E144C381CBE` |
| 创建输出流 | `004CD30C` | `CreateStreamOnFile(path, 0x1022, ...)` |
| Open | 扩展虚表 `+0x20`，slot 8 | `601014C7(stream, format)` |
| Start | `00412723`，实例虚表 `+0x10` | `601015B0` |
| Write | `00412723`，实例虚表 `+0x18` | `601015F4` |
| Finish | `00412723`，实例虚表 `+0x14` | `601015DE` |

`004CD65A` 的反汇编明确压入 `00522EF8`，该位置的 GUID 字节与 APE 的流扩展相同。APE 确实暴露它，所以正常使用流初始化；只有没有这一扩展的其他编码器才回退到路径 Open。

`004128D4` 内嵌 `CConvertDlg::CWorkThread::Run` 名称，执行 `CoInitialize → 00412723 → CoUninitialize`，再向转换窗口发送完成消息。实际 PCM 写入发生在转换工作线程中。播放 APE 则走另一个 Reader 类别，这两条职责不能混为一谈。

### 11.5 原宿主给 APE 的数据是 float64

正常支持格式的调用链为：

```text
源文件 Reader / Decoder
  → 004B0D1A 建立处理格式
  → 004B1375 读取并处理音频
  → float64（double；可按选项重采样及应用音频处理）
  → 004122CD / 004CD30C 将该格式传入 Encoder::Open
  → 00412723 将同类 PCM Buffer 交给 Encoder::Write
  → ttp_ape!60101C60 转成 PCM16
  → APE 压缩
```

关键证据：

- `004B0D1A` 检查源格式是否为 float64；不满足时建立转换，选择整数转 double 的 `004B0560` 或 float32 转 double 的 `004B08A0`。
- 反汇编 `004B0F31` 写入格式标记 `3`（IEEE float），`004B0F38` 写入位深 `0x40`（64）。源已是 float64 且无需转换时可直接使用源格式。
- `00411EA1` 按转换状态返回源格式或处理后的格式，`004122CD` 拷贝它传给 Encoder。
- `004122CD` 只有在 `DAT_00547DC8 == 0`，即内置 Wave 分支，才按公共位深设置重新改成整数 PCM。
- `00412723` 也只在输出格式标记为 PCM 时进行对应整数转换，APE 的 float64 路径直接交给插件。

因此上轮“宿主可能先规范化输入”现已可以收敛为：**原版正常 APE 转换会先提供 double，插件再量化到 16 位；不是把原始 24／32 位整数直接送到那条错误路径。**

这消除了正常路径被误诊为时长错误的疑问，但高位深源最终降为 16 位的限制仍然存在。APE 算法无损，不意味着这条完整转换链保留了源文件全部位深。即使升级 MACLib，若继续沿用插件强制 PCM16 的包装逻辑，输出也不会自动恢复为 24／32 位。

对原 EXE 而言，Encoder 收到 double 本身并不能可靠恢复源文件原始位深。要增加保留高精度输出，需要明确的插件输出选项或重建宿主额外传递原始格式信息；必须与默认兼容行为区分。

### 11.6 元数据与错误结果也有真实调用

`004122CD` 打开输出后向源 Reader 和目标 Encoder 查询 Metadata；两边都成功才调用 `004121C4` 复制非空文本字段，跳过 `replaygain_` 前缀。这里是文本字段复制证据，不能推断它也完整复制全部封面。

另一个兼容边界是 Finish：

- 原插件 `601015DE` 忽略内部核心 Finish 错误。
- 原 EXE 在 `00412897` 调用 Encoder::Finish 后，也没有读取该 HRESULT，而是继续停止源 Reader。
- 随后 `004128A6`～`004128B1` 使用之前的循环状态与进度决定结果；进度达到 99 时还可能把已有失败转成成功。

因此只修复重建插件的 Finish 返回码，仍不能让**未经修改的原 EXE**可靠显示全部收尾失败。重建宿主可以正确检查返回值；原宿主则有这个既有接口使用限制。重建兼容性报告应把“能正常调用”和“能完整报告所有保存失败”分开描述。

### 11.7 对重建范围的影响

APE Encoder 是原版可达且实际执行的功能。完整恢复 ttp_ape 时应保留工厂、流初始化扩展、压缩等级设置、float64 输入、写入／结束流程和标签接口；只实现 Reader 会使原版“转换格式”中的 APE 输出功能缺失。

本节为静态伪代码、二进制与反汇编交叉核对。没有新增一次原播放器 UI 转换实测；此前 58 次观测仍是 DLL／SDK 独立探针，不能改称完整宿主测试。
