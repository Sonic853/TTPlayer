### 短读的安全差异

原版只在读到零时停止处理，对正数短读仍把固定 512 点工作区交给效果。
但这不能保证未写入尾部有确定内容。本次恢复“正数继续推进”，**不复制未初始化读取**。
因此对原版短读时偶然的堆内容，不承诺逐像素一致。完整输入的算法未改变。

### 屏幕与内存目标的差别

Win11 的 600×360 窗口中，同一帧的屏幕读回与内存 DIB 可存在像素差异。
等待稳定后该差异仍可重现，但生产 HWND 与独立 DrawDib HWND 输出为零差异；
内存目标之间也为零差异。故不能把跨目标类型的差异归因为重建算法错误，
也不能仅凭这组数据断言一定由 DPI 缩放引起。没有为消除测量差异而改动 DPI 或放宽像素断言。

内存 DIB 上，原 `StretchDIBits` 与 `DrawDibDraw` 在本轮覆盖条件下同样未产生差异。
这次更换 API 是恢复原版调用方式，不能据此声称已证明旧 API 会在所有机器上画错。

## 4. 剩余边界

- 原版多实例共享全局尺寸、随机与计数状态。现有串行保护不等同于完全独立实例。
- 一个工作线程仍共用调度；未为多个不同类型的扩展视觉窗口建立独立时钟。
- 不复现未初始化内存；原版正弦表邻接字段行为仍按重建核心既有显式数值兼容保留。
- 未穷尽所有随机种子、坏参数、显示驱动、色深或其他发行包 DLL。
- 此阶段尚未加入高分辨率和高刷新模式；随后按用户要求增加的调用频率与尺寸配置见第 5 节。
  逻辑更新与显示的完全分离仍未实现，不能把提高调用频率称为同速度的平滑插帧。

## 6. 全屏梦幻星空间歇闪黑

### 6.1 原因与复现

修复前存在两层提前清屏：

1. `VisualRuntime::Paint` 的 Dream 分支先 `PaintCachedBackground`，向可见 DC 拉伸绘制黑底，
   然后才调用 `DrawDibDraw` 画完整帧。工作线程每帧都经过这里。
2. `PaintVisualControl` 在全屏 `WM_PAINT`／`WM_PRINTCLIENT` 路径又先 `FillRect(BLACK_BRUSH)`。
   这个清屏发生在取得渲染器锁之前；若渲染线程正在处理较慢的一帧，黑底会在等待期间保留。

最终画面虽然正确，两次绘图之间的黑底仍可能被桌面合成器或显示刷新采到。
因此不能用“最终截图逐像素相等”证明绘制过程中没有闪烁，也没有证据应把问题归于音乐解码或 Dream 算法。

私有测试在自身 EXE 的 `DrawDibDraw` 导入入口记录**实际绘图之前**的目标 DC，再转发到原 API。
覆盖工作线程直接绘制、`WM_PAINT`、`WM_PRINTCLIENT`。修复前 9 次观测全部看到全黑，
而同轮最终帧仍与独立绘制结果一致，确认是中间清屏问题。

### 6.2 修复

- 有有效 Dream 帧时直接绘制其完整不透明画面，不预先画缓存背景。
- Dream 窗口重绘直接进入渲染器，由其在同一锁内决定绘制完整帧还是无帧背景；
  不在锁外执行黑色填充或普通窗口背景预绘制。
- 无有效帧或绘图失败时仍允许显示缓存背景；停止仍清空帧，暂停仍保留画面。
- 分辨率、裁剪、帧率、核心版本和原版尺寸重配置语义保持不变。

本次只修改 `src/ui/player_window_visual.cpp`，没有新增逐帧复制或全屏缓冲，也不更换绘图 API。
私有回归位于 `tests/ui/dream_host_tests.inc`；日志保存在 `tests/dream_flicker_20261026/`。
最终帧的严格像素比较保留，并增加上述中间状态观测，避免相同问题再次漏检。

## 7. 其它视觉效果与皮肤插件内容区域

### 7.1 剩余原因

继续检查后，发现相同的中间画面问题仍存在于两条路径：

- `PaintVisualControl` 对频谱、示波以及普通窗口封面仍先绘制背景，再调用已经能够
  输出完整帧的渲染器。全屏频谱和示波会先填黑；普通窗口则先画皮肤底图。
- `PaintSkinPluginContent` 接收插件提供的 DC，先填黑，再依次绘制视觉和歌词。
  若插件传入窗口 DC，用户可能看到清屏或尚未叠加歌词的中间画面；若传入内存 DC，
  这些步骤本身没有直接显示的问题。

韵动脉冲、水波荡漾已有完整帧合成；节拍星环和星环 lazer 的常规绘制也不经过上述
原生控件提前清屏分支。此次不改变它们的算法、帧率设置或动画。

### 7.2 修复方式

1. 已初始化的原生视觉控件统一直接调用渲染器，由其在渲染锁内决定输出完整帧或无帧背景。
   删除外层重复预绘制，保留尚无渲染器时的背景处理。
2. 插件传入可见 DC 时，在可复用的内存画布中完成背景、视觉和歌词，再一次 `BitBlt`
   提交。插件已经传入内存 DC 时仍直接绘制，不额外复制。缓冲按需扩容，具有尺寸上限、
   分配失败检查和重入保护；失败时不先清空目标窗口。
3. 保留非零／负逻辑原点、目标 DC 的裁剪区域以及歌词叠加／分区规则。
   内容缓冲使用独立锁，避免读取曲目状态时持有效果渲染锁。
4. 渲染器完成 GDI 绘制后，在释放锁前执行 `GdiFlush`，确保当前线程排队的 GDI 读取
   已完成，再允许其它线程复用 DIB。此项为缓冲复用的同步保护，不作为已测定的闪黑根因。

生产代码仍只修改 `src/ui/player_window_visual.cpp`。原版 EXE、原版 DLL 和视觉核心未修改。
