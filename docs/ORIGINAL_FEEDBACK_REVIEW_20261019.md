# TTPlayer 5.7.9 压缩包与四项用户反馈审计（2026-10-19）

> 后续实际样本已提供，并按要求生成同结构压缩 RAR4；样本身份、原版／重建实测及剩余差异见 [实际 RAR 样本对照](ARCHIVE_REAL_RAR_SAMPLE_AUDIT_20261019.md)。本文此前“尚未取得实际样本”的表述保留为当时验证范围。

## 1. 结论与分析范围

本次按 reverse-engineer-anything 工作流，对原版二进制、已有伪代码和当前重建版源码进行交叉检查，分析压缩包解析，以及大 RAR 首播慢、双安装文件关联、最小化歌词弹出、ASIO／KS 输出四项反馈。

**这是分析与改进方案，尚未实施下表中的新修复。** 本轮没有启动播放器、修改系统关联、加载声卡驱动或进行 XP／Win7 播放测试。旧文档中的通过记录属于历史验证，不能当成本轮对反馈的实机复现。

| 反馈 | 本轮结论 | 证据强度 |
|---|---|---|
| 大 RAR 内 WAV 等很久才播放 | 原版支持解压前缀就绪后读取；当前底层也支持，但播放打开时的同步封面枚举会等待 RAR 引擎锁，WAV 尾部扫描和列表完整 CRC 校验还会增加等待 | 阻塞调用链已由源码确认；用户具体包的耗时分布待测 |
| 两个安装目录关联报“文件占用” | 当前代码在 Owner 路径冲突时主动生成错误 32；同时存在多键登记失败后留下半套状态的风险 | 错误生成分支确定；反馈机器实际注册表状态未知 |
| 最小化后切到有歌词的歌曲，歌词窗弹出 | 原版自动显隐也没有最小化门控；当前仍有此路径，并遗漏原版的全屏门控 | 原版与当前静态路径确定；窗口隐藏时差未量化 |
| ASIO／KS 不能播放 | 两种后端已经实现；存在激活、采样率、设备筛选和缓冲时序差异 | 多项具体代码问题确定；尚不能确定用户声卡的唯一失败原因 |

本次“原版”特指当前仓库的 5.7.9，不等同于反馈中未提供二进制的所有 5.7 安装包。用户随后补充了反馈 1 的 WinRAR 截图，未提供该 RAR 本体；声卡型号／驱动版本／错误日志也未提供，因此不宣称复现了相同现场。

## 2. 原版压缩包解析和播放机制

### 2.1 工厂、枚举和包内 CUE

| 原版入口 | 已确认职责 |
|---|---|
| 004739DB／004742DD | 文件分类、导入分发 |
| 004738B5 | 选择 ZIP 对象 0041ECD1 或 RAR 对象 00473287 |
| 00473338 | RAR 成员枚举 |
| 00474051 | 保留成员枚举顺序；构造外层包与包内成员的逻辑路径；区分 CUE 和已注册音频 |
| 00473EC5／00473F27 | CUE 内容解析、子曲目导入 |
| 004C4984／004C4A6D | 构造包内 IStream，并取得共享成员任务 |
| 004DFDED | 复用当前成员任务；成员不同则释放管理器持有的旧任务并创建新任务 |
| 004DFBF9／004DFD8E | 创建映射、启动读取、更新已产生字节数和完成／失败状态 |
| 004C4CA8 | 只等待本次 Read 所需的前缀；响应取消和超时 |

00474051 不是先把所有音频解压到目录再导入：

1. 取得成员列表。
2. 构造“外层包路径 | 包内成员路径”。
3. CUE 读取文本后展开子曲目。
4. 其它成员按播放器注册格式分类。
5. 真正打开音频时才经过包内流。

原版 ZIP／RAR 工厂及旧 RAR 引擎在 **TTPlayer.exe** 内。单独替换原版的 ttpcomm.dll，不会自动把原 EXE 的归档工厂升级为重建版实现。

### 2.2 RAR 读取、缓存与首播

原版 00473580 打开 RAR，设置 004DFF63 回调，区分同步读入小文本与后台读取成员；00473702 定位目标成员并解压，0047366F 请求停止工作。

004DFBF9 使用：

- CreateFileMappingW(INVALID_HANDLE_VALUE, ..., memberSize)；
- MapViewOfFile 映射整个成员大小；
- 后台解压把字节填入映射；
- 004DFD8E 发布已产生长度、完成或失败状态。

这属于**以分页文件为后备的整成员映射**，不能简单称为“所有字节立即驻留物理内存”，也不能说“原版没有缓存”。

004C4CA8 比较“当前位置＋本次长度”与“已解压字节数”：

- 当前读取范围已就绪即可复制返回。
- 不必等整个 WAV 解压完成。
- 尚未就绪时以 200 ms 步长等待，并检查取消／超时。
- 原版使用 32 位成员长度和整段地址空间映射，对大文件和进程地址空间有局限。

004C4B17 的定位还要求目标位置不超过当前已产生长度；它并不是任意位置立即随机解压。重建版允许先改变游标、在随后 Read 等待相应数据，是可以保留的改进。

### 2.3 原版 WAV 为什么有利于首播

原版 004E9EE7 → 004E8239 → 004E82CA。

本轮反汇编确认：

- 004E8395：比较 chunk 标识与 0x61746164，即 data。
- 004E839C：相等则跳到 004E83AD。
- 004E83AD 起：保存 data 长度和当前位置，结合流长度修正可用长度。
- 004E83F2 起：按数据字节数和每秒字节数计算时长。
- 随后结束打开；没有继续读取 data 后面的 LIST／INFO 才允许播放。

因此，“先读 WAV 头和数据区描述，再读首段 PCM”的路径和后台解压可以配合。**这是原版能快速开始播放的实现依据；实际是否立刻出声仍取决于目标成员位置、固实依赖、加密及硬件速度。**

原版解析对 fmt 顺序等要求较严格。重建版已有的格式验证与容错无需回退；只应把完整尾部标签读取从首播必经路径拆开。

### 2.4 原版能力边界

- 工厂只覆盖 ZIP／RAR，不能把现代 7z／TAR／gzip／OSZ 视为原版已有功能。
- 旧 RAR 解析不支持 RAR5；已有历史对照也区分了 RAR4 与 RAR5。
- 包内流 Write／SetSize／Commit 对应 0040F7F0／0040BE91／00407310，返回 E_NOTIMPL；继续保持压缩包只读符合既定要求。
- 固实压缩中的后续成员依赖前面文件留下的字典，不能承诺任意成员首次打开都无等待。[RARLAB 格式说明](https://www.rarlab.com/technote.htm)

## 3. 当前重建版压缩包实现：已有能力与剩余差异

应以当前源码为准。早期 ARCHIVE_RAR4_RAR5_ANALYSIS.md 正文里的“Shell 解压、整首等待、字母排序”已被后续实现替代，不是当前状态。

| 方面 | 当前实现／保留价值 | 尚需改进 |
|---|---|---|
| 容器引擎 | 音乐归档通过 ttpcomm 扩展接口；RAR 使用固定 UnRAR 7.3.1 | 首播调用层尚未充分利用流式能力 |
| 流 | 后台 Task、独立游标 Clone、进度、取消、最终错误传播 | 多个上层读取会主动访问尾部 |
| 内存／磁盘 | 默认小成员 16 MiB 内存门槛，大成员自动删除临时文件 | 仍需测量磁盘写入与读取竞争；不能简单改成整首常驻内存 |
| 缓存 | 当前成员任务＋最多两个已完成历史成员；历史单成员不超过 128 MiB | 这是完整成员复用，尚非共享固实解码状态 |
| 身份 | 整组分卷身份、文件变更判定、密码候选校验 | 播放器与独立信息进程不共享同一个 Task |
| 导入 | 后台、可取消、保留归档顺序、CUE 相对成员处理 | 列表信息查询仍可能启动全成员校验 |
| 格式扩展 | ZIP／RAR／7z／TAR／gzip、分卷及 OSZ 专门解析 | 不是所有加密／压缩方法均支持；固实跨成员预取仍未做 |
| 辅助内容 | 包内歌词、同目录图片、OSZ 背景封面 | 辅助内容不应阻塞第一段音频 |
| 写入 | 继续只读 | 本方案不增加写回 |

- [archive.cpp](../../ttpcomm/src/archive.cpp)：RAR 枚举、解压及引擎锁；223–228、276–301、335–368。

## 4. 反馈 1：大 RAR 内 WAV 首播慢

### 4.0 用户补充截图后的判断

截图显示“齐豫1993-LOVE OF MY LIFE”整轨专辑包：

| 可直接读出的信息 | 对分析的意义 |
|---|---|
| WinRAR 标明 RAR 4.x | 与原版旧 RAR 解析能力范围相符；不能归因于 RAR5 不兼容 |
| 11 个文件，总解压大小 517,774,075 字节，约 493.8 MiB | 主要负担来自一个大成员，而非海量文件枚举 |
| 一个 WAV，大小栏显示约 514.9 MB，压缩后约 299.8 MB（末位被截断） | 若首播等待整个成员，就会多等待数百 MB 的解压／缓存工作；不能据截图计算耗时 |
| 一个 1,550 字节的 CUE | 多首列表曲目可能共用同一整轨 WAV；要验证子曲目复用及定位 |
| 同目录有 cover.jpg（960,768 字节）、back.jpg、disc.jpg | 当前默认 cover 命名规则可命中，外置封面同步枚举路径与样本结构吻合 |

图片强化了“普通整轨 RAR/WAV 的首播路径退化”这一调查方向。没有内嵌封面时，查找 cover.jpg 会先与音频解压争用引擎锁；即使图片很小，也不意味着这一步能立刻结束。

仍不能从截图确定：

- 是否为固实压缩、是否加密、字典大小、压缩方法或是否依赖其它卷。
- 文件列表是否按名称排序；不能把可见行顺序当作归档物理顺序。
- WAV 内部是否为 PCM、采样率／位深／声道、尾部是否有 LIST／INFO。
- CUE 的 FILE／INDEX 内容，以及反馈使用的播放器具体构建。

因此下一步样本对照应先用“RAR4＋单大 WAV＋CUE＋同目录 cover.jpg”建立受控用例，再与用户原包核对。CUE 切到后半首首次需要等待相应前缀属于另一项定位指标，不应和第一首首播混在一起。

### 4.1 直接阻塞：出声前的封面查找

[RecoveredFileSource::Open](../src/audio/audio_engine.cpp) 的 1111–1143：

1. 打开解码来源。
2. 必要时补读内置元数据。
3. 若是包内成员、没有内嵌封面，同步调用 ReadArchiveSidecarCover。
4. 完成这些工作后才返回打开成功。

ReadArchiveSidecarCover 在 archive_member.cpp:297 首先调用 ListArchiveMembers。RAR 枚举和 ExtractRar 都持有 archive.cpp 的 engine_mutex，后者持锁直至 RARProcessFileW 完成整个目标成员。

因此，**无内嵌封面、音频解压仍进行时，即使包里没有图片，封面枚举也会等到音频解压释放锁。** 这是当前源码中确定存在的首播全成员等待链。

此互斥用于保护 UnRAR 的进程全局错误状态。直接删锁或启动更多线程会引入新的并发问题；应首先将封面从播放准备的必经步骤移开。

### 4.2 WAV 播放和元数据都继续扫描尾部

对于可由内置 PCM 读取器打开的 WAV，当前 [PcmFileSource::OpenWave](../src/audio/audio_engine.cpp):833–891：

- 找到 fmt 和 data 后没有立即完成。
- 继续按 chunk 长度跳到后续 chunk，并读取后续头。
- 大 data 后若还有 LIST／INFO／JUNK，读取后续头必须等前面大数据完成解压。

[ReadWaveSource](../src/audio/builtin_file_info.cpp):1053–1103 也扫描至文件末尾，用于完整 LIST／INFO 标签；归档 PCM 打开还会经 ReadBuiltinStreamInfo 再走一次元数据读取。

边界必须说清：**只有 fmt＋data 且 data 到容器结尾的普通 WAV，不会仅因循环变量跨过 data 就主动读取全部 PCM。** 阻塞发生在实际读取其后字节时；不能把一次 Seek(END) 或 Stat 已知长度也算成全解压。

不过上一节的同步封面枚举仍可以独立造成等待，因此不能只修 WAV 循环就认为问题已解决。

### 4.3 列表信息查询强制等待最终 CRC

[file_info_worker.cpp](../src/app/file_info_worker.cpp):166–178 的 VerifyArchiveInfo：

1. Clone 流。
2. Seek 到结尾。
3. 再 Read 一个字节。
4. 查询最终归档状态。

archive_stream.cpp:179、207 对末尾读取明确要求 Task 完成。因此即使已经得到 WAV 头、时长和码率，列表查询也会等待整个成员解压与 CRC。调用包括 226、337、450 行。

这项检查原意是避免把损坏成员当成完整有效文件，不能简单删除而让坏包永远成功。建议区分：

- 播放／列表的初步头信息；
- 后台完整信息；
- 显式属性查询及最终完整性结果。

初步信息应标为待验证，并有后续成功／失败更新。

### 4.4 独立信息进程导致潜在重复解压

[player_window_playlist_info.cpp](../src/ui/player_window_playlist_info.cpp):315–331 使用独立信息会话；[file_info_probe_client.cpp](../src/ui/file_info_probe_client.cpp):309、331–395 启动／复用信息子进程。

ttpcomm 的 cached／Task 是进程内对象。因此：

- 同一进程内 Clone／同成员复用有效。
- 播放器主进程和信息子进程无法因此共享解压工作。
- 两边同时读同一大 WAV 时可能产生重复 CPU、I/O 和临时文件。
- 列表自身有缓存和单工作队列，不能夸大成“每首都无限并发”。
- 本轮未测得反馈现场实际重复次数。

### 4.5 不属于同一原因的等待

| 等待 | 是否能用本次快速首播方案直接消除 |
|---|---|
| 同步封面枚举、可延迟的尾部标签 | 可以从首播路径移走 |
| 列表全量 CRC、同成员重复信息任务 | 可以分阶段并调度／复用 |
| 加密成员最终密码与完整性验证 | 当前故意等完成；不应未经设计就放宽 |
| 固实包中目标前面的字典依赖 | 不能凭空跳过；需固实状态复用／预取 |
| 缺卷、密码交互、慢磁盘、很大字典 | 应提供明确阶段和进度，不能统称卡死 |
| 远端或受损归档 | 需要独立错误与取消处理 |

当前 Wait 的默认 30 秒是“无进展超时”，产生字节或引擎活动会刷新计时；它不是每个大包最多等待 30 秒的承诺。

### 4.6 推荐实现路径

1. **先拆出首次可播放信息。** 格式、数据位置、采样参数、首段 PCM 就绪即可进入播放；尾部标签、图片等后补。
2. **WAV 快速打开。** fmt 和首个可播放 data 已找到且边界验证成功后停止播放用扫描；保留完整标签解析用于后台／属性流程。
3. **封面异步更新。** 复用导入目录快照；图片读取不占首播关卡。结果用曲目路径、子曲目、播放代号核对，防止旧封面覆盖新歌。
4. **信息读取分阶段。** 列表先接受有明确验证状态的轻量结果；完整 CRC 最终仍要处理。主动读取文件属性可显示验证进度。
5. **播放优先调度。** 同包的信息／封面工作降级或合并；保留插件隔离。第一阶段不必重构所有进程间通信。
6. **再设计跨进程复用。** 由受控归档任务服务持有成员缓存，提供只读数据及进度／取消／最终校验协议；避免只按临时文件名共享未完成数据。
7. **最后做固实状态复用和下一曲预取。** 严格限制字典、内存、磁盘及后台预算，切歌取消不破坏仍在使用的流。

快速首播必须同时处理晚到的 CRC 错误：未完成任务不能作为“已验证缓存”发布；当前播放遇到最终错误要报告并停止，不能吞掉。CUE 子曲目在成员末尾之前结束时，也需定义后台校验和任务生命周期。

### 4.7 验收条件

分开记录：导入开始 → 列表首条出现 → 播放请求 → Reader 打开 → 首段 PCM → 首次提交设备 → 可确认的首声 → 解压／校验结束。

- 普通未加密、非固实、头部可解码大 WAV：首段 PCM 应在整个成员完成前可用。
- 不用固定“多少毫秒”代替结构验证；记录软硬件、冷／热缓存、压缩方法和文件大小。
- 对照 RAR4 原版／重建版；RAR5、7z 等作为扩展测试，不要求原版通过。
- 覆盖 data 后有／无 LIST，内嵌／外置／无封面，首／中／末成员，固实、密码、分卷、CUE 多子曲目、CRC 损坏、取消和立即切歌。
- 检查源文件摘要不变、临时文件回收、进程内存和磁盘峰值。
- 底层“前缀 Read 成功”的已有测试不足以证明播放器首播成功，必须加入完整 RoutingAudioSource 打开与出声链路。

## 5. 反馈 2：两处安装的文件关联

### 5.1 当前错误的真实含义

[file_association.cpp](../src/settings/file_association.cpp):276–298 的 InstallManagedValue：

- 读取 TTPlayer.Rebuild.Owner。
- 旧 Owner 与当前 EXE 路径不同，就主动返回 ERROR_SHARING_VIOLATION（32）。
- 60–74、94–102 行再通过 FormatMessageW 显示 Windows 的“另一个程序正在使用此文件”。

**这个分支没有打开音频文件或 EXE，也没有收到文件 API 的共享冲突；它表达的是安装归属冲突，错误码和文案选错了。**

同类人为错误 32 还用于 Win7 备份 Owner、Capabilities Owner 和固定 RegisteredApplications 名称冲突（508–510、1075–1076、1087–1088）。

### 5.2 冲突如何形成

当前使用固定 ProgID：TTPlayerRebuild.Audio.<ext>，固定 Capabilities 路径和固定注册应用名 TTPlayerRebuild；Owner 却是各安装的 EXE 完整路径。

两份安装共享名字、分属不同路径，后者自然被当成“另一程序”。现有私有测试 default_programs_tests.cpp:238–239 明确要求拒绝第二安装，说明此前只实现了防覆盖保护，尚无交接流程。

还有部分提交风险：

1. A 只有旧 ProgID／Owner，没有 Capabilities。
2. B 先登记自己的 Capabilities（1098–1103）。
3. 随后遇到 A 的 ProgID Owner 失败（1112–1127）。
4. 没有回滚，可能留下 Capabilities=B、ProgID=A。
5. 两份安装后续都可能被另一半状态拦住。

这是代码推导的风险，本轮未改注册表进行注入复现。

### 5.3 原版如何处理

| 原版函数 | 行为 |
|---|---|
| 0049B3AA | 按当前 EXE 构造打开与 /a 添加命令 |
| 0049B420 | 比较 Shell 命令是否属于当前 EXE |
| 0049BB64 | 使用共享 Audio.<ext>；备份旧默认值、写当前命令和图标 |
| 0049C3D4 | 恢复 Backup、取消关联 |
| 0049CA63／0049D8C0 | 提交勾选改变并通知 Shell |
| 0049CD41 | /unreg 先检查属于当前 EXE，再取消 |

原版没有“另一个 TTPlayer 安装目录的 Owner 就拒绝”的相同门槛，因此权限允许时新目录能接管共享关联。但它也不是双安装完全隔离：取消 B 不保证自动切回 A。

原版还处理／删除旧 Explorer 覆盖和 UserChoice。现代 Windows 默认应用必须通过用户选择机制完成，不能把旧删除策略照搬。微软旧 Default Programs 文档也明确其默认设置 API 已废弃，且该文档不适用于 Windows 10 的默认选择行为。[旧注册契约](https://learn.microsoft.com/en-us/windows/win32/shell/default-programs)、[现代默认应用平台](https://learn.microsoft.com/en-us/windows/apps/develop/windows-integration/default-apps-platform)

### 5.4 推荐方案

优先采用“一个活动关联安装、用户主动交接”：

- 归属冲突单独分类，显示旧安装路径、当前路径、具体关联项。
- 用户在关联设置里选择保留现有或使用当前安装。
- 提交前整批预检查；提交失败回滚并保留可恢复状态，正确传播已改变标志。
- 交接同时迁移命令、图标、Owner、Capabilities 和恢复记录。
- 保留最初第三方备份；A→B→A 不反复覆盖备份。
- 旧安装取消／卸载不能删除新安装已接管的值；用户后来改成其它播放器也要保留。

如果未来需要两份安装都作为系统候选，再引入稳定 install-id，统一修改 ProgID、Capabilities、注册名、Shell 动词与卸载。不要仅给 ProgID 加目录哈希，而遗漏其它共享项。

还需处理全局单实例：main.cpp:20 的 TTPlayer 身份和共享事件／映射可把 B 的启动转给正在运行的 A；关联维护命令的执行对象也要纳入测试。这与错误 32 是两个问题。

验收：A 首装／幂等登记、A→B→A、取消交接逐值不变、B 接管后 A 卸载、旧目录失效、半套状态、各阶段拒绝访问、第三方后续选择、带空格／中文路径、两安装同时运行，以及 XP／Win7 与现代系统默认应用流程。

## 6. 反馈 3：最小化时歌词弹出及隐藏时差

### 6.1 原版确实允许自动弹出

原版 0044A692（伪代码 74579 起）：

- 检查 AutoVisible、有效歌词窗口和非全屏。
- 用“歌词行数是否大于零”与“歌词实际是否显示”比较。
- 不一致时投递 WM_COMMAND 0x7D64。
- **没有检查主窗口最小化或隐藏到托盘。**

后续 004A3ACF → 0044A8AB → 0044E2FB 会显示歌词窗口。主窗口的 IsIconic 检查不是显示前的阻止条件。

这说明反馈是原版也可能具有的交互缺陷。关闭自动显隐能避开它，并不说明行为就没有改进必要。

加载来源也不只“下一首”：内嵌、关联、本地异步消息 0x7F1、在线消息 0x7F2 都能到达自动显隐决策。

### 6.2 当前仍有缺口，并额外漏了全屏保护

[player_window_lyrics.cpp](../src/ui/player_window_lyrics.cpp):4414–4427：

- 直接设置 ActiveLyricVisible。
- 窗口模式直接 ShowWindow(SW_SHOWNOACTIVATE) 后 BringWindowToTop。
- 没有最小化／托盘／fullscreen_mode_ 门控。
- 没有经过统一 SetSkinWindowVisible 处理。

已有异步结果 path＋subtrack 检查能避免旧歌覆盖新歌，但不能防止当前歌在最小化时弹出。

此前桌面歌词恢复修复主要处理 desktop_lyric_mode_。私有 desktop_minimize_tests.inc:16、desktop_position_tests.inc:9 明确关闭 auto_visible，因此历史通过不能覆盖此反馈。

### 6.3 不能把所有歌词都随最小化隐藏

原版 004615A6 保存最小化前可见状态；0046162B 在最小化后，若原本可见且“普通／迷你歌词置顶，或桌面歌词”，投递 0x7D64/-2 重新显示。

建议策略：

| 状态 | 自动加载新歌词时 |
|---|---|
| 主窗正常、普通窗口歌词 | 按有／无歌词应用自动显隐 |
| 主窗最小化／托盘、普通非置顶歌词 | 只更新期望状态，不把窗口弹出 |
| 主窗最小化、已启用桌面歌词 | 保持桌面歌词独立行为 |
| 主窗最小化、普通置顶歌词 | 保留原版的独立显示语义 |
| 全屏 | 更新内容和期望状态，退出后统一恢复 |
| 关闭中／过期请求 | 不再显示窗口 |

建议将“内容决定是否需要歌词”和“当前模式允许显示哪个窗口”分开，通过一个幂等同步函数收敛。恢复时使用最新状态，不能只回放进入全屏／最小化前的旧快照。继续保持桌面／窗口歌词互斥、普通／迷你位置及吸附状态。

原版自动逻辑投递的是切换命令，排队后可能状态已改变；当前“设目标状态”的方向值得保留，无需照搬切换竞态。

### 6.4 各窗口消失略有时差

原版包含默认 owner 最小化、WM_SIZE 后排队重显、各窗口独立 alpha 过渡；当前也有主窗最小化后隐藏、桌面控制层和绘制层独立显隐。它们没有同一合成帧同时消失的保证。

是否存在明显长延迟或闪烁，需要记录 WM_SYSCOMMAND／WM_SIZE／WM_SHOWWINDOW、alpha 过渡和帧时间。不能仅凭文字反馈认定是系统问题或给出毫秒数。

先修自动显隐，再测量隐藏时序；如确有长拖尾，再统一需要一起隐藏的普通窗口过渡。桌面歌词和置顶歌词不能被误归入统一隐藏。

验收覆盖：所有最小化入口、普通／迷你、窗口／置顶／桌面、有→无／无→有、本地与在线延迟结果、搜索中恢复、编辑器、全屏、淡化开启／关闭、XP、Win7 Aero 开／关和 Windows 11。

原版对照入口：

- 004E1C87：ASIO 注册目录。
- 004E207B：ASIO 激活、初始化和能力查询。

### 7.2 ASIO 明确差异

| 差异 | 当前位置 | 后果／建议 |
|---|---|---|
| 特殊驱动激活缺回退 | asio_sink.cpp:79–94 | 原版 ASIO Kernel-Streaming driver 工厂失败后还尝试直接 DllGetClassObject(CLSID, CLSID)，再回到 COM；当前直接失败 |

### 7.3 KS 明确问题与兼容性差异

| 问题 | 当前位置 | 后果／建议 |
|---|---|---|
| deadline=0 被直接判超时 | output_devices.cpp:551；调用 812 | 详情查询进入 pin 循环即失败；零值应沿用默认单次等待语义 |
| 只接受完全匹配的三个格式 GUID | output_devices.cpp:584–588 | 原版允许 GUID_NULL 通配；可用设备可能在目录层就被排除 |
| topology-nodes 查询失败否决整个设备 | output_devices.cpp:621–622 | 可选音量／节点能力不应必然阻断已可用 PCM pin |
| 多声道 mask 只实现 1／2 声道 | kernel_streaming_sink.cpp:233–234 | 原版还给出 4=0x33、6=0x3F、8=0xFF；应结合源布局生成 |
| 枚举 3 秒总预算＋按成功结果顺序编号 | output_devices.cpp:659 起；audio_engine.cpp:2988 | 某设备慢／消失后，旧序号可能对应别的设备；应迁移到稳定物理身份 |

KS 零 deadline 是详情查询的确定错误，**不能单独用它解释所有播放失败**，因为播放重新枚举使用非零期限。topology 失败兼容建议也不等于已证明原版在所有错误码下都接受设备。

声道 mask 决定实际位置和顺序，不能仅靠声道数随意填值；优先保留源布局，并在无布局时使用明确兼容表。[微软 WAVEFORMATEXTENSIBLE](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ksmedia/ns-ksmedia-waveformatextensible)

### 7.4 需要保留的环境边界

- 播放器为 x86，必须能加载 x86 ASIO DLL；读取到 x64 注册信息也不能直接加载 x64 DLL。[微软 WOW64 进程说明](https://learn.microsoft.com/en-us/windows/win32/winprog64/running-32-bit-applications)
- 设备占用、外部时钟、固定采样率、缺驱动依赖、特定驱动线程要求，均需真实返回码。
- 当前 KS streaming pin 实现不等于所有 WaveRT 路径都已覆盖。
- VirtualBox 能验证旧系统 API、受控设备／模拟接口和生命周期，不能替代用户实体 ASIO／KS 声卡的发声证明。
- 不建议所选输出失败后静默换 WaveOut；应明确失败阶段，并由用户决定切换。

### 7.5 推荐实现和测试

先保留具体错误码、阶段、CLSID／设备路径、请求／实际格式；再依次修激活链、输出声道数限制、采样率条件、KS deadline、ASIO 预填／耗尽、KS 范围与布局，最后补稳定身份和回调协商。

受控测试包括：

- 工厂失败但直接导出成功；特殊路径失败但 COM 成功。
- 128 输出设备播放双声道；CanSampleRate=false 但 SetSampleRate=true；真正不支持的采样率。
- 首次回调、短于一周期、刚好一周期、尾部不满周期、暂停／定位重启、停止时同步回调。
- KS 默认期限、精确／通配范围、缺可选 topology、16 位回退、多声道 mask。
- 枚举前方设备超时／消失后，不把配置静默指到另一设备。

实机对照应固定同一声卡／驱动，比较原版与重建版在 44.1／48／96 kHz、16／24／32 位、单／双／多声道、播放／暂停／定位／EOF／拔出的行为和错误码。
