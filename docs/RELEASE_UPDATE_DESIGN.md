# 基于 GitHub / Gitee Releases 的更新方案分析

分析日期：2026-09-25。本文是设计与可行性分析，尚未实现新的在线检查、下载或安装功能。

## 1. 结论

可以采用，而且适合目前的日期版本号和双版本 ZIP 发行方式。

建议保留原版的检查周期、手动检查和更新提示交互，重新实现数据源与安装器：

1. 查询 GitHub / Gitee 已发布 Release 的 `tag_name`。
2. 按现有构建规则解析为年、月、日、修订号，与正在运行的重建版比较。
3. 确认对应版本分支的 ZIP 和校验文件已经上传完成，再提示更新。
4. 提供“查看发行页面”和“下载并安装”两个入口。
5. 下载、校验完成后，由独立更新器等待播放器退出，备份、替换文件并重新启动。

Tag 可以作为发现入口，但单独的 Tag 不代表存在可安装的更新。当前 Actions 发布的 ZIP 是重建版 EXE 的增量发行包，仍需要原版 5.7.9 的运行依赖；新更新器应按这个范围更新。

## 2. 当前工程已经具备什么

| 位置 | 已确认行为 | 新方案中的用途 |
| --- | --- | --- |
| `cmake/version.ps1` | 接受 `yyyy.MM.dd` 和 `yyyy.MM.ddpN`，检查真实日期；修订号不能超过 65535 | 作为唯一的版本格式依据 |
| `cmake/resolve_release_version.ps1` | 根据已有 Tag / Release 分配同一天的修订号 | 沿用现有版本分配方式 |
| `src/app/version.rc.in` | 字符串版本写入日期版本；固定数值版本为年、月、日、修订号 | 读取本机版本，不必从窗口标题或文件名猜测 |
| `.github/workflows/manual-build.yml` | 同一构建生成普通版和 XP / Win7 版 ZIP，支持发布 GitHub、Gitee | 沿用发行来源和附件命名 |
| `include/ttplayer/settings/settings.h` | 默认每 7 天检查，保留检查日期等设置 | 恢复后台检查调度 |
| `src/ui/player_window_options.cpp:6968` | “立即检查”按钮发送 `WM_TIMER`，ID 13 | 改接新的检查服务 |
| `src/ui/player_window.cpp:3198` | 主窗口定时器分支未处理 ID 13 | 当前按钮尚未接通真正的更新检查 |
| `src/lyrics/lyric_http.cpp` | 已有 WinHTTP、代理、超时及取消处理 | 可提取通用网络基础，但不能直接当 ZIP 下载器 |
| `src/skin/skin_package.cpp:135` | ZIP 解压依赖 `ttpcomm.dll` 的 80 / 81 / 82 号导出 | 独立更新器需要自己的解压实现 |

注意：`CMakeLists.txt` 的 `project(... VERSION 0.1.0)` 是工程版本，不能用于更新比较。原版 `TTPlayer.exe` 的 5.7.9.0 也不能作为重建版的当前版本。

现有歌词 HTTP 实现只接受 HTTP 200，将响应放在内存中，限制 2 MiB；旧系统上不支持重定向策略时还会关闭自动重定向。Release API 的缓存响应和下载站的跨域重定向都需要额外处理。

## 3. 与原版更新链路的关系

详见 [原版 Updater.exe 分析](ORIGINAL_UPDATER_ANALYSIS.md)。原版链路的业务分工可以借鉴，协议和安装方式需要更换。

| 原版行为 | 建议的新行为 |
| --- | --- |
| 主程序按周期或用户操作启动检查线程 | 沿用周期设置，新增统一的异步检查服务 |
| 解析旧服务器响应，生成本地更新任务 | 将两个平台的 Release 响应转换为统一的更新描述 |
| Updater 读取 `setuppackinfo`，下载 EXE 安装包 | 下载当前版本分支的 ZIP，在本地完成替换 |
| 安装前比较 MD5 | 下载后检查 ZIP SHA-256、包内 EXE SHA-256 和版本身份 |
| 启动下载得到的 EXE，由该 EXE 安装 | 新更新器直接负责备份、替换、恢复与重启 |
| 使用旧的命名事件协调 | 使用真实进程句柄等待退出，并以一次性会话握手协调 |

旧事件在主程序启动时就会置位，不能证明主程序已经退出。旧 Updater 也没有完成 ZIP 安装事务的代码。因此不适合只替换下载地址后继续使用原二进制。

## 4. 版本号应怎样转成数字

### 4.1 与 Actions 使用同一语法

```text
2026.09.25       -> (2026, 9, 25, 0)
2026.09.25p1     -> (2026, 9, 25, 1)
2026.09.25p10    -> (2026, 9, 25, 10)
2026.09.26       -> (2026, 9, 26, 0)
```

规则为 `^[0-9]{4}\.[0-9]{2}\.[0-9]{2}(p[1-9][0-9]*)?$`，另做日历日期、整数溢出和修订号上限校验。没有 `pN` 时修订号为 0。`p0`、`p01`、不存在的日期以及超过 65535 的修订号都拒绝。

目前构建不生成 `v` 前缀，不应擅自将任意带前缀的标签都视为本产品版本。若以后兼容 `v2026.09.25`，应同时调整构建端和客户端规范。

### 4.2 比较方式

优先比较四个整数的元组；如果需要单个数字，用无符号 64 位值：

```cpp
uint64_t key = (uint64_t(year)  << 48)
             | (uint64_t(month) << 32)
             | (uint64_t(day)   << 16)
             | uint64_t(patch);
```

每段在校验后占 16 位，与 Windows 固定版本资源的四段布局对应。C++ 必须先转换成 64 位再移位。若经过 JSON 传递，优先保存原始版本字符串和分段值，不依赖 JavaScript 数字承载完整的 64 位范围。

| 比较 | 结果 |
| --- | --- |
| `2026.09.25` 与 `2026.09.25p1` | 后者更新 |
| `2026.09.25p2` 与 `2026.09.25p10` | 后者更新 |
| `2026.09.25p65535` 与 `2026.09.26` | 后者更新 |
| 本机与远端都是 `2026.09.25p1` | 不提示升级 |
| 远端版本比本机旧 | 不自动降级 |
| `2026.02.30` 或 `2026.09.25p65536` | 无效，不能安装 |

不能直接比较字符串、转浮点数或删除所有标点再转整数。删除标点会让修订号改变位数，甚至使较早日期的修订版大于下一天的版本。

本机版本应读正在运行的重建版 EXE 固定版本资源，或使用同源生成的编译期数据。若本地开发版本无法解析，应显示无法比较，而不是默认当成版本 0。

只构建、不发布的同一天产物可能有相同日期版本；版本比较无法区分它们。正式发行应保持一个版本对应一组固定文件，重发修改后的二进制时分配新的 `pN`。

## 5. 应获取 Tag 还是 Release

建议直接读取 Release 列表中的 `tag_name`。GitHub 的 Releases API 与普通 Git Tag 列表是不同资源；Release 带有附件、预发布标记和发行页面地址。[GitHub 官方文档](https://docs.github.com/en/rest/releases/releases)

如果从 `/tags` 开始，也必须再按 Tag 查找对应 Release，并检查可安装附件。因此会增加请求次数，不能省掉 Release 查询。

候选版本的处理顺序：

1. 只查询预设的 `Sonic853/TTPlayer` 仓库。
2. 过滤草稿和预发布版本；平台未提供的标记不要臆造同等语义。
3. 严格解析标签，按四段数字排序，不依赖接口返回顺序。
4. 确认对应分支、架构和系统要求匹配。
5. 确认目标 ZIP 与外层 `SHA256SUMS.txt` 存在、无同名歧义且大小合理。
6. 提示其中最新且完整的版本。

`/releases/latest` 可以用于快速探测，但不能作为本项目“数值版本最大”的证明。需要按本项目规则检查结果，列表查询也必须处理分页；未读完且无法证明完整时，不应显示“已是最新版本”。GitHub 的分页优先遵循 `Link` 响应头。

### GitHub 适配

```text
GET https://api.github.com/repos/Sonic853/TTPlayer/releases?per_page=100
GET https://api.github.com/repos/Sonic853/TTPlayer/releases/tags/{tag}
```

使用 Release 的 `html_url` 跳转，用附件的 `name`、`size`、`state` 和 `browser_download_url` 选择文件。`digest` 存在时可以交叉检查，但不能要求所有历史附件都包含它。

不要下载 `zipball_url`：它是仓库源码归档，不是 `TTPlayerRebuild-版本号.zip` 二进制发行包。[GitHub Release 字段定义](https://docs.github.com/en/rest/releases/releases)

### Gitee 适配

```text
GET https://gitee.com/api/v5/repos/Sonic853/TTPlayer/releases
GET https://gitee.com/api/v5/repos/Sonic853/TTPlayer/releases/tags/{tag}
GET https://gitee.com/api/v5/repos/Sonic853/TTPlayer/releases/{id}/attach_files
GET https://gitee.com/api/v5/repos/Sonic853/TTPlayer/releases/{id}/attach_files/{asset_id}/download
```

Gitee 使用 `attach_files` 附件接口，不能直接套用 GitHub 的 `assets` API。公开读取在其接口定义中不强制提供令牌；具体仓库的匿名读取与下载仍须实测。[Gitee 官方 API 入口](https://gitee.com/api/v5/swagger)

本地已有 `out/gitee-release-cli-review/docs/gitee-api-snapshot.json`，记录 2026-09-17 获取的官方 Swagger 5.4.93。其 `Release.assets` 静态类型与该目录分析记录中的实际响应有差异，新客户端应验证用到的字段，必要时调用专用附件列表接口，不能照搬不准确的静态类型。

### 双来源策略

建议设置 GitHub / Gitee 首选来源，连接失败或限流时尝试备用来源。镜像同步有时间差，不把两个平台的文件随意拼成一份更新。

同一版本应由同一次 CI 构建的相同文件分发到两个平台。跨源切换下载时必须匹配已确定的 ZIP 摘要；同版本摘要不一致就停止安装并提示来源不一致。部分下载只有在资源身份、长度和范围响应均验证后才能续传，否则重新下载。

当前发布任务已经能把同一组产物上传到两个平台，可沿用这一点。

## 6. 后台检查与提示

保留现有“不检查 / 每天 / 每周 / 每月”设置，默认每周。启动稳定后再发起到期检查，网络工作放在后台线程，通过窗口消息返回结果。重复点击手动检查应复用正在进行的任务。

建议区分三个状态：检查成功且有新版、检查成功且无新版、检查失败。离线、TLS 失败、限流、响应损坏都不能显示“已是最新”。自动检查失败安静退避，手动检查显示具体原因。

检查成功的日期与失败重试时间分开记录，防止一次网络失败让一整周不再检查；也防止每次启动都立即重试。关闭自动检查不影响用户手动检查。

提示显示当前版本、新版本、普通版或 XP / Win7 版、更新摘要，提供：

- **查看发行页面**：打开检测到的具体版本页。
- **下载并安装**：下载期间继续播放，校验后再请求退出播放器。
- **稍后提醒**：本次关闭，不修改检查周期。
- 可选“跳过此版本”：只跳过这一个版本；与永久关闭检查分开保存。

GitHub 公开 API 匿名请求的主限额为每 IP 每小时 60 次，共用出口的用户会共享额度。客户端应缓存元数据、尊重限流响应并控制分页请求；不能把 CI 的访问令牌编进播放器。[GitHub 限流说明](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)

可使用 ETag / Last-Modified 条件请求减少传输，但不能声称匿名的 304 响应不计额度：GitHub 文档的豁免条件包含正确的 Authorization 认证。[条件请求说明](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api)

## 7. ZIP 应如何选取和校验

| 当前运行分支 | 目标附件 |
| --- | --- |
| 普通版 | `TTPlayerRebuild-<版本>.zip` |
| XP / Win7 版 | `TTPlayerRebuild-XP-Win7-<版本>.zip` |

以程序自身的构建分支为主，再检查操作系统是否允许。用户在 Windows 11 上运行 XP / Win7 版，也应默认继续更新该分支；不能仅根据当前 Windows 版本偷偷切换发行类型。当前是 x86，未来增加架构时需要明确的架构字段。

现有校验层次要区分：

1. Release 附件中的 `SHA256SUMS.txt` 记录两个 ZIP 的 SHA-256。
2. ZIP 内部同名文件记录 `TTPlayerRebuild.exe` 的 SHA-256。
3. 解压后的 EXE 固定版本必须等于所选 Tag，产品与构建分支也必须匹配。

先验证整个 ZIP，再受限解压、验证 EXE。只验证包内自带的摘要无法证明下载包本身可信；同一来源的摘要也不等于发布者签名。自动安装正式启用时建议增加签名更新清单，并把验证公钥随程序分发，私钥仅留在发布端。

解压只允许清单中的固定文件；拒绝绝对路径、`..`、盘符、备用数据流、重复或大小写冲突的名称，以及越界链接。限制文件数量、总解压大小和压缩方法。ZIP 中其他文件不能获得任意安装或执行权限。

目前只应更新重建版 EXE，不覆盖原版 `TTPlayer.exe`、`ttpres.dll`、`ttpcomm.dll`、`AddIn`、皮肤、歌词、配置和播放列表。`ttp_aac` 是独立项目与发行链路，不能混入这次播放器升级。

## 8. 新更新器的安装流程

```text
检查版本 → 用户选择 → 下载到临时文件 → 验证 ZIP → 解压并验证 EXE
    → 准备更新器并握手 → 保存播放器状态 → 真正退出播放器
    → 等待进程结束 → 备份旧文件 → 替换 → 启动新版 → 确认成功
```

### 下载与准备

- 使用流式下载写入 `.part` 文件，支持取消、超时与明确进度；小型 EXE 更新包没有必要采用多连接分段下载。
- 允许下载服务必要的 HTTPS 重定向，逐跳校验，不接受降级 HTTP，不把认证信息转发给不相关主机。
- 下载和校验期间保持播放器可用。更新器能够启动、目标路径与空间检查通过、任务握手完成之后，才进入退出阶段。
- 更新器使用绝对路径和可靠的参数编码，不能把文件路径拼成 shell 命令。

### 等待退出

更新器应在播放器仍存活时取得目标进程句柄，并验证进程路径和会话身份。随后等待该句柄结束，避免只靠 PID 导致进程复用误判，也避免只等窗口消失。

当前关闭设置可能将 `WM_CLOSE` 变成隐藏到系统栏；更新必须走已有显式退出语义或专用退出原因，完成歌词、选项和播放列表保存。退出被用户取消时保留已下载包，不替换文件。

同一路径还有其他播放器实例或进程占用文件时，应等待或提示重试，不强杀进程。原版命名事件不能作为退出证明。

### 替换、恢复与重启

1. 将已验证的新文件准备到目标目录所在卷，再次确认目标目录和暂存路径。
2. 写入更新事务记录，保留旧 EXE 的可恢复备份。
3. 在文件不再被占用后替换，失败时恢复旧文件；多文件升级不能假设一次重命名能保证整批原子性。
4. 从安装目录启动新版，在单实例初始化及必要配置加载完成后发送成功握手。
5. `CreateProcess` 成功仅表示进程创建成功，不能当作升级已完成。明确启动失败时恢复旧版；仅握手超时而新版仍运行时保留备份并提供恢复选项，不直接强杀。
6. 中途断电后根据事务记录恢复；成功确认后清理已知临时文件，保留必要日志。

安装目录不可写时，可以在用户点击安装后通过系统机制请求所需权限；拒绝提升就终止安装并保留原程序。若使用提升权限的辅助进程，应让新版回到原用户权限运行，避免播放器以后都以管理员权限启动。

更新器必须在受控的临时位置运行，避免自身被覆盖时锁定。也不能在提升权限后直接信任普通权限进程可修改的 ZIP、清单或路径；应用阶段须重新验证并使用受保护的暂存目录。

## 9. 是否需要单独分发 Updater.exe

建议新增独立 C++ 构建目标，例如 `TTPlayerUpdater.exe`，对话框可使用现有 WTL 10.01 / Win32 基础。它应有自己的资源、ZIP 解压与校验实现，不能依赖播放器或原版 DLL。

有两种分发方式：

| 方式 | 优点 | 代价 |
| --- | --- | --- |
| ZIP 中增加独立更新器 | 主程序不携带更新器资源，调试直接 | ZIP 内容增加；以后还要处理更新器自身版本与首次补装 |
| 更新器嵌入主程序资源，需要时释放到临时目录 | 可以保留当前 ZIP 只有 EXE 和摘要的布局；首次更新就有可用安装器 | 主 EXE 会增大，构建需先生成更新器再嵌入 |

结合当前精简发行包，推荐第二种。更新器与主程序共用生成的版本数据，避免循环构建依赖；普通版和旧系统版各自嵌入兼容的更新器。具体体积应在实现后比较，当前没有新增构建体积测量结果。

离线安装也可以使用同一安装引擎：由播放器选择本地 ZIP 并完成验证后调用临时更新器。签名清单应能随包离线提供；没有可信清单的历史包只能明确作为用户手动选择的旧包处理，不能冒充已认证的在线更新。

## 10. XP / Win7 的关键边界

**程序可执行兼容性与 HTTPS 兼容性是两个问题。** YY-Thunks / VC-LTL 等兼容构建不能自动补全旧系统的 TLS 协议、密码套件或证书链。

| 系统 | 推荐路径 | 必须确认的条件 |
| --- | --- | --- |
| Windows 10 / 11 | 原生 WinHTTP 检查和下载，独立更新器安装 | API、附件重定向与代理行为 |
| Windows 7 | 显式启用可用的 TLS 1.2，提供失败后的网页和本地包入口 | 补丁、证书、站点密码套件以及实际虚拟机连通性 |
| 原生 Windows XP | 首期保证更新器和离线 ZIP 安装可运行；在线能力单独解决 | 不能假设系统 WinHTTP 能访问现代 HTTPS 服务 |

Microsoft 文档说明 WinHTTP 默认安全协议随系统与补丁变化，Windows 7 的默认值不等于已启用 TLS 1.2。工程现有歌词 HTTP 已显式设置 TLS 1.2，因此不能笼统地说所有 Win7 都必须改注册表；应检查实际错误。[WinHTTP 协议选项](https://learn.microsoft.com/en-us/windows/win32/winhttp/option-flags)

XP 上即使存在移植补丁或特殊系统镜像，也不能将其作为普通 XP 的保证。Microsoft 的相关 TLS 1.1 / 1.2 WinHTTP 补丁文档指定的是 Windows Embedded POSReady 2009 / Standard 2009，不能把它当作所有 XP 安装的现成功能。[Microsoft 补丁适用范围](https://support.microsoft.com/en-us/topic/update-to-enable-tls-1-1-and-tls-1-2-as-secure-protocols-in-winhttp-on-windows-embedded-posready-2009-and-windows-embedded-standard-2009-f51ec93b-9988-7ac6-98a1-b8968c40ab7f)

如果要求 XP 也完整支持自动检查与下载，需要另外选择并实测可在 XP 编译运行的 TLS 实现，包含证书验证和维护方案。可将网络实现放入辅助进程，控制对播放器体积和依赖的影响；不能通过忽略证书错误解决。

打开 Release 页面由默认浏览器完成，但旧浏览器同样可能打不开现代网站。如果 XP 无法查询接口，客户端只能提供手动页面入口或本地包安装，不能声称仍能自动判断有无新版。

旧系统更新器应复用现有已验证的兼容构建体系，并做导入表审计；不依赖 PowerShell、.NET 或系统图形界面的 ZIP 解压功能。

## 11. Actions 需要怎样配合

### 首期：提示和网页跳转

可继续使用现有两个 ZIP 和外层 SHA256SUMS 布局。客户端严格检查附件完整性即可，不需要维护独立更新服务器。

当前 GitHub 发布没有显式采用“草稿上传完成后再公开”的流程；Gitee 则先创建 Release 再依次上传附件。客户端不能在看到 Tag 或刚创建的 Release 时就认定可以安装。

### 后续：自动安装

建议增加版本化的 `update-manifest.json`，描述产品、版本、分支、架构、系统要求、最小更新器协议、ZIP 名称、大小与摘要；可加独立签名。

- 清单中的文件名必须来自这次 CI 的已验证产物，不根据网页正文推断。
- ZIP、摘要和清单全部生成后再发布；支持草稿的平台最后公开。
- 不适合草稿发布的平台先上传数据文件，最后上传完整性标记，例如签名文件；新客户端要求整组材料完整。
- 两个平台使用同一份产物、清单和签名，不各自重新打包。
- 保留现有日期和 `pN` 分配逻辑；已发布版本不覆盖，修复后生成更大的版本号。
- 测试仍保留在本地 `tests` 中，发行 Actions 不执行测试，不上传测试代码。

清单和签名属于建议新增的发行附件，尚未修改当前工作流。若要严格维持仅三个外层附件，需要另行约定把清单与签名封装进现有附件的格式，不能默默破坏已有 SHA256SUMS 消费者。

## 12. 建议实施顺序与验收

1. **版本解析与 Release 检查**：补齐手动按钮和检查周期，支持两个来源、正确排序、分页、错误状态和网页跳转。
2. **ZIP 下载与校验**：正确选取普通版 / 旧系统版，复用代理设置，下载不阻塞播放；损坏包、错误版本、同名附件一律不能进入安装。
3. **独立更新器**：完成正常退出、文件替换、失败恢复、启动确认和本地包安装。
4. **发布协议完善**：加入清单、签名与发布完成约定，处理更新器协议演进。
5. **XP 在线能力**：根据真实虚拟机的 TLS 测试选择网络实现，不能以普通版联网成功替代旧系统验收。

第 3 阶段可在本地验证安装引擎；对外正式启用在线自动安装前，应完成第 4 阶段的包身份与发布协议验证。

必要的本地验收包括：`p2/p10` 与跨日比较、非法日期、尚未上传完的 Release、镜像延迟、403/429、取消下载、截断包、错分支、ZIP 路径越界、托盘关闭模式、歌词未保存、文件占用、不可写目录、安装中断、重启失败、XP / Win7 / 现代 Windows 的不同网络条件。

本次完成了代码、构建脚本、原版分析和官方接口资料的核对，没有执行发布、下载更新包、替换程序或虚拟机升级。当前环境直接访问项目公开 API 时受到网络限制，尚未实测两个仓库的匿名附件下载，也不能据此承诺特定 XP / Win7 镜像可以联网更新。
