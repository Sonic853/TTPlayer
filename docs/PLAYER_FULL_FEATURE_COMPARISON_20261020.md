# TTPlayer 5.7.9 与当前重建版：全功能对照、剩余差异与改进顺序

日期：2026-10-20。性质：**只读审计＋私有针对性验证**。本轮没有修复生产代码、替换发行包、提交 Git 或改动用户文件。

后续实施见：[修复与验收记录](PLAYER_FULL_FEATURE_FIXES_20261020.md)。下文保留审计时的状态，修复后的结果及剩余边界以该记录为准。

## 1. 结论和阅读顺序

重建版已经覆盖原版播放器的大部分主要用户流程：播放／输出、列表／媒体库、歌词／编辑器、标签／封面、转换／增益、皮肤／窗口、网络缓存／下载和系统关联均有实际实现。当前不适合再用“界面已恢复、后台基本没做”描述，但也**不能认定全功能完全等价**。

这次不是把上一轮缺口再列一遍。已以当前提交重新核对，确认原来的 G01–G15、内置 MPEG Decoder、格式纠错及 RAR/CUE 任务交接等修复已经进入当前树。新发现的问题主要有三类：

1. **格式和缓冲状态的边界错误**：扩展 PCM 结构被切片；恢复播放需要的缓冲量在部分状态下永远不可达；普通定位少了原版的前缀 PCM 丢弃。
2. **操作成功但状态发布不完整**：媒体库、编号列表、独立播放队列、打开曲目和歌词关联仍有不同更新入口。
3. **已有 UI 或配置没有完整兑现**：M3U 相对路径、手动读取内嵌歌词后的自动显隐、下载时同步歌词，以及部分旧 Decoder／设备控制能力。

优先修复前两类，再补明确缺少的能力。音乐窗继续按用户要求暂不恢复；压缩包继续只读；Winamp 经典 16 位桥、用户指定随机策略和进度松开提交，不作为需要撤回的缺陷。

### 三个例子说明为什么需要修复

**扩展 PCM 不是损坏音频。** `WAVEFORMATEXTENSIBLE` 的基础部分是 18 字节，后面还有扩展字段。当前局部值只保存了基础部分，标志却仍说明扩展存在。正确办法是携带完整格式，不能简单清掉 `cbSize` 来掩盖越界。

**缓冲“还有空位”不代表能继续填。** 2 秒缓冲分成 4 个 500ms 块；低水停止时剩 80ms。恢复后最多再装 3 块，得到 `80+3×500=1580ms`，仍低于 1600ms 的恢复水位；下一整块又装不下。设备已停止，残余也不会继续消耗。这是本轮模型证明的状态，不声称已在真实声卡上重现。

**写盘成功不等于所有窗口和队列已更新。** 原版常共享同一个歌曲对象；重建版多个容器持有 Track 值副本。值副本可以保留，但每个成功修改入口必须发布到相同歌曲的所有消费者。前一轮属性窗口已接入发布，不代表本轮发现的歌词、监视和 RG 入口也自动接上。

## 8. 哪些代码值得简化

建议以修复已经发现的分叉为目的。当前已经共用的 PCM 效果、PlaybackOptions、格式目录、JSON、HTTPS 加载、逻辑来源收集不要再平行实现一套。

| 可简化点 | 当前重复／遗漏的实际后果 | 最小改进路径 | 适合放哪里 |
| --- | --- | --- | --- |
| 元数据成功发布 | 属性已同步，歌词、监视、RG 路径仍各改几个容器 | 补齐现有 PublishTrackMetadata 调用；逐步明确字段差量、删除标记、版本、CUE/归档身份 | 播放器的歌曲／列表业务层；不放 ttpcomm UI 回调 |
| 文件名迁移 | 错后缀改名有配套处理，普通重命名漏 RLL | 共用迁移计划：旧／新身份、所有列表、opened、library、关联、缓存 | 播放器文件操作层 |
| 保存结果聚合 | XML/list 反馈与 RLL dirty 状态脱节 | 返回逐项 SaveResult，失败只清成功项，退出可重试 | 播放器持久化协调层 |
| 用户导出写入 | XML 未检查最终写结果，XML/M3U 先截断已有目标 | 共用临时文件、完整写入／flush 检查与替换，保留旧目标 | core 文件工具；配置格式和提示仍属宿主 |
| 队列记录持久化 | 唯一 saver 被 worker0 下载阻塞，落盘前清 dirty | 按代数快照，成功提交才确认；独立调度保存和失败退避 | 下载队列记录层；继续复用当前共享缓存任务 |
| 完整 PCM 格式对象 | WAVEFORMATEX 值复制容易丢扩展 | 完整字节所有者或明确借用 view，统一规范化子类型／有效位／声道 | 可复用格式工具放 ttpcomm SDK；对象生命周期仍由宿主管理 |
| 精确定位 | CUE 自己裁前缀，普通播放只记录位置 | 公共 decoded source 位置调整和帧对齐；effect 前完成 | 音频 source 层，避免 CUE 双裁剪 |
| 音频缓冲恢复 | DS 和 WAVE/native 两条分支复制阈值，粒度不同 | 共用可达阈值和填充进展合同；设备队列仍独立 | 音频协调层；不把不同设备硬塞进同一传输模型 |
| MPEG 头读取 | 格式探测、HTTP、mp3PRO 有相同位域处理但不同准入规则 | 共用纯 header parser，保留强探测、直播、增强识别各自政策 | ttpcomm／audio 的纯数据工具 |
| 选项和菜单动态能力 | 静态资源相同，但有的旧配置没有消费者 | 给选项和菜单登记可用能力与目标命令；无后端就明确禁用 | UI 层；先处理实际无效项，不重写全部 15 页 |
| 热路径皮肤区域 | 主窗绘制／命中复建区域，代码已正确区分两种顺序 | **先测性能**；可按皮肤代数／尺寸／图像帧缓存不可变几何，动态 LED／play 状态正确失效 | 皮肤层；不得为了缓存把 paint/hit 顺序合并 |
| 历史文档 | 相同功能有“分析—修复—再次回归”多份记录，旧缺口容易被当现状 | 加统一当前状态索引，保留历史日期与哈希，不篡改过去失败记录 | docs |

不建议为“减少代码行数”合并所有异步线程／取消对象，或把 PlayerWindow 整体移入 ttpcomm。通用 DLL 适合稳定的字节流、格式、数学和 ABI 服务；曲目身份、用户意图、窗口和配置属于宿主。

## 9. 建议修复顺序与验收标准

### 第一批：内存正确性和保存可靠性

1. 修 RG 的完整 PCM 格式生命周期。用 EXTENSIBLE 整数／浮点、多声道，以及 Reader 和系统 source 两条路径验证。
2. 将 RLL 保存纳入整体保存结果。私有文件只读、共享占用、目录不可写、解除占用后重试；确认退出不会静默丢修改。
3. 修 DS／WASAPI 的可达恢复水位。先状态模型与模拟消费端，再真实端点；同时覆盖 EOF、暂停、取消，不能只加超时重开掩盖状态矛盾。

同批补 XML/M3U 用户导出的完整写入检查和旧目标保全（D08）。该项为 P2，但与保存错误反馈相邻，适合一起验收；用私有目标做磁盘满／短写／替换失败注入。

### 第二批：统一成功发布和路径迁移

4. 内嵌歌词写／删、媒体库监视、手动／自动 RG 的完成入口统一发布。
5. 普通重命名迁移显式歌词关联。验证非当前歌曲、多列表、无歌词标记、改名失败和目标冲突。
6. 手动读取内嵌歌词后汇合到文档／可见性入口；保持最小化、托盘、桌面与普通／迷你模式的互斥规则。

验收时至少有两份编号列表＋独立媒体库播放队列＋opened 快照；媒体库开／关、停止／播放分别检查。不能只验证当前可见行。

同时实测 CUE 整碟字段对其它列表子轨的传播（W01）。若确认缺口，按物理来源＋整碟影响范围发布，不把单曲身份和整碟身份混为一项。

### 第三批：定位、导出与 Decoder 覆盖

7. 普通 Seek 根据 Reader 实际回写位置裁前缀，首个输出样本与顺序解码目标位置比较；明确更晚定位、未知实际位置和 CUE 内层策略。
8. M3U/M3U8 相对路径接入配置；验证同目录、子目录、不同盘符、中文编码，确认关闭选项仍输出绝对路径。
9. 恢复通用 ACM Decoder，再量化本地 MPEG 系统 Reader 与原版 Reader 的差异；保留可用后备直到替代路径通过。

### 第四批：下载持久化、产品能力和扩大验证

10. 补队列独立保存和成功提交后确认代数（D05）；用慢 HTTP 服务验证下载期间新增／取消／完成状态能落盘，失败解除后能重试。正常退出已有最终 Save，不重复做一套退出保存。
11. 补下载记录移除和完成历史清理（D06），验证活动任务取消、条目引用及容量恢复；与实际文件删除分开。
12. 处理下载时同步歌词的现行后端或禁用提示；旧推荐／举报／音乐窗另按产品范围管理。
13. 有设备时验证 KS 拓扑、ASIO 外部时钟／重置、物理 CD/DTS-CD；当前虚拟验证继续保留，不伪造硬件结果。
14. 原生逐屏 DPI、动态拓扑、长时 GDI／线程资源压力、更新中断恢复作为独立增强。

每批先原版合同和小样本，再 XP／Win7／Windows 11。Windows 11 继续按用户要求代表现代 Windows 验证，但记录应写 Win11，不能改称 Win10 实机。
