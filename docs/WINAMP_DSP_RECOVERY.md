### 线程、生命周期与退出

`src/audio/dsp_dispatcher.h` 为每条共享 DSP 链建立一个进程内消息线程，初始化 OLE。
Init、Config、ModifySamples、Quit 均在该线程运行。同一歌曲切换族中的 AudioEngine 继续共享同一条链。
这恢复了原版的同实例和串行处理约定；**线程布局不是原版 UI 线程／播放线程安排的逐行照搬**。

配置以异步消息投递，允许模态配置窗口打开时继续泵入音频请求。PCM 请求使用队列消息；等待者只处理跨线程 SendMessage，避免把任意 UI 命令重入播放路径。
AudioEngine 调用第三方回调前释放自身互斥锁，防止插件查询父窗口时形成锁等待环。

如果配置回调仍在调用栈上，此时取消或修改插件列表会合并为待处理请求，等回调退出后再执行 Quit／卸载。
故障模块也在最外层回调结束后释放。退出时先让消息循环及模态回调结束，再执行 Quit；清理该线程中仍属于待卸载 DLL 的窗口后才 FreeLibrary。

仍保留原版：header 至少 0x20、PaceMaker 排除、0..9 中首个非空模块、忽略 Init 的整数返回值、16 位交错 PCM、超过 0x3FFF 帧只对半拆一次、忽略 ModifySamples 返回长度。
两倍缓冲区是对 Winamp ABI 的容量保护，不会让变速／增减帧插件获得原版没有的变长输出语义。

## 2. REG 文件修正

这些是 `D:/Projects/Backup/TTPlayer/Plugins` 中的本地文件修改，**没有执行或自动导入 REG**，也没有把授权资料放进发行 ZIP。

- DFX 清理文件：从删除整个 DFX 产品树，缩小到两种显式路径下的 `DFX/11/REGISTRATION` 子键；保留用户状态、资源路径和其它版本。
- Ozone 清理文件：只删除 `Ozone/Winamp2` 的 `EmailAddress`、`RegName`、`RegCode` 三个值；不再删除整个 `iZotope` 厂商树，保留界面状态。
- 三个添加文件：增加“历史安装快照、含固定路径或个人登记资料、不由重建版导入”的说明；保留原有数据供用户核对。

两个 DFX 添加文件原有的不同窗口尺寸等值没有被选成新的通用默认值；否则会把旧机器的偏好覆盖到当前机器。
本次宿主适配从实际 DLL 位置派生配置程序路径，不依赖导入这两份安装快照。
旧添加文件仍不适合作为跨机器的自动部署脚本。

## 3. 能否不更改系统注册表？

**可以分阶段实现，但“不用手动导入 REG”与“插件完全不写系统注册表”是两个不同目标。**

### 3.1 本次已经做到的部分

Winamp DSP 根据 DLL 导出加载，不需要 COM 注册或 `regsvr32`。
播放器不自动导入附带 REG，也不为了 DFX 配置程序的路径写入 HKLM。
在已确认的 DFX 布局下，配置按钮直接启动 DLL 同目录树中的现有辅助程序，解决迁移到 D 盘后仍查找 C 盘的问题。

这仅替代该 Config 的路径查找。DFX 的初始化、其辅助 EXE、Ozone 和其它插件仍可能自己读取或写入注册表。
没有声称 DFX 全功能已经便携化，也没有绕过插件的授权校验。

### 3.2 可选技术路径

| 方法 | 是否真正避开系统注册表写入 | XP | Win7／新系统 | 结论 |
| --- | --- | --- | --- | --- |
| 运行时写正确路径到 HKCU／HKLM | 否 | 可用 | 可用 | 只是自动配置，不满足完整免注册表目标 |
| 写入前备份、退出恢复 | 否 | 可用 | 可用 | 崩溃、并发使用同产品时难以正确恢复，不采用 |
| UAC 注册表虚拟化 | 否，仍写用户的注册表 VirtualStore | 无 | 有条件 | 不应作为便携实现的依赖 |
| RegOverridePredefKey 重定向到临时 HKCU | 否，临时键仍属于系统注册表 | 可用 | 可用 | 且影响整个调用进程，不能只围住一段 Config |
| 私有 hive 文件 + 有范围的 API 重定向 | 可将目标数据放到独立文件 | 无 RegLoadAppKey | 可行 | 还需要让插件的 Reg* 调用使用私有句柄 |
| 插件范围的文件型注册表兼容层 | 可行，需覆盖所有目标访问 | 可实现 | 可实现 | 跨 XP／Win7 的统一方向，开发和验证范围较大 |
| 修改插件源码，直接使用配置文件 | 可行 | 取决于构建 | 可行 | 有可维护源码时最清楚；不能假定现有 17 个二进制都具备源码 |

Microsoft 说明 `RegOverridePredefKey` 的映射作用于**调用进程**，不是某一个 DLL 或线程；传空句柄才恢复默认映射。
因此在播放器进程直接把 HKCU／HKLM 全部换掉，会连带影响宿主的 Shell／COM／其它插件；插件异步线程也可能在 Config 返回之后继续访问。
仅在 Config 前后短暂重定向并加互斥锁，不能覆盖这些访问。[API 文档](https://learn.microsoft.com/en-us/windows/win32/api/winreg/nf-winreg-regoverridepredefkey)

`RegLoadAppKeyW` 可以加载独立的应用 hive，通过返回句柄访问，不挂到正常的注册表命名空间。
它要求 Vista 及以上；Win7 每个进程只能同时加载一个此类 hive，Windows 8 起支持多个。它本身不会自动改写第三方 DLL 的 HKCU／HKLM 调用。
因此不能直接拿这个 API 作为 XP 通用方案。[API 文档](https://learn.microsoft.com/en-us/windows/win32/api/winreg/nf-winreg-regloadappkeyw)

UAC 虚拟化将部分写入转移到用户注册表位置，并非配置文件存储；微软也明确不建议新实现依赖这一兼容机制。
[Registry Virtualization](https://learn.microsoft.com/en-us/windows/win32/sysinfo/registry-virtualization)

### 3.3 建议的后续便携架构

先对已明确的 DFX／Ozone 分支建立插件范围的文件存储适配，数据放在用户可写的专用配置目录；不全局替换播放器的注册表根句柄。
需要保留注册表数据类型、大小查询、默认值、A/W 字符编码、枚举、删除、句柄生命周期、错误码及 32／64 位视图语义，并处理并发和原子保存。
用户提供的有效授权资料可以原样迁移到该存储，不生成、不硬编码、不替代校验结果。

不能只改一次导入表就宣布覆盖全部插件：这里有 12 个压缩／保护的 DLL，可能动态解析 API；依赖 DLL 和 DFX 辅助 EXE 也会独立访问注册表。
全部访问点、子进程和资源路径都应纳入验证。

另一条路线是将某个插件的 **Init／PCM／Config／Quit 一起**放进持久 worker，再在那个进程内部使用私有 hive 或文件型兼容层。
这样需要新增共享 PCM 缓冲区、超时／退出协议和延迟验证；不能退回“只把 Config 放进另一进程”的旧缺陷。
当前先完成宿主同实例修复和已证实的路径替代；完整注册表兼容层尚未实现。

## 5. 当前边界

- 本次是 DSP 宿主修复，不是 17 个插件算法的重建；不能断言全部插件与原版逐像素、逐采样一致。
- DFX 独立辅助程序的全功能、Dee 完整窗口行为、全部预设、所有 Winamp 宿主 IPC 仍需真实插件专项测试。
- 进程内第三方回调永久阻塞不能靠 SEH 安全终止；插件自行建立的其它线程及外部辅助进程也不能统一按本线程窗口处理。
- 普通模态消息循环可服务音频请求；插件如果在回调中长时间不处理消息，仍可能阻塞音频／配置更新。
- 本次不会把注册表清空当作修复，不会自动写入附带的授权数据。完整“零系统注册表写入”尚未完成。
