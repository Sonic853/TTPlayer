# MP3 旧标签中文乱码：原版行为与修复记录

日期：2026-10-07。

## 1. 结论

两个样本的 ID3v2.3 文本帧都声明编码 `0`，实际文本字节是 GBK。
原版 5.7.9 对这类文本采用 Windows 当前 ANSI 代码页；重建版此前逐字节扩展为 Latin-1 Unicode 字符，导致文件属性、播放列表和播放信息同时出现乱码。

本次恢复原版的 ANSI 读写行为：

- 读取编码 `0`：`MultiByteToWideChar(CP_ACP, 0, ...)`。
- 保存编码 `0`：`WideCharToMultiByte(CP_ACP, 0, ...)`。
- 编码 `1 / 2 / 3` 的 UTF-16 / UTF-8 分支保持不变。
- 不更改用户提供的原文件，不自动重写歌曲标签。

这项修复在共同的 MP3 标签层生效，不依赖皮肤或字体。

## 3. 原版伪代码与二进制调用链

依据：`reverse/decompiled/TTPlayer.exe.pseudo.c` 及本地原版 `TTPlayer.exe` 的反汇编。
以下地址属于原版 EXE，不能作为重建版地址使用。

### 3.1 ID3v2 读取：004DB2F0

`FUN_004DB2F0` 通过 `ttpcomm` 的 ID3 接口读取头部、帧及字段。
拿到帧的编码后，逻辑分成两条路径：

```text
编码为 1、2、3：
    ttpcomm Ordinal_62 -> Unicode 文本 -> 写入元数据

编码为 0：
    ttpcomm Ordinal_61 -> 窄字节文本
    FUN_00408544(text, codepage = 0)
    FUN_004DA49B(...) -> 写入元数据
```

关键二进制证据：

```text
004DB6EB..004DB6FB   分别判断编码 1 / 2 / 3，跳往 Unicode 路径
004DB6FE            call 00508044          ; Ordinal_61 跳板
004DB708            push 0                ; 代码页参数
004DB70D            call 00408544
004DB720            call 004DA49B
```

`FUN_00408544` 内部调用：

```cpp
MultiByteToWideChar(codepage, 0, text, -1, ...);
```

参数 `0` 即 `CP_ACP`。因此，这不是根据选项中的 “ISO-8859-1” 字样，简单将每个字节转换成相同数值的 Unicode 字符。
在当前简体中文系统上，`GetACP()` 为 `936`，恰好能解释两个样本的 GBK 中文。

### 3.2 标签优先级：004DC174

`FUN_004DC174` 读取 ID3v2、APEv2、Lyrics3 和 ID3v1，再按优先级合并：

| 标志值 | 标签类型 |
| ---: | --- |
| 1 | ID3v1 |
| 2 | Lyrics3 |
| 4 | APEv2 |
| 8 | ID3v2 |

默认 `0x04080000` 补全后优先读取 APEv2、ID3v2，再用后续标签补充缺项。
两首歌没有 APEv2，ID3v2 中已经存在非空标题、艺术家和专辑。此前即使 ID3v1 能正确解码，也不会覆盖这些非空的乱码值。

因此，调整显示字体或者简单交换标签优先级只能掩盖问题；正确修复点是 ID3v2 文本转换。

### 3.3 ID3v2 保存：004DC59D

`FUN_004DC59D` 的编码选择：

| 配置值 | 实际保存编码 |
| ---: | --- |
| 0 | 旧 ANSI 字节文本 |
| 3 | UTF-8 |
| 其它非零值 | UTF-16 |

编码 `0` 时，在 `004DC7B1` 压入值为零的 `EBX`，在 `004DC7B8` 调用 `FUN_0040175C`，之后交给 `ttpcomm Ordinal_66`。
`FUN_0040175C` 调用 `WideCharToMultiByte(codepage, 0, text, -1, ...)`，与读取路径使用同一个系统代码页。

重建版此前的保存分支只接受 `wchar_t <= 0xFF`，其它字符写成 `?`。仅修正读取，用户随后保存时仍可能损坏中文，所以本次也恢复了对应的写入转换。

## 4. 重建版修改

生产代码仅修改 `src/audio/builtin_file_info.cpp`：

1. 新增有边界检查的 `DecodeAnsi`，先限制在首个 NUL 之前，再用系统 ANSI 代码页转换。
2. `DecodeText(0, ...)` 改用 `DecodeAnsi`。
3. `EncodeText(..., 0)` 改用两次 `WideCharToMultiByte`，先计算长度，再写入缓冲区，并检查 API 结果。
4. ID3v1／Lyrics3 既有的“有效 UTF-8 优先，否则 ANSI”策略保持不变，仅复用相同的 ANSI 转换函数。
5. 将 URL 字节编码与普通文本编码分开，保留网址原有的 Latin-1 读写规则。
6. 更正编码选择处的注释，区分界面标签与原版实际行为。

读取转换失败时保留原有旧标签回退策略；保存 API 失败时进入现有写入错误处理，不静默提交不完整结果。
这些转换使用 XP 已有的 API，没有新增现代系统依赖。

### 影响到的使用路径

- 文件属性：实际 EXE 的 `read` 文件信息工作进程。
- 播放列表：实际 EXE 的 `playlist-read` 工作进程。
- 播放时曲目信息：`RecoveredFileSource` 在 MP3 解码器打开后使用 `ReadBuiltinMpegFileInfo` 补全元数据。
- 共享此标签层的普通文本、注释、内嵌歌词和 TXXX 字段。

URL 本身仍用 Latin-1 读取；APEv2 仍用 UTF-8。封面二进制、MPEG 音频及不透明帧不参与字符转换。

## 5. 兼容性边界

[ID3v2.3 规范](https://id3.org/id3v2.3.0)将编码 `0` 定义为 ISO-8859-1；本次恢复的是原版对历史 ANSI 标签的兼容处理。
[`CP_ACP` 的含义](https://learn.microsoft.com/en-us/windows/win32/api/stringapiset/nf-stringapiset-multibytetowidechar)是当前 Windows ANSI 代码页。

- 不强制将所有文件视为 GBK，也不把已经正确的 UTF-8、UTF-16 文本重新解释一遍。
- 非简体中文系统下，编码 `0` 的结果仍与该系统 ANSI 代码页有关，与原版相同；本次不宣称实现了通用编码自动检测。
- ANSI 无法表达的字符，在保存为编码 `0` 时仍可能被系统转换成替代字符。需要跨语言保存完整 Unicode 时应使用 UTF-8／UTF-16。
- 本次没有迁移或重写已持久化的播放列表缓存。若旧列表仍显示先前缓存的名称，可重新添加曲目以重新读取；文件属性可使用“重新读取文件”。

### 测试程序弹窗的修复

第一次完整回归中，`GetTempFileNameW` 在默认临时目录返回错误 `5`（拒绝访问），随后测试的 `assert` 触发 `0x40000015` 异常终止弹窗，尚未进入标签测试。

仅对本地测试做了以下处理：

- 临时文件 API 失败时打印函数名和 Windows 错误码，正常返回失败状态。
- 设置 `SetErrorMode`，避免回归测试出现系统错误对话框。
- 本机运行脚本将 `TEMP/TMP` 限定到 `tests/tag_encoding_20261007/temp`。
- 复测默认不可写目录：输出错误 `5`，退出码 `1`，无弹窗。
- 复测可写测试目录：完整回归退出码 `0`。

测试源码、样本副本、临时文件和日志均在本地 `tests` 中；没有添加到发行包或 Actions 测试流程，也没有执行提交或上传。
