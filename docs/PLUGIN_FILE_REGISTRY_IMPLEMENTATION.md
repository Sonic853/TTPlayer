# 插件范围的文件型注册表兼容层

实施日期：2026-09-27。

## 1. 当前交付范围

**第一阶段已实现并验证 Ozone 的文件型注册表适配。** 这是重建版宿主的兼容功能，没有修改插件算法、登记校验或 DLL 文件。

适配对象是本目录已分析的 `dsp_izOzone.dll`，SHA256：

```text
e3bb0eef979ea8016fb1278b373c7c70ae4507719524bfefe802b5bc3c800e59
```

文件名和摘要同时匹配才启用。其它插件继续使用原有宿主路径；同名但摘要不同的 Ozone 会给出“未覆盖文件型适配、仍使用原生注册表”的诊断。

**DFX 及其辅助进程尚未接入这套文件存储，不能把当前结果理解为所有音效插件均不再访问系统注册表。** 第 7 节记录了已经检查的跨进程障碍及后续接口要求。

## 2. 用户可见行为与文件位置

播放器将配置放在当前播放器设置文件旁：

```text
<播放器设置文件所在目录>/PluginState/Ozone/
    registry.json          当前配置
    registry.json.bak      最近一次成功保存前的配置
    registry.json.lock     进程间独占锁文件
    registry-import.reg    可选的一次性导入来源
```

独立使用 DSP 链、未指定播放器存储目录时，默认使用插件旁的 `Ozone` 文件夹。

首次建立文件配置按以下顺序处理：

1. 如果用户把已有 Ozone 登记 REG 文件放到上述目录并命名为 `registry-import.reg`，解析指定分支下的三个登记字符串。
2. 如果没有该导入文件，只读迁移当前用户系统注册表中 Ozone 的 `EmailAddress`、`RegName`、`RegCode`、`Minimized`；不会回写源分支。
3. 两者都没有时，由原插件显示自己的登记窗口。用户正常输入后，原插件的写入调用保存到文件配置。
4. `registry.json` 已存在后，仅使用它，不再用旧 REG 文件或系统注册表覆盖文件中的配置。

导入器接受本地现有 REG 文件中的两级空父键声明；仅接受目标分支的三个登记字符串，忽略历史 `Minimized` 值。其它分支、删除语法、额外值、错误编码或重复字段均拒绝。不会调用 regedit，也不会自动寻找、执行 `+添加…reg`。

导入成功后可移走 `registry-import.reg`。已有登记资料仍由原插件校验；兼容层不生成登记码、不预置个人资料、不跳过校验。JSON 中的十六进制是原始字节的表示，**不是加密**，应作为用户配置保管，不随程序发布。

Ozone 的音效参数文件 `Ozone/iZOzone.cfg` 仍由原插件按原路径处理。这次重定向的是注册表数据；完整搬迁插件时还需要保留它的参数文件和资源。

## 3. 调用路径与生命周期

```mermaid
flowchart LR
    A[播放器 DSP 宿主] --> B[加载并核对 Ozone]
    B --> C[替换该 DLL 的注册表导入项]
    C --> D[原插件 Init / Config / PCM / Quit]
    D --> E[限定分支的内存键值树]
    E --> F[后台保存 registry.json]
```

实现位置：

- `src/audio/plugin_registry.h/.cpp`：文件存储、有限 REG 导入、API 适配及已知插件识别。
- `src/audio/winamp_dsp.cpp`：在加载 DLL 后、调用插件 header / Init 前接入，并保留至 Quit、窗口销毁和 FreeLibrary 完成。
- `AudioEngine::SetDspStorageDirectory`、`WinampDspChain::SetStorageDirectory`：播放器传入自己的配置位置；活动实例存在时禁止切换存储位置。
- `PlayerWindow`：将存储目录与实际设置文件绑定。

只替换已知 Ozone 模块的导入地址表，不全局修改 ADVAPI32 或播放器的注册表函数。根据调用地址所属模块及虚拟句柄归属选择上下文，覆盖该模块自身后台线程发起的调用，不依赖“当前是否正在 Config”的线程局部开关。

同时接管该模块的 `GetProcAddress`，使受支持的动态 Reg* 查询返回同一套包装函数。未知 Reg* 动态查询返回不支持，避免把虚拟句柄交给系统 API。卸载时在 DLL 仍映射的情况下恢复导入项；文件存储在最终回调结束后才释放。

这不是通用注入框架，也不是安全沙箱。对其它 DLL、未审核的动态加载模块、NT 原生注册表接口、COM 组件、子进程没有全局接管。

## 4. 分支与 API 语义

可写范围：

```text
HKCU/Software/iZotope/Ozone/Winamp2
```

允许通过父键句柄逐级打开目标分支。目标分支及其子键使用虚拟句柄；其它分支允许只读查询，拒绝来自适配调用的创建、设置及申请写权限。父键网关自身不允许存储值。

| 项目 | 已实现的范围 |
| --- | --- |
| API | RegOpenKeyEx、RegCreateKeyEx、RegQueryValueEx、RegSetValueEx 的 A/W 版本，RegCloseKey、RegFlushKey |
| 值 | 保存类型编号和原始字节；空名称即默认值；支持零字节值 |
| 字符串 | W 侧保存 UTF-16 字节，A 侧按当前 ACP 转换；按显式长度处理，保留缺少结尾 NUL 的原始写入语义 |
| 查询 | 支持只查询大小、返回实际大小、ERROR_MORE_DATA，不越界复制 |
| 访问 | 查询/设置权限分别检查；失效、重复关闭的句柄返回错误 |
| 名称 | 对已知 Ozone ASCII 路径大小写不敏感；值名中的斜杠、尾部反斜杠保留 |
| 视图 | 当前只有已审核插件使用的 32 位配置；明确拒绝 64 位视图请求 |
| 创建选项 | 当前支持默认非易失键；不假装实现易失键、类字符串或自定义安全描述符 |
| 未覆盖操作 | 枚举、删除、通知、事务等尚未实现；已知 Ozone 静态导入没有这些 API |

不能将这张表等同于完整 Win32 注册表实现。新增插件需要重新核对实际调用、参数和错误分支，并补足它需要的接口。

## 5. 保存、并发和故障处理

- 配置操作先在互斥锁保护下更新内存；XP 已支持的系统线程池定时回调约 200 ms 合并保存，普通查询/设置不直接读写磁盘。回调有防重入保护，不会为慢磁盘不断堆叠写入任务。
- 写入临时文件并 FlushFileBuffers，备份旧文件后使用 MoveFileEx 替换；RegFlushKey 和插件卸载时也会刷新。
- 保存失败保留待写状态并重试；卸载时仍失败会产生诊断。故障不会触发“退回系统注册表写入”。
- 卸载时取消定时任务并等待回调完成，期间服务同步窗口消息，再执行最后刷新。不会在插件清理过程中额外创建、销毁一条专用保存线程。
- 独占锁防止两个进程对同一配置文件互相覆盖；当前不支持多进程同时编辑同一文件，第二个进程加载该配置会失败。
- 输入文件最大 4 MiB，单值最大 1 MiB，存储还检查编码后的保守容量预算。超过预算返回错误。
- 虚拟句柄关闭后保留失效记录，避免旧句柄因地址重用指向新键；每个实例有 65,536 次句柄分配上限。
- JSON 格式错误、目录不可写或锁冲突时，该插件加载失败，不覆盖损坏文件。保留 `.bak` 供人工恢复，不自动用旧登记资料覆盖当前数据。

这是单插件、单进程编辑模型。未来 DFX 的多个进程不能直接共用当前文件后端的独占锁模式。

## 6. 验证结果

所有测试源代码和诊断产物仅放在本地 `rebuild/tests`；没有提交测试、没有增加 Action 测试步骤，也没有把登记资料放进发行包。

| 测试 | 本机 | XP VM | Win7 VM |
| --- | --- | --- | --- |
| 文件后端类型、大小查询、短缓冲区、失效句柄、权限 | 通过 | 通过 | 通过 |
| 并发设置、关闭重开、独占锁、损坏文件拒绝 | 通过 | 通过 | 通过 |
| 现有资料首次导入后真实 Ozone Init / Config / PCM / Quit | 通过 | 通过 | 通过 |
| 移走 REG 文件后再次启动 | 通过 | 通过 | 通过 |
| 插件与文件配置迁至另一目录 | 通过 | 通过 | 通过 |
| 原插件登记窗口输入已有资料，写文件后重启 | 通过 | 通过 | 通过 |

真实插件测试均使用同一活动实例调用 Config，并验证 `Module+0x1C` 已创建且在 Quit 后清空。44.1 kHz 下 4096 个测试样本有 4092 个改变，48 kHz 下有 4094 个改变。

登记写入测试从空文件配置启动，通过原登记窗口输入已有资料并走原校验和确认窗口；随后逐项比较三个文件值与输入资料，再无输入地重新启动。插件写入 REG_SZ 时没有把结尾 NUL 算入长度，这条实际路径也已通过。

VM 测试把**测试子进程**的 HKCU 映射到父进程持有的空临时分支，用于检测意外落回原生注册表的写入。每次结束后该分支下仍没有 Ozone 目标键，父进程再移除临时分支。生产实现不调用 RegOverridePredefKey，不建立测试注册表分支。

测试驱动最初错误地假定登记成功确认框按钮为 IDOK=1；实际唯一按钮为 ID=2，导致等待超时。修正后两台 VM 完整通过；没有因此修改原插件或保留无依据的初始化调度变更。

### Ozone 快速启停导致加载锁遗留

连续测试进一步捕获了独立于注册表读写的退出故障：加载锁的持有线程已经不在进程线程列表中，其他线程阻塞于 LdrLoadDll / LdrUnloadDll / LdrShutdownThread。

二进制证据是：`5944496C` 创建 `59444A20` 线程，主体 `59443D30` 循环，`594441C2` 检查对象 `+0x100` 的运行标志；清理函数先在 `59445706` 把标志清零，却紧接着在 `5944570D` 调用 TerminateThread。强杀正在执行 DLL 初始化的线程会遗留加载锁，单纯调整保存线程的等待方式不能解决这个根因。

兼容层仅对已审核摘要的这一个调用位置（返回地址 RVA `0x35713`、退出码 0）替换为等待线程按原停止标志自行退出，并在等待期间处理同步窗口消息。原线程已经提供合作退出路径，不需要改音频算法或登记逻辑，也不修改磁盘 DLL。其它调用位置不会套用这条规则。

测试还取消了为观察 userData 而保留的额外 DLL 引用，改为在 Quit 回调返回时检查；最终卸载保持在 DSP 线程，与产品路径一致。

修复后本机连续 10 轮“重启 + 迁移启动”（共 20 次子进程启动）通过，随后登记写入与再启动通过；XP、Win7 也重新通过登记、同实例 Config、PCM 和退出测试。

DLL 的自定义入口 `59456652` 直接返回成功，外层 `5944FA8B` 仍执行 CRT 初始化。IAT 接管发生在 LoadLibrary 之后，无法拦截此前的 DLL 初始化；当前空原生分支验证覆盖了该已知二进制的实际加载路径，不能推广为任意版本的加载期保证。

Release EXE 已通过 XP / Win7 静态导入检查：x86、子系统 5.01；具体导入数量以发行目录的 `legacy-imports.json` 为准。

## 7. DFX 接入检查与下一阶段

现有 `Dsp_Dfx.dll` 摘要为 `987e7d531b92df9a582c1ab803f92856e948cc87f0a6b1ed900d3a7898a0eb03`。
该 DLL 导入 RegOpenKeyExA/W、RegCreateKeyExW、RegQueryValueExA/W、RegSetValueExW、RegCloseKey；还使用 HKLM 下的安装路径和 HKCU 下的会话、窗口、登记信息。

它的 Config `10001070` 会读取 `HKLM/SOFTWARE/DFX/11/top_folder` 并启动 `Apps/dfxwsettings.exe`。前一轮宿主修复已经让设置入口从实际插件目录启动这个 EXE，但这不代表 EXE 内部的访问已经被接管。

已检查的 `dfxwsettings.exe` 为 48,128 字节，入口 `00401DC1`，启动导入包含 LoadLibraryA/GetProcAddress；它的静态导入表不足以给出实际注册表调用全集。DFX 二进制中还存在 `fileRegCreateKey` 等字符串，单凭名字也不能认定已有可直接启用的完整便携模式。

因此本阶段没有对 DFX 单独打开 DLL 层重定向，否则 DLL 与设置 EXE 会读写两个不同的数据源，设置界面可能无法控制正在播放的实例。

后续应当按以下依赖顺序实施：

1. 对设置 EXE 及其运行时模块记录打开、读写、枚举、删除和进程创建轨迹，确定完整分支及调用方。
2. 为 DFX 建立单一配置服务，通过进程间协议让 DLL 和设置 EXE 共享同一份内存状态；服务统一执行文件落盘，避免多个 JSON 写入者覆盖数据。
3. 在辅助进程执行其业务初始化之前安装适配，覆盖动态解析和后续模块加载；接入失败必须终止该次便携启动并给出诊断。
4. 实现该插件实际需要的多根键、默认值、缺失值、枚举/删除和视图规则，从实际 DLL 路径生成资源位置；保持原插件登记校验。
5. 验证正在播放时改设置立即生效、两个界面同时修改、异常退出、目录迁移，以及 XP/Win7 的全过程原生写入检查，再启用 DFX 文件型模式。

这部分需要独立的跨进程实现与验证，不能通过给当前 Ozone 路径白名单增加 `Software/DFX` 就完成。
