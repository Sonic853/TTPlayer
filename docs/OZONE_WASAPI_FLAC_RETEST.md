## 原版调用行为的核对

来源为 `reverse/decompiled/TTPlayer.exe.pseudo.c`：

- `FUN_004ac166`：转为 16 bit PCM 调用 Winamp DSP，再转换回后续输出所需格式；空数据不调用 DSP。
- `FUN_0042898d`：按插件列表顺序串行处理。
- `FUN_004280cd`：按实际字节数换算帧数，超过 `0x3fff` 帧仅分成两半调用，忽略 `ModifySamples` 返回长度。
- `FUN_004b1375`：读取解码数据再进入处理链；没有证据支持为这个 FLAC 强行合并若干 1,024 帧块作为“原版行为”。

直接调用与重建版调度线程的整首 PCM 一致，说明本次参数下不能仅凭线程模型不同就认定它造成了 Ozone 音频变化。原版没有当前重建版新增的 WASAPI 后端，不能声称恢复了原版 WASAPI 实现。

### 等待路径与代码改动

对随后运行中的线程做了 80 轮短暂上下文采样；栈中候选返回地址通过模块可执行区识别，未使用匹配的私有 PDB，因此它是采样证据，不是逐回调计时：

- DSP 所在线程 `33364` 有 69/80 次采样命中同一睡眠路径，栈内出现 Ozone RVA `0x32ff0`、`0x35fd1`。
- 对实际 DLL 的只读反汇编确认：`59442EE0` 检查界面刷新间隔，尚未到期时在 `59442FE8` 压入 `1`、`59442FEA` 调用导入的 `Sleep`，返回到 `59442FF0`；调用方位于界面消息处理函数。
- 播放线程 `6364` 的采样分别停在同步消息等待和 PCM 队列请求等待。宿主 RVA `0x193f2e` 对应处理后诊断读取路径，`0x188c2b` 位于 PCM 调度返回后的样本转换处。

原热路径每次解码返回 1,024 帧，先 `WinampDspChain::Process` 等待 DSP 窗口线程，再用 `TakeDiagnostics` 同步等待同一线程，即使没有错误也必须等待。插件在两次调用之间处理界面刷新并睡眠，会把空诊断查询变成音频生产的额外等待；独立 WASAPI 渲染线程无法弥补持续生产不足。

修复在同一次 PCM 调度内收集诊断，播放线程随后只取本地结果。初始化和配置更新仍可显式查询插件诊断，DirectSound 分支也消费合并返回的错误。保留原先的队列式 PCM 调度、串行插件顺序、1,024 帧输入、16 bit 转换、同实例配置及延迟卸载，不更改 DLL、插件登记校验、预设或输出缓冲大小。

Windows 的短睡眠受计时器分辨率和调度影响，不能把 `Sleep(1)` 当作严格的 1 ms；参见 [Microsoft Sleep 说明](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-sleep)。跨线程同步消息同样要等接收线程处理消息，参见 [Microsoft SendMessage 说明](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendmessagew)。本轮没有通过全局提高计时精度来掩盖重复等待。
