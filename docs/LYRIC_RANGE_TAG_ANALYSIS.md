# 歌词起止区间标签兼容性分析

日期：2026-09-29。第 1—6 节记录实施前的分析；用户确认后已完成适配，实施说明见第 7 节。

## 1. 样例与格式判断

```text
[00:54:310,00:56:970]電波が違くても
[00:57:730,01:01:240]きっとね何か掴んでくれてる
[01:01:240,01:03:540]あなたの事が好き
```

按“分钟:秒:毫秒，开始时间在前、结束时间在后”解释，样例含义如下。该解释与三行的时间排列一致，但仅凭片段不能确认生成软件及其完整格式定义。

| 行 | 开始 | 结束 | 持续时间 |
| --- | --- | --- | --- |
| 1 | 54.310 秒 | 56.970 秒 | 2.660 秒 |
| 2 | 57.730 秒 | 61.240 秒 | 3.510 秒 |
| 3 | 61.240 秒 | 63.540 秒 | 2.300 秒 |

第一句结束至第二句开始有 760 ms 空档；第二句结束与第三句开始重合。区间若定义为 `[start, end)`，在 61.240 秒进入第三句，不会同时选中第二句。

这种同括号内用逗号连接两个绝对时间的写法应视为待兼容的扩展格式，不能假定普通 LRC 播放器都支持。时间中的冒号本身不能作为非法依据：Sony 的官方说明使用 `[mm:ss:xx]`，但其中 `xx` 是两位百分秒，并未定义本例的三位毫秒起止区间。[Sony 官方说明](https://helpguide.sony.net/gbmig/42708101/v1/eng/contents/03/03/11/11.html)

作为现有实现的对照，LDDC 的解析代码分别识别点号小数的行标签、多个独立方括号标签和尖括号逐字标签，不能据此将本例逗号区间当作通用 LRC 语法。[LDDC 解析源码](https://github.com/chenmozhijin/LDDC/blob/main/LDDC/core/parser/lrc.py)

本例只有句子起止时间，没有每个字／词的时间。可实现整句渐进高亮，不能还原真实逐字演唱节奏。

## 2. 当前重建版行为与实测

`src/lyrics/lrc_parser.cpp`：

- `ParseLrcTimestamp` 识别 `分钟:秒`，可带点号及 1～3 位小数；数字字段要求完整匹配。
- `00:54:310` 的秒字段包含第二个冒号，解析失败。
- `00:54.310,00:56.970` 仍包含逗号及第二个时间，解析失败。
- `ParseLrc` 没有区间标签分支；没有有效行时间的行被跳过。
- `PlayerWindow::LoadLyricsFrom` 对零有效行按加载失败处理。

本地 `tests/lyrics/range_tag_analysis.cpp` 直接编译当前生产解析源码，结果：

```text
原样三行：0 行
仅将毫秒分隔符改成点号，保留逗号区间：0 行
单个冒号毫秒标签 [00:54:310]：0 行
[00:54.310][00:56.970]text：2 行
转成行时间＋末尾尖括号结束标记：3 行
```

因此不能将 `[start,end]` 简单拆成 `[start][end]`；现有后者表示同一句在两个时刻重复出现。

## 3. 现有能力可复用的部分

内部已经支持末尾结束标记，例如：

```text
[00:54.310]電波が違くても<00:56.970>
```

`WordTime{text_offset=text.size()}` 可表示无可见字符的结束标记，`LyricLine::Progress` 在它之前按本句开始至结束插值，在它之后达到全文高亮。本地探针确认，样例转换后的首句在 56.970 秒达到全文高亮。

但是，`Lyrics::LineAt` 只按开始时间选择最近一行：57.000 秒仍选择第一句，64.000 秒仍选择最后一句。桌面歌词与窗口歌词的整行进度、滚动和淡入淡出也有按下一行起点或末行加一分钟估算的分支。

所以“利用末尾标记兼容高亮”可行，但不等于已完整支持结束时隐藏、空档显示、区间重叠等语义。不能直接把过期行返回为空，否则显示层可能进入原有“无歌词／尚未开始”的处理。

## 4. 编辑器存在独立风险

`src/ui/player_window_lyrics.cpp` 的 `ParseEditorTimestampLiteral` 为恢复原版编辑行为，保留 `swscanf_s(L"[%d:%f]")` 宽松扫描。

探针输入 `[00:54:310,00:56:970]`，实际返回两个成功字段：分钟 0、秒 54.000。扫描在第二个冒号处停止，虽然未消费完整标签，调用者仍把它视为成功。若沿用这一路径替换整个标签，可能丢掉 310 ms 和结束时间。

适配需要覆盖：

- 标签着色、插入、替换与删除；
- 提前／延后及整体偏移：起止时间一起移动；
- 压缩／展开：同文本但不同持续时间的区间不能错误合并；
- 保存、另存为、非零 offset 的自动序列化及内嵌歌词写回。

只增加播放解析，编辑后仍可能损坏时间信息。

## 5. 推荐实施方式与对旧逻辑的影响

建议新增独立的起止区间解析分支，并保存可选结束时间；普通行不设置该字段，继续走原有逻辑。

1. 在行首方括号标签中精确识别两个完整时间与一个逗号；毫秒冒号形式先限定为三位，秒为 00～59，结束不得早于开始，检查数值溢出。
2. 不在整份文本上全局替换冒号或逗号，不把其他 `[整数,整数]` 格式推断成本格式。
3. 普通 `[t1][t2]` 重复行、元数据以及 `<time>` 逐字标签保留既有含义；新增区间允许逐行识别，不切换整个文件的解析模式。
4. 区间毫秒按字面解析，不参与旧逐字歌词 `.100` 百分秒溢出兼容判定。旧行的判定也不应因新格式预转换而改变。
5. 统一有效结束时间的计算，窗口、迷你、桌面与全屏歌词共用。普通 LRC 仍按下一行起点／原有末行规则处理。
6. 建议默认在结束时间完成本句高亮，保留文字供阅读，下一句开始再切换。若需要按字幕语义在空档清空，应只作用于具有明确区间的行，并单独处理空档状态。
7. 保存须保留结束时间；若导出普通 LRC，明确其信息损失。利用末尾尖括号标记可保留本播放器的高亮结束信息，但不能保证其他播放器识别。

| 对象 | 预期影响 |
| --- | --- |
| 原有普通 LRC | 时间、排序、重复行与显示结果保持不变 |
| 原有逐字歌词 | 继续使用真实词／字时间，不人为平均拆字 |
| 新区间歌词 | 新增明确结束时间和相应高亮处理 |
| 混合文件 | 每行独立识别，旧行不被重新解释 |
| 编辑与保存 | 需要专项补齐，避免截断时间或丢失结束值 |
| XP／Win7 | 属于解析与界面时序逻辑，不要求新增现代系统 API |

这可以作为重建版的兼容扩展；当前没有证据证明原版播放器原生定义或完整支持这种起止标签。不能将新增能力描述成原版既有格式的恢复。

## 6. 实施后的必要验证

分析阶段确定了以下必要验证，实施结果见下一节：

- 提供的三行、760 ms 空档、相邻端点、最后一句结束。
- 普通 LRC、重复时间标签、逐字歌词及其混合文件保持既有结果。
- `.100` 旧兼容例与三位毫秒区间混合时不互相干扰。
- 非法时间、逆序区间、缺失字段、过大数字、重叠／同起点区间。
- 编辑的提前／延后、替换、压缩／展开、offset、保存后重读不丢结束值。
- 窗口、迷你、桌面及全屏显示一致。

分析探针与输出只保存在本地 `rebuild/tests`。

## 7. 已完成的适配与验证

新增 `LyricTimeRange`、`LyricLine::end_time` 和统一的 `Lyrics::LineEnd`。区间保留独立的结束值，不伪造逐字时间。

- 严格解析 `[mm:ss:fff,mm:ss:fff]`，冒号后限定三位毫秒；也兼容点号小数端点。缺失字段、额外逗号、非法字符、秒数越界、倒序或数字溢出均不接受为区间。
- 每行独立识别。单个 `[00:54:310]` 不会因此变成新的普通 LRC 时间格式；`[t1][t2]` 仍表示重复句。
- 区间及其行内逐字标记使用字面毫秒，不参与普通逐字歌词的 `.100` 导出错误兼容判定。
- 普通、迷你、全屏和桌面歌词在结束时间完成卡拉 OK 高亮。760 ms 空档保留文字，最后一句也保留。滚动和下一句切换仍以起点为依据。
- 重叠区间的显示终点最多到下一句开始；原始结束值保留，保存不会截短它。零时长句在起点完成高亮；明确的长末句不再受普通末句一分钟估计值限制。
- 提前／延后同步移动两端；替换起点保留原时长并移动逐字时间；插入重复区间沿用原时长；删除一次移除整个区间标签。
- 压缩、展开、保存、展示文档序列化及内嵌写入共用的序列化路径保留区间，采用三位毫秒，offset 同时计入两端。普通编辑标签仍保留原有百分秒输出规则。
- 格式化负时间与已有逐字时间格式化保持一致，最小输出为零；不新增有符号时间标签语法。

### 验证结果

主机、XP SP3、Win7 SP1 的 `lyric_main_menu_tests` 通过。覆盖用户三行样例、间隙／末句／零时长／重叠、非法区间、重复句、混合普通与逐字格式、毫秒和 `.100` 隔离、offset、RichEdit 编辑命令、保存重读。普通／迷你／全屏下，横向和纵向绘制的像素结果与等效逐字结束标记一致。

主机 `lyric-parser`、`lyric-shift`、`desktop_lyrics_tests`、`playback_navigation_tests` 通过。桌面测试直接检查 `UpdateLayeredWindow` 提交的位图，核对到期完成高亮、空档保留和末句停留；这组绘制／滚动回归也已在 XP、Win7 通过。

测试源码和输出留在本地 `rebuild/tests`，未提交或上传。Actions 不变，发行构建仍为 `BUILD_TESTING=OFF`。快捷键及编辑时播放结束的配套修复见 [LYRIC_EDITOR_SHORTCUT_EOF_RECOVERY.md](LYRIC_EDITOR_SHORTCUT_EOF_RECOVERY.md)。
