# 播放列表框选及菜单逐项核对（2026-09-15）

参照仅为根目录 5.7.9 `TTPlayer.exe.pseudo.c`、`ttpres.dll`，未使用
TTPlayer6120 的菜单／输入实现。本文区分“有命令实现”“本次验证了行为”及
“尚未完全一致”；不能由反编译伪代码保证逐字恢复丢失源码或二进制一致。

## 框选缺失的原因与恢复依据

`00482BAF` 创建歌曲区 `Files`，ID `0x2802`、样式 `0x50015001`，再用
`LVM_SETEXTENDEDLISTVIEWSTYLE(0, 0x4420)` 设置列表样式。
`00425DEC` 明确以 `SysListView32` 为底层类：报告视图、虚拟数据、多选、整行选中。
原版框选由 Windows 列表控件处理，不能在伪代码中寻找一个独立的“画选框”私有函数。
`004894AF` 则是歌曲行上的 `LVN_BEGINDRAG` → OLE 拖放，和空白处框选不是同一条路径。

重建版的 `ListCtrl` 是透明消息转发子窗口，父窗口自行绘制。此前空白处按下仅清空
`playlist_selected_rows_`，既不捕获鼠标，也没有框选状态，因此系统控件的框选没有被继承。

本次补充：

- 从歌曲区空白处按下，越过系统拖动阈值后框选；歌曲行上的拖动仍走原有移动／OLE 路径。
- 普通框选替换选区；Ctrl 对按下时的选区取异或；Shift 合并选区。
  每次都从按下时的快照计算，缩回矩形能还原选区，不会每帧反复切换。
- 焦点行和正在播放的歌曲不随框选改变；关闭“允许拖动文件”也不禁用框选。
- 锚点保存为内容坐标，捕获期间每 50 ms 检查上下越界滚动；滚动不会移动锚点。
- 选框在原有离屏绘制中绘制并裁剪到歌曲区域，不直接对屏幕反复 XOR，避免残影。
- 松开、Esc、捕获转移、取消模式、隐藏、尺寸改变、刷新列表／切换皮肤、销毁均清理状态。

宿主机另创建了与原版相同样式的真正 `SysListView32`，用真实鼠标／键盘输入验证。
初始选区为第 0、4 行，从最后一行下方拖到第 2 行，实测如下（行号从 0 开始）：

| 修饰键 | 原生控件结果 | 焦点行 |
| --- | --- | --- |
| 无 | 2,3,4,5,6,7 | 0 |
| Ctrl | 0,2,3,5,6,7 | 0 |
| Shift | 0,2,3,4,5,6,7 | 0 |

重建版真实子窗口 → 父窗口消息测试取得相同结果。这里的原生对照是 Windows
公共控件，不是重新启动原版播放器做完整端到端对比；这是由伪代码确认的底层输入机制。

## 菜单是否复用

| 入口 | 原资源 | 重建版路径 |
| --- | --- | --- |
| 底部 添加／删除／列表／排序／查找／编辑／模式 | 139 / `0x8B` 的七个子菜单 | `InvokePlaylistToolbar` |
| 歌曲区空白处右键 | 139 的七组子菜单转换为 popup | `ShowPlaylistContextMenu` |
| 单选歌曲右键 | 152 / `0x98` | 同上，按本地／网络／CD/CUE 类型裁剪 |
| 多选歌曲右键 | 153 / `0x99` | 同上，全为网络曲目时裁剪本地文件操作 |
| 目录条目／目录空白右键 | 156 / `0x9C` | 同上，区分命中项和空白状态 |

标签、顺序和 ID 来自同一 `ttpres.dll`；每次打开创建独立 HMENU，并非多个窗口同时
持有一个菜单句柄。公共命令都进入 `HandlePlaylistCommand`，媒体库分流到
`HandleMediaLibraryCommand`，选项入口回落到 `HandleContextCommand`。
原版也是共用命令 ID／处理，而非强行让单选、多选和空白菜单完全相同。

本次额外修复：

1. `00483C26 → 0047FC61` 取第一条 **LVNI_SELECTED** 歌曲来播放。重建版此前取焦点行，
   框选后会播放旧焦点所在歌曲；普通列表和媒体库均改为第一条选中歌曲。
2. 评分单选标记必须传入评分子菜单句柄（`00488FEF`），不能传根菜单。
3. 模式单选标记同理；补上 `00461BAE` 在 **WM_INITMENUPOPUP** 时刷新模式、跟随光标、
   自动切换列表的行为。主窗口和播放列表共用 `PreparePlaylistModeMenu`，空白区菜单
   无须改变原资源的默认启用规则也可显示正确模式。
4. `0048516E` 的重命名目标是已选目录项，而非无条件回落到活动列表。
5. `00486209` 全选写入 state=2/mask=0xB，清除旧焦点；“全部不选”写入 0/0xB；
   `0048622A` 反选依次对新选中的行写入 state=3，最后新选中的行取得焦点。
   普通列表和媒体库补齐此差异，Ctrl+A 复用全选命令。空白处点击／框选仍保留焦点。

## 回归方法

`playlist_marquee_tests` 链接真实 UI 核心和 Common Controls v6 manifest，使用原 DLL
资源和解压默认皮肤，歌曲条目只存在内存中，不启动解码器、不加载用户播放列表。
覆盖策略、子窗口坐标转发、父窗口捕获、离屏绘制、Ctrl/Shift、滚动、释放／取消／隐藏、
歌曲行移动与框选分流，以及四份资源的逐项 ID 枚举、嵌套评分／模式和选择命令。

```powershell
cmake --build build --config Release --target playlist_marquee_tests ttplayer_rebuild
ctest --test-dir build -C Release -R 'playlist_(marquee|list_contract|network_commands|local_search)_tests' --output-on-failure
# 可选：会临时移动真实鼠标，在独立原生列表测试窗内比较输入，再恢复鼠标位置。
build/Release/playlist_marquee_tests.exe .. --native
```

本次不是所有皮肤、所有文件格式、所有 Shell 目标及所有网络后端的全量一致性认证。
框选使用当前皮肤的统一 `MakePlaylistGeometry`，未写死某个皮肤的像素坐标。

最终宿主机结果：上述四项 CTest **4/4 通过**；Win32 Release 编译成功，输出至
`build/Release/TTPlayerRebuild.exe`。没有改动用户的播放列表、歌曲或运行时配置。
